# 本番デプロイ要件

> 本番デプロイ環境が**アプリの前提を満たすために保証すべきこと**を1箇所に集約する（アプリ側のコードだけでは強制できない、リバプロ/エッジ・実行環境・秘匿供給の保証事項）。
> ここは「決定の記録」ではなく「デプロイ時チェックリスト」。**決定の正は各 ADR**（本書は参照＝DRY・[`規約/ドキュメント作成規約.md`](規約/ドキュメント作成規約.md)）。本番イメージ/インフラ構築時に本書を上から満たすこと。

---

## 1. リバースプロキシ／クライアント IP（ADR-0006）

正＝[`ADR/ADR-0006_クライアントIPの確定.md`](ADR/ADR-0006_クライアントIPの確定.md)。ログインのレート制限（[`ADR/ADR-0001_認証・セッション基本パラメータ.md`](ADR/ADR-0001_認証・セッション基本パラメータ.md) §2.6）・アカウント一時ロック（[`ADR/ADR-0005_アカウント一時ロック.md`](ADR/ADR-0005_アカウント一時ロック.md) §2.2）が **(IP+login_id) 単位**で成り立つには、backend が**実クライアント IP**を見られる必要がある。

- [ ] **最外の信頼プロキシ（エッジ）が `X-Forwarded-For` を確定させる**＝クライアント由来の `X-Forwarded-For`/`X-Real-IP` を**破棄または上書き**し、自分が受けた実ピア IP を付与する（クライアント詐称値を通さない）。
- [ ] **backend 手前の信頼プロキシ段数と env `TRUSTED_PROXY_COUNT` を一致**させる（例＝エッジのみ経由なら 1）。ズレると実 IP を誤取得する。
- [ ] 推奨: **`/api/v1/*` はエッジから FastAPI へ直結**（Next.js を API データ経路から外す）＝ホップ数を 1 に固定でき、Next の XFF 転送挙動に依存しない。Next.js の `rewrites()` を本番の API 経路に使う場合は、**Next が XFF を正しく転送するか検証**したうえでホップ数に算入すること（ADR-0006 §5・未検証）。
- [ ] 起動ログに `TRUSTED_PROXY_COUNT=0` の警告が出ていないこと（`APP_ENV=prod` で 0 は設定漏れの疑い・ADR-0006 §2.2）。

## 2. Cookie / TLS

正＝[`API設計/A_認証・セッション.md`](API設計/A_認証・セッション.md) A.0（Cookie 表）・[`ADR/ADR-0001_認証・セッション基本パラメータ.md`](ADR/ADR-0001_認証・セッション基本パラメータ.md) §2.3。

- [ ] **`COOKIE_SECURE=true`**（本番は必ず Secure Cookie）。TLS 終端されていること（`iq_session`/`iq_csrf`/`iq_preauth`/`iq_trust` は Secure 前提）。
- [ ] 同一オリジン構成（ブラウザは 1 オリジンのみと通信・CORS 不要）を維持。別オリジンにする場合は許可オリジン（`ALLOWED_ORIGINS`）を明示。
- [ ] **セキュリティ応答ヘッダ（§10）**＝backend が全応答に `X-Content-Type-Options: nosniff`／`X-Frame-Options: DENY`／`Referrer-Policy: no-referrer`／`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` を付与し、**`COOKIE_SECURE=true` のとき `Strict-Transport-Security` も付与**（`app/main.py` middleware）。**フロント（Next）配信側の CSP／エッジ（リバプロ/CDN）で付与するヘッダとの整合**を本番構成で確認すること（backend は API 用の最小 CSP＝画面配信の CSP は別途）。API の `/docs`（Swagger UI）・`/redoc`・`/openapi.json` は **`APP_ENV=prod` で自動無効化**（`app/main.py` `_docs_kwargs`・SEC-TC-045）＝本番はスキーマ/Swagger 非公開。

正＝[`ADR/ADR-0003_設定と秘匿情報の置き場所.md`](ADR/ADR-0003_設定と秘匿情報の置き場所.md) §2.3/§2.4。

## 5. データストア / 起動

正＝[`API設計/A_認証・セッション.md`](API設計/A_認証・セッション.md) A.10（Redis セッション）・[`データモデル.md`](データモデル.md)。

- [ ] **Redis** が可用（セッション・OTP/pre-auth・レート制限/ロックの保持先＝即時失効の確定要件）。永続/フェイルオーバ方針を決めること（消失＝全ログアウト相当）。
- [ ] **PostgreSQL**（管理DB＋会社DB N）と **MinIO** が可用。会社DB は全文検索 PGroonga。**PostgreSQL は PGroonga 同梱のカスタムイメージが必須**（dev＝`impl/db/Dockerfile`＝`postgres:16`＋`postgresql-16-pgdg-pgroonga`）。本番も同等の pgroonga 導入済み PG16 を用意し、会社DB migration `0018_company_pgroonga_fts`（`CREATE EXTENSION pgroonga`＋索引）を各会社DBへ適用すること（マネージド PG で拡張不可の場合は要検討＝別エンジンへ差し替え・データモデル §6）。
- [ ] backend の bootstrap（DB 作成→`alembic` head→seed）が本番でどう走るか。**`APP_ENV=prod` では demo 会社/アカウント（`_SEEDS`）を自動スキップ**し、OPS テナント＋初期 system_admin（`BOOTSTRAP_ADMIN_PASSWORD` 供給時）＋migration のみ実行する（`scripts/bootstrap.py` `_seed_demo_enabled`・SEC-TC-046）。よって entrypoint 冪等 bootstrap は本番でも安全に使えるが、**`APP_ENV=prod` を必ず設定**すること（未設定＝dev 扱いで demo が入る）。

## 6. 決定（本デプロイ要件で確定・2026-08-27／セキュリティ非妥協で採用）

> いずれも**セキュリティ強度を保つ/上げる方向**で確定した本番既定。値の env 反映は §1–§4 のチェック項目で行う。

### 6.1 本番トポロジ → `TRUSTED_PROXY_COUNT`

- **決定＝`Browser→エッジ(TLS終端)→FastAPI`（`/api/v1/*` 直結・ホップ1）**。エッジで `/api/v1/*` を FastAPI へ、それ以外を Next へ振り分ける。→ **`TRUSTED_PROXY_COUNT=1`**（エッジのみ経由の場合。多段なら実段数に一致）。
- **セキュリティ根拠**＝認証のレート制限/一時ロックは実クライアント IP 前提（ADR-0006）。ホップを 1 に固定し Next の XFF 転送挙動（ADR-0006 §5・未検証）への依存を排除＝実 IP 誤取得による制限崩れを防ぐ。**非妥協**＝最外エッジは client 由来 `X-Forwarded-For`/`X-Real-IP` を破棄/上書きし実ピア IP を付与（§1）。`Browser→エッジ→Next(rewrite)→FastAPI`（ホップ2）は Next の XFF 転送を実測検証できるまで採らない。

### 6.2 メール送信基盤

- **決定＝マネージド送信サービス（SES/SendGrid/Postmark 等）を SMTP 接続**。コードは汎用 SMTP 非同期 outbox（`mail_worker`）で完成済＝プロバイダ選定は env 設定のみ（コード変更ゼロ）。
- **セキュリティ根拠/非妥協**＝**`SMTP_START_TLS=true`（587・STARTTLS）**で送信経路を TLS 化・**`SMTP_USER`/`SMTP_PASSWORD` はシークレットマネージャ供給**（`.env` に焼かない・§3）。送信ドメインの **SPF/DKIM/DMARC を本番前に設定**（なりすまし送信・到達率対策）。自前 SMTP は到達率/逆引き運用負荷が高く既定にしない。

### 6.3 Redis 永続 / HA

- **決定＝マネージド Redis（HA＋自動フェイルオーバ）**。最低ラインでも **AOF 永続（`appendonly yes`）** を必須とする。
- **セキュリティ根拠/非妥協**＝セッション・OTP/pre-auth・レート制限/ロックの保持先＝消失は全ログアウト＋認証不能に直結（可用性がセキュリティ機構の前提）。**接続は TLS＋認証（`requirepass`/ACL）**・**ネットワークは backend からのみ到達可能な私設ネット**に隔離（公開しない）。永続なし（dev 相当）は本番不可。

### 6.4 DB バックアップ

- **決定＝日次フルバックアップ＋WAL アーカイブによる PITR**。会社DB は N 個に増えるため**サーバ/クラスタ単位で全 DB を一括**対象にする。
- **前提確認（1点）**＝会社DB は **PGroonga 拡張が必須**（§5）。マネージド PostgreSQL を使う場合は **PGroonga 拡張の可否を先に検証**し、可なら自動バックアップ＋PITR を採用／不可なら自前 PGroonga 像（`impl/db/Dockerfile`）＋`pg_basebackup`＋WAL アーカイブで PITR を構築する（マネージドで拡張不可なら別エンジン検討＝データモデル §6）。
- **セキュリティ根拠/非妥協**＝**バックアップは保存時暗号化**・**復元手順を定期リハーサル**（復元できないバックアップは無価値）・アクセスは最小権限。

### 6.5 監査ログの保存先 / 期間

- **決定＝直近は control DB `system_audit_logs`（追記専用）で検索可・期限超過分はオブジェクトストレージ（WORM 相当）へアーカイブ移送**。既定期間の叩き台＝**DB 180 日／アーカイブ 1 年**（[`API設計/A_認証・セッション.md`](API設計/A_認証・セッション.md) A.8）。
- **セキュリティ根拠/非妥協**＝監査は**追記のみ**（アプリからは INSERT のみ・更新/削除経路を作らない）＝改ざん耐性。アーカイブ先も**保存時暗号化＋WORM/バージョニングで上書き/削除を防止**。**最終的な保存期間は法務/社内コンプラ規定に従う**（規定確認を別タスクで起票）。
- **関係**＝§6.6 の**システムログ**（アプリ/アクセス/エラーの運用ログ・ファイル）とは別物。監査ログ（§6.5）は「誰が何をしたか」の**業務証跡**（DB・改ざん耐性）、システムログ（§6.6）は「何が起きたか」の**運用診断**（ファイル・障害/不整合の追跡）。両者は `request_id`／`actor` で相関できる。

### 6.6 システムログ（アプリ/アクセス/エラーのファイル記録）

> 本番稼働時の問題・データ不整合を後から追跡・解析するための運用ログ。実装＝[`app/core/logging_config.py`](../impl/backend/app/core/logging_config.py)（集中設定）・[`app/core/log_context.py`](../impl/backend/app/core/log_context.py)（相関）・アクセスログは [`app/core/audit_context.py`](../impl/backend/app/core/audit_context.py)。テスト＝[`テスト/O_システムログ.md`](テスト/O_システムログ.md)（O-TC-xxx）。セキュリティ要件＝[`WEBアプリ開発時のセキュリティ対策一覧.md`](WEBアプリ開発時のセキュリティ対策一覧.md) §15。

- **形式＝JSONL**（1行1 JSON・機械解析容易）。フィールド＝`ts`（ISO8601）/`level`/`service`/`logger`/`msg`＋相関 `request_id`・`actor`（account_id）・`tenant`（会社DB識別子）・`ip`・`ua`＋呼び出し側の構造化 `extra`。`LOG_FORMAT=plain` で人間可読にも切替可（dev 向け）。
- **相関**＝`request_id`（レスポンスの `X-Request-ID` と一致）とテナントを contextvar で全ログへ自動注入＝1リクエストを層をまたいで串刺しで追える。監査ログ・problem+json の `request_id` とも突合可能。
- **収録範囲（full）**＝①**アクセスログ**（全 HTTP・method/path/status/所要ms／5xx=error・4xx=warning・`/healthz` は除外）②**エラー/未捕捉例外**（`request_id` 付きでスタックをサーバー側にのみ記録＝画面には出さない・§14）③**データ変更トレース**（監査記録・outbox ワーカの各パス＝管理DB→会社DB ミラーの結果整合を追える）。
- **出力先**＝stdout（`docker logs`／集約基盤取り込み用・常時）＋ファイル `LOG_DIR/<service>.jsonl`（service＝`backend`/`worker`/`mail-worker`）。WARNING 以上は `<service>.error.jsonl` にも集約（障害の一次切り分け）。ディレクトリが書けない環境では**stdout へ自動フォールバック**（アプリは落とさない）。
- **ローテーション/保持/アーカイブ**＝**日次**（0時・`when=midnight`）。前日分を **gzip 圧縮**してアーカイブ（`<service>.jsonl.YYYY-MM-DD.gz`）。**保持日数＝`LOG_RETENTION_DAYS`（既定 30・env で調整可）**を超えた古い分（.gz 含む）は削除。**超長期保管が要る場合は §6.5 同様オブジェクトストレージ（暗号化＋WORM/バージョニング）へ移送する（フェーズ2）**。最終的な保持期間は法務/社内コンプラ規定に従う。
- **永続化（本番の非妥協）**＝`LOG_DIR` は**永続ボリューム/永続ホストパス**にマウントすること（コンテナ再作成でロストしない）。dev は `impl/logs` バインドマウント（gitignore・消えて可）。
- **秘匿（§15）**＝PW/セッションID/トークン/OTP/CSRF/Cookie/APIキー等は**キー名で検出しマスク**（`***`）。ネストした dict/list も再帰マスク。ログイン識別子（login_id）等の**追跡に要る非秘匿値は残す**。
- **設定 env**＝`LOG_LEVEL`（既定 INFO）/`LOG_FORMAT`（json|plain）/`LOG_TO_FILE`（既定 true）/`LOG_DIR`（既定 `/var/log/ideaquest`）/`LOG_RETENTION_DAYS`（既定 30）/`LOG_UTC`（ローテーション境界の UTC 化）。
- **フェーズ2（TODO）**＝①長期アーカイブのオブジェクトストレージ移送（§6.5 と統合・WORM）②集約基盤（CloudWatch Logs / ELK / Loki 等）への転送と保持・アラート③異常検知（大量 4xx/5xx・不審ログイン）とアラート通知先/対応手順（§15 の残要件）。

# テスト規約（設計書→テストパターン→テストコードの連鎖）

> 目的＝**「設計書 → テストパターン → テストコード」を一直線に辿れる**ようにする。
> 仕様の正は各設計書（`doc/API設計/`・`doc/画面設計/`・`doc/データモデル.md`）、
> 「何を確認するか」の正は本ディレクトリの**テストパターン md**（`doc/テスト/<ドメイン>_*.md`）、
> 「どう確認するか」の正は**テストコード**。三者を **TC-ID** で結ぶ。

---

## 1. トレーサビリティ（本規約の核）

- **TC-ID**＝テストケースの一意識別子。形式＝`<ドメイン>-TC-<連番3桁>`（例 `A-TC-001`）。
  - ドメイン記号は API設計のファイル接頭辞に合わせる（A〜L）。
  - 連番はドメイン内で一意・欠番可（削除しても再利用しない＝履歴の安定）。
- **3方向リンクの規約**:
  1. テストパターン md の各行は **`根拠` 列に設計節**を必ず書く（例 `A_認証・セッション.md A.1`・`SC-00 §5`）。
  2. テストコードは **関数名と docstring に TC-ID を埋める**（例 `def test_a_tc_001_login_success():` ／ docstring 先頭に `A-TC-001`）。
  3. 逆引き＝TC-ID で全文検索すれば「パターン md の行」と「テスト関数」が対で見つかる。
- **SoT（Single Source of Truth）の分担**（重複を書かない・規約 §2.3 DRY）:
  - 期待する**振る舞い/エラーcode/スキーマ**＝設計書・**OpenAPI**（エラーcodeの網羅は OpenAPI が SoT＝API設計 README §1.7）。テストパターン md はそれを**参照**し、値を再定義しない（`code=unauthenticated`（A.1）のように出典を併記）。
  - **確認すべきケースの集合**＝テストパターン md。
  - **実行手順・アサーション**＝テストコード。

## 2. テスト階層（レベル）

| レベル | 対象 | 依存 | 例 | ツール |
| --- | --- | --- | --- | --- |
| **unit** | domain 層の純粋関数（§3.1・DB非依存） | なし | `daily_login_bonus_due()`（A.1/G）・入力正規化 | pytest |
| **integration（int）** | repository＋実DB（テナント解決・Tx・冪等） | Postgres | セッション永続・台帳の一意制約 | pytest＋テストDB |
| **api** | エンドポイント（router→application→domain→repository の縦貫） | Postgres＋Redis | `POST /api/v1/auth/login` の status/Set-Cookie/body | pytest＋ASGI TestClient |
| **e2e**（任意） | ブラウザ実操作（画面↔API） | フルスタック（compose） | SC-00 でログイン→SC-01 到達 | Playwright |

- **原則＝ピラミッド**: unit を厚く、api を要所に、e2e はハッピーパス中心に薄く。
- **どのレベルで書くか**はテストパターン md の `階層` 列で指定する。

## 3. バックエンド（pytest）の約束

- place＝`backend/tests/<domain>/`。ファイル名＝`test_<domain>_<観点>.py`。
- **命名**＝`test_<tcid小文字>_<短い説明>`（例 `test_a_tc_002_wrong_password_401`）。docstring 1行目に `A-TC-002` と根拠設計節。
- **DBフィクスチャ**＝テストごとにトランザクションを張って**ロールバックで隔離**（副作用を残さない）。マルチテナントは「管理DB＋テスト用会社DB1つ」を**セッションスコープで用意**し、行データはテスト単位でロールバック。
- **シード/ファクトリ**＝最小の「1社＋1アカウント（＋必要なら会社DB users）」を作るヘルパを用意（`conftest.py`）。値は決め打ちを避け factory 関数で生成。
- **秘匿値をログに出さない**（PW/セッションID/OTP/トークン＝セキュリティ一覧 3・15）。テストでも生の秘匿値をアサーションメッセージに出さない。
- **失敗を繰り返す TC はレート制限/将来のアカウントロックに引っかからないよう隔離する**＝テストごとに別 `login_id`/IP を使うか、失敗回数を閾値未満に保つ（ADR-0001 §2.6・ロックは MFA スライスで導入予定のため、既存 TC が将来も壊れないようにする）。

## 4. フロント（Playwright・e2e／任意レベル）

- place＝`frontend/e2e/`。ケースは `<screen>.spec.ts`（例 `sc-00-login.spec.ts`）。
- テスト名に TC-ID を含める（例 `test('A-TC-020 login happy path', …)`）。
- e2e は**契約の最終確認**（Cookie セッションが実ブラウザで確立し保護画面へ到達する等）に限定し、細かな分岐は api レベルで担保する。

## 5. 追加・変更のフロー

1. 設計書が確定/変更 → 2. 該当ドメインのテストパターン md に TC 行を追加/更新（`根拠` を明記）→ 3. テストコードを TC-ID 付きで実装 → 4. 変更に伴い旧 TC を消す場合は md とコードの両方から消す（TC-ID は再利用しない）。

## 6. 共通の必須観点（全ドメイン・認可の抜け穴防止）

各エンドポイントのテストパターンには、その性質に応じて次を**必ず**含める（drift しやすい認可の穴を体系的に塞ぐ）:

- **セッション必須EP**＝「**セッション無し → 401 `unauthenticated`**」を必ず1件置く（例 A-TC-012／A-TC-015）。
- **状態変更系EP（CSRF 対象）**＝「**CSRF トークン無し/不一致 → 403 `csrf_failed`**」を1件（例 A-TC-014）。認証と CSRF の**評価順序**（セッション無し＝401 が先・セッション有り＋CSRF 欠落＝403）が対で分かるようにする。
- **テナント/門番のあるEP**＝「**他テナント/権限外 → 404（存在秘匿）**」を1件（該当ドメインで追加）。
- **冪等EP（`Idempotency-Key`）**＝「**同一キー再送 → 同一結果（副作用1回）**」を1件（該当ドメインで追加）。

# 画面API連携 SC-00 ログイン

> **本書が定めるのは次の3つだけ**です：**(1) 画面が API をどの順番で呼ぶか（呼び出し順序）／(2) 返ってきた結果（成功・各エラー）を画面にどう反映するか（画面の状態と文言）／(3) Cookie・CSRF の配線**。
> **リクエスト・レスポンスの項目やエラーコードの一覧はここには書きません**——それらは OpenAPI と [`../../API設計/A_認証・セッション.md`](../../API設計/A_認証・セッション.md) が正（同じ内容を2箇所に書かない＝DRY・規約 §2.3）。
> 実装＝`impl/frontend/src/features/auth/`（`app/` はルーティングのみ・§4.1）。対象＝**状態A（PWログイン）／状態D（再設定リクエスト）／状態B（初回・再設定PW設定）**（MFA=状態C は後続）。

## 1. 呼び出しシーケンス

| # | 契機 | 呼び出し | 成功時 | 失敗時 |
| --- | --- | --- | --- | --- |
| 1 | ログイン押下 | `POST /api/v1/auth/login`（同一オリジン→backend へ rewrite プロキシ） | `authenticated` → `/`（SC-01）へ遷移＋`router.refresh()` | code に応じて §3 の文言表示・パスワード欄クリア |
| 2 | 認証後ページ描画 | Server Component が `GET /api/v1/auth/session`（Cookie 転送） | セッション表示（display_name 等） | `null` → `/login` へ redirect |
| 3 | ログアウト押下 | `POST /api/v1/auth/logout`（`X-CSRF-Token`＝`iq_csrf`） | `/login` へ遷移 | いずれにせよ `/login` へ |

## 1b. 状態D/B の呼び出しシーケンス（初回・再設定パスワード）

状態D→メール→状態B→A は**ログインフローと独立**（トークンが本人性を担保・A.7）。実装＝`PasswordResetRequestForm`（状態D）／`PasswordSetupForm`（状態B・`app/(auth)/password-setup?token=` がメールのリンク先）。

| # | 状態 | 契機 | 呼び出し | 成功時 | 失敗時 |
| --- | --- | --- | --- | --- | --- |
| D1 | D | 「再設定リンクを送信」押下 | `POST /api/v1/auth/password-setup/request`（`{company_code, login_id}`） | **常に**同一の確認メッセージへ切替（実在・成否を出さない＝列挙耐性） | 通信/サーバ例外のみ一般文言。**202 は成功扱い**（レート超過でも 202・§3） |
| B1 | B | ページ表示（`?token=` 受領） | `POST /api/v1/auth/password-setup/verify`（`{token}`） | `valid:true` → 設定フォーム表示 | `410 token_expired`／`valid:false`／token 無し → **期限切れ/無効表示＋再要求導線**（`/password-reset`） |
| B2 | B | 「パスワードを設定してはじめる」押下 | `POST /api/v1/auth/password-setup/complete`（`{token, new_password}`） | `200 ok` → **完了表示→ログイン画面（A）へ**（設定後は通常ログイン・**ここではセッションを張らない**） | `422 validation_error`→`errors[]` をフィールド直下／`410`→期限切れ表示へ遷移／他→一般文言 |

- **クライアント補助検証**＝新PW（8文字＋英字＋数字・ADR-0002 §2.2）と確認一致をフロントで先に指摘。**最終判断はサーバ**（`complete` の 422 `errors[]`）。
- **列挙耐性**＝状態D は入力の正誤・アカウント実在を UI に出さない（送信後は一律確認メッセージ）。`request` は超過時も 202（`429` を返さない・ADR-0002 §2.3）。

## 2. 状態（loading / error / empty）

- **loading**＝送信中はボタンを `disabled`＋「送信中…」。二重送信を防ぐ。
- **error**＝`role="alert"` で1行表示（§3）。フィールド単位のエラー（422 `errors[]`）は将来フィールド直下に出す（現状は全体表示）。
- **empty/未認証**＝保護ページはセッション無しで即 `/login` redirect（画面ちらつきを避けるためサーバー側で判定）。

## 3. エラー code → UI 文言（列挙耐性を守る）

| code / 状況 | 文言（SC-00 §7） |
| --- | --- |
| `unauthenticated`（会社コード/ID/PW 不一致・PW未設定を一律） | ログインIDまたはパスワードが正しくありません。 |
| `company_suspended` | このアカウントは現在ご利用いただけません。管理者にお問い合わせください。 |
| `rate_limited` | 試行回数が多すぎます。しばらくして再度お試しください。 |
| `validation_error` | 入力内容をご確認ください。 |
| その他/通信失敗 | エラーが発生しました。時間をおいて再度お試しください。 |

- **どちらが誤りかは示さない**（列挙攻撃対策・A.1）。`password_setup_required` 等は返らない前提。

## 4. 認証・セキュリティ配線（§4.1・A.0）

- **同一オリジン方針**＝ブラウザは常に `:3000` と通信し、`/api/v1/*` は `next.config` の rewrite で backend へプロキシ。**CORS 不要**。
- **Cookie**＝`iq_session`（httpOnly・ブラウザが自動送出）／`iq_csrf`（非httpOnly・JS が読んで `X-CSRF-Token` に載せる＝ダブルサブミット）。fetch は `credentials: "include"`。
- **CSRF**＝状態変更系（logout）のみ付与。login および **password-setup の request/verify/complete は未認証起点＝CSRF 免除（Origin/Sec-Fetch のみ・A.1/A.7）**。これらは Cookie を張らない（設定完了後も新規セッションを発行しない）。
- **401 リダイレクト**＝保護ページの Server Component が `getServerSession()` で判定し `/login` へ。

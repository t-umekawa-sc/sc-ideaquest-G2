## 1. 概要・目的

- **コンセプトの新規登録・編集モーダル**。**由来アイデア（複数・選別済み）を選び、成果物スキーマ（§4）を入力**する（ISO 56001 ②③段＝概念の創造）。
- **ISO 56001 準拠の「コンセプトとは何か・何を・どの粒度で入力するか」を理解したうえで入力してもらう**のが狙い＝**フォーム冒頭＋難解な項目ラベル横にガイダンス ⓘ**（[デザイン標準](../デザイン標準.md) §4.13）を置く。
- **一覧（SC-12「🧩 コンセプト」タブ）／詳細（SC-61）から開くモーダル差し込み**。保存で **SC-61 コンセプト詳細**へ（新規は作成後の詳細）。
- **前提と検証のリンク・評価・投票・議論・総合判定・選定は本モーダルでは扱わない**（成果物スキーマの入力に限定）＝それらは **SC-61 コンセプト詳細**で行う（P.3/P.4/P.5/P.5b/P.6/P.2 decision・select）。

## 2. アクセス条件・権限

| 項目 | 内容 |
| --- | --- |
| 新規作成 | **当該クエストのパーティーメンバー**（門番＝パーティー所属 AND クエストグループ所属・[API設計 P_コンセプト](../../API設計/P_コンセプト.md) P.0）。作成は `draft`（本人のみ可視・P.2） |
| 編集 | **作成者本人＋owner/quest_admin**（サーバー認可・`PATCH /concepts/{id}`）。SC-61 の編集ボタンは作成者本人のみ表示（SC-22 と同方針）だが、認可自体は作成者/owner |
| 由来アイデア | **同一クエストの選別済みアイデア**のみ選択可（他クエスト・未選別は不可＝門番・スコープ境界・[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §1.1） |
| 公開（投稿する） | **作成者＋owner/quest_admin**＝本モーダルの「投稿する」で `draft→active`（アイデアの publish と同型・確定 2026-09-25）。「下書き保存」は draft のまま |
| 保管・選定・総合判定 | 本モーダル外（SC-61・owner/quest_admin） |

## 3. レイアウト構成（決定）

- **入力モーダル標準**（`.modal.sectioned`＝ヘッダー/本文/フッターの3部・ドラッグ/最大化/Esc/バックドロップは共通適用）。サイズ＝`.modal--lg`（項目が多いため）。
- **フォーム冒頭に ⓘ「コンセプトとは？」ガイダンス**（[デザイン標準](../デザイン標準.md) §4.13）＝ISO 56001 準拠の定義・狙い・粒度を、既定は ⓘ＋短ラベル、ホバー/フォーカスでフローティング展開（在来フローを動かさない）、クリックで全文ダイアログ。**入力の前提理解を促す**（本画面の主目的）。
- **入力項目は `.field` の余白で区切る**（仕切り線なし＝`is-quiet`・[デザイン標準](../デザイン標準.md) 入力ダイアログ標準）。**難解な項目のラベル横に ⓘ ガイダンス**（`viability`＝価値実現モデル 等）。
- **フッター順**＝閉じる（左・`.dialog-close-left`）→（編集時）下書き保存 →（主）保存。
- 業務層のクリーン基調。

## 4. 表示・入力項目（コンセプトの成果物スキーマ・[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.3 / API P.2）

| 項目 | 種別 | 必須 | 補足・ガイダンス |
| --- | --- | --- | --- |
| コンセプト名 | テキスト | **必須** | `title`。§4.7 入力検証（空/上限） |
| 由来アイデア | **アイデア選択（複数）** | 任意（推奨） | `source_idea_ids[]`（同一クエストの選別済み）。ピッカーは SC-22/SC-25 の対象選択と統一。**ラベル横に ⓘ**＝「由来＝このコンセプトの元になった選別済みアイデア（複数可）」 |
| 課題・機会 | テキストエリア | 任意 | `problem` |
| 狙う価値（価値提案） | テキストエリア | 任意 | `value_proposition`。**ラベル横に ⓘ**＝「誰の・どんな価値か（価値提案）」 |
| 対象 | テキスト/エリア | 任意 | `target`（ユーザ／既存顧客／市場） |
| 競合・差別化 | テキストエリア | 任意 | `differentiation` |
| 解の形態＋必要な能力 | テキストエリア | 任意 | `solution_form`（粗い形態＋必要能力） |
| 採算・事業性（viability） | **ラベル付き構造入力** | 任意 | `viability`（jsonb）＝価値実現モデル。**JSON 直接入力はユーザー負荷が高いため、ラベル付きテキスト項目に分解**（**確定 2026-09-25・ユーザー指摘**）＝**コスト（`cost`）／収益モデル（`revenue`）／ROI・投資回収（`roi`）／備考（`notes`）**。入力を非空キーのみ組み立てて jsonb に保存。**既存の他キー（API 等で入った任意キー）は編集時に温存**（分解対象4キーのみ差し替え）。**ラベル横に ⓘ ガイダンス**＝「価値実現モデル（value realization model）＝"how value can be realized"＝business/operational/marketing model・ISO §8.3.3」。構造の完全固定化（項目の必須化・複数行）は Phase2（§9） |

- **前提と検証・評価・投票・議論・総合判定・選定は本モーダルに含めない**（SC-61 で扱う・§1）。
- **`draft` 既定**（作成時）＝本人のみ可視。公開（`active`）は SC-61 の「活性化」（owner/quest_admin・P.2）。

## 5. アクション・遷移

| トリガー | 条件 | 遷移/結果 |
| --- | --- | --- |
| 閉じる/キャンセル | — | モーダルを閉じる（呼び出し元へ戻る） |
| ガイダンス ⓘ をクリック | 全員 | 全文ダイアログ（定義・狙い・粒度／用語説明）を開く（[デザイン標準](../デザイン標準.md) §4.13） |
| 由来アイデアを選ぶ | パーティー | 同一クエストの選別済みアイデアから複数選択（`source_idea_ids[]`） |
| 保存（新規） | パーティー | `POST /quests/{quest_id}/concepts`（既定 `draft`）→ **SC-61 コンセプト詳細**へ。**作成時に総合ルーム（`overall`）自動生成**（P.2/§3.7） |
| 保存（編集） | 作成者/owner | `PATCH /concepts/{id}`（`source_idea_ids[]` 差し替え含む）→ SC-61 へ。公開後は版として記録（版管理は Phase2・P.10） |
| 下書き保存（編集時） | 作成者/owner | 内容のみ保存し `draft` 維持（新規は既定 `draft`） |

## 6. 状態・バリエーション

| 状態 | 表示 |
| --- | --- |
| 新規 | タイトル「コンセプトを登録」・既定 `draft`・由来アイデア未選択可 |
| 編集 | タイトル「コンセプトを編集」・既存値をプリフィル |
| 入力エラー | §4.7 入力検証（必須・上限）をフィールド直下に表示 |
| 由来アイデア候補なし | 「選別済みアイデアがありません」＋空のまま作成可 |
| ガイダンス reduce-motion | ⓘ 展開の流れは静止（[デザイン標準](../デザイン標準.md) §4.9/§4.13） |

## 7. データ・API（想定）

- **POST `/quests/{quest_id}/concepts`**（P.2）: `{title(必須), source_idea_ids[], problem?, value_proposition?, target?, differentiation?, solution_form?, viability?〔jsonb〕}` → 作成 `concept`（`draft`）＋総合ルーム自動生成。
- **PATCH `/concepts/{concept_id}`**（P.2）: 上記フィールドの部分更新＋`source_idea_ids[]` 差し替え → 更新後 `concept`。
- 由来アイデア候補＝同一クエストの選別済みアイデア（既存アイデア API を流用・スコープはサーバーで最終制御）。
- 認可（作成者/owner・門番）・`draft` 可視制御はサーバー側で最終判定（P.0/P.8）。

## 8. アクセシビリティ / 表示配慮

- 入力検証は §4.7（色のみに依存しない・フィールド直下メッセージ）。
- **ガイダンス ⓘ**（[デザイン標準](../デザイン標準.md) §4.13）＝ボタン扱い＋`aria-haspopup="dialog"`＋`aria-label`。展開の流れは reduce-motion（OS／`accounts.reduce_motion`・§4.9）で静止。フォーカスリングは `outline` でなくベース＋展開部の枠線を青で一続きに。
- モーダルはフォーカストラップ・`aria-modal`・`Esc`/バックドロップで閉じる（モーダル標準）。

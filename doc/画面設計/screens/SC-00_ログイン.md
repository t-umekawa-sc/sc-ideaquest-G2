## 1. 概要・目的

- 独自アカウントで **ログイン／ログアウト** を行う入口画面（未認証者向け）。
- **アカウントは管理者発行のみ**（自己新規登録は無い）。一般ユーザーは**管理者発行後にメールで届く「初回パスワード設定リンク」**（有効72時間・単回）から初回パスワードを設定する（**仮パスワードは使わない**）。
- **多要素認証（MFA）**: ID＋パスワード（第1要素）成功後、**メールで認証コード（OTP・第2要素）**を送信し、その入力成功でログインを許可。**会社ごとに MFA の ON/OFF（既定 ON）**。
- **信頼デバイス**: OTP入力時に「このデバイスを信頼する」ON で、次回以降その端末では **OTP をスキップ（有効期限30日）**。別端末では常に OTP を要求。**セッション保持はデバイス信頼に一本化**（別途の「ログイン状態を保持する」は設けない）。
- ログイン成功で所属会社を判定し、当該会社DBへ接続してダッシュボード（SC-01）へ遷移。**ログインで XP 付与（ログインボーナス・1日1回・日次上限対象）**。

## 2. アクセス条件・権限

| 項目 | 内容 |
| --- | --- |
| アクセス可能者 | 全員（未認証）。認証済みでこの画面に来た場合は SC-01 へリダイレクト |
| ロール | 不問（ログイン後にシステムロール＝一般／クエストグループ管理者／システム管理者を判定） |
| テナント | **全社同一 URL**。ログイン画面で**会社コード（`companies.company_code`）を手入力**して会社を特定（会社一覧からの選択式にはしない＝クロステナントを見せない）。会社コードは端末に記憶してプリフィル可 |

## 3. 画面状態

本画面は3状態を持つ（モックではデモ切替）。

1. **A: ログイン** — 会社コード＋ID＋パスワードでの第1要素認証。
2. **C: 認証コード入力（MFA）** — メール送信されたOTPを入力（第2要素）。「このデバイスを信頼する」チェックあり。
3. **B: 初回パスワード設定** — **管理者発行後にメールで届く「初回パスワード設定リンク」から開く専用状態**（ログインフローの途中では表示しない・リンクのトークンが本人性を担保）。新パスワードを設定して利用開始。

> 標準ログインフロー: A（会社コード＋ID＋PW）→（信頼端末なら C をスキップ）→ C（OTP）→ SC-01。
> 会社特定: 送信時にまず会社コードで会社を解決（`company_id`＋`db_identifier`）→ その会社内で ID＋PW を検証。**会社コード/ID/PW いずれの誤りも同一のエラー文言**（列挙耐性）。**初回パスワード未設定（`password_set=false`）のアカウントも他の失敗と区別せず同一の 401 に倒す＝login からは状態 B へ遷移させない**（列挙耐性・ドメインA F3）。
> 初回パスワード設定フロー（A とは独立）: 管理者がアカウント発行 → **メールで初回パスワード設定リンク**（`otp_challenges` purpose=`password_setup`・72h・単回）を送信 → 受信者がリンクを開く＝**状態 B** → 新パスワード設定 → **ログイン画面（A）へ**（設定後に通常ログイン）。
> MFA=OFF の会社: C を経由せず A → SC-01。

## 6. バリデーション

- **ログインID**: 必須・メール形式。空/形式不正はクライアント側で指摘。
- **パスワード（ログイン）**: 必須（強度チェックはしない＝既存値の照合のみ）。
- **認証コード（OTP）**: 必須・6桁数字。期限内・単回・試行上限内であることをサーバーが判定。
- **新パスワード**: 必須・**ポリシー準拠**（最小長・文字種など。値はTBD＝要件で確定）。
- **新パスワード（確認）**: 新パスワードと**完全一致**。
- サーバー側でも同一の検証を行う（クライアント検証は補助）。認証・所属会社判定・**初回パスワード設定リンクの有効性（72h・単回）**などはサーバーが最終判断。

## 8. API 入出力（案・API設計フェーズで確定）

> **認証APIの正＝`doc/API設計/A_認証・セッション.md`（詳細確定）**。実パス（`/api/v1/auth/*`）・Cookie セッション（`iq_session`/`iq_preauth`/`iq_csrf`/`iq_trust`）・エラーcodeはそちらが SoT。以下は SC-00 の UI 対応の当たり。

- **POST `/api/v1/auth/login`**（第1要素・未認証起点）
  - in: `{ company_code, login_id, password }`（信頼端末 Cookie `iq_trust` があれば送信される）。`company_code` で会社を解決してから会社内で認証
  - out(MFA不要＝OFF or 信頼端末): `200 { status:"authenticated", session:{…} }`＋`Set-Cookie: iq_session, iq_csrf` → SC-01
  - out(要OTP): `200 { status:"mfa_required", mfa:{ masked_to, expires_in, resend_available_in } }`＋`Set-Cookie: iq_preauth, iq_csrf` → 状態C
  - out(失敗): `401 { code:"unauthenticated" }`（**会社コード/ID/PW 不一致・初回PW未設定を一律に扱う**）／会社停止 `503 { code:"company_suspended" }`
  - ※**初回PW未設定でも `password_setup_required` は返さない**（状態Bへは遷移しない・列挙耐性・F3）
- **POST `/api/v1/auth/mfa/verify`**（第2要素・pre-auth 必須）
  - in: `{ code, trust_device }`（CSRF＝`X-CSRF-Token`＋`iq_csrf`）
  - out(成功): `200 { status:"authenticated", session:{…} }`＋`Set-Cookie: iq_session, iq_csrf`（`trust_device=true` は `iq_trust`・30日 も発行）→ SC-01
  - out(失敗): `401 { code:"otp_invalid"|"otp_expired"|"preauth_expired" }`
- **POST `/api/v1/auth/mfa/resend`**（pre-auth 必須）: 新OTP送信（クールダウン中は `429`＋`Retry-After`）。
- **初回パスワード設定（メールリンク起点・ログインフローとは独立）＝`A_認証・セッション.md` §A.7**
  - **POST `/api/v1/auth/password-setup/verify`** in: `{ token }` → out: `200 { valid:true, login_id }`／無効・期限切れ・使用済 `410 { code:"token_expired" }`（＝**状態Bの表示可否**）
  - **POST `/api/v1/auth/password-setup/complete`** in: `{ token, new_password }` → out: `200 { status:"ok" }` → **ログイン画面（A）へ**（設定後に通常ログイン。ここではセッションを張らない）。PWポリシー違反は `422 { code:"validation_error", errors:[…] }`
- **POST `/api/v1/auth/logout`**: 現端末のセッション破棄（`iq_session` 失効）。全端末は `logout-all`（信頼端末も失効）。
- 補足: OTP生成・送信・照合、信頼端末照合、ログインボーナスXP付与（1日1回・日次上限）、所属会社判定→会社DB接続はすべてサーバー側。MFA要否は Company の `mfa_required` を参照。

## 9. 非機能・セキュリティ

- パスワードは**ハッシュ保存**（アルゴリズムは実装で確定）。通信は HTTPS 前提。
- 認証失敗の**理由を詳細に返さない**（アカウント存在の推測を防ぐ）。
- **総当り対策**: ログイン/OTP双方に試行回数制限・一時ロック・レート制限（閾値はTBD）。
- **MFA（メールOTP）**: 6桁数字・有効期限10分・単回使用・試行上限（例5回）・再送クールダウン60秒/回数上限。OTPは**ハッシュで保持**し平文で残さない。
- **信頼デバイス**: 暗号乱数トークンを**ハッシュ保存**、Cookieは HttpOnly/Secure/SameSite=Lax。有効期限30日。パスワード変更/リセット・全端末サインアウト・管理者操作で失効。**信頼はOTPスキップのみを意味し、パスワードは毎回必要**。
- **セッション**: デバイス信頼に一本化。**信頼端末はセッションも長期（〜信頼期限のローリング）／非信頼端末は短命セッション**（具体値はTBD）。
- **残存リスク**: ログインIDとメールは別項目にしたが、OTP 配送がメールのため登録メール侵害はログイン突破の一要因になり得る（将来 TOTP 追加を検討）。
- **クロステナントアクセス禁止**: 会社DB接続はログインで確定した所属会社に限定。
- CSRF/XSS 対策、Cookie 属性（HttpOnly/Secure/SameSite）は実装で担保。

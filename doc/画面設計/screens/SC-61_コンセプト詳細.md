- 最終更新: 2026-09-25
- ステータス: ドラフト（機能詳細）

## 1. 概要・目的

- 1 つのコンセプト（ISO 56001 ②③段＝創造・検証の成果物）の詳細画面。**成果物スキーマ・前提と検証・投票・評価結果・総合判定・議論**を集約し、**検証と選定の中心**になる。
- コンセプトは**アイデア段の成果物を昇華したもの**（複数の選別済みアイデアが由来）で、**1 クエスト内に複数候補（N 個）が競合**し、評価と検証を経て owner が勝ち残りを選定する（[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.4）。
- 表示のみでなく**投票（賛成/反対）はインラインアクション**として本画面で完結。評価は評価者権限で **SC-62 コンセプト評価**へ、編集は作成者/owner で **SC-60 コンセプト登録・編集**へ、議論の本体は各**議論ルーム（総合/グループ/前提スレッド）**へ。
- **一覧（SC-12 クエスト詳細の「🧩 コンセプト」タブ）から開く際はモーダル差し込み、URL 直/リロードは本フルページ**（UI標準）。詳細はモーダルでなくフルページを既定とする（**情報量が多い**＝スキーマ7項目＋前提検証プール＋評価8観点）。

## 2. アクセス条件・権限

| 項目 | 内容 |
| --- | --- |
| アクセス可能者 | **当該クエストのパーティーメンバー**（門番＝パーティー所属 AND クエストグループ所属・[API設計 P_コンセプト](../../API設計/P_コンセプト.md) P.0）。非メンバーはアクセス不可 |
| 表示 | パーティーなら全員が閲覧可（`active` のコンセプト）。`draft` は**作成者本人のみ**（[API設計 P_コンセプト](../../API設計/P_コンセプト.md) P.1） |
| 投票 | **コンセプト投票権限**（既定でパーティーに付与）。賛成/反対の 1 人 1 票・変更/取消可・自分のコンセプトにも投票可（P.5b） |
| チャット投稿 | **コメント作成権限**（既定でパーティーに付与）。閲覧はパーティー全員。機構は E ドメイン再利用（P.6） |
| 編集 | **編集ボタンは作成者本人のみ表示**（`is_mine`・SC-22 と同方針）。サーバー認可は作成者 or owner/quest_admin（`PATCH /concepts/{id}`）。**SC-60 登録・編集モーダル** |
| 公開（活性化）・保管・選定・判定 | **公開（活性化 `draft→active`）＝作成者＋owner/quest_admin**（アイデアの publish と同型・確定 2026-09-25）。**公開は SC-60 の「投稿する」で行い、SC-61 ヘッダーに専用ボタンは置かない**（SC-22 に無い UI を増やさない）。**保管（`active→archived`）/★選定/総合判定（推進/方向転換/中止）＝owner/quest_admin のみ**（P.2） |
| 前提の作成・検証追記・編集 | **検証プール所有（owner/quest_admin）**＝共有前提は複数コンセプトに影響するため編集をプール所有に寄せる（[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.5・P.3）。前提⇔コンセプトのリンク/重要度変更は作成者＋owner |
| 評価 | **評価者権限**のみ「評価する（SC-62）」を表示 |
| 評価結果の閲覧 | **評価者が指定した公開範囲（visibility）に従う**（既定＝パーティー全員。限定時は投稿者＋評価者＋所有者/管理のみ）→ 第9節 |

## 3. レイアウト構成（決定）

- **ヘッダー（全幅カード）**＝クエスト名パンくず（SC-12 のコンセプトタブへ）・コンセプト名・ステータスバッジ・**総合判定 Go/Pivot/Kill バッジ**・★選定・**由来アイデア chip**・（権限で）編集/活性化・保管・メタ（作成者/公開範囲/作成日/最終更新）。
- **関連情報パネル（全幅・ヘッダー直下の独立パネル）**＝ヘッダーカードの直後・2カラムの上に配置（**ユーザー確定 2026-09-25**＝SC-22 の「関連情報ストリップ」と同 strip で統一・[SC-22 アイデア詳細](SC-22_アイデア詳細.md) §4.6b・FR-41／§4.2）。
- **メイン＋右レールの2カラム**。**狭い画面/モーダル/モバイルでは1カラムに縦積み**（SC-12/SC-22 と一貫）。
  - **メイン（左）**＝成果物スキーマを**意味の束（項目グループ）**で区切り、各グループ末尾に**仕切り線＋議論ルームへの遷移ボタン**を文脈配置（[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.7 グループ・ルーム 3〜5）。最後に**⑥前提と検証（核心）**。
  - **右レール**＝①投票 ②評価結果 ③**総合判定（最下部）**（**ユーザー確定 2026-09-25**＝総合判定を右レール一番下に置く／SC-22 の「情報（メタ）」ブロックは廃止しメタはヘッダーに集約）。
- **下部＝総合チャット（総合ルーム）**＝[SC-22 アイデア詳細](SC-22_アイデア詳細.md) §4.4 と同型の**議論アクティビティ・グラフ＋直近プレビュー＋開く導線**（UI 統一）。
- **ガイダンス（[デザイン標準](../デザイン標準.md) §4.13 ＝`.screen-purpose`）＝ヘッダー固定ではなく、説明が要る各要素の傍に配置**（コンセプト名の横「コンセプトとは？」／`viability`・前提と検証・評価観点 の各見出し横に ⓘ）。既定は ⓘ＋短ラベル、ホバー/フォーカスでフローティング展開（隣を押し出さない）、クリックで全文ダイアログ。ISO 56001 準拠の定義・目的・粒度を理解させる（配置＝§4.1 コンセプト名横／§4.3 `viability` 横／§4.4 前提と検証 横／§4.6 評価観点 横）。
- 業務層のクリーン基調。ゲーム要素は共通ヘッダーの Lv/コインと投票 XP の表記のみ。

### 4.2 関連情報パネル（🔗・ヘッダー直下・全幅・独立・情報インプット連携・FR-41）
- **ヘッダーカードの直下・全幅の独立パネル**（横スクロール棚 strip）に配置（**ユーザー確定 2026-09-25**＝SC-22 の関連情報ストリップと同型で統一）。**本コンセプトに紐づいた情報**の一覧（外部情報の知識レイヤ・FR-41）。データ＝`info_links`（`target_type='concepts'`）を**成果物側 read で合成取得**（`GET /concepts/{id}` の `related_info[]`・[API設計 P_コンセプト](../../API設計/P_コンセプト.md) P.1／N 委譲・一致度 `score` 降順・`rejected`/archived 除外）。
- **カード**＝タイトル＋要約＋種別バッジ（🔗関連／✅裏付け／⚠反証）＋由来（🤖自動／✋手動＝関連付けた人のアバター＋氏名）。**カードクリックで情報詳細（SC-52＝`/info-items/{id}`）**。⚠反証を先頭固定・「⤢ 全画面で一覧」で Modal グリッド。
- **反証（refuting）は⚠強調**＝当該コンセプト/前提の前提を揺さぶる情報。1 情報の反証 → 1 前提 → 複数コンセプトへ波及（P.7・§4.6）。
- **「＋ 関連情報を追加」導線**（パネルヘッダー）＝成果物→情報の逆向きピッカー（既存情報を検索＝`GET /info-items` 流用 →種別選択→`POST /info-links`〔`target_type='concepts'`〕流用・新規 EP 不要）。**⚠ 付随課題**＝関連リンク対象ピッカーに `concepts`/`assumptions` を追加する backend 対応が必要（`impl/backend/app/tenant/info/repository.py::search_link_candidates` が現状 `else: return []`・[API設計 P_コンセプト](../../API設計/P_コンセプト.md) P.10・本ドメイン実装と同時対応）。

### 4.3 メイン: 成果物スキーマ（項目グループ・仕切り線＋議論導線）
- スキーマ7項目（[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.3）を**意味の束（グループ）**で表示。各グループ末尾に**仕切り線＋💬「このグループを議論 →」**を置き、対応する**グループ・ルーム**（`concept_chat_scope_kind=group`）へ遷移する（グループは 3〜5 の固定集合＝断片化回避・§3.7）。

| グループ | 含む項目（フィールド） | 末尾の導線 |
| --- | --- | --- |
| **A. 価値・対象・競合** | ① 課題・機会（`problem`）／② 狙う価値＝価値提案（`value_proposition`）＋対象（`target`）／③ 競合・差別化（`differentiation`） | 仕切り線＋💬「このグループを議論 →」（group ルーム） |
| **B. 解の形態** | ④ 解の形態＋必要な能力（粗）（`solution_form`） | 仕切り線＋💬「このグループを議論 →」（group ルーム） |
| **C. 採算・事業性** | ⑤ viability＝価値実現モデル（`viability`＝jsonb・コスト/収益モデル/ROI・**経営説得の核**・ISO §8.3.3） | 仕切り線＋💬「このグループを議論 →」（group ルーム） |

- グループ⇔ルームの対応は固定集合。ルームが未作成なら owner/quest_admin が作成（`POST /concepts/{id}/chat-scopes`・P.6）。閲覧は全員・投稿はコメント権限。
- **`viability` の見出し横に ⓘ ガイダンス**（[デザイン標準](../デザイン標準.md) §4.13）＝「価値実現モデル（value realization model）とは＝コスト/収益モデル/ROI で "how value can be realized" を示す・ISO §8.3.3」を短ラベル＋全文で補足（用語が難解なため）。

### 4.4 メイン: ⑥ 前提と検証（核心・検証プール）
- **ISO ③（検証）の実体**。各前提を**リンクされたカード**で表示（`assumptions` × `concept_assumption_links`・M:N・データモデル §5.40-5.42）。**同じ前提を競合コンセプトで共有**し、一度の検証を再利用（DRY・[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.5）。
- **セクション見出し「前提と検証」の横に ⓘ ガイダンス**（[デザイン標準](../デザイン標準.md) §4.13）＝「前提＝コンセプトが成り立つ仮説／検証＝証拠で支持・反証・保留を判定・否定結果こそ価値（筋の悪い方向を早く止める）・ISO 56001 §8.3/§9」を短ラベル＋全文で説明（この段の中核概念のため）。
- **前提カードの表示項目**:
  | 項目 | 補足 |
  | --- | --- |
  | 前提（記述） | `assumptions.statement` |
  | 重要度（criticality） | `critical`（致命的）/ `major`（重要）/ `minor`（補助的）バッジ。**リンク単位**＝同じ前提でもコンセプトごとに重みが違う（`concept_assumption_links.criticality`） |
  | 現在判定 | 支持（`supported`）/ 反証（`refuted`）/ 保留（`inconclusive`）＝最新の検証イベントから導出（`assumptions.current_verdict`）。色のみに依存しない |
  | 検証履歴 | 時系列（新しい順）＝検証方法 / 結果 / 判定 / **検証実施日（`validated_on`）** / **規模（`scale`＝サンプル数/対象）**（`assumption_validations`・§3.5）。**実施日と規模は必須**（エビデンスは古びる＝再検証を促す・規模＝検証の強さ） |
  | 要再評価（stale） | **⚠ stale マーク**＝共有前提が反証に転じるとリンク先の全コンセプトが「要再評価」に（`concept_assumption_links.is_stale`・P.7 反証波及）。評価者が織り込んだら解除（`is_stale=false`） |
  | ＋前提リンク / 情報リンク | 既存前提をこのコンセプトにリンク（`POST /concepts/{id}/assumptions`）／新規前提作成（`POST /quests/{id}/assumptions`・プール所有）。情報リンクは §4.2 の関連情報から前提へも張れる |
  | 💬 前提スレッド → | **前提1件＝1スレッド**（`concept_chat_scope_kind=assumption`）へ遷移（§3.7・前提リンク時に自動生成） |
- 検証イベントの追記＝プール所有（`POST /assumptions/{id}/validations`）。`verdict=refuted` は**反証波及を発火**（リンク先の全コンセプトを stale・作成者＋評価者へ通知・P.7）。

| 総評・観点別コメント | 評価者アバター＋氏名＋総評（`overall_comment`・確定時必須）＋観点別コメント |
| 未評価時 | 「評価待ち」表示 |
| 評価する（SC-62） | **評価者権限のみ表示**。新規/再評価。公開範囲は評価時に指定（**SC-62 コンセプト評価モーダル**） |

### 4.7 右レール: 総合判定（最下部）
- **右レールの一番下**に配置（**ユーザー確定 2026-09-25**）。**Go / Pivot / Kill / 未判定**（`concept_decision`）＋**根拠**（`decision_rationale`）。
- **owner/quest_admin のみ操作可**（`PUT /concepts/{id}/decision`・P.2）。それ以外は表示のみ。
- コンセプト自身の総合判定＝**評価者の推奨（§4.6 の分布）とは別概念**（owner が推奨・投票・検証を総合して決める・データモデル §3 `concept_decision` 注記）。**"Go/Pivot/Kill" は当社ラベル**。

### 4.8 下部: 総合チャット（総合ルーム・議論の活発度＋導線＋直近プレビュー）
- **総合ルーム（`concept_chat_scope_kind=overall`・1・必須）**＝横断議論＋最終 Go/Pivot/Kill の場（アイデアの単一ルームに相当する母屋・[設計ドラフト コンセプト機能_ISO56001_再設計](../../設計ドラフト/コンセプト機能_ISO56001_再設計.md) §3.7）。**作成時に自動生成**（P.2）。
- **議論アクティビティ・グラフ**（[SC-22 アイデア詳細](SC-22_アイデア詳細.md) §4.4 と同型・UI 統一）＝**直近14日の日次メッセージ数の棒グラフ**＋サマリ（今週件数/先週比↑↓・参加人数・最終投稿）＋状態ラベル（🔥活発/落ち着き気味/💤停滞）。**評価の頃合い**の判断材料。データ＝`chat_messages`（`concept_chat_scope_id` で総合ルームに紐付け）の日次集計。
- **直近メッセージを数件プレビュー**（アバター＋氏名＋時刻＋本文・`@`メンション強調）＋「**チャットを開く（総合ルーム）→**」。
- **未読/メンション/活発度はコンセプト単位でロールアップ＋各ルーム個別**の二段（§3.7）。0件なら「まだコメントはありません」＋開くボタン。
- チャット機構（メッセージ本体・リアクション・編集/削除）は **E ドメイン再利用**（`chat_messages`/`chat_reads` を `concept_chat_scope_id` で一般化・最小侵襲拡張・P.6・データモデル §5.16/5.31/5.45）。

## 7. データ・API（想定）

- **GET `/concepts/{concept_id}`**（合成・P.1）: `concept`（スキーマ全項目 problem/value_proposition/target/differentiation/solution_form/viability〔jsonb〕/decision/decision_rationale/status/is_selected）・`source_ideas[]`・`assumptions[]`〔リンク＝criticality/is_stale・現在判定〕・`evaluation`（集計要約）・`chat_scopes[]`・`related_info[]`・`my_permissions`。
- **POST/PATCH/DELETE `/concepts/{concept_id}`** ほか（P.2）: 作成/編集/論理削除・`activate`/`archive`/`select`/`decision`。
- **GET `/assumptions/{assumption_id}`**・**POST `/assumptions/{id}/validations`**（P.3）: 前提詳細（検証履歴）・検証イベント追記（`verdict=refuted` は波及）。
- **POST/PATCH/DELETE `/concepts/{id}/assumptions/{assumption_id}`**（P.4）: リンク・重要度変更・stale 解除。
- **GET `/concepts/{id}/evaluation`**・**PUT `/concepts/{id}/evaluation`**（P.5）: 評価集計（visibility 適用）・自分の評価 upsert。
- **POST/DELETE `/concepts/{id}/vote`**（P.5b）: 投票 upsert/取消・+5 XP（初回）。
- **GET `/concepts/{id}/chat-scopes`**・**GET/POST `/concept-chat-scopes/{scope_id}/messages`**・**POST `…/read`**（P.6）: ルーム一覧・メッセージ・既読。機構は E 再利用。
- **議論アクティビティ**（§4.8）＝総合ルームの `chat_messages` 日次集計（アイデア `activity` と同型の集計を P で提供・詳細エンドポイントは TBD・第9節）。
- 匿名化・評価公開範囲・状態遷移/選定/判定の認可は**サーバー側で最終制御**（クライアント表示だけに依存しない・P.0/P.8）。

## 8. アクセシビリティ / 表示配慮

- 投票・評価スコア・総合判定・前提の現在判定は**色のみに依存しない**（数値＋テキスト＋アイコン）。
- 投票ボタンは `aria-pressed`。★選定トグルも `aria-pressed`。
- スコアバーは数値併記。「前提検証の強さ」観点や `viability` は **ⓘ ガイダンス（[デザイン標準](../デザイン標準.md) §4.13）**で意図を明示。
- **ガイダンス ⓘ**（§4.13）＝ボタン扱い＋`aria-haspopup="dialog"`＋`aria-label`。**展開の流れは reduce-motion（OS／`accounts.reduce_motion`）で静止**（§4.9）。フォーカスリングは `outline` でなくベース＋展開部の枠線を青で一続きに。
- 前提の⚠ stale は色＋アイコン＋「要再評価」テキストで示す。
- モーダル差し込み時（SC-12 タブから）はフォーカストラップ・`aria-modal`・`Esc`/バックドロップで閉じる（モーダル標準）。
- 議論ルームへの💬導線は各グループの見出し文脈に紐づけ（スクリーンリーダーで「グループ名の議論を開く」と読める `aria-label`）。

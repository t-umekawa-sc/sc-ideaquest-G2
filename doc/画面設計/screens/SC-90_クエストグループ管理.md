# SC-90 クエストグループ管理（画面設計 / 機能詳細）

> 画面遷移図: `doc/画面設計/画面遷移図.md` ／ モック: `doc/画面設計/mocks/SC-90_クエストグループ管理.html` ／ 要件: `doc/要件定義/README.md`（FR-17・第2/6節・データモデル）
> API 仕様の正: `doc/API設計/B_会社・アカウント・所属.md`（**B.4 QG管理者 API＝参加選択専任**・B.0/B.0.1 認可）。本画面は追随。

## 1. 概要・目的

- **クエストグループ管理者（QG管理者）** が、**自分が `admin` として管理するクエストグループ**の **参加メンバー（メンバーシップ）を選択・管理** する画面。
- **職務分離（SoD・2026-08-01・データモデル §8-⑯／B.4）** により、QG管理者は **「参加管理（メンバーシップ）専任」** に縮小。**自社アカウント・ディレクトリ**から既存アカウントを選び、**自分が `admin` のグループへ参加追加 / 除外** する。
- **アカウント本体のライフサイクル操作（発行 / 無効化 / ログインID・メール編集 / パスワード再設定）は持たない**＝これらは **会社アカウント管理者（SC-93）** または **システム管理者（SC-92）** の領分。
- 導線: ダッシュボード（SC-01）のロール条件付き管理導線（QG管理者＝1 グループ以上で `admin` 所属を持つユーザーのみ表示）。

## 2. アクセス条件・権限

| 項目 | 内容 |
| --- | --- |
| アクセス可能者 | **クエストグループ管理者＝`quest_group_members.role=admin` の有効所属（`removed_at IS NULL`）を 1 つ以上持つユーザー**（B案 2026-07-27・`system_role` では判定しない）。管理対象＝その `admin` 所属のグループのみ。`admin` 所属が 0 件なら本画面は **403** |
| できること | **参加管理のみ**＝自社ディレクトリ参照＋自分が `admin` のグループへ**既存アカウントを参加追加 / 除外**（`quest_group_members` の per-group 操作・`role=member` 固定） |
| できないこと | **アカウントの発行 / 無効化 / ログインID・メール編集 / パスワード再設定**（＝会社アカウント管理者 SC-93 ／ システム管理者 SC-92）・**グループ内ロール `admin`（QG管理者）の付与/剥奪**（＝システム管理者 SC-92）・システムロール変更・他社/他グループ操作 |
| SoD の肝 | 参加追加/除外は **会社DB `quest_group_members` の per-group 行だけ**を操作＝**アカウント本体（`accounts.status`・identity）には一切触れない**。よって「任意垢を追加→無効化で会社全体を破壊」という権限昇格を構造的に遮断（B.4） |

## 3. レイアウト構成（決定・業務層）

- **共通ヘッダー**（管理者もゲーム層ステータスを持つため Lv/コイン/SP＋ベル＋アバターメニュー）。
- **管理グループの選択**: 管理者が複数グループを管理する場合に切替（`select`）＋メンバー数。**表示されるのは自分が `admin` のグループのみ**。
- **ツールバー（一覧標準 `.list-toolbar`）**: 検索（氏名/ログインID）＋**「＋メンバーを追加」**（ディレクトリ・ピッカーを開く）。
- **参加メンバー一覧テーブル（`.table`）**: 氏名 / ログインID / 参加日 / 操作（**このグループから除外**）。
- **メンバー追加モーダル（ディレクトリ・ピッカー）**: 自社アカウント・ディレクトリを検索し、既存アカウントを選んで**このグループにメンバーとして追加**。

## 4. 表示・入力項目

### 4.1 参加メンバー一覧テーブル
- **氏名 / ログインID / 参加日 / 操作**。※このグループの `quest_group_members`×`users`（`removed_at IS NULL`）。
- 操作＝**このグループから除外**（per-group トゥームストーン `removed_at`・アカウント本体は無効化しない）。
- **状態・グループ内ロール・PW再設定・無効化は表示/操作しない**（アカウント本体の属性＝SC-93/SC-92 の領分）。参加ロールは常に `member`（`admin` 付与は SC-92）。

### 4.2 メンバー追加モーダル（ディレクトリ・ピッカー）
- **検索（氏名/ログインID のターゲット照会）** → 候補一覧（**最小射影**＝氏名・アバターのみ）から選択 → **このグループに `member` として参加追加**。
- ディレクトリは `GET /admin/company-directory`＝**`email` / システムロール / 他グループ所属は返さない**（PII・組織構造・system_admin 標的化を防ぐ最小射影・B.4/B.7.2）。`status='active'` のみ。
- **既に当該グループに参加中のアカウントは候補から除外**（重複所属不可・部分ユニーク §5.5）。
- 発行（新規アカウント作成）はここでは行わない＝目的の人が未発行なら会社アカウント管理者（SC-93）へ依頼。

## 5. アクション・遷移

| トリガー | 条件 | 遷移/結果 |
| --- | --- | --- |
| ＋メンバーを追加 | — | ディレクトリ・ピッカー→検索→候補選択→**このグループに `member` で参加追加**（`quest_group_members` 行作成 or `removed_at` を NULL に戻す） |
| このグループから除外 | 参加中メンバー | 確認→**per-group トゥームストーン**（`removed_at` 設定・監査保持）。**アカウント本体・他グループ所属は不変**。それまでの入力（アイデア/投票/評価/コメント）は保持 |
| 行/カードクリック | — | **主アクション割当なし**（[デザイン標準.md](../デザイン標準.md) §4.5 ⑪ の例外＝唯一の操作「除外」が破壊的なため、行/カード全体のクリックには束ねない）。除外は ⋯メニューから `confirm` 付きで実行・指カーソルも出さない |
| 管理グループ切替 / 検索 | — | 一覧を更新 |

- **参加追加が与えるもの＝eligibility のみ**: グループ参加は「そのグループのクエストのパーティーに入れる資格」を与えるだけ。**クエスト/アイデアの実閲覧はパーティー追加が必要**（ドメイン C／非パーティーは 404）＝一方的追加でも業務コンテンツは露出しない。

## 6. データ・API（正＝`B_会社・アカウント・所属.md` B.4）

- **GET `/api/v1/admin/quest-groups`**: 自分が `admin` のグループ一覧（メンバー数付き・セッション会社固定）。空なら本画面は 403。
- **GET `/api/v1/admin/quest-groups/{group_id}/members`**: そのグループの参加メンバー一覧（`removed_at IS NULL`）。
- **POST `/api/v1/admin/quest-groups/{group_id}/members`** `{account_id}`: 既存アカウントを自グループに **`member` で参加追加**（ディレクトリで選択・`admin` 付与不可）。
- **DELETE `/api/v1/admin/quest-groups/{group_id}/members/{account_id}`**: 自グループから除外（per-group トゥームストーン・204）。
- **GET `/api/v1/admin/company-directory`**: 参加追加の候補選択（**最小射影**＝`account_id`/`display_name`/`avatar_url`・`status='active'` のみ）。
- 権限は**サーバーで判定**＝`group_id` がセッション会社に属し・呼び出し元が当該グループに有効 `admin` 所属を持つこと（満たさなければ 404＝存在秘匿）。**アカウント発行/無効化/identity/PW の API は本画面からは呼ばない**（SC-93/SC-92）。

## 7. アクセシビリティ / 表示配慮

- 除外は**破壊的でない per-group トゥームストーン**＋確認ダイアログで誤操作を防止。
- ディレクトリ・ピッカーはキーボード操作可・候補にラベル。最小射影で PII を出さない。
- テーブルはキーボード操作可・操作ボタンにラベル。

## 8. 状態・バリエーション

| 状態 | 表示 |
| --- | --- |
| 管理グループが1つ | グループ切替は単一表示 |
| `admin` 所属が 0 件 | 本画面に到達不可（403・ダッシュボードに導線を出さない） |
| メンバー該当なし | `.list-empty`（「＋メンバーを追加」を促す） |
| ディレクトリ候補なし | ピッカー内 `.list-empty`（未発行なら SC-93 へ依頼を案内） |

## 9. 残TBD（この画面）

- **職務分離（SoD）＝ 決定（2026-08-01）**: QG管理者は **参加選択専任**に縮小（データモデル §8-⑯・B.4）。**なぜ**＝会社DB内アカウント参照の緩和（B.7.2）と両立させても、QG管理者が破壊系（発行/無効化/identity/PW）を持つと「任意垢を自グループに追加→無効化/改変で会社全体を破壊/乗っ取り」の権限昇格が生じるため、破壊系を撤廃し **会社アカウント管理者（`company_account_admin`・SC-93）** へ移管。ロール付与（`admin`）は system_admin のみ（§8-①）。
- **QG管理者の表現＝グループロール一本化（B案）＝ 決定（2026-07-27）**: 「クエストグループ管理者」は `system_role` では表さず、**会社DB `quest_group_members.role=admin`（per-group）のみで表現**。**SC-90 のアクセス可否＝`admin` の有効所属を 1 つ以上持つこと**。データモデル §8-⑭・§3・§4.2・§5.3・§5.5、SC-92/SC-93/SC-01、API設計 §1.6 に反映。
- **グループ内ロールの権限範囲 ＝ 決定（2026-07-20）**: `role`（`quest_group_role`=`admin`/`member`）の **`admin` 付与/剥奪はシステム管理者のみ**（B案でも維持）。QG 管理者の参加追加は `member` 固定。データモデル §5.5 に反映。
- **参加追加の同意要否 ＝ MVP は一方的追加で可（B.7）**: グループ参加は eligibility のみで業務コンテンツ非露出（ドメイン C/D のパーティー門番）。厳密化するなら招待/同意フローを将来検討。
- **参加除外の運用 ＝ 決定（2026-07-20）**: QG 所属の解除は `quest_group_members.removed_at` トゥームストーン（監査保持・一覧/参照範囲から除外）。アカウントの有効/無効（`accounts.status`）とは**独立**（本画面では触れない）。データモデル §5.5 に反映。
- **監査ログ表示 ＝ 決定（2026-07-20・後回し）**: 参加追加/除外は `system_audit_logs` に記録済み（B.6）。専用の監査ログ一覧 UI は MVP スコープ外。

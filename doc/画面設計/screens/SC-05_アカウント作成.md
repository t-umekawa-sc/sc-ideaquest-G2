# SC-05 アカウント作成（セルフサインアップ・画面設計 / 機能詳細）

> FR-48②（セルフサインアップ）の画面。正本＝[要件 FR-48](../../要件定義/README.md#6-機能要件)／[設計ドラフト §8.2/§8.4](../../設計ドラフト/アイデアコンテスト機能_設計.md)／[API設計 A §A.11.2-A.11.4](../../API設計/A_認証・セッション.md)／データモデル [§4.4a signup_challenges](../../データモデル.md)。
> OTP 入力は **SC-00 状態C を再利用**（UI を増やさない）。確定後は **SC-00 ログイン画面へプリフィル誘導**（自動ログインしない・SEC I）。

## 1. 概要・目的

会社フラグ `self_signup_enabled=true` の会社に対し、利用者が自分でアカウントを作成する。公開（コンテスト専用）会社のデモ参加導線が主用途（`private` 会社でも opt-in 可）。**検証前にアカウントを作らない**（決定A）＝入力はメール認証成功まで pending（`signup_challenges`）で保持し、成功して初めて `accounts` を作る。

## 2. アクセス条件・権限

- **未認証**で到達（ログイン前）。SC-00「アカウント作成」リンクから遷移。
- 作成されるアカウントは常に `role=general`（権限はサーバー権威・client 指定不可・SEC E）。
- 会社の `self_signup_enabled` 状態・会社コードの存在は**画面には明かさない**（列挙耐性・SEC B）＝送信は一律「認証コードを送信しました」。

## 3. 画面状態

| 状態 | 内容 |
|---|---|
| 状態1: 入力 | 会社コード・ログインID・メール・表示名・パスワードの入力フォーム |
| 状態2: 認証コード入力 | **SC-00 状態C を再利用**（6桁 OTP・再送・残り時間）。`POST /public/signup` 成功（202）で遷移 |
| 状態3: 完了 | 「アカウントを作成しました」→ **SC-00 ログインへ**（会社コード/ログインID プリフィル）。`POST /public/signup/verify` 成功（200）で遷移 |

## 4. 表示項目

### 状態1: 入力フォーム
- **会社コード**（text・必須）。※public デプロイで既定会社コード（`GET /public/bootstrap` の `default_company_code`）がある場合は**欄を隠して自動セット**（§8.1）。
- **ログインID**（text・必須）＝希望ID。重複可否はここでは判定しない（列挙耐性・確定時に一意チェック）。
- **メールアドレス**（email・必須）＝認証コード送信先。
- **表示名**（text・必須）＝PII 最小化のため要求するのは表示名まで（SEC J）。
- **パスワード**（password・必須）＋確認入力。最低文字数表示。**漏洩PW拒否（HIBP・SEC D）実装済**＝漏洩PWはサーバーが 422（field=password）で拒否（env-gated）。
- **CAPTCHA（Turnstile・SEC G）実装済**＝`GET /public/bootstrap` が `turnstile_site_key` を返す時だけウィジェットを表示（入力/認証コード両フェーズ＝再送トークン用）。トークンを `POST /public/signup` に同梱。未設定（dev）は非表示。
- 送信ボタン「認証コードを送信」。下部に「既にアカウントをお持ちの方は ログイン」。

### 状態2: 認証コード入力（SC-00 状態C 流用）
- マスクされた送信先（`masked_to`）・6桁入力・再送（`resend_available_in`）・残り時間（`expires_in`）。

### 状態3: 完了
- 成功メッセージ＋「ログインへ進む」（会社コード/ログインID プリフィル）。

## 5. アクション・遷移

| 操作 | 条件 | 遷移/結果 |
|---|---|---|
| 「認証コードを送信」押下 | 形式OK | `POST /public/signup` → **一律 202** → 状態2（内部条件を満たさなくても同一応答・SEC B） |
| 「認証コードを送信」押下 | 形式NG | 状態1 で §4.7 検証表示（必須/email形式/PW最低文字数） |
| 認証コード押下 | 正しい | `POST /public/signup/verify` → 200 → 状態3 → SC-00 ログイン（プリフィル） |
| 認証コード押下 | 誤り/期限切れ/試行超過 | 状態2 でエラー（試行超過は当該 pending 失効＝再送/やり直し・SEC C） |
| 「ログイン」リンク | — | SC-00 状態A へ |

## 6. バリデーション（§4.7＝4部品で表示）

- 必須＝会社コード/ログインID/メール/表示名/パスワード。email 形式。パスワード最低文字数＋確認一致。
- **会社の存在・`self_signup_enabled`・ID/メール重複は client 検証しない**（列挙耐性・サーバーが一律 202）。
- 入力検証エラー表示は [デザイン標準 §4.7](../デザイン標準.md) の4部品（Field error／FormSummary／useFormErrorNotice／FormFooterError）。

## 7. エラー・メッセージ（例）

| ケース | 文言（例） | 補足 |
|---|---|---|
| 形式不正 | 各 Field に個別表示（§4.7） | 状態1 |
| 送信完了（一律） | 「認証コードをメールに送信しました。」 | 状態2・成否に関わらず同一（SEC B） |
| コード誤り | 「認証コードが正しくありません。」 | 状態2・残り試行 |
| コード期限切れ/試行超過 | 「有効期限が切れました。お手数ですがもう一度お試しください。」 | 状態2・やり直し |
| 確定失敗（汎用） | 「アカウントを作成できませんでした。」 | 一意性先約等も in-band で明かさない（SEC B・out-of-band 通知） |

## 8. API 入出力（正＝[API設計 A §A.11.2-A.11.4](../../API設計/A_認証・セッション.md)）

- `GET /public/bootstrap` → `{ default_company_code, self_signup_available }`（会社コード欄の出し分け）。
- `POST /public/signup` `{ company_code?, login_id, email, display_name, password }` → **202** `{ status:"verification_sent", masked_to, expires_in, resend_available_in }`。
- `POST /public/signup/verify` `{ company_code, email, code }` → **200** `{ status:"created", company_code, login_id }`（自動ログインしない）。

## 9. 非機能・セキュリティ（SEC A〜J・正＝[設計 §8.4](../../設計ドラフト/アイデアコンテスト機能_設計.md)）

- **A**＝検証前に `accounts` を作らない（pending＝`signup_challenges`）。**B**＝一律 202・out-of-band。**C**＝OTP 短命/単回/試行ロック/再送レート制限。**D**＝PW 即 Argon2id・最低文字数＋**漏洩PW拒否〔HIBP・実装済・env-gated〕**。**E**＝権限固定（role/company はサーバー権威）。**F**＝会社コード再検証。**G**＝Origin/Sec-Fetch＋IP/メールレート制限＋**CAPTCHA〔Turnstile・実装済・env-gated〕**＋**使い捨てメール判定〔ローカル blocklist・実装済〕**。**H**＝新規投稿レート制限・**管理者通知ダイジェスト〔`signup_registered`・クールダウン・実装済・env-gated〕**。**I**＝自動ログインしない（確定後ログイン誘導）。**J**＝PW/コードをログに出さない・監査・PII最小化。

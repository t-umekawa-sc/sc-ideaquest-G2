# SC-50 情報インプット（一覧・登録・詳細＋関連情報パネル）（画面設計 / 機能詳細）

> 外部 WEB 情報を**手動貼り付け**で登録し、属性を付け、アイデア/コンセプト/クエストへ**動的に関連づけ**る会社横断の知識レイヤ。**サービスの差別化の芯**。
> 仕様の正＝[情報インプット機能 設計](../../設計ドラフト/情報インプット機能_設計.md)（残論点は §11 で確定）・[API設計 N](../../API設計/N_情報インプット.md)・[データモデル §5.33〜5.37/§3（`info_*` enum）](../../データモデル.md)。通知は [H](../../API設計/H_通知.md)。要件＝[FR-41](../../要件定義/README.md#6-機能要件)。UI 標準＝[デザイン標準 §4.1](../デザイン標準.md)（ダイアログ内コンテンツ標準）・一覧は [フロントエンド実装フロー規約 §4.1](../../規約/フロントエンド実装フロー規約.md)（サーバー委譲）。
> 画面 ID＝**SC-50 一覧／SC-51 登録・編集（モーダル）／SC-52 詳細（モーダル）**（本ファイルに束ねる。SC-13 が掲示板＋ダイアログを1ファイルにする流儀に倣う）。

## 1. 概要・目的

- 参加者**全員**が外部 WEB 情報を**無造作に登録**（低摩擦＝タイトル＋本文＋出典URL）→ **`info_curator`（情報判定権限）が属性付与/判定** → **アイデア/コンセプト/クエストへ動的リンク** → **反証は能動的に“揺さぶる”**（要再評価）。
- **受動的なスクラップ帳でなく、絞り込みの流れを能動的に駆動する知識レイヤ**（ISO56002 §7 知識/インテリジェンス・機会特定の燃料）。
- **取り込みは手動貼付のみ**（サーバは外部URLを取りに行かない＝SSRF 対象外・§7）。

## 2. アクセス条件・権限

- **会社横断の知識プール**＝クエスト門番（`can_access_quest`）ではなく、**会社内の active ユーザーなら一覧/詳細を閲覧可**（テナント内・他社は不可）。グローバルナビ（`.appnav`）業務群に1項目「情報インプット」を追加。
- 書き込みは**フィールド群ごとにオーナーが違う**（2026-09-21 確定・[API N.0](../../API設計/N_情報インプット.md)）:
  - **内容（タイトル/本文・説明/出典URL/参考資料）＝作成者のみ**（`status` 非依存＝raw/curated 問わず作成者が編集可・**`info_curator` も内容は編集不可**）。**内容の編集履歴を保持**（誰が・いつ・何を＝アイデア版管理と同型・Phase C）。
  - **キュレーション（属性値・情報判定 triage・`status` 遷移 raw→curated→archived・アーカイブ/解除）＝`info_curator` のみ**（＝情報のキュレーション全般）。属性/triage を付与すると raw→curated へ遷移。
  - **関連リンク（情報側）＝会社内 active 全員が任意に設定可**（追加・種別変更〔関連/裏付け/反証〕・自分が付けた分の棄却／`status` 非依存・**`info_curator` 管轄外**）。低摩擦で関連づけを“発生”させる層。
  - **リンクの採否・統制は成果物側に委任**＝クエスト/アイデア/コンセプトの**管理権限者**が、貼られたリンクをどう取り込む/却下するかを判断（成果物側の採否ワークフロー＝各ドメインの別スコープ・§8）。反証の「要再評価」発火の受領も成果物側で扱う。
  - **`info_curator` の付与/剥奪＝会社アカウント管理者/system_admin**（導線は SC-90 系に同居・§8）。**管理者に情報の上書き編集権は無い**（必要なら自分に curator を付与）。
- 認可失敗＝403／他テナント＝404／未認証＝401。**編集可否はサーバーが `can` で返す**（`can.edit_content`＝作成者／`can.curate`＝curator／`can.add_link`＝全員）＝フロントは表示/UX 出し分けのみ・PATCH/リンクEP で再検証（コーディング規約 §1/§2.2）。

## 3. レイアウト構成（SC-50 一覧）

- ヘッダー（画面名「情報インプット」）＋主操作「＋情報を登録」（全ユーザー）＋一覧ツールバー（`.list-toolbar`）。
- **タブ構成（クエスト詳細 SC-12 と同じ体裁＝`.tabs`/`.tab`）**＝①「🧭 情報インプット」（一覧）／②「🔍 全文検索」。**全文検索の結果表示も SC-12 の全文検索タブに揃える**（検索ボックス＋対象セレクト＋件数＋結果カード `card-accent ft-result`＝状態/影響分類バッジ＋タイトル＋一致箇所のハイライトスニペット`<mark>`）。
- **全文検索タブ**＝**タイトル＋本文＋要約**を対象とする全文検索（`GET /info-items?q=`＝title/`body_text` の PGroonga）。対象セレクト＝すべて/タイトル/本文/要約。**これが差別化の核**であり、一覧タブの DataTable 標準の横断検索/列フィルタとは**別建て**（本文まで探すのは全文検索タブの役割・標準検索は表示項目のみ）。スニペットは `dangerouslySetInnerHTML` 不使用＝キーワードのみ `<mark>`（§2.2④）。**一致箇所は要約ではなくサーバーが返す「一致抜粋」（`match_snippet`＝title＋本文からキーワード周辺を切り出し）を優先表示**し、タイトルの一致語も強調する＝**要約に出ない箇所での一致（例＝『コメ』が本文の『コメント』にバイグラム一致）でも該当箇所を必ず見せる**（DFT-N-003・§1.11）。`match_snippet` が無い（正規化のみの一致 等）時だけ要約にフォールバック。結果クリックで詳細（SC-52・intercept）。
- **一覧タブは DataTable サーバーモード委譲**（`GET /info-items`・§1.8.1・フロント実装フロー規約 §4.1）＝**標準の横断検索（表示項目のみ＝title/summary/created_by。本文は含めない）**・分類フィルタ（`status`/`priority`/`source`/`classification`/`scope`/`target_business`/`impact_class`/`impact_level`/`impact_timing`/`triage`／`category` #8 多値）・ソート（`-created_at`/`priority`/`-impact_level`/`due_date`）・番号/カーソルページャ・列設定/密度/CSV。列 `sortable`/`filter` は backend ホワイトリスト一致。
- **ワードクラウド パネル**（一覧タブ内）＝一覧の上部（`GET /info-items/word-cloud`）。**現在の絞り込み範囲**のトークン頻度を可視化＝語クリックで全文検索タブの `q` に流し込み（絞り込み動線）。
- 既定表示＝`status=archived` を除外（アーカイブは絞り込みで明示表示）。

## 4. 表示項目（一覧カード/行）

- タイトル／**要約プレビュー**（`summary`・§12-3）／`status` バッジ（`raw`＝未判定・`curated`＝判定済み・`archived`）／`priority`（優先度）／`impact_class`（機会/脅威/その他バッジ・色分け）／情報カテゴリ(#8) チップ／情報ソース（#2）／出典URL（リンク・別タブ・`rel="noopener noreferrer"`）／`due_date`（対応/有効期限・切迫度）／登録者（アバター/氏名）／登録日時／💡関連リンク数（`link_count`）／**🧵続報バッジ**（`follow_up_count>0` で数を表示・§12-1）。
- **要約/本文プレビューはサニタイズ済み**（要約は平文 `summary`／本文は `body_html` の許可リストサニタイズ・XSS・§9）。`roots_only` で続報を根に束ねる切替。

## 6. SC-51 登録・編集（モーダル）

- **標準モーダル**（`.modal.sectioned`・URL付き＝Parallel＋Intercept・[デザイン標準 §4.1](../デザイン標準.md)）。フッター文言＝フォームなので「**キャンセル**」。
- **ダイアログ内コンテンツ標準**（§4.1）＝囲まず**項目ごとに仕切り線**（`.dialog-section`）。
- **入力グループ（項目ごとに区切り）**:
  1. **基本（全ユーザー・低摩擦）**＝タイトル（必須）／内容・説明（**リッチテキスト**＝WEBページを書式込みで貼付・§6a）／出典URL（http/https のみ・422 `invalid_url`）。
  2. **分類（`info_curator` のみ・raw では非表示 or 読取）**＝優先度／情報ソース／情報分類（単一）／大分類／対象事業／**情報カテゴリ（#8・複数可）**。
  3. **影響評価（環境スキャン・curator）**＝影響度／**影響分類（機会/脅威/その他）**／影響発生時期。
  4. **判定（トリアージ・curator）**＝情報判定日／情報判定／判定理由。
  5. **期限日**＝対応/有効期限（任意・#11 影響発生時期とは別軸）。
- **出し分け**＝一般ユーザーは基本のみ（保存で `status=raw`）／`info_curator` は全項目（属性を付けると `status=raw→curated`）。編集時、raw の登録者本人は基本のみ編集可・curated 後は `info_curator` のみ。
- 保存（`POST`/`PATCH /info-items`）＝本文/タイトル変更時に**サニタイズ→`body_text` 派生→`info_tokens` 再生成→抽出要約 `summary` 生成→類似度で auto リンク（既定 `related`）再計算**（同期・[API N.6](../../API設計/N_情報インプット.md)・§12-2/12-3）。§4.7 入力検証（必須=タイトル・URL 形式・上部サマリ＋足元ヒント＋エラースナックバー）。

### 6a. リッチテキスト本文・ワードクラウドプレビュー・続報（2026-09-19 追加・§12）
- **リッチテキスト入力（§12-4）**＝WEBページを**書式（太字/箇条書き/見出し/リンク/表）＋画像込みで貼付**。エディタ候補＝Tiptap(ProseMirror) 等（`shared.css` に馴染ませる・選定は実装フェーズ）。**画像は貼付時に MinIO 再ホスト**（`POST /info-items/images`・paste ハンドラで blob→自社 URL 置換）。保存時 nh3 サニタイズ（§9）。
- **ワードクラウドプレビュー（§12-2）**＝本文入力欄の近くに「この情報の語」プレビュー＝草稿を `POST /info-items/word-cloud-preview` で**同期トークン化**して表示（トリガ＝本文 **blur かボタン**・キー入力毎は不可）。保存後は詳細（SC-52）のミニ・ワードクラウドに引き継ぐ。
- **要約プレビュー**＝保存後に抽出要約 `summary` が付く（選別で使う・SC-52/一覧で表示）。
- **続報登録（§12-1）**＝SC-52 詳細 or 一覧行の「**続報を登録**」から開くと、**親の属性を初期プリフィル**した状態で本モーダルが開く（本文/URL は新規）。保存時に `parent_info_id` を送り、**親の未棄却リンクを `origin=auto` でスナップショット複製**。

## 7. SC-52 情報ダイアログ（詳細＝参照／編集を1枚に統合）＋関連リンク

- **1ダイアログ・ロール別モード起動（決定 2026-09-21）**＝行クリック（＝⋯「詳細を開く」）で、**クリックした人の権限に応じて編集可セクションは編集可の状態で開く**（別途「編集」ボタンを踏ませない）。3パターン画面は作らず、**能力フラグでセクション別に編集/参照を出し分け**る:
  - **その他**（作成者でも curator でもない）＝**参照モード**（全て read・フッター「閉じる」のみ）。
  - **作成者**＝**内容**（タイトル/本文/出典URL/参考資料）が編集可・属性は read。
  - **`info_curator`**＝**属性**（属性値・triage）が編集可・内容は read。
  - **作成者かつ curator**＝内容＋属性が編集可。
  - **関連リンクは全モードで read 表示**（編集は別導線「🔗 リンクを編集」＝全員）。
- **フッター**＝**閉じる**＋（編集可セクションがある人のみ）**保存する**（`§4.1` 入力モーダル準拠。従来の参照系フッターから変更）。
  - **保存ボタンは常時活性**（決定 2026-09-22＝dirty ゲートは「なぜ押せないか」が分かりにくいため採らない）。**無変更で保存した時は版を増やさず、ダイアログを閉じてから「変更はありません」を通知**（アイデア D.3 の無変更保存と統一＝早期 return で開いたまま残さない）。
  - **未保存で閉じる時（dirty 時のみ）は破棄確認**＝**フッター「閉じる」・背景クリック・Esc・× の全経路**をガードする（一経路だけだとステージした参考資料/編集が黙って破棄されるため）。保存成功・アーカイブ・画面遷移での閉じはガード対象外（既に確定済み）。
  - **内容変更は編集履歴（`info_item_revisions`）に記録**。
- **表示（read セクション・全モード共通）**＝**要約**（`summary`・§12-3）＋**ミニ・ワードクラウド**＋**この情報からクエストを作成 CTA**＋**続報スレッド**。編集不可セクションは整形 read 表示（無効化入力ではない）。
- **続報スレッド（§12-1）＝全アイテムで時系列表示＋「自分の位置」を強調**（根でも続報でも `根→続報1→続報2…` を表示し、開いているアイテムを「表示中」で示す＝ダイアログ内で時系列と自位置を把握）。「スレッドを見る」メニューは廃止（詳細で辿れるため）。「続報を登録」は⋯メニュー（全員・親プリフィルで SC-51）。
- **この情報からクエストを作成（機会特定→行動の動線・2026-09-19 追加）**＝判定の結果「新しく取り組む価値がある」と判断したら、**「＋ この情報からクエストを作成」**（primary）で **SC-11 クエスト作成**を開く。**元情報バナー（`.disclosure--ref`）＋目的・テーマを情報の要約からプリフィル**（編集可）。保存時に **`info_link`（情報→新クエスト・`origin=manual`・`kind=related`）を自動作成**＝最初から関連付いた状態（API＝C クエスト作成の `from_info_id`／§N と突合）。※判定＝`innovation活動`/カイゼン系のとき特に目立たせる。
- **関連リンク（§N.3・情報側は開放）**＝この情報が紐づく成果物の一覧（`links[]`）＝相手（アイデア/コンセプト/クエスト/前提）へのリンク＋**種別バッジ**（関連/裏付け/**反証**・色分け）＋由来（auto/manual）＋一致度（score）。
  - **追加・種別変更・棄却は会社内 active 全員**（`can.add_link`・`info_curator` 管轄外・`status` 非依存）＝相手を選んで関連付け（`POST /info-links`）／関連↔裏付け↔反証の変更／自分が付けた分の棄却（`rejected_at`・パネルから除外）。
  - **成果物側で採否済み（`disposition != pending`）のリンクはロック表示**＝`links[]` の `disposition` を露出し、リンク編集で**種別コンボを非活性**＋**「🔒 採用/不採用」バッジ**を出す（✕棄却は出さない）。解除は成果物側で未処理に戻す（N.3-採否・FR-41 Phase2）。
  - **反証（refuting）化**は「根底を揺さぶる」シグナル＝post-commit で作成者＋評価者へ通知＋要再評価フラグ（[コンセプト機能 §3.5](../../設計ドラフト/コンセプト機能_ISO56002_再設計.md)）。確認ダイアログ。**このリンクをどう取り込む/却下するか（＝統制）は成果物側の管理権限者に委任**（成果物側の採否ワークフロー・§8＝別スコープ）。
- **能力フラグ**（`can.edit_content`＝作成者／`can.curate`＝curator／`can.add_link`＝全員）はサーバー算出＝フロントは反映のみ・保存時にサーバー再検証（越権 403）。内容セクションに**「🕘 更新履歴」**（`info_item_revisions`・**登録直後から版1が出る**＝作成時に初版を記録）。**各版は「何が変わったか」を見せる**（アイデア SC-22/D.4 相当）＝版番号/編集者/日時に加え、前版比の**変更フィールドのバッジ**（タイトル/本文・説明/出典URL/📎 参考資料）と、**「差分を表示」の展開で差分**（タイトル/本文はテキストの add/del 色分け〔本文はタグを外しプレーンで比較〕・出典URL/参考資料は旧→新）。差分は展開時に `GET /info-items/{id}/revisions/{revision}/diff` で遅延取得。参考資料も版の追跡対象（追加/削除が履歴・差分に出る・§17）。
- **curator の属性（環境スキャン・判定）は折り畳み（`disclosure`・既定は開いた状態）**＝登録ダイアログの「属性を付与」と同じ UI に統一（非curator の参照属性はそのまま）。
- **参考資料（添付）は登録/詳細とも「保存でまとめて反映」**（アイデア D.3 と同仕様）＝追加はステージ・既存削除は「削除予定」マーク（元に戻せる）→**「保存する」/「登録する」で確定**。添付だけの変更でも保存が走り完了で閉じる（[API N.4](../../API設計/N_情報インプット.md) フロント UX 注記）。
- **アーカイブ/解除・削除・続報は⋯メニュー**（§5）＝フッターを「閉じる／保存する」に絞る（ボタン過多の解消）。
- **関連リンクの編集は「その場でインライン編集」**＝ダイアログ内「🔗 リンクを編集」で当該欄だけを編集モード（種別変更/棄却/追加）に切替え、**別ダイアログは開かない**。⋯メニュー「リンクを編集」も詳細を開いて同欄を編集モードにする。保存はフッター「保存する」で確定（全員が編集可＝`can.add_link`）。

### 7-採否. 成果物側コンテキストで開く採否モード（FR-41 Phase2）

- **成果物（クエスト/アイデア）の関連情報パネルのカードから SC-52 を開いたとき＝採否モード**（対象コンテキスト＝どの成果物から開いたかを渡す。例＝`/info-items/{id}?from=quests:{targetId}`）。**この情報が複数成果物に紐づいていても、開いた成果物のリンク（1本）の採否だけを扱う**。
- **本体は全面参照モード**（内容・属性・関連リンクも read＝この文脈では情報自体を編集しない）。**「＋ この情報からクエストを作成（機会特定→行動）」・「アーカイブ（情報判定権限）」・「続報スレッド」は非表示**（成果物側で採否する文脈に不要なため）。
- **ダイアログ最下部に「この情報の扱い」入力**（管理権限者のみ操作可＝クエスト owner/quest_admin・アイデア作成者/所属クエスト owner/quest_admin）＝**状態ラジオ（未処理／採用／不採用）＋処理メモ（どう処理・反映したか）＋「保存する」**。保存は**情報本体でなく成果物側リンクの採否データ更新**（`PATCH /{quests,ideas}/{id}/related-info/{link_id}`・C.8b/D）。非管理権限者には現在の状態＋メモを read 表示のみ。
- **ロック**＝採用/不採用済みは棄却/種別変更ができない（`pending` に戻すと解除）。保存後は関連情報パネルへ `INFO_CHANGED_EVENT` で反映（採用はクエスト「🏁 結果」タブにも集約）。

## 8. 関連情報パネル（各成果物へ内包＝共有セクション）

- **アイデア詳細（SC-22）／クエスト詳細（SC-12）／コンセプト（新設）** に「**関連情報**」パネルを内包＝`GET /{artifact}/related-info`（一致度上位 N・`rejected` 除外）。

## 9. セキュリティ・ガバナンス（§7 設計に準拠）

## 1. 概要・目的

- **タスク（要件/作業）の新規登録・編集モーダル**。WBS ツリー（SC-71）から開く。**URL 付きモーダル**（RouteModal＋Intercept＋フルページ fallback・クエストと同方式）＝`/projects/{projectId}/tasks/new`（`?parent={親id}`＝子タスク追加／`?dup={元id}`＝複製）・`/projects/{projectId}/tasks/{taskId}/edit`。
- 単一 `tasks` テーブル＋自己参照ツリーのため、**親（`parent_task_id`）と粒度（`kind`）を選ぶだけで階層に載る**（[設計ドラフト](../../設計ドラフト/ソリューション開発機能_設計.md) §3.1）。
- **入力検証は §4.7 標準**（フィールド単位のインライン＋上部サマリ＋足元ヒント＋自動消滅トースト・[フロントエンド実装フロー規約](../../規約/フロントエンド実装フロー規約.md) §2.1b）。

## 2. アクセス条件・権限

| 項目 | 内容 |
| --- | --- |
| 作成・編集 | project owner ＋ 開発 `lead` ＋ owner/quest_admin（[API Q](../../API設計/Q_ソリューション開発.md) Q.0） |
| 状態更新のみ | 担当者(assignee) も可（自分のタスクの status/done）＝ツリー上のインライン操作（SC-71）。本モーダルは主に作成/編集で使用 |
| 担当（assignee）候補 | **その プロジェクトの開発メンバー（`project_members`）に限る**（範囲外は 422・Q.0）。0名なら先に開発メンバー追加を促す |

## 3. レイアウト構成（決定）

- **入力モーダル標準**（`.modal.sectioned`＝ヘッダー/本文/フッター・ドラッグ/最大化/Esc/バックドロップ共通適用）。サイズ＝`.modal--md`。
- 入力項目は `.field is-quiet`（余白区切り・仕切り線なし）。
- **§4.7 の検証部品を必ず使う**＝先頭 `FormSummary`／各 `Field error`／フッター `FormFooterError`／送信失敗で `notify()`（[フロントエンド実装フロー規約](../../規約/フロントエンド実装フロー規約.md) §2.1b）。
- **フッター順**＝キャンセル（左・`.dialog-close-left`）→（主）保存。主ボタンは常に押せる（§4.1）。

## 4. 表示・入力項目

| 項目 | 種別 | 必須 | 補足 |
| --- | --- | --- | --- |
| タイトル | テキスト | **必須** | `title`。§4.7 検証（空/上限）＝欠落時はこの項目だけ赤く |
| 粒度（kind） | セレクト | 任意（既定 `task`） | `requirement`（要件）／`task`（作業）。深さと緩く対応（強制しない） |
| 親タスク | セレクト（ツリー） | 任意 | `parent_task_id`（未選択＝プロジェクト直下）。同一プロジェクト内のみ・循環禁止（422） |
| 担当者 | セレクト（開発メンバー） | 任意 | `assignee_account_id`。候補＝`project_members`（開発担当・単一）。0名なら「先に開発メンバーを追加」ヒント |
| 状態 | セレクト | 任意（既定 `todo`） | `todo`/`doing`/`done`/`blocked`。**`done` に変更で完了報酬**（開発XP＋コイン・Q.3・トースト） |
| 期日 | 日付 | 任意 | `due_date`（MVP で運用する唯一の日程列） |
| 説明 | テキストエリア | 任意 | `description` |

- **工数見積・計画/実績日程（`estimate_*`/`planned_*`/`actual_*`）は本モーダルに出さない**＝データの器のみ（MVP 未使用・[設計ドラフト](../../設計ドラフト/ソリューション開発機能_設計.md) §3.6）。依存関係（`task_dependencies`）も Phase2。
- **CSV 取込**は本モーダルではなく Phase2 の取込ダイアログ（本画面には出さない）。

## 5. アクション・遷移

| トリガー | 条件 | 遷移/結果 |
| --- | --- | --- |
| キャンセル/閉じる | — | モーダルを閉じる（RouteModal `close`／standalone は SC-71 へ戻る） |
| 保存（新規） | 管理権限 | `POST /projects/{id}/tasks`（作成時に `chat_thread owner_type='task'` を冪等生成・Q.2/Q.4）→ 閉じて `PROJECTS_CHANGED_EVENT` でツリー更新 |
| 保存（編集） | 管理権限 | `PATCH /tasks/{id}`（部分更新・無変更は info「変更はありません」§14）→ 閉じて `PROJECTS_CHANGED_EVENT` でツリー更新 |
| 状態を done に変更して保存 | 担当者/lead/owner | 完了報酬（開発XP＋コイン・冪等・Q.3）＋成功トースト |
| 検証エラー | — | §4.7＝欠落項目をインライン赤＋上部サマリ＋足元ヒント＋自動消滅トースト（スナックバー1本のまとめ表示は不可） |

## 6. 状態・バリエーション

| 状態 | 表示 |
| --- | --- |
| 新規 | タイトル「タスクを登録」・既定（kind=task, status=todo, 親=選択中ノード or 直下） |
| 編集 | タイトル「タスクを編集」・既存値プリフィル |
| 複製（任意・§4.5 複製標準） | 追加モードで値プリフィル（別レコード新規・任意採用） |
| 担当候補0名 | 担当セレクトは無効＋「先に開発メンバーを追加してください」ヒント |
| 入力エラー | §4.7（フィールド直下＋サマリ＋フッター＋トースト） |

## 7. データ・API（想定）

- **POST `/projects/{project_id}/tasks`**（Q.2）＝`{parent_task_id?, kind, title(必須), description?, assignee_account_id?, due_date?, sort_order?}` → `task`＋`chat_thread` 冪等生成。
- **PATCH `/tasks/{task_id}`**（Q.2）＝部分更新（`assignee` は `project_members` に限る・`parent` は循環禁止・`status→done` で完了報酬）。
- 認可・担当範囲・循環禁止・完了報酬の冪等はサーバーが最終判定（Q.0/Q.2/Q.3）。

## 8. アクセシビリティ / 表示配慮

- §4.7 検証（色のみに依存しない・フィールド直下メッセージ・フォーカスは奪わない）。
- モーダルはフォーカストラップ・`aria-modal`・Esc/バックドロップで閉じる（モーダル標準）。
- 担当/状態のセレクトはラベル紐付け（`Field`）。

# 情報インプット テンプレート機能 — 設計ドラフト（内部情報の定型フォーマット化）

> 状態: **ドラフト（2026-10-02 起票・主要論点すべて確定＝A〜C＋§9）**。情報インプット（FR-41）を外部 WEB 情報だけでなく**内部情報の蓄積**（報告書・電話対応履歴・作業履歴 等）にも広げるため、登録時に**テンプレートを選ぶと「内容・説明」に定型フォーマットが入り、穴埋め箇所だけ入力**できるようにする。テンプレートは**会社共通のマスタ**で管理（追加・編集・削除）。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) 準拠。
> 関連正本＝[情報インプット機能 設計](情報インプット機能_設計.md)（本書はその拡張）／[コーディング規約](../規約/コーディング規約.md) §2（セキュリティ・nh3 サニタイズ）・§2.3（DRY）／[データモデル](../データモデル.md)（`info_items`・enum）／[API設計 N_情報インプット](../API設計/N_情報インプット.md)／[画面設計 SC-50/51/52](../画面設計/screens/SC-50_情報インプット.md)／[デザイン標準](../画面設計/デザイン標準.md)（§4.5 DataTable・§4.7 入力検証）。

## 0. 位置づけ・狙い

- 情報インプットは当初「外部 WEB 情報の手動貼り付け」を主眼にしたが、**本来の目的は内部情報も含めた会社横断の知識レイヤ**（[情報インプット機能 設計](情報インプット機能_設計.md) §0）。報告書・電話対応履歴・作業履歴といった**反復して発生する内部文書**も情報インプットの対象とする。
- しかし毎回ゼロから本文を打つと **(1) 手間が大きい・(2) フォーマットがバラつく**（後工程のトークン化/検索/要約/整合分析の質も落ちる）。
- **狙い**＝よく使う情報種別を**テンプレート化**し、登録モーダル（SC-51）で選ぶだけで**本文のひな形＋属性の既定値**が入る状態にする。入力者は**穴埋め箇所だけ**を埋める。フォーマットが揃うことで、後段の分析（ワードクラウド・類似リンク・LLM 要約/整合）も安定する。
- **なぜマスタ管理か**＝会社ごとに扱う内部文書の型は違い、運用の中で増減する。コードに焼き込まず**会社共通マスタ**で保守できるようにする（[spec is source of truth] の思想・運用主体＝会社管理者）。

## 1. ユーザー要望 → 設計要素

| ユーザー要望（2026-10-02） | 対応する設計要素 | 本書の節 |
| --- | --- | --- |
| 内部情報（報告書/電話対応履歴/作業履歴）も蓄積対象にしたい | テンプレート種別の例として内部文書を想定。属性既定で `scope=内部` 等をプリセット | §2・§3 |
| テンプレートを選ぶと内容・説明に定型フォーマットが入る | SC-51 にテンプレートピッカー → `body_html` に本文ひな形を流し込み | §4・§6 |
| 入力が必要な箇所だけ入力させたい | **見出し構造＋プレースホルダ**方式（記入欄を明示）。A〜C 合意 | §4 |

| マスタ画面で追加・編集・削除（B＝会社共通） | 新規マスタ画面（会社管理者）＋ `info_templates` テーブル＋管理 API | §3・§5・§7 |

## 2. スコープと前提

- **対象フィールド**＝「内容・説明」(`body_html`) の**本文ひな形**を主とし、加えて**属性の既定値**（分類系を中心に）をセットする（A＝合意）。タイトルは任意で既定文字列を持てる（例「電話対応履歴 YYYY-MM-DD」の雛形。穴埋め前提）。
- **管理主体・共有範囲**＝**会社共通のみ**（B＝合意）。個人テンプレート／部門別は MVP 対象外（将来判断）。編集権限は**会社管理者**（`company_account_admin`／`system_admin`）。curator への開放は将来論点（§9）。
- **穴埋め方式**＝**見出し構造＋プレースホルダ**（C＝合意）。本文はリッチテキスト（`body_html`）なので、見出し（h2/h3）＋「記入欄」を表すプレースホルダ段落で構成する（§4）。
- **既存機構の再利用**＝低摩擦登録・リッチテキスト（nh3 サニタイズ）・属性プリフィル（続報が既にプリフィルを実装）・ワードクラウドプレビュー等は[情報インプット機能 設計](情報インプット機能_設計.md) をそのまま踏襲。テンプレートは**登録フォームの初期値供給元が増えるだけ**で、保存後の `info_items` 構造は不変（＝後方互換・DRY）。
- **テンプレートと情報は疎結合**＝テンプレートはあくまで**入力の起点**。登録後の `info_items` はテンプレートを参照しない（テンプレートを後から編集/削除しても既存情報は不変＝続報のスナップショット思想と同じ）。由来の記録は任意で `source_template_id`（§5 任意列）に残せる（分析/集計用・NULL 許容）。

## 3. テンプレートの構成（`info_template`）

1 テンプレート＝「本文ひな形 ＋ 属性既定値 ＋ メタ」。

| 要素 | 内容 | 備考 |
| --- | --- | --- |
| 名称 (`name`) | ピッカーに出す表示名（例「電話対応履歴」「作業報告書」「競合動向メモ」） | 必須・会社内で一意 |
| 説明 (`description`) | 用途の補足（ピッカーの副文） | 任意 |
| 本文ひな形 (`body_html`) | 見出し＋プレースホルダの定型文（§4） | 保存時 nh3 サニタイズ（本文と同じ許可リスト） |
| タイトル雛形 (`title_template`) | タイトル欄の既定文字列（任意・穴埋め前提可） | 例「電話対応履歴（）」 |
| 属性既定値 (`defaults`) | 選択時にフォームへ入れる各属性の既定（§3-1） | jsonb・**全て任意**（キーが無い属性は手動のまま） |
| 並び順 (`sort_order`) | ピッカーの表示順 | int |
| 有効フラグ (`is_active`) | 無効化で新規選択から除外（既存情報は不変） | boolean |

### 3-1. 属性既定値（`defaults`）に持てるキー

[情報インプット機能 設計](情報インプット機能_設計.md) §2 の単一選択属性を対象（会社 enum）。**指定したキーだけ**プリフィルし、未指定は手動のまま。

- `priority`（優先度）／`source`（情報ソース）／`classification`（情報分類）／`scope`（大分類＝外部/内部/その他）／`target_business`（対象事業）／`impact_class`（影響分類）／`impact_level`（影響度）／`impact_timing`（影響発生時期）
- カテゴリ（M:N・複数可）＝`category_ids[]`（任意）
- **例**：
  - 「電話対応履歴」→ `scope=内部`・`source=取引先・顧客`・`classification=情報`
  - 「作業報告書」→ `scope=内部`・`classification=ナレッジ`
  - 「競合動向メモ」→ `scope=外部`・`source=競合`・`impact_class=脅威`
- **プリフィルは編集可**（続報のプリフィルと同じ挙動）。テンプレートは“時短”であって強制ではない。

## 4. 本文ひな形の記法（見出し＋プレースホルダ）

- 本文は `body_html`（リッチテキスト）。ひな形は**見出し（h2/h3）＋記入欄プレースホルダ**で構成する。
- **プレースホルダ**＝記入すべき箇所を視覚的に示す段落。表記は**プレーンな目印文字列**を既定とする（例：`（記入）`／`＿＿＿`）。独自のテンプレ変数構文（`{{...}}`）は**MVP では導入しない**（理由＝置換エンジン/バリデーションの複雑化を避ける。穴埋めは人が見出しを頼りに埋めれば足りる＝C 合意の「見出し構造＋プレースホルダ」）。
- **動的な既定差し込み**は**日付のみ**サポート（任意）＝タイトル雛形/本文で `今日の日付` を表す目印（例 `{{today}}`）を**登録時にクライアントで一度だけ置換**して展開（サーバ側テンプレートエンジンは持たない）。将来、作成者名・クエスト名などの差し込みが要れば拡張（§9）。
- 例（「電話対応履歴」本文ひな形・HTML は省略表記）：
  ```
  ## 対応日時
  （記入）
  ## 相手・会社
  （記入）
  ## 用件
  （記入）
  ## 対応内容
  （記入）
  ## 次アクション / 期限
  （記入）
  ```
- サニタイズ＝テンプレート保存時・情報保存時の**両方**で nh3 許可リスト（本文と同一）。テンプレートは管理者作成だが**例外にしない**（多層防御・[コーディング規約] §2）。

## 5. データモデル（新規 `info_templates`・会社 DB）

> テナント分離（会社 DB）。物理名は複数形・共通監査列（`created_at/by/program`・`updated_*`）を付与（[データモデル] §5 共通規約）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `name` | 名称 | text | NOT NULL | **有効（`deleted_at IS NULL`）内で一意**（§9-2 確定）。論理削除済みの名前は再利用可 |
| `description` | 説明 | text | NULL 可 | ピッカー副文 |
| `title_template` | タイトル雛形 | text | NULL 可 | 既定タイトル（穴埋め可） |
| `body_html` | 本文ひな形 | text | NOT NULL | サニタイズ済ひな形 |
| `defaults` | 属性既定値 | jsonb | NOT NULL, default `{}` | §3-1 のキー（任意）。enum 値はキー検証（§7） |
| `sort_order` | 並び順 | int | NOT NULL, default 0 | ピッカー表示順 |
| `is_active` | 有効 | boolean | NOT NULL, default `true` | 無効＝新規選択から除外（既存情報は不変） |
| `deleted_at` | 削除日時 | timestamptz | NULL 可 | 論理削除（トゥームストーン・監査保持。`ideas` 方式を踏襲） |
| `deleted_by_id` | 削除者ID | uuid | NULL 可, FK→users | 削除実行者 |

- インデックス：`(is_active, sort_order) WHERE deleted_at IS NULL`。
- **`info_items` への追加列（§9-1 確定＝持つ）**＝`source_template_id uuid NULL FK→info_templates`（由来記録・分析用。論理削除前提のためテンプレ削除後も ID は残す＝由来の履歴として保持）。手動登録・テンプレ不使用は NULL。

## 6. 画面

### 6-1. SC-51 登録・編集モーダル（既存拡張）

- **テンプレートピッカーを追加**＝モーダル上部に「テンプレートから作成」を置く（新規登録時のみ・編集時は非表示）。
- 候補は `GET /info-templates`（有効のみ・`sort_order` 順）。各候補に名称＋説明。
- 選択で **本文（`body_html`）にひな形を流し込み＋属性既定値をフォームにプリフィル**（タイトル雛形があればタイトルにも）。日付目印は選択時に展開。
- **上書き確認**＝本文や属性に入力済みの場合、テンプレ適用で消える旨を確認（[デザイン標準] の確認ダイアログ標準）。空ならそのまま適用。
- プリフィル後は**全項目編集可**。以降は通常の登録フロー（低摩擦／ワードクラウドプレビュー／nh3）に合流。
- 「テンプレートを使わない」も当然可能（＝従来どおり白紙から）。

### 6-2. SC-5x テンプレート管理（マスタ・新規・会社管理者）

- [reuse existing UI]＝**DataTable 一覧（[デザイン標準] §4.5）＋ URL 付きモーダルの登録/編集**（[URL-modal standard]）を踏襲。新規 UI は作らない。
- 一覧列＝名称／説明／既定属性サマリ（チップ）／有効フラグ／並び順／更新者・更新日時。
- 行操作＝編集（URL モーダル）／有効・無効トグル／削除（論理・確認付き）／複製（[デザイン標準] の複製標準・既存テンプレを雛形に新規）。
- 編集フォーム＝名称・説明・タイトル雛形・**本文ひな形（情報登録と同じリッチテキストエディタを再利用）**・属性既定値（各属性のセレクト＝「既定にしない」を含む）・並び順・有効フラグ。入力検証は §4.7 の4部品（[form validation §4.7] 標準）。
- 配置＝会社設定/マスタ系メニュー配下（既存の会社マスタ画面群に合わせる・[リポジトリ構成規約] / 遷移図はルートの正）。

## 7. API（`N_情報インプット` に追記）

> [API design endpoint table format] に従い既存節と同じ表形式で追記。認可・カーソル等は [API設計 README] §1.x 準拠。

**テンプレート（閲覧＝全ユーザー／管理＝会社管理者）**

| メソッド | パス | 機能 | 主フィールド / 認可 |
| --- | --- | --- | --- |
| `GET` | `/info-templates` | ピッカー供給（有効のみ・`sort_order` 順） | 認証ユーザー全員。`{data:[{id,name,description}]}`（軽量） |
| `GET` | `/info-templates/{id}` | 1件詳細（適用用・本文/既定含む） | 認証ユーザー全員。`{..., body_html, defaults, title_template}` |
| `GET` | `/info-templates?admin=1` | 管理一覧（DataTable 契約 §1.8.1） | 会社管理者。無効/論理削除の扱い含む |
| `POST` | `/info-templates` | 追加 | 会社管理者。`{name, description?, title_template?, body_html, defaults?, sort_order?}` |
| `PATCH` | `/info-templates/{id}` | 編集 | 会社管理者。部分更新 |
| `POST` | `/info-templates/{id}/activate` `/deactivate` | 有効・無効 | 会社管理者 |
| `DELETE` | `/info-templates/{id}` | 削除（論理） | 会社管理者。既存情報は不変 |

- **サーバ側検証（application 層・違反は 422＋明示コード）**＝(1) `body_html` を nh3 サニタイズ（許可外は除去）／(2) `defaults` の**キーが既知属性に限る**・**値が当該 enum（会社拡張含む）に存在**・`category_ids` が実在／(3) `name` 一意。
- **適用はクライアント主体**＝`GET /info-templates/{id}` で取得した本文/既定をフォームに流し込むだけ（専用の「適用」EP は不要＝登録は従来の `POST /info-items`）。`source_template_id` を採用する場合は `POST /info-items` のボディに任意で載せる。

## 8. 要件定義への反映（FR）

- **FR-41 の拡張**として位置づけ（別 FR を新設せず FR-41 に「内部情報テンプレート」を追記する案を第一候補）。理由＝情報インプットの登録入口の強化であり、独立機能ではない。
- 反映時の記述＝「①内部情報の蓄積を明示（報告書/対応履歴/作業履歴）②会社共通テンプレートで本文ひな形＋属性既定をプリフィル③マスタ画面で追加・編集・削除（会社管理者）」。MVP 境界＝会社共通・見出し＋プレースホルダ・属性既定プリフィル／Phase2 送り＝個人/部門別テンプレ・変数差し込み拡張・curator 開放。
- 正式反映の順序は[ドキュメント作成規約]＋既存運用に合わせ **FR 追記 → データモデル（`info_templates`）→ API（N 追記）→ 画面（SC-51 拡張＋マスタ SC-5x）→ 遷移図 → テスト md（TC 採番）**。

## 9. 論点の確定（2026-10-02）

1. **`source_template_id` を持つか**＝**持つ**（`info_items` に NULL 許容の FK）。列1つで「どのテンプレがよく使われるか」を集計でき、将来のテンプレ改善に効く（保存後は参照しないので結合コストなし）。→ §5。
2. **`name` 一意の範囲**＝**有効（`deleted_at IS NULL`）内で一意**。削除済みの名前は再利用可。無効（`is_active=false`）は一意対象に含める（紛らわしさ回避）。→ §5。
3. **curator への管理開放**＝**MVP は会社管理者のみ**（B 合意）。マスタは会社の型の統制。運用で要望が出たら Phase2 で拡張。
4. **変数差し込みの範囲**＝**MVP は日付のみ**（クライアント展開・§4）。作成者名/クエスト名などは Phase2。
5. **マスタ画面の採番（SC-5x）と配置**＝会社マスタ系メニューの既存番号体系に合わせて採番（遷移図確定時）。単独では決めない。

**正式反映の順序**＝FR-41 拡張追記 → データモデル（`info_templates`＋`info_items.source_template_id`）→ API（N 追記）→ 画面（SC-51 拡張＋マスタ SC-5x）→ 遷移図 → テスト md（TC 採番）。

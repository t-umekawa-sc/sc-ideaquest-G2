## 0. 位置づけ・狙い（差別化の核）

- **参加者全員が外部 WEB 情報を無造作に登録 → 権限者が属性付与 → アイデア/コンセプトへ動的リンク → 反証は能動的に“揺さぶる”**。
- ISO56001 では **§7.1.6 知識/インテリジェンスのマネジメント**、および **① 機会の特定の燃料**にあたる。受動的なスクラップ帳でなく、**アイデア→コンセプト→検証の絞り込みの流れを能動的に駆動する知識レイヤ**にするのが狙い（＝競合と差がつく）。
- アイデア段・コンセプト段の**両方**を駆動する（[コンセプト機能 ISO56001 再設計](コンセプト機能_ISO56001_再設計.md) §3.5／§4 と接続）。

## 1. 取り込み方式＝全て手動貼り付け（サーバフェッチ無し）

- ユーザーが**WEB ページの気になる記事部分をコピペ**＋**出典 URL を手入力**して登録する。**サーバは外部 URL を取りに行かない**。
- **なぜ**＝サーバフェッチを持たない＝**SSRF 対象外**、クロール規約・著作権の面でも安全側、MVP を軽くできる。取り込みの高度化（半自動抽出等）は将来判断。

## 3. 運用・低摩擦登録と、暫定案からの変更

- **低摩擦の初期登録**＝**タイトル＋内容・説明（＋URL）**は**全ユーザー**が登録できる（「無造作に登録」）。**残り（優先度・各分類・影響評価・判定）の属性付与は「情報判定権限」を持つユーザーのみ**（raw→curated・サーバー再検証）＝casual な登録者に全項目を強いない。
- **新規権限「情報判定権限」＝`info_curator`（会社/テナント単位・§11-①で確定）**＝属性値（各分類・影響評価・情報判定 等）を付与でき、判定後(curated)情報のアーカイブもできる役割。情報プールは会社横断のため quest 単位の権限（owner/quest_admin/evaluator/comment）とは**別軸の会社レベル権限**。**付与＝会社アカウント管理者（system_admin も可）**。正本化先＝[データモデル](../データモデル.md)（権限）・権限設計。
- **削除/アーカイブ（§11-③で確定）**＝**本人は自分の未判定(raw)情報を削除可**（casual 登録の取消）／**判定後(curated)は `info_curator` がアーカイブ（論理削除・監査保持）**。物理削除はしない（既存の「物理削除しない」方針に整合・§2）。
- **enum（マスタ）の拡張（§11-②で確定）**＝**MVP は固定マスタ（コード定義 enum・全社共通）／会社ごと拡張は Phase2**（特に #7 対象事業・#8 情報カテゴリ）。最初からテナント拡張にするとマスタ管理UI＋テナント master テーブルが要るため MVP は固定で出す。
- **暫定案からの変更（すり合わせ）**：
  - 私の暫定「情報分類マルチタグ＋自社技術・ナレッジの一値」は**取り下げ**。実際は **情報分類(#3) は単一**、マルチは **情報カテゴリ(#8) のみ**。従来言っていた「自社/外部・技術知見（＝実現可能性ヒント/高信頼）」は **大分類(#6)＝内部 ＋ 情報カテゴリ＝内部｜技術・能力** で表現する。
  - 「機会/脅威」は情報分類でなく **影響分類(#10)** で持つ。→ §3.5「反証で揺さぶる」との関係は**要確認**（§5 冒頭の注記）。
- **重複**＝同一 URL 検出（MVP は警告、将来統合）。

## 4. ワードクラウド／類似度（動的リンクの中核）

- **日本語＝形態素解析**。**`janome`（FR-39 のチャット要約で導入済み・純Python・MIT）を再利用**（or Sudachi）＝依存を増やさない（DRY）。ストップワード除去。
- **ワードクラウド**＝情報本文群のトークン頻度を可視化（画面表示）。**単一情報は保存時に同期トークン化（`info_tokens` 永続）＋入力ダイアログ内プレビュー（同期・ephemeral エンドポイント）＝§12-2**（バックグラウンド不要）。トークン化対象は `body_text`（タグ除去後）。
- **一致度（類似度）**＝情報 と アイデア/コンセプト本文の**キーワード重なり／TF-IDF**。**閾値＋上位 N** で件数を抑える。
- **再計算トリガ**＝情報の追加/更新・アイデア/コンセプトの保存など関連変化時。**事前計算して `info_link.score` に保存**（都度計算しない）。
- **MVP＝キーワード/TF-IDF**。**Phase2＝埋め込みベクトル（意味的関連の類似検索）**、および**矛盾（反証）の自動検出**（意味解析／将来 LLM・コスト/データ保護判断つき）。

## 5. 動的リンクの動作（MVP・再設計 §4 と一致）

> **決定（情報レベルの「影響分類」× リンクの「種別」＝併用）**：情報本体は **影響分類(#10)＝機会/脅威/その他**を持つ（環境スキャン＝この情報の一般的性質）。加えて、下の 1〜3 の**リンク種別（関連/裏付け/反証）は「この特定のアイデア/コンセプト/前提に対して」の関係**として**別に持つ**（例＝“脅威”な情報でも、あるコンセプトには“裏付け”になり得る）。**「反証→要再評価」の発火は per-link の反証**で行う（影響分類=脅威 は per-link 種別の初期値サジェストに使ってよい）。

1. **自動・動的リンク**＝一致度が高い情報は、アイデア/コンセプト画面に**自動で関連リンクを動的に表示**（種別の既定＝**関連（中立）**）。**通知は出さない**（低コミット・ノイズ許容）・閾値＋上位 N。
2. **種別は後から手動変更**＝人が**裏付け／反証・脅威**へ変更（→**反証なら通知＋要再評価**が発火＝[再設計](コンセプト機能_ISO56001_再設計.md) §3.5）。
3. **任意リンクの手動追加**＝自動で拾われない情報も、人が**任意にアイデア/コンセプト（や前提）へ手動リンク**できる（＋不要な自動リンクは棄却可）。
4. **Phase2**＝矛盾（反証・脅威）の自動検出。

## 6. 利用先（統合点）

- **アイデア作成/編集**＝関連情報サジェスト＋**自社技術・ナレッジ＝実現可能性ヒント**。
- **コンセプトの前提と検証**＝情報を**前提の証拠/出典**にリンク（裏付け/反証）。**前提1件＝1スレッド**（再設計 §3.7）に情報を貼る動線と噛み合う。
- **コンセプトの競合・採算**＝外部記事/市場データをリンク。
- **根底ゆるがし**＝反証情報が既存アイデア/コンセプトに **flag＋通知**（作成者＋評価者・要再評価）。**1 情報の反証 → 1 前提 → 複数コンセプト**へ波及（再設計 §3.5）。
- **動的関連リンク・パネル**＝クエスト/アイデア/コンセプト画面に一致度上位の情報をリンク表示（元要件）。
- **双方向**＝情報→成果物（提示・揺さぶり）／成果物→情報（前提が証拠として情報を引用）。

## 7. セキュリティ・ガバナンス

- **貼付本文の XSS サニタイズ**＝ユーザー持ち込み**リッチテキスト（HTML）**なので、**許可リスト方式で保存時＋表示時に無害化**（`nh3` 推奨・§12-4）。on* 属性/style/script/`javascript:` を全弾き。**出典 URL は http/https のみ許可**。**貼付画像は MinIO 再ホスト**（外部 img src は除去 or 再ホスト・許可 src は自社ホストのみ・§12-4）（[コーディング規約](../規約/コーディング規約.md) §2.2・[セキュリティ対策一覧](../WEBアプリ開発時のセキュリティ対策一覧.md)）。
- **SSRF＝対象外**（サーバフェッチ無し・§1）。
- **著作権/PII**＝外部本文の**保存・保持期間**の方針を定める（出典 URL 明記で引用性・トレーサビリティ）。
- **出典の信頼性**＝`自社/外部`＋`情報ソース`で**重み付け**でき、**根底をゆるがす反証は信頼できる出典を伴う**ことを担保しやすい（検証の厳密さ・採算の説得力に効く）。
- **テナント分離**＝会社横断の知識プール（テナント DB・門番は既存に準拠）。

1. **情報判定権限＝`info_curator`（会社/テナント単位）**。付与＝会社アカウント管理者（system_admin も可）。quest 系権限とは別軸の会社レベル権限（§3）。
2. **enum は MVP 固定マスタ（コード定義・全社共通）／会社拡張は Phase2**（特に #7 対象事業・#8 情報カテゴリ）（§3）。§2 に列挙の値を初期値とする。
3. **削除/アーカイブ**＝本人は自分の未判定(raw)を削除可／判定後(curated)は `info_curator` がアーカイブ（論理削除・監査保持）・物理削除なし（§3）。
4. **期限日(#5)＝対応/有効期限**（任意）。**#11 影響発生時期（事象の予測時期）とは別軸**（§2）。
5. **影響分類(#10)〔情報本体・機会/脅威/その他〕とリンク種別〔per-link・関連/裏付け/反証〕は併用**＝情報の一般的性質は本体で1回判定、相手ごとの効き方はリンクごと。**「反証→通知＋要再評価」は per-link の反証だけで発火**（影響分類=脅威は per-link 種別の初期サジェストに使うのみ・誤爆防止）。写像＝`info_item.impact_class`／`info_link.kind`+`origin`+`score`（§5）。
6. **重複（同一URL）**＝MVP は警告のみ（登録は許可）／統合は Phase2（§3）。

## 12. 追加機能（2026-09-19 レビューで合意）

> 4機能を追加＝**続報**／**ワードクラウドの同期化・ダイアログ内可視化**／**要約（既存抽出型を再利用）**／**リッチテキスト入力（画像は MinIO 再ホスト）**。3つの分岐は 2026-09-19 に確定（12-1 リンク継承＝スナップショット複製／12-3 要約＝抽出型再利用／12-4 画像＝MinIO 再ホスト）。**既存資産を再利用して分量を抑える**方針＝janome（トークン化）・抽出型 `summarize_text`（要約）・MinIO 画像アップロード＋マジックバイト検証（画像）・`info_links` の `origin`/`score`/per-link 揺さぶり機構（続報リンク）。

### 12-1. 続報（follow-up）＝情報の親子スレッド
- **狙い**＝機会/脅威が時間で進展する様子を、元情報に紐づけて**時系列で追う**（環境スキャンの継続監視）。受動スクラップでなく「進展を能動的に追える」＝差別化に効く。
- **モデル**＝`info_items` に自己参照 FK **`parent_info_id`（null 可）**。続報は親を指す。続報の続報（チェーン）も許容＝根（`parent_info_id IS NULL`）でグルーピングしてスレッド表示。
- **リンク継承（確定＝登録時スナップショット複製）**＝続報登録時に**親の有効な `info_links`（quest/idea/concept）を `origin=auto` で複製**して続報にも張る。以後は続報側で独立編集可（親のリンク変更には追随しない）。**why**＝予測可能・既存 `info_link` 機構（origin/score/per-link 揺さぶり）をそのまま再利用でき、続報が反証なら独立に発火する。
- **属性継承**＝続報フォームは親の属性（優先度/情報ソース/影響評価 等）を**初期値プリフィル・編集可**。本文/URL/判定は新規。**why**＝同一話題の低摩擦入力と、影響度・判定は変わり得る現実の両立。
- **UI**＝情報詳細（SC-52）／一覧行（SC-50）に「**続報を登録**」＝親を prefill して SC-51 登録モーダルを開く。詳細は親スレッドを時系列表示。
- **権限**＝続報登録は通常登録と同じ（全ユーザー・低摩擦）。親リンクの auto 複製は判定前(raw)でも張られる（既存 raw/curated 扱いに整合）。

### 12-2. ワードクラウド＝同期化＋ダイアログ内可視化（§4 を具体化）
- **単一情報のトークン化は保存時に同期**（janome・数十ms）＝`info_tokens` に永続。**バックグラウンド worker 不要**。
- **一覧の集約ワードクラウド**＝各保存で貯めた `info_tokens` を集計（読み取り側も高速・バッチ無し）。
- **ダイアログ内プレビュー**＝草稿本文を**その場でトークン化する同期エンドポイント（永続しない ephemeral）**を叩きクライアント描画。**トリガ＝本文 blur かボタン**（キー入力毎は不可・コスト/ちらつき回避）。保存後は `info_tokens` から描画。
- **トークン化対象**＝リッチテキストの**プレーンテキスト抽出（`body_text`）**（タグ除去後）。

### 12-3. 要約＝既存抽出型を再利用（選別時の長文対策）
- **確定＝MVP は既存 `summarize_text`（`impl/backend/app/tenant/quests/summarize.py`・janome 抽出型・オフライン・無料・決定的）を再利用**。保存時に**同期生成**し `info_items.summary` に格納。**why**＝外部送信ゼロ＝**内部情報（大分類=内部/財務・人事等）を外部 LLM に出す privacy 問題が起きない**・追加依存なし・決定的で再現容易。
- **表示**＝SC-50 一覧／SC-52 詳細／判定（トリアージ）時に要約を先頭表示＝長文を読まず選別可能に。
- **stale**＝本文編集時に要約再生成（同期なので即）。
- **LLM は将来 seam**＝`summarize_text` 差替えで高品質化（要約用途は `claude-haiku-4-5` が速度/コスト適）。その時に内部データの外部送信ポリシーを別途決める（Phase2）。

### 12-4. リッチテキスト入力（WEBページそのまま貼付）
- **格納**＝**`body_html`（サニタイズ済リッチ）＋派生 `body_text`（プレーン）**。body_text は検索/トークン/要約に使用。一覧は body_text 抜粋。※§2「内容・説明(text)」を本 2 本立てに置換。
- **サニタイズ（必須・新規依存）**＝サーバ側**許可リスト方式**の HTML サニタイズ＝**Python は `nh3`（Rust製・高速・メンテ良）を推奨**。**保存時＋描画時で一貫**。許可タグ例＝p/br/h1-3/strong/em/ul/ol/li/a(href http(s))/blockquote/code/table 系/img（**自社ホスト src のみ**）。on* イベント属性・style・script・`javascript:` は全弾き。XSS が最大リスク（[コーディング規約](../規約/コーディング規約.md) §2／[セキュリティ対策一覧](../WEBアプリ開発時のセキュリティ対策一覧.md)）。
- **画像（確定＝MinIO 再ホスト）**＝貼付画像は**自社 MinIO にアップロード**（既存の画像アップロード＋マジックバイト検証 §8 を再利用）し `img src` を自社ホスト URL に置換。**why**＝私有・追跡防止・リンク切れなし。外部 `img src` はサニタイズで除去 or 再ホスト（許可 src は自社ホストのみ）。実装＝エディタの paste ハンドラで blob を検出→アップロード API→返却 URL を挿入。
- **エディタ（フロント新規依存）**＝Tiptap(ProseMirror) 等が候補（`shared.css` デザインシステムに馴染ませる）。ペースト時にクライアント側でも許可外要素を一次除去（多層防御）。**依存選定は実装フェーズで確定**。
- **§7 との整合**＝§7「表示時サニタイズ」を「**保存時＋表示時**の許可リストサニタイズ（nh3）」へ格上げ。URL は従来どおり http/https のみ。

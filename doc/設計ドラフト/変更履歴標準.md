# 変更履歴の標準装備（設計ドラフト）

> ステータス: **ドラフト（レビュー用・2026-09-26）**。方針合意済み（ユーザー決定）。本ドラフト承認後にデータモデル/API/画面の各正本へ反映し、フェーズ実装する（設計書ファースト）。
> 関連正本: [データモデル](../データモデル.md)（監査列 §2・`idea_revisions`/`info_item_revisions`/`quest_outcomes`/`concepts` 等）／[API設計](../API設計/README.md)（D.4 版タイムライン/差分）／[要件定義 FR](../要件定義/README.md)。

## 1. 背景・目的（なぜ）

ISO 56001 のイノベーション・マネジメントは**一度実行して終わりではなく、反復して更新し続ける**（②創造→③検証→判定→再検証…）。その際、**「その当時の判断材料（投票/評価/検証状況）」と「判断結果（総合判定/ステータス/学び）」が後から追えないと、正しい振り返りができない**（ユーザー指摘）。

現状、変更履歴は**アイデアと情報インプットにだけ**存在し、実装が 2 つコピーされている。これを**共通の標準機構に一般化**し、**クエスト・コンセプト・評価・振り返り（学び/次アクション）にも標準装備**する。あわせて「内容の版」だけでなく**「意思決定（ステータス/判定）の変遷ログ」**も残す。

## 2. 現状評価（既存資産）

| エンティティ | 内容の版履歴 | 実体 |
|---|---|---|
| アイデア | ✅（概要パネルのリンクUI） | `idea_revisions`（JSONB `changes` スナップショット・`revision`/`editor_id`/`created_at`/`memo`・差分はサーバー算出・初版=1・無変更は版を作らない）／`RevisionHistory.tsx`・API D.4 |
| 情報インプット | ✅（折り畳みUI） | `info_item_revisions`（**アイデアと同型**・migration 0029）／`InfoRevisionHistory.tsx` |
| コンセプト | △ カウンタのみ | `concepts.current_revision` は +1 するが `concept_revisions` **実体なし** |
| クエスト | ❌ | `updated_at` のみ |
| 評価 | ❌ | draft/submitted 状態のみ・内容編集履歴なし |
| 振り返り（`quest_outcomes`） | ❌ | summary/learnings/next_actions/metrics を**都度上書き** |

**既存の prior art**:
- 版スナップショット方式は**アイデア＝情報で既に同型**（`changes` JSONB・`UNIQUE(entity_id, revision)`・差分サーバー算出・初版=1・無変更スキップ）。共通化の土台は揃っている。
- **前提の検証（`assumption_validations`）は既に追記型（append-only）の判定ログ**＝「意思決定ログ」の先行事例。verdict（supported/refuted/inconclusive）の変遷を時系列で残している。

## 3. 標準設計

変更履歴を **2 系統**に分けて標準化する。目的が違うため分離する。

### 3.1 内容の版（content revision）＝「何が変わったか」

- **データ＝per-entity テーブル**（polymorphic 単一テーブルにしない）。各エンティティに `<entity>_revisions` を1つ:

  | 物理名 | 型 | 説明 |
  |---|---|---|
  | `id` | uuid PK | |
  | `<entity>_id` | uuid FK | 親エンティティ |
  | `revision` | int | 版番号（初版=1） |
  | `editor_id` | uuid FK→users | 版を作った人 |
  | `changes` | jsonb | **版時点の追跡フィールド全値スナップショット** |
  | `memo` | text NULL可 | **変更理由**（§3.4 で一部必須級） |
  | `context_snapshot` | jsonb NULL可 | **その時点の判断材料の数値サマリ**（§3.3・軽量・任意） |
  | （監査列は全表共通で自動付与） | | |
  - 制約: `UNIQUE(<entity>_id, revision)`（楽観ロックの検出にも使う）。

  > **なぜ per-entity か（chat_thread の一般化とは逆の判断）**: 履歴は「そのエンティティ固有の付属物」で**他ホストから再利用しない**。FK 整合・テナント境界・クエリが素直。一般化するのは**テーブルではなくロジックとUI**。

- **backend＝共通ヘルパ**（`app/tenant/_shared/revisions.py` 想定）:
  - `record_revision(session, *, entity, editor_id, snapshot_fn, tracked_fields, memo=None, context_fn=None)`＝スナップショットを作って版+1。**無変更（前版と `changes` 同一）は版を作らない**。
  - `list_revisions(session, entity_id, *, limit, cursor)`＝新しい順・`changed_fields[]` 同梱。
  - `get_revision_diff(session, entity_id, revision, from_revision=None)`＝前版比較（サーバー算出）。
  - エンティティ側は「スナップショット関数」「追跡フィールド」「（任意）判断材料関数」を注入するだけ。

- **frontend＝1 コンポーネント 2 バリアント**: 既存 `RevisionHistory`（リンクUI）と `InfoRevisionHistory`（折り畳みUI）を**単一の共有コンポーネント**へ統合。
  - props: `revisions`・`currentRevision`・`onDiffLoad(revision)`・`fieldLabels`・`variant: "inline-link" | "collapsible"`。
  - **バリアント割当ルール（ユーザー決定）＝概要パネルがある画面は「リンク」／無ければ「折り畳み」**。

### 3.2 意思決定ログ（decision / status transition log）＝「いつ・誰が・なぜ その判断をしたか」

内容版とは**別軸**の**追記型（append-only）タイムライン**。ステータス/判定の遷移を、判断者・日時・理由つきで残す。

- **データ＝per-entity の遷移ログ** `<entity>_decision_log`:

  | 物理名 | 型 | 説明 |
  |---|---|---|
  | `id` | uuid PK | |
  | `<entity>_id` | uuid FK | |
  | `kind` | text | 遷移の種類（`status` / `decision` 等） |
  | `from_value` | text NULL可 | 遷移前 |
  | `to_value` | text | 遷移後 |
  | `actor_id` | uuid FK→users | 判断者 |
  | `reason` | text NULL可 | **判断理由**（§3.4） |
  | `context_snapshot` | jsonb NULL可 | 判断時の材料サマリ（§3.3） |
  | `created_at` | timestamptz | |

- 適用:
  - **コンセプト**: `decision`（Go/Pivot/Kill/未判定）＋`status`（draft/active/archived）の遷移。
  - **クエスト**: `status`（recruiting/active/completed 等）の遷移（**ユーザー追加要望**）。
  - （**前提の `assumption_validations` は既存の判定ログ**＝本標準の先行事例。統合はせず「同型の別テーブル」として並置）。

  > 内容版（3.1）とログ（3.2）の役割分担＝**版＝本文/属性の変遷／ログ＝状態・意思決定の変遷**。両方あると「本文をこう直し、その結果この判定にした」が追える。

### 3.3 判断材料スナップショット（context_snapshot・軽量）

版・ログの各エントリに、その時点の**判断材料の数値サマリだけ**を凍結する（重い本体は持たない）。
- コンセプト版/判定ログ: `{votes:{approve,oppose}, eval:{evaluator_count, avg_by_aspect...}, assumptions:{supported,refuted,inconclusive}}` 程度。
- 「当時なぜその判断をしたか」を後から再構成できる（ISO の反復検証の核）。

### 3.4 変更理由メモ（memo / reason）

- 版・ログに理由欄を持たせる（`idea_revisions.memo` は既存）。
- **コンセプトの `decision` 変更・振り返りの更新では実質必須級**（UI で入力を促す・空でも保存は可だが警告）。「なぜ変えたか」が判断材料の中核。

### 3.5 通知連動

- アイデア版は既に投票者/フォロワーへ `idea_updated` 通知（post-commit・H.1）。
- **コンセプト版/判定・振り返り更新も関係者へ「更新」通知**を出す（宛先＝投票者/評価者/フォロワー/owner 等・重複排除は既存 H 基盤）。種別は generic（例 `concept_updated`/`outcome_updated`/`quest_decision`）。

## 4. エンティティ別の適用

| エンティティ | 内容版の追跡フィールド | 意思決定ログ | UIバリアント | 備考 |
|---|---|---|---|---|
| **コンセプト**（優先1） | 課題/価値提案/対象/差別化/解の形態/viability/decision_rationale | `decision`＋`status` | **リンク**（SC-61 概要あり） | current_revision 既存→`concept_revisions` 追加。判断材料スナップ重要 |
| **振り返り `quest_outcomes`**（優先2） | summary/learnings/next_actions/metrics | （なし） | 画面に概要パネルが**無ければ折り畳み**（SC-12 結果タブ内） | ISO §10 改善の記録＝最重要。更新時 memo 推奨 |
| **クエスト**（優先3） | title/purpose/categories/deadline/color（**定義項目に限定**） | `status` 遷移 | **リンク**（SC-12 概要あり） | パーティー/権限/参加部署は L.4 等別意味＝内容版に含めない |
| **評価（アイデア＋コンセプト）**（優先4） | 観点スコア/観点別コメント/総評/推奨/公開範囲 | recommendation の変遷（任意） | **折り畳み**（評価結果表示内・概要パネル無し） | **アイデア評価（`evaluations`）・コンセプト評価（`concept_evaluations`）の両方**。版は下記 3.6 の確定起点ルール |

> UI 割当は「概要パネルがあればリンク／なければ折り畳み」の原則（ユーザー決定）で機械的に決める。各画面の該当は実装時に確認。

### 3.6 評価の版の起点（ユーザー確定 2026-09-26）

評価は他エンティティ（本文の PATCH で版）と起点が違うため明記する。**アイデア評価・コンセプト評価とも**:
- **版は「評価を確定（submit）」で作成**する。**初回の確定＝初版（revision 1）**、以降は**確定するたびに版を取る**。
- **下書き保存（draft）は版を作らない**（確定した内容のみが履歴に載る）。
- **無変更の確定は版を進めない**（前版と `changes` 同一ならスキップ＝既存の版管理仕様を踏襲）。
- 追跡フィールド＝観点スコア（中核5＋補助3）／観点別コメント／総評／推奨（Go/Pivot/Kill）／公開範囲（visibility）。
- 評価者ごとに独立した版列（`UNIQUE(evaluation_id, revision)`）。再評価（前提反証→stale 後の見直し等）の変遷を追える。

## 5. データモデル/ API 追加（概要）

- **新テーブル（migration・会社DB）**: `concept_revisions`・`concept_decision_log`・`quest_outcome_revisions`・`quest_revisions`・`quest_decision_log`・`concept_evaluation_revisions`（命名は実装時に確定）。各 `UNIQUE(entity_id, revision)`／ログは append-only。
- **既存流用**: `idea_revisions`・`info_item_revisions` はそのまま（共通ヘルパへ寄せる）。
- **API**: 各エンティティに `GET .../revisions`・`GET .../revisions/{n}/diff`・`GET .../decision-log` を D.4 と同契約で追加。差分/一覧の DTO 形は共通。
- **監査列との関係**: 監査列（created_by/updated_by・全表共通）＝最終状態のメタ／版・ログ＝変遷。役割分担を各正本に明記。

## 6. フェーズ計画（合意順）

- **Phase 0（共通化・回帰保護）**: 既存アイデア/情報の版ロジックを backend 共通ヘルパへ、frontend を共有 `RevisionHistory`（2バリアント）へリファクタ。**既存テスト緑維持＋差分の red-green**。挙動不変が DoD。
- **Phase 1（コンセプト）**: `concept_revisions`＋`concept_decision_log`（decision/status）＋判断材料スナップ＋SC-61 リンクUI＋更新通知。
- **Phase 2（振り返り）**: `quest_outcome_revisions`＋SC-12 結果タブに折り畳みUI＋memo 促し。
- **Phase 3（クエスト）**: `quest_revisions`（定義項目）＋`quest_decision_log`（status 遷移）＋SC-12 リンクUI。
- **Phase 4（評価）**: **アイデア評価＋コンセプト評価の両方**に版（`evaluation_revisions`／`concept_evaluation_revisions`）＝§3.6 の確定起点ルール（初回確定=初版・確定ごとに版・下書き/無変更は版なし）＋折り畳みUI。ボリューム/権限（公開範囲）に留意。
- 各フェーズ＝設計書ファースト（データモデル/API/画面の正本更新→TC 先行→red-green）。

## 7. リスク・留意

- **Phase 0 の回帰**: アイデア/情報の版は稼働中＝共通化で挙動が変わらないことをテストで担保（差分算出・無変更スキップ・通知）。
- **書き込み量**: 評価の版は複数人×観点で増えやすい＝submitted 時のみ・差分ゼロスキップで抑制。
- **判断材料スナップの鮮度**: あくまで「当時の値の凍結」＝再計算しない（後から数値が動いても版の材料は不変）。
- **通知過多**: 版のたびに通知すると煩い＝「意味のある更新（本文/判定/学び）」に絞る。

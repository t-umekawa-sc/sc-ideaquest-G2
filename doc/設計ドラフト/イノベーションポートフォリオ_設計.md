# イノベーション・ポートフォリオ（G2 / ISO 56001 §6.4）設計ドラフト

> 状態＝**設計ドラフト（未実装）**。本ファイルは調査/設計セッションの成果物。正本反映・バックログ起票は実装セッションが実施する（[引継ルール](../セッション調整/引継/README.md)）。
> 出典ギャップ＝[バックログ台帳](../バックログ/未実装・ギャップ一覧.md) `G2`／[ISO56001 準拠状況 再チェック](../ISO56001/ISO56001_準拠状況_再チェック_2026-09-28.md) §6.4。

## 1. 目的（ISO が求めるもの）

ISO 56001:2024 **§6.4 イノベーションのポートフォリオ**は、組織のイノベーション取組みを単なる一覧ではなく、**評価・改善・優先順位付けの基準を持つポートフォリオとして一元管理**することを要求する。要旨＝「限りある資源（人・金・時間）を、全取組みにどう配分するか（どれに張る／どれを減らす・やめる／全体バランスは健全か）を判断するための経営レイヤーの盤面」。

本システムの現状＝クエスト／アイデア／コンセプト／プロジェクトの**個別一覧はあるが、種別を横断して共通基準でランク付けし取捨選択する"ポートフォリオ・ビュー"が無い**（§6.4＝×判定）。これが G2。

### 位置づけ（レイヤー）

| レイヤー | 誰が | 見るもの | 既存/新規 |
| --- | --- | --- | --- |
| 現場 | メンバー／リード | 個々のクエスト・プロジェクトの進捗・タスク | 既存 |
| **経営** | **経営者／会社管理者** | **全取組みを横断した資源配分・取捨選択** | **G2（本設計）** |

**G3（§9.1 指標ダッシュボード）とセット**＝G2 は「配分を決める盤面」、G3 は「判断材料の指標」。評価軸データ（価値／確度／整合率／機会脅威率）は両者で重複するため、**正規化・集計ロジックは共通モジュール化する**（§7）。

## 2. 設計判断（確定事項）

- **取組み単位＝パイプライン横断で各1行**（ユーザー確定 2026-10-10）。公開/選定アイデア・コンセプト・プロジェクトを**それぞれ1行**として1つの表に統合。クエストは行にせず、**テーマ/文脈のフィルタ軸**として扱う（クエスト自体に評価データが無いため）。
- **TRL は専用9段階を新設しない**＝**パイプライン上の位置（アイデア→コンセプト→プロジェクト）＋各ステータスを成熟度ラダー**として用いる。既存データで埋まり、新規データ追加を最小化できる（§3-③）。
- **アクセス＝専用の能力フラグ `portfolio_viewer`（会社アカウント管理とは独立）**（ユーザー確定 2026-10-10）。経営者が会社アカウント管理（SC-93）を兼ねないケースを想定し、`system_role` ではなく**②会社レベル能力（`user_capabilities`）に新語彙を追加**（既存流儀）。付与は会社アカウント管理者／`system_admin`（§6.1）。
- **行の既定＝選定アイデア（`is_selected`）＋コンセプト＋プロジェクト。チェックで未選定アイデアも表示**（ユーザー確定 2026-10-10）。
- **ポートフォリオ判断は専用テーブル `portfolio_decisions` で記録する（MVP に含める）**＝経営側（`portfolio_viewer`）が横断の配分判断（継続/増資/縮小/撤退/保留）を下し、**実エンティティ（アイデア/クエスト/コンセプト/プロジェクト）への反映はチームリーダーが行う**（判断と反映の責務分離・§4-(3)/§6.2）（ユーザー確定 2026-10-10）。
- **マトリクスのバブルサイズ＝投資規模を組み込む**（ユーザー確定 2026-10-10・§3.1 investment／§4-(2)）。
- **MVP は読み取り集約を土台**＝評価軸は既存データの join/集計で賄い、新規は上記 `portfolio_decisions` と `portfolio_viewer` 能力に限定（§6）。新規性カテゴリ・TRL 詳細カラムは新設しない（評価点・段階で代替）。

### 3.1 正規化（共通軸への写像）

各行を次の共通スキーマに正規化して返す（種別差を application 層で吸収）：

- **stage**（成熟度ラダー）＝ `idea` < `concept` < `project`、副位＝各 status（例 project: planning<in_progress / on_hold=停滞 / done）。
- **value**（0..1／低中高）＝ 種別別の評価集計を正規化（idea: impact・desirability 寄り／concept: desirability・viability／project: KPI or 由来コンセプト値）。
- **confidence**（0..1＝確度・リスクの裏返し）＝ idea: feasibility・cost／concept: feasibility・assumption_strength／project: status進捗。
- **novelty**（任意）＝ novelty 観点点。
- **opportunity_domain**（機会分野）＝ idea: alignment の focus_areas／concept・project: 由来から継承。
- **alignment_rate**（整合率 0..1）＝ idea: `idea_alignment.score`／他: 継承。
- **time_horizon**＝ 期日バケツ。
- **decision**（判断）＝ §4。
- **investment**（投資規模＝マトリクスのバブルサイズ・採用確定）＝ その取組みに「どれだけ賭けているか」を丸の大小で表す。既定 proxy＝**関与人数＋タスク数**（project: 開発メンバー数＋`tasks` 件数／concept・idea: 関与メンバー数）を正規化。将来 `portfolio_decisions` に**手動の投資規模上書き**（人月/予算）を持たせて精緻化。MVP でも一様サイズにせず proxy を入れる（大きい丸が高リスク象限に居る＝危険、が一目で分かることが狙い）。
- **priority_score**＝ 既定の加重和（§3.2）。

### 3.2 優先度スコア（ランク付けの基準）

既定＝`priority = w1·value + w2·confidence + w3·alignment_rate`（例 0.45/0.35/0.20・④おすすめクエスト選出と同系の加重和思想）。既定重みは固定で開始し、**会社別可変は将来拡張**（§7 で G3 と共通化）。これが ISO §6.4「優先順位付けの基準」の中核。

## 4. 画面設計（SC-97 想定・`portfolio_viewer` 向け）

2ビュー切替。既存の共有部品（DataTable サーバー委譲／§4.5）を土台にする。

### (1) テーブルビュー（既定）

- 共有 **DataTable（サーバー委譲・クエリ契約）**。列＝取組み名・種別/段階・価値・確度・新規性・機会分野・整合率・時間軸・判断・優先度スコア。
- **ランク**＝優先度スコア降順を既定ソート。
- **行の既定スコープ＝選定アイデア＋コンセプト＋プロジェクト**。ツールバーに **「未選定アイデアも表示」チェック**（ON で `is_selected=false` の公開アイデアも含める）。
- **絞り込み**＝種別／段階／機会分野／時間軸／判断／クエスト（テーマ）。
- 行クリック→当該エンティティ詳細（既存 SC：アイデア/コンセプト/プロジェクト）へ遷移。

### (2) マトリクスビュー（リスク×リターン バブル）

- x=確度（←→リスク）・y=価値・**バブルサイズ=投資規模（§3.1 investment）**・**色=段階 or 機会分野**。
- 4象限ラベル：左上「手堅い」・右上「やる（増資）」・右下「要検討（ハイリスク）」・左下「撤退候補」。
- バブルクリック→詳細遷移。ホバーで要約（取組み名・価値/確度/投資規模/判断）。
- 大きい丸が右下（高リスク）に居る＝大博打の警戒、が一目で分かることが本ビューの価値。

### (3) ポートフォリオ判断（MVP に含める・`portfolio_decisions`）

- 経営側（`portfolio_viewer`）が各取組みに横断の配分判断「継続／増資／縮小／撤退／保留」＋理由を記録（ISO §6.4「優先順位付け/改善」の証跡を1箇所に残す）。
- **判断と反映の責務分離**＝ここで記録するのは**経営の意思（ディレクティブ）**であり、**実エンティティへの反映操作（クエスト/アイデア/コンセプト/プロジェクトの status・decision 変更等）はチームリーダーが各画面で行う**。判断行には反映状況（未対応/反映済）を持たせ、リーダーが反映後にマークする（§6.2）。

## 6. データモデル影響

### 6.1 新規（MVP に含める）

- **能力語彙 `portfolio_viewer` を追加**＝`CAPABILITIES`（`impl/backend/app/tenant/capabilities/orm.py:23`）に 1 値追加。付与/剥奪/判定・UI は既存の汎用 `CapabilitiesSection`／`require_company_account_admin` 流儀をそのまま流用（新規 UI 不要）。データモデル §（能力）に追記。
- **`portfolio_decisions`**（取組み横断の経営判断の正本）。列案＝`id`／`target_type`(ideas/concepts/quests/projects)＋`target_id`（ポリモーフィック参照・既存 `info_links` 流儀に倣う）／`decision`(continue/invest/reduce/withdraw/hold)／`rationale`(text)／`decided_by_id`・`decided_at`／**反映状況** `reflection_status`(pending/reflected)＋`reflected_by_id`・`reflected_at`／（任意）`investment_override`(numeric・人月/予算)。監査6列（§2.1 方針に従う）。

### 6.2 判断と反映の責務分離（重要）

`portfolio_decisions` は**経営の意思決定の記録であり、実エンティティを直接変更しない**。例＝経営が「withdraw（撤退）」を記録→チームリーダーが対象コンセプトを `decision=kill` にする/プロジェクトを `on_hold` にする等を各画面で実施→ポートフォリオ側で `reflection_status=reflected` にマーク。これにより「誰がいつ配分を決め、誰がいつ現場反映したか」が分離して追える。

### 6.3 新設しないもの

- 読み取り集約で賄う軸（価値/確度/新規性/整合率/機会分野/時間軸）は既存 ideas/concepts/solutions/evaluations/concept_evaluations/idea_alignment の join/集計で算出。**新規性カテゴリ・TRL 詳細カラム・concept/project 版整合率テーブルは MVP では新設しない**（評点・段階・由来継承で代替）。将来の精緻化候補として注記のみ。

## 7. API 設計（想定）

- 全 EP で **`portfolio_viewer` 能力を要求**（`has_capability(..., "portfolio_viewer")`・会社スコープ）。
- `GET /portfolio/items` — サーバー委譲・DataTable クエリ契約。ideas/concepts/projects を共通スキーマに正規化して UNION 返却・会社スコープ・フィルタ（type/stage/domain/horizon/decision/quest・`include_unselected`）・priority_score ソート・investment（バブルサイズ）含む。
- `GET /portfolio/matrix` — バブル用集計（or `items` からフロントで算出）。
- `POST /portfolio/decisions`（新規記録）・`GET /portfolio/decisions`・`PATCH /portfolio/decisions/{id}`（判断更新／`reflection_status` マーク）。記録は `portfolio_viewer`、`reflected` マークはチームリーダー想定（§5-(d)）。
- **G3（§9.1 指標）と集計ロジック共通化**＝価値/確度/整合率/機会脅威率の正規化を共有モジュール化し、G2（盤面）と G3（指標）で再利用。

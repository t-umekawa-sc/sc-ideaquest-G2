## 0. 位置づけ・狙い（なぜ独立の横断基盤か）

- 秘密情報（APIキー・パスワード・トークン・暗号鍵・DB資格情報）の**保管・暗号化・配布・ローテーション・監査**を、**単一の標準**として設計する。
- **なぜ独立させるか**＝秘密保護は**特定機能の都合ではなく全機能に共通**する。カメリオ連携のためだけに作ると、SMTP/Turnstile/HIBP/DB資格情報/将来の各連携が**バラバラの流儀**になり、守りに穴が空く。LLM ゲートウェイ（provider 隠蔽の横断層）・Jasper レンダラ port（疎結合の横断層）と同じく、**横断で1本化**する。
- **現状**＝[本番デプロイ要件](../本番デプロイ要件.md) §3 で「秘匿はシークレットマネージャ供給（`.env` に本番実値を焼かない）」と**方針だけ**定義済み（`SMTP_PASSWORD`/`TURNSTILE_SECRET_KEY`）。本書はその**具体化＝「どう供給し・どう守るか」の実装設計**。
- **非目標**＝独自暗号アルゴリズムの実装（§13「独自の暗号方式を作らない」）・常設シークレットサーバの即時導入（§9 で将来オプション）。

## 1. 脅威モデル（何から守るか＝段階で考える）

| # | 脅威 | 代表例 | 本設計で守る層 |
|---|---|---|---|
| T1 | **ソース管理・配布物への焼き込み漏洩**（最多） | うっかり `git commit`／public イメージに鍵残存／compose に実値 | §4-A（SOPS）・§5 |
| T2 | **保存データ漏洩** | DB ダンプ／バックアップ／ディスク流出 | §4-B（AES-GCM）・§6 |
| T3 | **実行環境への侵入** | コンテナ侵入・`docker inspect`・`/proc/environ`・子プロセス継承 | §5（env→ファイルマウント）・§8 |
| T4 | **アプリ権限での RCE** | 脆弱性経由の任意コード実行で“アプリが使える秘密”に到達 | **原理的に完全防御不可**＝§8 で被害最小化＋侵入させない側（DAST） |

> **設計の芯**＝T1/T2 は**完全に塞げる**（at-rest）。T3 は**露出面を大きく減らせる**。T4 は**完全には防げない**ので、被害 window の縮小・検知・侵入防止（DAST）で対処する——と**正直に段階化**する。

## 2. 秘密の分類（棚卸し）

守り方が変わるため、まず**2種類に分類**する：

| 種別 | 定義 | 例 | 守り方 |
|---|---|---|---|
| **(A) デプロイ秘密** | **デプロイ時点で判明**している静的な秘密 | SMTP_PASSWORD／TURNSTILE_SECRET_KEY／DB 資格情報／**AES-GCM マスター鍵**／age 秘密鍵 | **SOPS+age**（§4-A/§5） |
| **(B) 実行時入力秘密** | **運用中にユーザー（会社管理者）が画面から入力**する秘密 | **カメリオ API キー**／将来の各連携キー | **DB に AES-GCM 暗号化**（§4-B/§6）。復号用マスター鍵は (A) |

- **なぜ分ける**＝(A) は Git/デプロイで配れるが、(B) は**実行時に DB へ入る**ため SOPS では扱えない（デプロイ時に存在しない）。(B) は DB 暗号化し、**その暗号鍵を (A) で守る**＝二層が噛み合う。

## 3. 全体像（二層構造）

```
            ┌─────────────────────────── (A) デプロイ秘密 ───────────────────────────┐
  Git ──▶  secrets.enc.yaml (SOPS 暗号化・値は暗号文・Git にコミット可)
            │                                   │
            │  復号は age 秘密鍵でのみ可          │
            ▼                                   ▼
  age 秘密鍵  ── compose `secrets:` ファイルマウント(/run/secrets/age_key) ──▶ 起動時に SOPS 復号
            │                                                                    │
            │                                                                    ▼
            │                         SMTP_PASSWORD / AES-GCM マスター鍵 / … をプロセスへ
            └───────────────────────────────────────────────────────────────────┘
                                                 │ AES-GCM マスター鍵
                                                 ▼
            ┌─────────────────────────── (B) 実行時入力秘密 ──────────────────────────┐
  管理者入力 ──▶ カメリオ API キー ── AES-GCM 暗号化 ──▶ DB(credentials_encrypted)
                                     （復号は上記マスター鍵でのみ可）
            └───────────────────────────────────────────────────────────────────────┘
```

## 4. 設計の芯

### 4-A. デプロイ秘密＝SOPS+age（Git に暗号化コミット）

- **SOPS（Secrets OPerationS・MPL-2.0）**＝構造化ファイル（YAML/JSON/.env）の**値だけを暗号化**し、キー名・構造は平文のまま残す。**変更した値だけ再暗号化**するので **Git の diff が意味を持つ**（変更監査）。
- **age（BSD・現代的で簡素な暗号ツール）**＝SOPS の鍵ソース。**age 公開鍵で暗号化／age 秘密鍵で復号**。
- **運用**＝`secrets.enc.yaml` を **Git にコミット**（値は暗号文）。デプロイ/起動時に **age 秘密鍵**で復号し、環境へ展開。
- **環境別分離**＝prod 用／dev 用で age 鍵を分ける＝**開発者が本番秘密を復号できない**。
- **CI**＝CI には **age 鍵1個**だけ持たせれば全復号可（CI 設定に N 個の秘密を散らさない）。

### 4-B. 実行時入力秘密＝DB に AES-GCM

- 管理者が画面入力する秘密（カメリオ API キー等）は **AES-GCM（認証付き暗号）**で暗号化し DB へ（§6）。
- **暗号ライブラリ**＝Python `cryptography`（Apache-2.0/BSD・無料商用可）。**独自暗号は書かない**＝**自作するのは「ライブラリを薄く呼ぶラッパー」まで**（§13）。
- **復号用マスター鍵は DB の外**＝(A) の SOPS 経由で供給（§3）。**暗号文と鍵を分離**（§12）＝DB ダンプが漏れても復号不能。

## 5. 鍵・秘密の配布（env ではなくファイルマウント）

- マスター鍵・age 秘密鍵・各デプロイ秘密は、**環境変数に置かず** **docker compose `secrets:`（ファイルマウント＝`/run/secrets/<name>`・読取専用）**でプロセスへ供給。
- **なぜ env でないか**＝env は **`docker inspect`／`/proc/<pid>/environ`／子プロセス継承**で覗ける（T3）。ファイルマウントはこれらに出ず、権限（0400）で読み手を限定できる。
- **実値は Git・Dockerfile・compose に書かない**（§13・既存 `SMTP_PASSWORD`/`TURNSTILE_SECRET_KEY` と同方針）。compose には**参照（`file: ./secrets/age_key`）だけ**書き、実ファイルは Git 追跡外。
- **注意（過信しない）**＝素の compose（非 Swarm）の `file:` は**ホスト上に平文ファイルが残る**＝「env の覗き見経路を塞ぐ」まで。保存時暗号化は SOPS（§4-A）が担う。
- **実装済み（2026-10-09・D6 (A) ファイル供給基盤）**＝backend は pydantic `secrets_dir="/run/secrets"`＋`settings_customise_sources` で **file > env**（迷い込んだ/残留 env に file が負けない＝T3）。`/run/secrets` が無い dev は従来どおり env（警告も出さない）。jasper（素の環境変数読取）は `_secrets.read_secret` で同じ **file>env**・`hmac.compare_digest` で定数時間比較（§8/§13）。本番オーバーレイ `impl/compose.secrets.yaml`（`mode:0400`・jasper は非 root uid 10001 指定・**最小権限＝使う backend と検証する jasper だけに配布**）。使い方＝`docker compose -f compose.yaml -f compose.secrets.yaml up -d`。
- **本番 fail-closed ガード（実装済み・(広)）**＝`app/core/config.py` の `insecure_prod_secrets(settings)` が、本番（`app_env=prod`）で **dev 既定値/プレースホルダのまま**（`postgres_password=ideaquest`・`minio_*`・`bootstrap_admin_password=Passw0rd!`・`jasper_shared_secret=dev-jasper-secret`）or **機能有効時に必須の秘密が空**（renderer=jasper の S2S 秘密）を検出し、`main.lifespan` で **`RuntimeError` 起動拒否**。**空が正当な秘密**（`bootstrap_admin_password=""`＝seed しない・`turnstile_secret_key=""`＝CAPTCHA 無効）は壊さない＝実際の footgun（dev 既定の本番流入）だけ塞ぐ。値はログに出さず**フィールド名のみ**（§15）。完全な秘密棚卸しによる精緻化は SOPS 本体で（§12-3）。

## 6. DB 暗号の実装方針（AES-GCM ラッパー）

- **envelope＋バージョニング**＝`{key_version, nonce, ciphertext, tag}` を保存（`credentials_encrypted`）。`key_version` を持たせ、**マスター鍵ローテ時も旧版を復号可能**にする。
- **AAD（Additional Authenticated Data）**＝`provider`/`company_id` 等を AAD に束ねて**付け替え（暗号文の使い回し）を検知**。
- **復号は使用の瞬間だけ**＝平文はメモリ上で使い即破棄（§8）。
- **マスク**＝API は末尾4桁等でマスク、平文は非返却、変更は再入力のみ。

## 7. 守れるもの／守れないもの（正直な線引き）

| | 守れる | 守れない |
|---|---|---|
| **SOPS+age（A）** | T1 Git/イメージ/配布物漏洩・T2 の一部（暗号化バックアップ）・変更監査・環境別分離 | **age 秘密鍵自体の漏洩**（漏れれば全復号可＝守りは age 鍵1点に集約）／T3・T4（runtime）／**自動ローテーション・短命化・中央アクセス監査**（＝サーバ型の領分）／**キー名（フィールド名）は平文**で見える |
| **AES-GCM DB暗号（B）** | T2 DB ダンプ/バックアップ漏洩（鍵が別管理なら復号不能） | T3・T4（復号後の平文がプロセス内に在る）／マスター鍵が漏れれば全復号可 |
| **ファイルマウント（§5）** | T3 の env 覗き見経路（inspect/environ/子継承） | ホスト上の平文ファイル自体／T4 |

> **メンタルモデル**＝本設計は **at-rest とサプライチェーン（T1/T2）を守り、全体の守りを「age 鍵1点＋マスター鍵の保護」に集約する**。**runtime（T3/T4）は at-rest では守れない**＝§8 で補完する。

## 8. 守れない部分（runtime/ローテーション）の補完策

- **復号後の平文はメモリ限定・ログ禁止**＝使用の瞬間だけ使い即破棄。**ログマスク**＝[本番デプロイ要件](../本番デプロイ要件.md) §6.6 のキー名再帰マスク（`***`）に**全ての秘密のキー名を登録**。例外/スタックトレース/エラー画面/CI ログにも載せない（§14/§15）。
- **最小権限**＝age 鍵・マスター鍵を読めるプロセスを限定（連携ワーカ等）。
- **ローテーション手順**＝(A) は age 再キー＋再暗号化＋再デプロイ／(B) は元サービスでキー再発行→DB 再暗号化。漏洩時の**被害 window を短縮**。手順を runbook 化。
- **異常検知**＝秘密悪用の兆候（外部 API 取得量急増など）をアラート（§15）。
- **原理的限界の明記（T4）**＝アプリ権限の RCE には完全防御不可＝**「そもそも侵入させない」側**（WAF・脆弱性対応・DAST＝既存の ZAP 動的セキュリティ検証計画）で守る。

## 9. 将来オプション（サーバ型シークレットマネージャ）

- **現時点は不採用**＝守る秘密が少なく、常設サーバの運用負荷（unseal／backup／HA／upgrade）と**新たな SPOF 化**（落ちる/封印中＝アプリ機能停止）に見合わない。
- **昇格条件**＝秘密の種類・サービス・部門が増え、**中央集権管理・動的シークレット・ランタイムのアクセス監査/即時失効**が要るようになったとき。
  - **OpenBao（MPL-2.0）**＝動的シークレット/監査重視。Vault の中立フォークでライセンスがクリーン。ただし本家 Vault 比でエコシステム成熟度は発展途上・運用は SOPS より重い。
  - **Infisical（MIT コア）**＝WebUI/開発者 UX 重視。アプリ秘密の保管/注入用途なら導入が素直。
  - **クラウド KMS（AWS/GCP/Azure・有料）**＝マスター鍵を HSM で守りアプリに降ろさない。本番でさらに堅くしたい時の選択肢（必須でない）。GCP Secret Manager は無料枠あり。
- **移行容易性**＝(A)/(B) の境界（§2）を保てば、マスター鍵・デプロイ秘密の**供給元を SOPS→サーバ型へ差し替えるだけ**でアプリ本体は不変（抽象を保つ）。

## 10. 工数・導入手順（SOPS+age）

- **工数の目安＝約0.5〜1人日**（サーバ不要）。
  1. `sops`/`age` 導入（CI/デプロイ環境）＋ age 鍵ペア生成（prod/dev 別）。
  2. 既存秘密（SMTP/Turnstile/HIBP/DB 資格情報）を `secrets.enc.yaml` に集約し SOPS 暗号化→Git コミット。実ファイルの平文は追跡外へ。
  3. compose `secrets:` で **age 秘密鍵をファイルマウント**（§5）。起動スクリプトで SOPS 復号→環境展開。
  4. AES-GCM ラッパー（§6）を backend に薄く実装（`cryptography`）＝(B) 用。
  5. ログマスク（§8）へ全キー名登録。runbook（ローテ手順）整備。
- **比較**＝OpenBao は初期**約4〜5人日＋継続運用**（§9）＝今回は過剰。

## 12. 残論点

1. **age 鍵のホスト保管**（ファイルマウント平文ファイルの権限/配置・将来 TPM/`systemd-creds` 併用の是非）。
2. **AES-GCM マスター鍵のローテーション運用**（`key_version` 設計は §6・自動化の範囲）。
3. **SOPS 対象の棚卸し**（既存 `.env` のどこまでを SOPS 管理へ寄せるか・移行順）。
4. **サーバ型への昇格条件の数値化**（秘密数・サービス数の閾値）。

# プロジェクト管理機能 拡張（カンバン／マイタスク横断／依存関係／仕様確定投票）— 設計ドラフト

> 状態: **ドラフト（2026-10-09 セッションで方向合意・詳細レビュー待ち）**。別セッションが solutions ドメインを実装中のため、本書は**設計ドラフトのみ**（正本・バックログ台帳は実装セッションが反映。[セッション調整/引継 README](../セッション調整/引継/README.md)）。
> **位置づけ**＝[ソリューション開発機能_設計](ソリューション開発機能_設計.md)（MVP の北極星）の **§9-7「保留（Phase2）」を具体化する拡張設計**。MVP は「WBS＋担当＋状態＋期日＋タスクチャット＋完了報酬」まで実装済（backend ドメイン Q 全 EP／SC-70・71・72）。本書はそこに **(A) カンバンボード・マイタスク横断、(B) 依存関係→ブロック可視化、(C) 仕様確定の投票**を段階追加する。

## 0. 要旨（何を・なぜこの順で）

現 MVP は「作れる・割り当てる・完了できる」までを縦に薄く通した。日常運用に耐えるには **(a) 俯瞰（今どこで詰まっているか）** と **(b) 毎日の入口（自分は何をやるのか）** が要る。この二欠落を**既存スキーマ・既存 EP でほぼ埋められる**のが本拡張の核。

| フェーズ | 機能 | 狙い | DDL | コスト |
|---|---|---|---|---|
| **A** | カンバンボード＋マイタスク横断 | 俯瞰＋毎日の入口（実用化） | **不要**（既存 `status`・新規集約 EP 1 本） | 小〜中 |
| **B** | タスク依存関係 → ブロック可視化 | 「なぜ止まっているか」の可視化・ガントの布石 | 器あり（`task_dependencies` 有効化） | 中 |
| **C** | 仕様確定の投票 | デリバリ中の争点決着・ISO トレーサビリティ・本プロダクト固有の強み | 器あり（`spec_decisions`/`spec_decision_votes` 有効化） | 中 |

- **投入順の理由**＝A は DDL ゼロ・最も早く実用価値が出る→先。B/C は器はあるが UI＋ロジック新規のため後。C は投票資産（コンテスト）流用で設計複雑度を下げられる。
- **各機能は独立して投入可能**（A→B→C の依存は弱い）。受入が通った単位で随時 main へ。

## A. カンバンボード ＋ マイタスク横断（Phase A・DDL 不要）

> この 2 つはセットで投入する。理由＝俯瞰（ボード）と入口（マイタスク）という PM の二大欠落を同時に埋め、どちらも既存スキーマ・既存認可で完結するため。

### A-1. カンバンボード（SC-71 新タブ「ボード」）

#### A-1.1 位置づけ・UI
- SC-71 プロジェクト詳細に **新タブ「ボード」**を追加（既存タブ＝WBS／開発メンバー／導入・価値実現 と並ぶ）。WBS ツリーは階層把握、ボードは**状態俯瞰**＝役割が異なるので両立させる（置換しない）。
- **レーン＝`tasks.status`**（`todo` / `doing` / `done` / `blocked`）の 4 列。各列ヘッダに件数。
- **カード＝タスク**。表示＝`title`・担当アイコン（`QuestIcon` 流用＝[strategy-picker-show-icons] 準拠の頭文字/画像）・`due_date`（期限超過は警告色）・`kind` ラベル・`blocked` バッジ・子タスク有無インジケータ。
- **カードクリック**＝既存のタスク編集モーダル（SC-72・URL 付きモーダル）へ。ボードから独自編集 UI は作らない（DRY）。
- **ツリー表現の扱い**＝ボードは**フラット表示**（親子を階層化しない）。ただしカードに「親: <要件名>」のパンくずを 1 行出し、WBS 文脈を失わせない。初期スコープは「葉タスク（`kind=task`）のみ表示／要件（`kind=requirement`）は除外」を既定とし、トグルで全粒度表示可（要件は進捗ロールアップ表示）。

#### A-1.2 ドラッグ&ドロップ（状態更新）
- カードを別レーンへ D&D → **`PATCH /api/v1/tasks/{task_id}`** の `status` 更新（**新規 EP 不要**）。
- `done` レーンへ投入 → **既存の完了報酬（`delivery_xp` ＋ coin）がそのまま発火**（`activities(reason='task_done', ref_type='tasks', ref_id=<task_id>)` の冪等チェック済。[ソリューション開発機能_設計](ソリューション開発機能_設計.md) §3.2）。`done` から戻しても取消しない（§9-6⑨＝差し戻し取消なし を踏襲）。
- **楽観的更新**＝D&D 即座にカード移動→PATCH 失敗時はロールバック＋トースト（[デザイン標準](../画面設計/デザイン標準.md) トースト）。
- **同一レーン内並べ替え**＝`sort_order` の兄弟順を使う。ただし初期スコープでは**レーン間移動（status 変更）だけ**を対象にし、レーン内並べ替えは WBS タブに委ねる（過剰実装回避・Phase A は status 一本）。

#### A-1.3 権限（既存認可を踏襲）
- `my_permissions`（`can_manage_tasks`＝lead／owner）を持つユーザー＝**全カードを D&D 可**。
- `member`＝**自分が担当（`assignee_account_id = me`）のカードのみ**レーン移動可（＝自分のタスク状態更新＝MVP の「状態更新は担当者＋lead＋owner」規則そのまま。[ソリューション開発機能_設計](ソリューション開発機能_設計.md) §7）。
- 移動不可カードは `draggable=false`＋tooltip（[completed-quest-freeze-ui-standard] 準拠＝押せない方を明示）。

#### A-1.4 アニメーション抑制（必須）
- D&D のドロップ/並びアニメは **OS reduce-motion OR `accounts.reduce_motion`** を尊重（[デザイン標準](../画面設計/デザイン標準.md) §4.9・[animation-reduce-motion-standard]）。抑制 ON 時は瞬間移動。D&D ライブラリは framer を使わず CSS/軽量 DnD で（[modal-no-framer-css-only] の精神＝過剰アニメ回避）。

#### A-1.5 backend
- **新規 EP 不要**。既存 `GET /projects/{id}/tasks`（ツリー）＋ `PATCH /tasks/{id}`（status）で完結。
- ボードはツリー応答を frontend で status ごとに bucketing（別クエリ不要・N は 1 プロジェクト分で小）。

#### A-1.6 テスト観点（TC 起こしの種）
- API: 既存 `PATCH /tasks/{id}` status 更新＋done 完了報酬冪等（既存 TC 流用）。
- e2e: ボードで D&D→status 反映・done 投入で XP/coin デルタ演出（[game-feel-8-xp-feedback-decision] のデルタ系）・member は自分のカードのみ移動可・reduce-motion ON で抑制。

### A-2. マイタスク横断ビュー（全プロジェクト横断＋ダッシュボード統合）

#### A-2.1 位置づけ・UI
- 現状は「プロジェクトを開かないと自分のタスクが見えない」。PM の**毎日の入口**として、**全プロジェクト横断で `assignee_account_id = me` のタスクを集約**する。
- **2 面で提供**：
  1. **専用一覧画面（新 SC・例 SC-73「マイタスク」）**＝共有 `DataTable`（サーバー委譲・[list-server-delegation-standard]）。列＝タスク名／プロジェクト名（リンク）／状態／期日／kind。既定ソート＝期日近い順、`blocked` 優先。クイックフィルタ＝すべて／進行中／ブロック／期限超過／今週。
  2. **ダッシュボード（SC-01）1 ゾーン**＝直近期日 N 件（[dashboard-redesign-announcements] のゾーン構成に 1 ゾーン追加・実装セッションと要調整）。「すべて見る」で SC-73 へ。
- **行クリック**＝当該タスクの編集モーダル or タスクチャットへ（SC-72 流用）。

#### A-2.2 backend（新規 EP 1 本）
- **`GET /api/v1/me/tasks`**（サーバー委譲・[API設計 §1.8](../API設計/README.md) の DataTable クエリ契約準拠）。
  - スコープ＝ログインユーザーが担当（`assignee_account_id = me`）かつ `can_access_project` が真なプロジェクト配下のタスク（削除済プロジェクト/タスクは除外）。
  - フィルタ＝`status` / `project_id` / `due_before` / 期限超過フラグ。ソート＝`due_date`・`status`。
  - 応答＝タスク行＋`project`（id/title）を join（N+1 回避＝プロジェクト名を結合返却）。
  - 列 flags＝ホワイトリスト一致（[list-server-delegation-standard]）。
- **配置**＝ドメイン Q に追加（[API設計 Q](../API設計/Q_ソリューション開発.md) に既存節と同じ表形式で追記。[api-design-endpoint-table-format]）。`/me/*` の前例（例＝`report_enabled` を返す `/me` 等）に倣う。

#### A-2.3 テスト観点
- API: 自分担当のみ返す・他社/非アクセスプロジェクトは漏れない（秘匿 404 ではなく単に対象外）・削除済除外・期日ソート・DataTable クエリ契約（ページ/ソート/絞込）。
- e2e: ダッシュボードゾーン表示→SC-73 遷移→期日順・blocked 優先。

## B. タスク依存関係 → ブロック可視化（Phase B・器あり）

> 器＝`task_dependencies(task_id, depends_on_task_id, dep_type)`（[データモデル](../データモデル.md) §5.52 相当・MVP 未配線）。Phase B で有効化。**本格ガント（クリティカルパス描画）はさらに次段**＝まずは依存の登録とブロック可視化まで。

### B.1 スコープ
- **先行タスク（depends_on）の登録/解除**＝タスク編集に「先行タスク」ピッカーを追加。候補＝**同一プロジェクト内のタスク**（対象選択ダイアログを流用＝[strategy-picker-show-icons] のアイコン付き候補）。
- **循環禁止＋同一プロジェクト制約**＝登録時に DFS で循環検出→ `409 conflict`（親子変更の循環禁止と同じ流儀。[ソリューション開発機能_設計](ソリューション開発機能_設計.md) タスク PATCH）。別プロジェクトのタスクは候補に出さない（422）。
- **ブロック可視化**＝先行タスクが未 `done` のタスクに「⏳ 先行 N 件未完」バッジを WBS／ボードに表示。
- **（オプション）自動ブロック**＝先行未完のタスクを `blocked` 相当として扱うかは**トグル方針を要確認**（自動 status 書換えは破壊的なので既定 OFF ＝バッジ表示のみを推奨）。

### B.2 backend
- **`POST /api/v1/tasks/{task_id}/dependencies`**（body＝`depends_on_task_id`・`dep_type` 既定 `finish_to_start`）／**`DELETE /api/v1/tasks/{task_id}/dependencies/{dep_id}`**。
- 認可＝タスク管理権限（lead／owner・既存ルール）。循環・越境バリデーション。
- タスクツリー応答（`GET /projects/{id}/tasks`）に各タスクの `dependencies`（先行 ID 群）と `blocked_by_count` を含める。

### B.3 ガント（次段・器の残り活用）
- `planned_start`/`planned_end`/`actual_start`/`actual_end`（器あり・MVP 未使用）＋依存を組み合わせ、タイムライン表示。**Phase B では列入力 UI の追加まで**に留め、ガント描画は別タスクに切る（過剰実装回避）。

### B.4 テスト観点
- API: 依存登録/解除・循環 409・越境 422・ツリー応答に blocked_by 反映。
- e2e: 先行登録→バッジ表示→先行 done でバッジ消滅。

## C. 仕様確定の投票（Phase C・器あり・固有価値）

> 器＝`spec_decisions` / `spec_decision_votes`（[データモデル](../データモデル.md) §5.52-5.53・[ソリューション開発機能_設計](ソリューション開発機能_設計.md) §7.1・MVP 未配線）。デリバリ中の「仕様で決めないといけない事案」を起票→**開発担当＋イノベーション担当が投票→確定**。

### C.1 位置づけ・固有性
- コンセプト段の Go/Pivot/Kill 投票とは**別目的**（＝デリバリ中の争点決着）で、[ソリューション開発機能_設計](ソリューション開発機能_設計.md) §1.2「投票は継承しない（コンセプトのループ機構を持ち込まない）」とは**矛盾しない**（明記）。
- **本プロダクト固有の強み**＝(1) 二層メンバーシップ（開発×イノベーション）が同じ場で意思決定、(2) 確定記録が ISO56001 のトレーサビリティ（決定の根拠と関与者）に効く、(3) 既存のゲーミフィケーション（投票参加に少額 XP）が乗る。

### C.2 スコープ・UI
- SC-71 に**新タブ「意思決定」**＝争点（`spec_decisions`）一覧（状態＝open/closed・結果）。
- 争点起票＝論点タイトル＋説明＋選択肢（複数）。投票＝選択肢に 1 票（`spec_decision_votes`）。確定＝owner/lead が締切り→結果を記録。
- **確定の効力**＝MVP では「記録＋チャット橋渡し」まで（決定内容をタスクチャット/`deployment` メモへ反映は手動）。自動タスク化は将来。
- **投票資産の流用**＝コンテスト投票（[idea-contest-feature]）の投票 EP/集計/UI を踏襲し新規設計を最小化。

### C.3 backend
- **`POST /api/v1/projects/{id}/spec-decisions`**（論点＋選択肢）／**`GET /api/v1/projects/{id}/spec-decisions`**（一覧）／**`POST /api/v1/spec-decisions/{id}/votes`**（投票）／**`PATCH /api/v1/spec-decisions/{id}`**（締切り・確定）。
- 認可＝投票＝`can_access_project`（両担当）／起票・締切り＝owner/lead。1 人 1 票（UNIQUE）。
- ゲーミフィケーション＝投票参加に少額 XP（`activities` 既存パターン・冪等）。

### C.4 テスト観点
- API: 起票・投票・1 人 1 票・締切り後投票拒否（409）・確定結果・権限。
- e2e: 争点作成→両担当投票→確定表示。

## D. 横断の設計方針

- **DRY（[コーディング規約](../規約/コーディング規約.md) §2.3）**＝共有 `DataTable`（サーバー委譲）・対象選択ダイアログ・チャット中核・完了報酬（G ドメイン委譲）・URL 付きモーダル（[url-modal-standard-for-dialogs]）・投票（コンテスト資産）を流用。新規 UI は極力作らない（[reuse-existing-ui-no-new]）。
- **フロント実装フロー**＝モック先行（`style-guide.html`／`mocks/`）→ 画面接続（[フロントエンド実装フロー規約](../規約/フロントエンド実装フロー規約.md)）。カンバンのカード/レーンは新規コントロールなので **style-guide にモック先行**（[style-guide-first-for-controls]）。
- **入力検証**＝争点起票・依存登録等のフォームは §4.7 の 4 部品（[form-validation-47-standard]）。
- **アニメ抑制**＝D&D 等の演出は reduce-motion 尊重・テスト必須（[animation-reduce-motion-standard]）。
- **受入ゲート**＝1 画面単位ループ＋ユーザー動作確認（[backend-connection-per-screen-loop]）。

# クエストの最終結果と ISO 56002 — 関係性と設計意図（FR-39 背景メモ）

> 目的＝FR-39「クエストの最終結果＝検証済みコンセプト票」で ISO 56002 を根拠に決めた仕様の**意図・なぜそうしたか**を1本にまとめる（[ドキュメント作成規約](../規約/ドキュメント作成規約.md)／[document-design-rationale の方針]＝結論だけでなく理由を残す）。
> 仕様の実体は [FR-39 設計ドラフト](FR-39_クエスト最終結果_ISO56002.md)・要件定義 FR-39。本書はその**思想・トレードオフ**の解説。ISO 56002 の節は「ISO56002 §x」と明記（本プロジェクト文書の §x と区別）。

## 0. ISO 56002 とは（前提）

ISO 56002 は **イノベーション・マネジメントシステム（IMS）の手引**。組織がイノベーションを「思いつき任せ」でなく**仕組みとして反復**するための指針で、要点は次の3つ。

1. **価値の実現（value realization）が最終目的**＝新規性そのものでなく、実現された価値。
2. **イノベーション・プロセス**（ISO56002 §8.3）＝おおむね「①機会の特定 → ②コンセプトの創造 → ③コンセプトの検証 → ④ソリューションの開発 → ⑤導入（価値実現）」。
3. **パフォーマンス評価（§9）と改善（§10）**＝継続的に測定・学習し、次サイクルへ回す（PDCA 的）。

## 1. ideaquest をこの枠組みに載せる（基本思想）

**1クエスト＝1つのイノベーション・イニシアチブ**と捉える。すると既存機能が §8.3 の工程に自然に対応する。

| ISO56002 工程 | ideaquest | 意図 |
|---|---|---|
| ① 機会の特定 | クエスト作成（テーマ・目的） | 「何のために取り組むか」を先に固定＝適合性評価の基準になる |
| ② コンセプトの創造 | アイデア投稿（＝「意図」の創出） | 提案価値＋本文で発想を形にする |
| ②' 精緻化 | チャット議論 | 意図を具体化し、論点・利害関係者・前提・リスクを洗い出す |
| ③ コンセプトの検証 | 評価（5観点採点＋総評）＋選定 | 公平な検証で「有望なコンセプト」を選ぶ |
| ④ 開発 / ⑤ 導入 | **アプリ対象外（将来拡張）** | 現行は③まで。④以降は別ツール/現場、または後続クエスト |

**この整理が全ての判断の土台**。「最終結果」は③の締めであり、④へ渡す橋（引き継ぎ）と位置づけた。

## 2. 決めた仕様と、その意図（ISO56002 との対応）

### 2.1 最終結果＝「検証済みコンセプト票」（新情報を作らず既存3成果物を凝縮）
- **意図**：アイデア/チャット/評価はバラバラに埋もれがち。クエスト全体として「何を得たか・なぜそう判断したか・次に何をするか」を1枚に**凝縮・翻訳**し、組織の学び・次アクションに再利用できるようにする。
- **ISO56002 対応**：§8.3 のゲート判断（採否と根拠）＋ §4.2 価値実現への橋渡し。
- **なぜ「新情報を増やさない」か**：③の締めは記録・意思決定・学びであって、新たな入力を課すと運用負荷で形骸化する。人手記入は④振り返り・⑤次アクション・KPI に絞った。

### 2.2 「④ソリューション開発」はアプリ内に作らない（今回スコープ外・将来拡張）
- **意図**：現行 ideaquest の価値は「機会→コンセプト→検証」の高速回転。開発・導入まで抱えると別物（プロジェクト管理）になり肥大化する。
- **手当て**：最終結果の「次アクション」から**後続クエストを複製で起票**できる＝③→（次サイクル）へ連結。将来 ④ を作るなら、この引き継ぎ書が入口になる。

### 2.3 各セクションの内訳と ISO56002 対応
| 結果のセクション | 由来 | ISO56002 | 意図 |
|---|---|---|---|
| ①検証済みコンセプト（選定） | 選定＋評価平均 | §8.3 | 「採用された有望案」を先頭に置く |
| ②検証サマリ（観点別平均・参加指標） | 評価/投票/パーティー | §9 パフォーマンス評価 | 定量で「どれだけ検証されたか」を可視化 |
| ③意思決定の記録（採否＋理由） | 選定＋評価総評 | §8.3 ゲート | 後から「なぜそう決めたか」を辿れる（説明責任） |
| ④議論の要点（(a)リンク+(b)ピン+(c)要約） | チャット | §8.3/§9 | 検証の証跡（なぜ有望と判断したか）を残す |
| ⑤振り返り・学び＋KPI | 人手記入 | §10 改善 | 学びを明文化し次サイクルへ（継続的改善） |
| ⑥次アクション | 人手記入＋複製 | §8.3/§10 | 展開・継続の入口 |

### 2.4 「議論の要点」を3方式（a/b/c）にした意図
チャットは大量で、そのままでは「結果」にならない。3段構えで**手間と確実性のバランス**を取る。
- **(a) リンク**：最小コスト。全文は原チャットで辿れる。
- **(b) ピン留め（owner/quest_admin がキュレーション）**：**検証の証跡を確実に残す**。「誰が重要と判断したか」も含め責任者が選ぶ＝結果の信頼性を担保（§9/§10）。だから一般メンバーでなく管理者権限に限定した。
- **(c) 自動要約（抽出型・オフライン・無料）**：人手を補助。**外部LLMは使わず**（会社データを外部に出さない・課金なし）`janome`＋頻度ベースの抽出で「重要文候補」を出す。品質は粗い前提で、人手（a/b）を置き換えず**補助**に留める。将来 LLM 生成要約へ差し替えられるよう要約関数を seam 化。

### 2.5 完了時の通知・成果フィード・総括XP
- **意図**：成果を**共有してこそ学びが広がる**（ISO56002 の狙い）。完了＝結果確定を数少ない重要イベントとしてパーティー通知＋チーム成果フィードに載せる。総括の初回記入に少額XPで「ちゃんと締める」行動を後押し（§10 の定着）。

### 2.6 途中経過の常時表示（2026-09-13 変更＝「完了後のみ」を上書き）
- **当初**：単純化のため「結果タブは完了後のみ」。
- **変更の意図**：ISO56002 §9 の**パフォーマンス評価は継続的**であり、一発の締めではない。参加者が**進行中に現状（評価平均・参加状況・暫定の選定）を把握**できると、活動の軌道修正・モチベーションに資する。「検証済みコンセプト票」は**育つ生きた文書**という 2.1 の思想とも整合。
- **手当て（誤解防止）**：完了前は**「暫定の途中経過」を明示**（タブに「暫定」チップ＋上部に進行中バナー＋見出しの語調）。評価スコアの早期露出は既に SC-12/SC-22 でパーティー公開済み（visibility 準拠）＝新たな露出ではない。門番・可視性はサーバー強制のまま。
- **結論**：常時表示は**不適切ではなく、むしろ ISO56002 に整合**。ただし「確定」と誤認させない見せ方が条件。

## 3. トレードオフと今後
- (c) 抽出型要約は品質が粗い＝あくまで補助。高品質化は seam（`app/tenant/quests/summarize.py`）を LLM に差し替え（別途データ保護・コスト方針の判断が要る）。
- KPI は自由記述（軽い測定）＝将来、固定指標や実測連携（§9 の定量化強化）へ拡張余地。
- ④開発フェーズをアプリ内に持つ場合は、本引き継ぎ書を入口に「開発フェーズのクエスト種別」を新設する案（将来）。

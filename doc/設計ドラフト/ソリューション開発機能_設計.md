# ソリューション開発機能（プロジェクト／タスク管理）— 設計ドラフト

> 状態: **ドラフト（2026-09-26 セッションで方向合意・詳細レビュー待ち）**。ISO 56001 の **④ ソリューションの開発 ／ ⑤ 導入（価値の実現）** を、これまで「クエスト外＝将来拡張」として棚上げしてきた段（[コンセプト機能 ISO56001 再設計](コンセプト機能_ISO56001_再設計.md) §1.1）を、いよいよアプリ内の**新ドメイン「プロジェクト／タスク管理」**として起こす。
> **なぜ今作るか**＝FR-39 が「go 判定済みコンセプトを *受け渡す成果物* とし、④⑤は別レイヤ（プロジェクトドメイン／外部 PM 連携）へ渡す」と定義していた、その **"受け渡し先" 本体**。1 サービス内で ISO 56001 の一連（機会特定 → コンセプト創造・検証 → ソリューション開発 → 導入）を、十分な粒度でなくとも**ワンストップで**通す、というプロダクト方針を実体化する（ユーザー明言・2026-09-26）。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) に準拠。ISO の節は「ISO56001 §x」と明記（本プロジェクト文書の §x と区別）。関連＝[要件定義 README](../要件定義/README.md)（FR-42／新規 FR-43）・[データモデル](../データモデル.md) §5.14b（チャット中核）／§5.27（activities 元帳）／§5.38〜5.46（コンセプト）・[API設計 README](../API設計/README.md)／[API設計 P](../API設計/P_コンセプト.md)・[SC-61 コンセプト詳細](../画面設計/screens/SC-61_コンセプト詳細.md)・[実装計画](../実装計画.md)。

## 0. 要旨（何を作るか）

- **機能としてはプロジェクト管理だが、MVP は「単純なタスク管理」に絞る**。ISO56001 ④開発・⑤導入を、薄くてもアプリ内で通せる最小形から積む。
- **ルート＝コンセプト**。go 判定済みコンセプトを入力データにして、**コンセプト単位でプロジェクト（＝タスクツリー）を起票**する。
- **階層は WBS 的にブレイクダウン**＝プロジェクト → 要件（アイデア粒度）→ タスク（具体的作業）。器は**単一 `tasks` の自己参照ツリー＋粒度ラベル**（案A・§3.1）。
- タスクには**担当者**が付き、**完了で報酬**（**開発 XP はイノベーション活動の XP と別軸**・コインは共通・§3.2）。
- タスクの起こし方＝**人手 ／ CSV 取込 ／ コンセプトからの種継ぎ**（**生成 AI 連携はしない**・§3.3）。
- **タスク単位の軽量チャット**を持つ＝機会特定からソリューション開発まで、議論・情報が **1 つのチャット中核に一元蓄積**され、束ねれば「仕様の塊」になる（§3.4）。
- 外部 PM サービスとの API 連携は**社内方針**として seam を残す（本格運用は外部へ・アプリ内は最低限・§4）。
- ISO④⑤で必要な入力（導入計画・価値実現の実測）は**プロジェクト側で拾い**、FR-39 の §9 パフォーマンス評価とループを閉じる（§3.5）。

## 1. ISO56001 対応（④⑤を引き受ける）

ISO56001 §8.3 のプロセス「① 機会の特定 → ② コンセプトの創造 → ③ コンセプトの検証 → ④ ソリューションの開発 → ⑤ 導入（価値の実現）」に対し、これまで ideaquest は **①②③（クエスト内）** までを担い、④⑤を将来拡張としていた。本機能で **④⑤（クエスト外・新ドメイン）** を引き受ける。

| ISO56001 工程 | ideaquest の段 | 成果物 |
|---|---|---|
| ① 機会の特定 | クエスト作成 | クエスト |
| ② コンセプトの創造 / ③ 検証 | コンセプト段（クエスト内・FR-42） | 検証済みコンセプト（Go/Pivot/Kill） |
| **④ ソリューションの開発** | **プロジェクト／タスク管理（本機能・クエスト外）** | **プロジェクト（タスクツリー・進捗）** |
| **⑤ 導入・価値の実現** | 同ドメイン＝プロジェクトの**導入・価値実現メタ**（§3.5） | 導入状態・KPI 実測（→ 次サイクルへ） |

> ISO56001 §8.3.5 の出力＝*"plans with established activities, resources, relationships, and timing"*（＝WBS そのもの）。③まで（validated concepts）とは仕事の質が変わる。

### 1.1 スコープ境界と、前段との一貫性

- **本ドメインはクエスト外**＝[コンセプト機能 ISO56001 再設計](コンセプト機能_ISO56001_再設計.md) §1.1 の「④⑤はプロジェクト管理（WBS/タスク）の領域＝別レイヤ」に**忠実**。クエストは検証済み（go）コンセプトを産出したら役目を終え、その成果物を本ドメインが**受け取る**。
- **別パラダイム**＝コンセプト段までは「探索的・協働・合議（ゲーム感）」、本ドメインは「決定論的なデリバリ管理（担当・進捗・完了）」。よって**継承は限定的**にする（§1.2）。
- **1 サービス内 ISO 一連の担保**＝十分な粒度でなくとも、機会特定〜導入までを1つのアプリで通す。本格的な PM は外部連携へ委ねられる（§4）が、アプリ内で最低限は完結できる。

### 1.2 継承するもの／しないもの（線引き）

| | 内容 | 方針 |
|---|---|---|
| **継承する（DRY）** | ゲーム感（XP/コイン機構＝[activities](../データモデル.md) §5.27）・横断 UI（DataTable 一覧＝サーバー委譲）・**チャット中核**（§5.14b・§3.4）・通知・添付・情報リンク（`info_links`）・権限（クエスト/パーティー権限＝FR-27 踏襲） | 機構を再利用（[コーディング規約](../規約/コーディング規約.md) §2.3） |
| **継承しない** | コンセプト/アイデア段の**ループ機構**＝議論ルーム群・投票・評価者評価・Go/Pivot/Kill ゲート | ソリューション段は "検証・合議" でなく "実行"。持ち込まない |

> **タスク単位の軽量チャットは継承する側**（§3.4）。ただし「議論ルーム＋投票＋評価」というループ機構全体ではなく、**チャット中核（thread）だけ**を再利用する点に注意。

## 2. ルート＝コンセプト（起票と受け渡し）

- **起票ゲート**＝`concepts.decision = 'go'`（＝検証を通り投資判断されたコンセプトのみ）。SC-61 コンセプト詳細に「**開発を始める（プロジェクト起票）**」導線を置く。
- **1 コンセプト＝1 プロジェクト**を既定（複数プロジェクト化は将来）。
- **受け渡しデータ**＝コンセプト成果物（狙う価値・対象／解の形態＋必要な能力（粗）／viability／前提と検証）をプロジェクトの初期メタ・要件タスクの種として引き継ぐ（§3.3）。
- これにより FR-39 の「次アクション → 後続クエスト複製」と対をなす、**「go コンセプト → プロジェクト起票」という正式な出口**が繋がる。

## 3. タスク管理の中身

### 3.1 階層（プロジェクト → 要件 → タスク）

「タスク」を全階層に使うと混乱するため、粒度に名前を付ける（呼称は仮）。

| 階層 | ユーザーの言葉 | 呼称 | 中身 |
|---|---|---|---|
| L0 | ルート | **プロジェクト** | コンセプト由来。導入・価値実現メタ、進捗ロールアップ |
| L1 | 「アイデア粒度のタスク」 | **要件／成果物**（≈エピック） | 要件・機能の束。コンセプトの "必要な能力" から派生 |
| L2 | 「具体的な作業」 | **タスク** | 担当が付く作業。完了で開発 XP |

- **器＝単一 `tasks` テーブル＋`parent_task_id` 自己参照ツリー＋`kind` 列**（案A）。任意深さ。
  - **理由**＝MVP「単純なタスク管理」に対し深さ固定の 3 テーブルは過剰。まず**担当付き作業タスクのフラット管理**から始め、後から中間層（要件）を挟める＝段階実装しやすい。CSV 取込や WBS の深さ揺れにも強く、一覧機構（DataTable）も 1 本で済む。
  - `kind`＝`requirement`（要件・L1）／`task`（作業・L2）等の粒度ラベル。深さと `kind` は緩く対応（強制しない）。

### 3.2 担当・ステータス・完了報酬（開発 XP は別軸）

- **担当**＝`assignee_account_id`（MVP は**単一**。複数担当は将来）。担当は由来クエストのパーティー所属者に限る（§7）。
- **ステータス**＝`todo` / `doing` / `done`（＋`blocked` は任意）。
- **完了報酬**＝タスク `done` で **開発 XP ＋ コイン**を付与。冪等は既存流儀を踏襲＝[activities](../データモデル.md) §5.27 に `reason='task_done'`, `ref_type='tasks'`, `ref_id=<task_id>` の存在チェック（二重付与防止）。
- **開発 XP はイノベーション XP と分離**（ユーザー確定）＝**ソリューション段は開発作業・業務であってイノベーション活動ではない**ため、見え方を濁さない。
  - 実装＝`users.delivery_xp`（別軸の累計）を新設し、`activities.kind` に `delivery_xp_gain` を追加（既存 `xp_gain` は `users.xp` を増やすため別 kind にする）。ゲージ/バッジは分離、**レベル式・称号の作り込みは後回し**（まず累計＋簡易バッジ）。
  - **コインは共通**（会社内共通通貨＝魔法/きせかえ購入に使う。分ける実益が薄い）＝`users.coin_balance` をそのまま加算。

### 3.3 タスクの起こし方（人手／CSV／コンセプト種継ぎ・AI なし）

- **人手作成**＝プロジェクト詳細のツリー上で追加。
- **CSV 取込**＝列マッピング（`title` / `parent`（親の識別） / `kind` / `assignee` / `status` / `due_date` 等）で一括起票。
- **コンセプトからの種継ぎ**＝コンセプト成果物の「**解の形態＋必要な能力（粗）**」の各項目を、**要件タスク（L1）の初期候補としてコピー提示**（人手で採否）。
- **生成 AI 連携はしない**（ユーザー明言）＝要件定義から機能数/画面数を自動算出する類はやらない。**将来の seam だけ残す**（種継ぎ関数を差し替え可能に）。

### 3.4 タスク単位チャット（チャット中核の再利用＝情報の一元蓄積）

- **各タスクに軽量チャットを持たせる**（ユーザー確定）。狙い＝**機会特定（アイデア）→ コンセプト → タスクまで、議論・情報が 1 か所に蓄積**され、それを束ねれば「仕様の塊」になる。情報が一元化されていると再利用しやすい（ユーザー着想・2026-09-26）。
- **実装＝チャット中核（thread）だけを再利用**（議論ルーム群・投票・評価は持ち込まない・§1.2）。現行ブランチで進行中の**ホスト非依存チャット**（[データモデル](../データモデル.md) §5.14b＝`chat_thread(owner_type, owner_id)`・中核はホスト無依存）に、**タスクをホストとして 1 ケース足すだけ**：
  1. `chat_thread.owner_type` の CHECK に `task` を追加。
  2. タスク作成時に `chat_repo.ensure_chat_thread(ts, "task", <task_id>)` を呼ぶ（owner_id ＝タスク PK。タスクは自身がホスト＝別リンク表不要）。
  3. 門番＝`chat/application._resolve_host` に `task` 分岐を 1 つ追加（由来クエストのパーティー権限で解決）。
  - **チャット中核（repository/CRUD/reaction/pin/mention/quote/attachment）と DB migration は無改修**。frontend は共有 `IdeaChatView` を `taskSource` で駆動＝同一 UI/機能。
- **「束ねて仕様に」は将来の読み出し機能**＝統一されたチャット中核（thread 単位）のため、プロジェクト配下の全 thread を横断集約する読み出しは後から素直に足せる（MVP は各タスクで会話できるところまで）。

### 3.5 ISO⑤ 導入・価値実現メタ（KPI ループを閉じる）

- ④開発・⑤導入で必要な入力は**プロジェクト（ルート）側で拾う**（ユーザー確定）。プロジェクトに**導入・価値実現メタ**を軽く持たせる＝導入計画メモ／ローンチ状態／**KPI 実測**（jsonb・自由記述＋状態から）。
- **なぜ**＝コンセプト段で立てた viability（コスト/収益モデル/ROI）や前提が、**導入後に実測で検証される**。これは [FR-39 設計意図](FR-39_ISO56001との関係と設計意図.md) の ISO56001 §9（パフォーマンス評価）・§10（改善）と**ループを閉じる**（実測 → 学び → 次サイクル）。MVP は最小（記述＋状態）で、固定 KPI・実測連携は将来。

### 3.6 将来拡張の器（依存関係・工数見積）

MVP では使わないが、**あとで作り直さないよう、データ構造だけは拡張を織り込む**（ユーザー要望）。

- **工数見積**＝`tasks` に `estimate_value`（数値）／`estimate_unit`（時間/人日等）を **nullable で予約**（MVP 未使用）。実績側 `actual_*` も同様に予約可。
- **期日/日程**＝MVP は `due_date` のみ運用。`planned_start` / `planned_end` / `actual_start` / `actual_end` は nullable で予約（ガント/WBS 化の布石）。
- **依存関係**＝`task_dependencies(task_id, depends_on_task_id, dep_type)` を**テーブルとして定義しておくが MVP は未配線**（Phase2 で有効化）。`dep_type` は `finish_to_start` 等の列挙余地。
- これらは列/表を先に用意するだけで、UI・ロジックは MVP に載せない（過剰実装を避ける）。

## 4. 外部 PM 連携（seam）

- **社内方針**＝外部プロジェクト管理サービスへデータを渡して本格運用する。本機能は**アプリ内で最低限、本格は外部**の二段構え。
- **MVP＝エクスポート（CSV／API push）を seam として設計に残す**＝プロジェクト/タスクを外部へ渡す一方向。双方向同期・Webhook 取り込みは将来。
- **連携メタ**＝プロジェクト/タスクに `external_link`（`provider` / `external_id` / `url`）を持たせ、外部側 ID との対応を保持（重複起票・往復の布石）。

## 5. データモデル第一版（スケッチ）

> 正本反映は本ドラフト合意後に [データモデル](../データモデル.md) へ。列名・enum は第一版の仮。

- **`projects`**（ルート・コンセプト単位）
  - `id` / 会社スコープ / `concept_id`（FK→concepts・NOT NULL＝由来）/ `quest_id`（由来クエスト・権限/検索用に冗長保持）/ `title` / `description` / `status`（planning/in_progress/on_hold/done）/ **`deployment`（jsonb＝導入計画・ローンチ状態・KPI 実測・§3.5）** / `owner_account_id` / `external_link`（provider/external_id/url・§4）/ 監査列。
- **`tasks`**（自己参照ツリー・§3.1）
  - `id` / `project_id`（FK）/ `parent_task_id`（FK self・nullable＝ツリー）/ `kind`（requirement/task…）/ `title` / `description` / `assignee_account_id`（nullable・単一）/ `status`（todo/doing/done/blocked）/ `sort_order`（兄弟順）/ `due_date` / `done_at`。
  - **将来拡張の器（nullable・MVP 未使用）**＝`estimate_value` / `estimate_unit` / `planned_start` / `planned_end` / `actual_start` / `actual_end`（§3.6）。
- **`task_dependencies`**（§3.6・**定義のみ・MVP 未配線**）＝`id` / `task_id`（FK）/ `depends_on_task_id`（FK）/ `dep_type`。
- **チャット**＝新テーブルなし。[chat_thread](../データモデル.md) §5.14b に `owner_type='task'` を足すだけ（§3.4）。owner_id＝`tasks.id`。
- **XP/コイン**＝`users.delivery_xp` 追加（別軸）／`activities.kind` に `delivery_xp_gain` 追加（`reason='task_done'`, `ref_type='tasks'`・§3.2）。コインは `users.coin_balance` 共通。
- **情報リンク**（任意）＝`info_links.target_type` に `projects`/`tasks` を足せば、情報インプットをタスクに紐付け可能（§1.2・後日判断）。

## 6. 画面（骨子）

> 番号は仮（コンセプト SC-60〜62 の次＝SC-70 番台を提案）。モック先行 → 接続の[フロントエンド実装フロー規約](../規約/フロントエンド実装フロー規約.md)に従う。

- **SC-70 プロジェクト一覧**（DataTable・サーバー委譲）＝由来コンセプト/クエスト・状態・進捗・担当で絞込。
- **SC-71 プロジェクト詳細**＝**WBS ツリー**（要件 → タスク・担当/状態/進捗ロールアップ）＋**導入・価値実現メタ**（§3.5）。
- **SC-72 タスク登録/編集モーダル**（担当・状態・期日・kind・親）＋**CSV 取込ダイアログ**。
- **タスク詳細（またはドロワ）**＝軽量チャット（共有 `IdeaChatView` / `taskSource`・§3.4）。
- **導線**＝SC-61 コンセプト詳細に「開発を始める（プロジェクト起票）」＋起票済みなら「プロジェクトへ」。
- **配置**＝ルートがコンセプトなのでコンセプト詳細から入る＋**グローバル「プロジェクト」領域**（クエストタブには混ぜない＝別パラダイム）。

## 7. 権限

- **由来クエストのパーティー権限（FR-27）を踏襲**＝プロジェクトは由来コンセプト→由来クエストのパーティーに属する。閲覧/操作は当該パーティー所属を門番に。
- **担当割当**＝当該パーティー所属者のみ。プロジェクト owner＝コンセプト owner／クエスト owner 相当（詳細は実装時）。
- チャット門番＝`chat/application._resolve_host` の `task` 分岐で由来クエスト権限に委譲（§3.4）。

## 8. 起票メタ

- **要件**＝[要件定義 README](../要件定義/README.md) に **FR-43「ソリューション開発（プロジェクト／タスク管理）」**として起票（FR-42 コンセプトの次）。優先度は実装計画で判断。
- **API ドメイン**＝**Q**（P＝コンセプトの次・要確認）＝`doc/API設計/Q_ソリューション開発.md`（プロジェクト CRUD／タスク CRUD・ツリー／CSV 取込／完了報酬付与は G ドメイン委譲／チャットは既存チャット EP を thread 単位で流用）。
- **呼称**＝機能名「ソリューション開発」・データ用語は「プロジェクト／タスク」（ユーザー語彙）。

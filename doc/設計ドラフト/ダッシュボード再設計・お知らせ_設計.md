## 1. 目的・背景

- **課題**：SC-01 のパネルが約13枚に増え、種類の違うもの（要対応／キャッチアップ／マイ／発見／ステータス）が平板に積まれて縦長。ここに新規パネルを素朴に足すと破綻する。
- **追加したいもの（ユーザー要望 2026-10-04）**：
  1. 運営からのお知らせ（全社告知・リッチテキスト）
  2. アイデアコンテストの告知・募集（参加できるコンテストへの応募動線）
  3. おすすめの参加可能クエスト
  4. 参加しているアイデアコンテストへの動線／コンテストのアイデアへの投票／応募中コンテストの参加動線
- **方針**：「足しながら減らす」＝**情報設計（ゾーン化）**＋**自分のクエストを一覧へ移設**＋**フォロー駆動**でマイ領域を圧縮。

## 4. 新規「お知らせ」機能（運営告知・リッチテキスト・**FR-49**）

### 4.1 概要
- **管理者（`company_account_admin`/`system_admin`）が全社向けお知らせを投稿**し、全ユーザーのダッシュボード（ゾーンD）＋専用一覧で読む。
- 本文は**リッチテキスト**（見出し/強調/リンク/箇条書き/画像程度）。
- 採番＝**FR-49**（要件）／**SC-95 お知らせ（閲覧一覧/詳細・全社）**・**SC-96 お知らせ管理（作成/編集・管理者）**／ダッシュボードパネルは SC-01 内。

### 4.2 リッチテキストは情報インプットの資産を流用（決定）
- **backend サニタイズ＝`info/derive.py::sanitize_html`（nh3・許可リスト）/`to_plain_text` を流用**。info 固有ではないので、**中立モジュール（例 `app/core/richtext.py`）へ抽出**して info・お知らせ双方から使う（DRY・§2.3）。
- **frontend エディタ/表示＝`.rt__area`（contentEditable＋onPaste＋`attachGrowableResize`）/`.rt-view`（`dangerouslySetInnerHTML`・nh3 済みで安全）を共有UI部品（`RichTextEditor`/`RichTextView`）へ抽出**し、info・お知らせで共用。CSS（`.rt__*`）は info-input.css から共有 CSS へ移す。
- **新規ライブラリ不要**。XSS は保存時 nh3 サニタイズで無害化（既存方針 §N.7 と同一）。
- **本文画像の再ホスト（対応済・2026-10-07）**＝共有 `RichTextEditor` は任意の `uploadImage` 注入を受け、渡された時だけ「🖼 画像」挿入＋paste/ドロップで再ホストする（未指定なら従来どおり画像無し）。お知らせは `POST /admin/announcements/images`（U-8・管理者のみ・情報インプット N.2 の再ホストと同パターン＝`validate_image_upload`→MinIO put→署名URL）を渡す。`sanitize_html` の許可スキームは http/https のみ＝`data:` 画像は保存時に落ちるため、自社ホスト署名URL へ置換してから保存する。

### 4.3 データモデル（会社DB・新規 `announcements`）＝決定 2026-10-04
- `announcements`＝`id` / `title` / `body_html`（サニタイズ済）/ `body_text`（派生・検索用）/ `status`（draft|published|archived）/ **`pinned`(bool・採用)** / `published_at` / **`starts_at`/`ends_at`（掲載期間・採用）** / `created_by_id` / 共通監査列。
- **`announcement_reads(announcement_id, user_id, read_at)`＝既読管理（採用）**。未読バッジ/「未読のみ」表示に使う。
- 表示対象＝`status=published` かつ 掲載期間内（`starts_at<=now<ends_at` または未設定）。並び＝`pinned` 優先→`published_at` 降順。

#### 4.3a ダッシュボード お知らせパネルの選別・並び（決定 2026-10-04・最大3件）
1. **ピン留めを最優先**（`published_at` の新しい順）。**ピンが3件超なら公開日時の新しい3件**。
2. 枠が余れば **未読**（`published_at` の新しい順）で埋める。
3. **既読かつ非ピンは出さない** ＝ ピン留め無し＆全て既読なら **0件（パネル非表示）**。
- ※ 一覧(SC-95)は全件（published・期間内）を `pinned`→`published_at` 降順で表示（既読も出す）。上記3件ルールはダッシュボードパネル限定。
### 4.4 API（新規ドメイン・FR-49）
- `GET /announcements`（全ユーザー read・published・掲載期間内・pinned 優先・カーソル・`unread` 絞り／未読数同梱）
- `GET /announcements/{id}`（詳細）／`POST /announcements/{id}/read`（既読化）
- 管理：`POST/PATCH/DELETE /announcements`（管理者のみ・body_html はサーバーで `sanitize_html`）
- ダッシュボードは `GET /dashboard` に最新N件＋未読数を同梱（I.3 の合成方針）。

### 4.5 画面
- **ダッシュボード パネル（ゾーンD・SC-01）＝表示のみ**。pinned を上位・`📌` バッジ＋未読バッジで表示。**ここにピン操作は置かない**（一般ユーザーは閲覧のみ）。
- **お知らせ一覧/詳細（SC-95・全社閲覧）**＝全文閲覧。pinned を上位表示（操作なし）。
- **お知らせ管理（SC-96・管理者）＝ピン留めの操作はここ**。
  - **ピン留め操作UI（2点・既存標準を流用）**＝
    1. **一覧（DataTable）の行 RowMenu（⋮）に「📌 ピン留めする／📌 ピン留めを解除」**（トグル・即時反映・デザイン標準 §4.5／クエスト等の RowMenu と同型）。一覧行にはピン中を示す `📌` 表示。
    2. **作成/編集モーダルに「📌 ピン留め」チェックボックス**（§4.7 の入力検証標準・style-guide の `.checkbox`）。
  - あわせて 下書き/公開（status）・掲載期間（starts_at/ends_at）・リッチテキスト本文（流用部品）を同モーダルで編集。
  - ※新規UIは作らず、一覧＝RowMenu、編集＝モーダル＋チェックボックスの既存パターンを踏襲。

### 4.6 権限・決定（2026-10-04）
- 投稿/編集/削除＝管理者のみ。閲覧＝全ユーザー。
- **既読管理＝要**（`announcement_reads`・未読バッジ）。
- **掲載期間＝有**（`starts_at`/`ends_at`・期限切れ自動非表示）。
- **ピン留め＝有**（`pinned`・上部固定）。
- **通知連携＝不要**（お知らせ投稿で H 通知は飛ばさない＝お知らせパネル/一覧で読む）。
- **公開会社での閲覧＝可**（Step3 の外周403許可リストに**お知らせ read を含める**＝`role=general` でも閲覧可。管理EPは管理者のみ）。
- 対象絞り（全社 or 部署）＝当面**全社**（部署絞りは将来拡張）。

| 参加中コンテストへの動線 | ゾーンE「参加中」に「参加中のアイデアコンテスト」（contests一覧 my_status=approved） |
| コンテストの告知・募集／応募動線 | ゾーンD（contests一覧 status=open・my_status=none → 応募ダイアログ＝既存 SC-53 の導線を流用） |

- **参加は常に明示（決定 2026-10-04）**＝`auto_approve=true`（誰でも参加可）でも**「参加する」ボタンを押して初めて参加状態**（押下で即 approved・現状どおり）。閲覧できることと参加状態は別。ダッシュボードの議論/投票統合は**参加状態のコンテストのみ**を対象にする（＝「見られるが参加していない」コンテストのアイデアは混ぜない）。

## 8a. おすすめクエスト選出アルゴリズム（Phase3・2026-10-08 確定）

> Zone D「おすすめのクエスト」（最大3件）に出す候補の選び方。ダッシュボードのゾーン再編（Phase1）とは独立に backend 単体で実装・検証する（ゾーンは後からこの EP を叩くだけ）。EP＝`GET /quests/recommended?limit=3`（読取・行DTOは発見カタログ SC-13 のカードを踏襲）。

**候補母集団（「参加可」＝ハードフィルタ）**＝発見門番 `can_discover_quest` を満たす（`discoverable=true` ∧ `status ∈ {recruiting, in_progress, evaluating}` ∧ グループ可視性 ∧ コンテスト backing でない）**かつ** 閲覧者が**未参加**（member でない）**かつ** 参加申請 `pending` でない（＝「これから参加できる」ものに限る）。

**スコア（各成分 0..1 正規化の加重和・上位 `limit` 件）**：

```
score(q) = w_align·align(q) + w_active·active(q) + w_admin·admin(q)
```

| 成分 | 定義 | 実装 |
|---|---|---|
| `align(q)` | 経営資料整合率（0..1） | 既存 `strategy.repository.quest_match_by_doc`（公開アイデア×適用資料の `idea_alignment` キャッシュ）を**適用資料横断で平均**。資料0件/アイデア0件→0 |
| `active(q)` | 直近活発度（0..1） | **直近30日**の〔公開アイデア追加＋チャット投稿＋新規参加/申請〕件数を、**候補母集団内の最大値**で相対正規化（母集団が全0なら全て0） |
| `admin(q)` | 管理者お勧め | `quests.recommended`（新 bool 列）が true→1.0・else 0。**加重和ブースト**（乗算でない＝整合率ゼロの無関係クエストを押し上げない） |

- 既定重み（`core/config.py`・env 可変）＝`recommend_weight_align=0.45` / `recommend_weight_active=0.35` / `recommend_weight_admin=0.20`、活動窓＝`recommend_active_window_days=30`。
- **「×（掛け）」の解釈**＝ユーザー原案「参加可 × 整合率 × 活発 × お勧め」のうち**「参加可」のみ掛け算的ハードフィルタ**、残り3成分は**足し合わせ**（文字通り乗算すると admin=0 の大多数が score=0 になり破綻するため）。
- tie-break＝`score` 降順 → `updated_at` 降順 → `id`。母集団0件→空配列（Zone D は空状態メッセージ・§3 空状態の扱い）。
- **グレースフル**＝整合率/活動の集計が欠けても評価を止めず 0 成分で続行（おすすめは補助機能）。
- **管理者お勧めの設定 UI/EP は follow-up**（本 Phase はスコアリングの読取まで。`recommended` の toggle は管理者（`company_account_admin`）向けに別途）。

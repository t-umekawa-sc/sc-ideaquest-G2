# ダッシュボード再設計 ＋ お知らせ機能 — 設計ドラフト（SC-01 情報設計の見直し／運営告知・発見動線の追加）

> 状態: **ドラフト（2026-10-04 起票・ユーザーと方向合意途中）**。SC-01 ダッシュボードのパネル過多（約13枚）を**情報設計（ゾーン化＋集約）で整理**しつつ、**運営からのお知らせ（リッチテキスト）**・**アイデアコンテストの告知/募集**・**おすすめの参加可能クエスト**・**コンテスト動線（議論/投票/参加中）**を追加する。足しながら総量を抑えるのが主眼。

## 1. 目的・背景

- **課題**：SC-01 のパネルが約13枚に増え、種類の違うもの（要対応／キャッチアップ／マイ／発見／ステータス）が平板に積まれて縦長。ここに新規パネルを素朴に足すと破綻する。
- **追加したいもの（ユーザー要望 2026-10-04）**：
  1. 運営からのお知らせ（全社告知・リッチテキスト）
  2. アイデアコンテストの告知・募集（参加できるコンテストへの応募動線）
  3. おすすめの参加可能クエスト
  4. 参加しているアイデアコンテストへの動線／コンテストのアイデアへの投票／応募中コンテストの参加動線
- **方針**：「足しながら減らす」＝**情報設計（ゾーン化）**＋**自分のクエストを一覧へ移設**＋**フォロー駆動**でマイ領域を圧縮。

## 3. 情報設計（案）＝5ゾーン

縦に平積みをやめ、意味でゾーン化する。各ゾーンは「1見出し＋その中にコンパクトなリスト/タブ」で、**フルカードの枚数を増やさない**。

| ゾーン | 目的 | 中身 |
|---|---|---|
| **A 最上段** | 自分の状態 | greeting＋ステータス(hero)＋週間ランキング（現状維持） |
| **B あなたの番（要対応）** | 自分が処理すべきこと | 未投票（**クエスト＋コンテスト統合**）／承認待ちリクエスト（クエスト・コンテストを同ゾーンに併置）／下書き |
| **C キャッチアップ** | 動き・会話の把握 | 新着＋最近の議論（**コンテストも含める**）／チームアクティビティ／最近の通知 |
| **D 見つける（新設）** | 参加機会・告知 | **運営からのお知らせ**／**アイデアコンテストの告知・募集**（応募動線）／**おすすめの参加可能クエスト** |
| **E マイ** | よく行く先 | 参加中クエスト＋**参加中コンテスト**（フォロー駆動）。**自分のクエストは一覧(SC-10)へ移設** |

> レイアウトの具体（2段組/タブ/「もっと見る」）はモック（`style-guide.html`／SC-01 モック）で詰める。本ドラフトは情報設計まで。

## 4. 新規「お知らせ」機能（運営告知・リッチテキスト・新規 FR）

### 4.1 概要
- **管理者（`company_account_admin`/`system_admin`）が全社向けお知らせを投稿**し、全ユーザーのダッシュボード（ゾーンD）＋専用一覧で読む。
- 本文は**リッチテキスト**（見出し/強調/リンク/箇条書き/画像程度）。

### 4.2 リッチテキストは情報インプットの資産を流用（決定）
- **backend サニタイズ＝`info/derive.py::sanitize_html`（nh3・許可リスト）/`to_plain_text` を流用**。info 固有ではないので、**中立モジュール（例 `app/core/richtext.py`）へ抽出**して info・お知らせ双方から使う（DRY・§2.3）。
- **frontend エディタ/表示＝`.rt__area`（contentEditable＋onPaste＋`attachGrowableResize`）/`.rt-view`（`dangerouslySetInnerHTML`・nh3 済みで安全）を共有UI部品（`RichTextEditor`/`RichTextView`）へ抽出**し、info・お知らせで共用。CSS（`.rt__*`）は info-input.css から共有 CSS へ移す。
- **新規ライブラリ不要**。XSS は保存時 nh3 サニタイズで無害化（既存方針 §N.7 と同一）。

### 4.3 データモデル（会社DB・新規 `announcements`）
- `id` / `title` / `body_html`（サニタイズ済）/ `body_text`（派生・検索用）/ `status`（draft|published|archived）/ `pinned`(bool) / `published_at` / `starts_at`?/`ends_at`?（掲載期間・任意）/ `created_by_id` / 共通監査列。
- 既読管理（任意・論点）＝`announcement_reads(announcement_id,user_id,read_at)` を持つか、通知で代替するか（§4.6 論点）。

### 4.4 API（新規ドメイン・仮 S? / 命名は採番時に確定）
- `GET /announcements`（全ユーザー read・published・掲載期間内・pinned 優先・カーソル）
- `GET /announcements/{id}`（詳細）
- 管理：`POST/PATCH/DELETE /announcements`（管理者のみ・body_html はサーバーで sanitize_html）
- ダッシュボードは `GET /dashboard` に最新N件を同梱 or 専用EPをフロントから直読み（I.3 の合成方針に合わせる）。

### 4.5 画面
- **ダッシュボード パネル**（ゾーンD）＝最新N件（pinned 優先）＋「すべて見る」。
- **お知らせ一覧/詳細**（SC-xx 新規）＝全文閲覧。
- **管理（作成/編集）**＝管理メニュー配下（SC-9x 系）。リッチテキストエディタ（流用部品）＋下書き/公開/ピン留め。

### 4.6 権限・論点
- 投稿/編集/削除＝管理者のみ。閲覧＝全ユーザー（公開会社の外周403の許可リストに含めるか＝Step3 と整合要確認）。
- **論点**：既読管理の要否／掲載期間（期限切れ自動非表示）／ピン留め／対象絞り（全社 or 部署）／通知連携（お知らせ投稿で通知も飛ばすか）。

## 5. コンテスト統合（既存データの組み替え・新規backend最小）

| 項目 | 変更 |
|---|---|
| 新着/最近の議論にコンテストを含める | `_unread_chats`/`_recent_chats` のスコープを「quest_member ∪ **コンテスト参加(approved)の backing quest**」に拡張（`ideas_with_unread` の quest_ids に contest backing を足す） |
| コンテストのアイデアへ投票（未投票統合） | `_unvoted` の母集合に**参加中コンテストの backing quest のアイデア**を足す |
| 参加中コンテストへの動線 | ゾーンE に「参加中のアイデアコンテスト」（contests一覧 my_status=approved） |
| コンテストの告知・募集／応募動線 | ゾーンD（contests一覧 status=open・my_status=none → 応募ダイアログ＝既存 SC-53 の導線を流用） |

## 6. 自分のクエスト → 一覧移設／フォロー駆動（ユーザー提案の採用）

- **自分のクエスト（owner）パネルはダッシュボードから撤去**し、**クエスト一覧(SC-10)に「自分が作成」スイッチ/絞り込み**を追加（owner 絞り）。
- **参加中クエストはダッシュボードに残す**（よく行く）。
- **フォロー（既存機能）をマイ領域の軸に**＝ダッシュボードのクエストは「参加中＋フォロー中」を中心に。フォロー中クエスト/コンテストを1ゾーンに集約。

## 7. Phase 分け（実装順）

- **Phase 1（既存データの組み替え・低コスト）**：ゾーン再編／コンテスト統合（議論・未投票・参加中・告知募集・おすすめ）／自分のクエスト→一覧移設＋スイッチ。新規backendほぼ不要（dashboard application のスコープ拡張＋contests/catalog の既存read利用）。
- **Phase 2（お知らせ機能・新規＋リッチテキスト流用）**：richtext 共有部品の抽出 → announcements ドメイン（モデル/API/管理画面/ダッシュボードパネル）。
- **Phase 3（精緻化・任意）**：おすすめのスコアリング、お知らせ既読/掲載期間、レイアウトのモック確定。

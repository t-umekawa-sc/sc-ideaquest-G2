# 経営資料整合・自動関連付け — 設計ドラフト（経営方針との整合 × 情報の機会/脅威 × 自動リンク）

> 状態: **ドラフト（2026-09-28 起票・同日に §11 の6論点をユーザー合意）**。社内要望（経営側の中長期計画/方針資料を基準に、アイデアの「整合率」〔高いとコイン〕・情報の「影響率/機会率/脅威率」を出す＋経営資料から ISO56001 の意図/戦略/方針を生成）への設計案。方式（決定的キーワード=Phase1／LLM=Phase2）と Phase 切りは合意済み。**次段＝Phase 1 を各正本（データモデル/API設計/画面設計/テスト）へ落とし込む**。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) 準拠。ISO 56001 の節は「ISO56001 §x」。
> 関連正本＝[情報インプット機能 設計](情報インプット機能_設計.md)（本書が土台にする知識レイヤ・N.6 類似度/ワードクラウド）・[コンセプト機能 ISO56001 再設計](コンセプト機能_ISO56001_再設計.md) §4（動的リンク）・[データモデル](../データモデル.md)（§5.36 `info_tokens`）・[API設計 G](../API設計/G_ゲーミフィケーション.md)（コイン台帳）・[コーディング規約](../規約/コーディング規約.md) §2（セキュリティ）・[WEBアプリ開発時のセキュリティ対策一覧](../WEBアプリ開発時のセキュリティ対策一覧.md)。

## 0. 位置づけ・狙い

- 経営の**中長期計画/方針資料**（＝会社の意思の基準）をアプリに取り込み、**現場のアイデア/情報がどれだけ経営方針に沿っているか**を可視化する。ISO56001 では **§4 組織の状況／§5.2 イノベーション方針／§6 計画（意図・戦略・方針）**にあたる上流を、下流（機会特定→アイデア→コンセプト）とつなぐ。
- 2つの独立した要望に分解する:
  - **(A) 整合・スコアリング**＝アイデアの「経営方針との整合率」（高いとコイン）／情報の「影響率・機会率・脅威率」。
  - **(B) 生成**＝経営資料をベースに ISO56001 の意図/戦略/方針の**たたき台を生成**。
- **設計判断の芯**＝「率」は本質的にあいまい。**決定的（キーワード/ワードクラウド）で出せる範囲**と、**意味理解が要る範囲（生成AI必須）**を切り分け、後者は**データ主権とコストを外に出す**（アプリは"AIに渡す材料"を整えるに留める）方針を推奨する。

## 1. 現状の地固め（実装事実・2026-09-28 コード確認）

- **トークン/ワードクラウド**＝**情報インプット（`info_tokens`）だけ**に存在（janome で名詞/動詞/形容詞を抽出・頻度集計・`GET /info-items/word-cloud`）。**クエスト/アイデア/コンセプト/前提は未トークン化**。
- **自動関連付け（類似度 auto-link）**＝FR-41③・[情報インプット機能 設計](情報インプット機能_設計.md) N.6 で「保存時に TF-IDF で自動 `info_link`（既定=関連・閾値+上位N・通知なし）」と**確定仕様だが未実装**（info ドメインに類似度計算は無く、`origin=auto` は続報のリンク複製のみ）。手動リンク/棄却/続報複製は実装済み。→ **本要望の土台（トークン基盤）と重なる**ため、本書で一緒に仕上げる。
- **情報の影響分類**＝`info_items.impact_class`（`opportunity`/`threat`/`other`）は **curator が手入力**する既存項目（トリアージ）。**機会/脅威は既に人手で判定済みのデータがある**。
- **経営資料エンティティ**＝**存在しない**（情報インプットは手動貼付の外部情報であり、経営の基準文書とは別物）。

## 2. スコープ方針（Phase 切り）

| | Phase 1（決定的・オフライン・生成AI不要） | Phase 2（生成AI・opt-in・データ保護ゲート） |
| --- | --- | --- |
| 経営資料 | アップロード/貼付＋トークン化（基準文書エンティティ） | 同左 |
| アイデア整合率 | **ワードクラウド重なり率**（Jaccard/TF-IDF cosine）→ % ／閾値でコイン | LLM で意味的整合スコア＋根拠文 |
| 情報の機会/脅威率 | **curator 手入力 `impact_class` の集計**（＋整合〔関連〕度はキーワードで補助） | LLM で per-info の機会/脅威を自動判定 |
| 自動関連付け | **TF-IDF auto-link を実装**（未実装分の仕上げ・N.6） | 埋め込み（意味類似）・矛盾自動検出 |
| ISO 意図/戦略/方針の生成 | **「AIに渡す用の構造化 Markdown エクスポート」**（生成は外部） | in-app 生成＝**オンプレの無料 LLM を既定**・**クラウド生成AIは有料オプション**（プロバイダ差し替え式・§8） |

**推奨＝Phase 1 から**。理由＝(1) 決定的で説明可能・オフライン・追加コストゼロ、(2) 「率」の粗さはゲーミフィケーション/補助表示なら許容、(3) 機微な経営資料を外部送信しない、(4) トークン基盤は自動関連付け（既定義の未実装機能）と共有で二度手間にならない。

## 3. データモデル案（Phase 1）

### 3.1 経営資料（strategy_documents・新規・会社DB・管理者のみ）

会社の基準文書（中長期計画/方針/戦略）。管理者（会社アカウント管理者 or 既存 `info_curator` 相当）のみ登録・編集。**入力画面は ISO56001 の用語・構造に合わせた項目立て**にする（2026-09-28 合意・点3）＝自由記述の丸ごと貼付だけでなく、ISO56001 §5.2 イノベーション方針／§6 計画 の要素に対応した**構造化フィールド**を持つ。これにより (1) 整合率の"どの方針に効いたか"の説明が ISO 用語で返せる、(2) 生成機能（§8）の出力先が同じ構造で対称になる。

| 物理名 | 論理名（ISO56001 対応） | 型 | 制約/既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `title` | タイトル | text | NOT NULL | 例「2027-2029 中期経営計画」 |
| `doc_kind` | 種別 | text | NOT NULL | `midterm_plan`/`policy`/`strategy`/`other`（論理 enum・varchar） |
| `intent` | イノベーションの意図・ビジョン（§4 組織の状況／§5.1） | text | NULL可 | なぜ・どこを目指すか |
| `policy_commitment` | イノベーション方針・コミットメント（§5.2） | text | NULL可 | トップの方針・約束（"コミットメントの方針入力"＝点3） |
| `strategy` | 戦略・方向性（§6.1 機会への取組み） | text | NULL可 | 重点の攻め筋 |
| `focus_areas` | 重点領域 | text[] | NULL可 | タグ的な重点テーマ（絞り込み・整合の軸） |
| `objectives` | イノベーション目標（§6.2） | text | NULL可 | 目標・KPI 方針（測定可能な狙い） |
| `body_md` | 補足・全文（Markdown/平文） | text | NULL可 | 上記に載らない全文貼付。トークン/整合率の追加素材 |
| `body_text` | 平文派生 | text | NULL可 | 上記テキスト項目を連結した平文（トークン化/検索用・`info_items.body_text` と同型） |
| `period_from`/`period_to` | 対象期間 | date | NULL可 | 中長期計画の期間 |
| `status` | 状態 | text | NOT NULL, default `active` | `active`/`archived`（改定で旧版アーカイブ） |
| `created_by_id` | 登録者 | uuid | FK→users | 管理者 |
| `created_at`/`updated_at` | 監査 | timestamptz | NOT NULL | |

- **トークン化は構造化フィールド＋`body_md` を連結した `body_text` を対象**にする（意図/方針/戦略/重点領域/目標がキーワードに効く）。整合率の"効いた方針"提示は、どの ISO セクションの語が重なったかで説明できる。
- 入力画面は **ISO56001 の項目立て**（意図・方針/コミットメント・戦略・重点領域・目標・期間）＝各項目に短いガイダンス（[デザイン標準](../画面設計/デザイン標準.md) §4.13 の `.screen-purpose`／ⓘ）を付す。
- アップロードは MVP で**テキスト/Markdown 貼付**を第一とする（PDF/Docx 抽出は seam・Phase 後段。SSRF/外部取得はしない＝情報インプットと同じ手動主義）。
- 版管理は当面「改定＝新規 active＋旧 archived」の簡易運用（[変更履歴標準](変更履歴標準.md) 準拠は後段判断）。

### 3.2 トークンの一般化（entity_tokens・`info_tokens` を横展開）

整合率・自動リンクの土台として、**アイデア/コンセプト/経営資料**をトークン化する。既存 `info_tokens`（§5.36）を踏襲し、**ポリモーフィックなトークン表**に一般化するか、エンティティ別トークン表を作るかは実装時に判断（DRY 観点ではポリモーフィック `entity_tokens(owner_type, owner_id, token, weight, count)` を推奨・`info_tokens` は移行 or 併存）。

- 抽出＝既存 `derive.extract_tokens`（janome・内容語・ストップワード）を再利用（外部送信ゼロ・決定的）。
- 生成契機＝各エンティティの保存時に同期（情報と同型）。テキスト量が少ないアイデアでも決定的に生成できる。

### 3.3 整合スコアの保存

- **アイデア整合率**＝`idea_alignment(idea_id, strategy_document_id, score, computed_at)`（事前計算・`info_links.score` と同思想＝都度計算しない）。複数の経営資料がある場合は**最大 or 加重**（実装時に確定）。
- **情報の率**＝Phase 1 は**集計値（都度算出でも可）**＝経営資料テーマに関連する情報集合に対する `impact_class` 別割合。専用テーブルは持たず read で集計（I ダッシュボード同方針）。

## 4. スコア算出方式（Phase 1・決定的）

### 4.1 整合率（アイデア↔経営資料）

- **重なり率**＝アイデアのトークン集合と経営資料のトークン集合の **TF-IDF 重み付き cosine**（or 単純 Jaccard を MVP）。0–100% に正規化。
- 表示は「**方針との関連度（キーワードベース）**」と**正直にラベル**（厳密な意味的整合ではない旨を明示・過信防止）。
- 複数経営資料時＝各資料とのスコアのうち最大＋「どの方針に効いているか」を上位トークンで提示（説明可能性）。

### 4.2 情報の影響率/機会率/脅威率

- **機会率/脅威率は キーワード重なりでは判定不可**（重なりは"関連度"であって機会/脅威の別を含まない）。→ **`impact_class` の手入力を正**とし、次で集計:
  - 母集団＝経営資料と**関連度が閾値以上**の情報（＝キーワードで"効いている"情報）。
  - **影響率**＝母集団サイズ / 全 curated 情報（どれだけ方針に触れる情報が入っているか）。
  - **機会率**＝母集団のうち `impact_class='opportunity'` の割合。**脅威率**＝`threat` の割合。
- これは「関連度＝キーワード（決定的）／機会・脅威＝人手（既存トリアージ）」の**役割分担**で、ユーザーの「管理者に入力してもらうのが良い」に一致。

## 5. ゲーミフィケーション（整合率→コイン）

- アイデア公開（or 版更新）時に整合率を計算し、**閾値超えでコイン付与**＝既存 G 台帳（`ledger.grant(kind=COIN_GAIN, reason='idea_alignment', ref_type='ideas', ref_id=idea_id)`）で**冪等付与**（`exists_ref` で二重防止＝コンセプト投票 XP と同型）。
- 段階（例＝80%↑で+N コイン・段階制）や再計算での増減は実装時に確定（**下げない/初回のみ**を推奨＝稼ぎ直し防止・アイデア投票 XP と同思想）。
- 表示＝SC-22 に「方針整合バッジ（関連度 %＋獲得コイン）」。**率が粗いことを踏まえ、コインは"方針を意識した加点"程度の軽い設計**にする（順位を厳密に決める指標にしない）。

## 6. 自動関連付け（TF-IDF auto-link・N.6 の未実装分を仕上げ）

- 情報保存/成果物保存時に、**トークン重なりで上位 N・閾値以上**の相手へ `info_links(origin=auto, kind=related, score)` を **upsert**（既存 `rejected_at` は尊重＝復活しない・通知なし）。設計は既に N.6 で確定済み＝**実装のみ**。
- 本要望のトークン基盤（§3.2）と**同じ土台**なので、整合率と一緒に作ると効率的。
- コンセプト/前提もトークン化するので、`search_link_candidates`（手動ピッカー・実装済）に加え**自動候補**も出せる。

## 7. ワードクラウドの扱い（集約でのみ UI 化）

- 単体（1アイデア/1コンセプト）のワードクラウド UI は情報量が少なく価値が薄い＝**作らない**（トークン化はするが可視化は集約時のみ）。
- **UI 化する所**＝(1) **経営資料**（方針のキーワード像）、(2) **クエスト**（配下アイデア横断の語像＝議論の主題把握）、(3) 情報一覧（既存）。個別ページは任意。

## 8. 生成（ISO56001 意図/戦略/方針）＝外部委譲を推奨

- **Phase 1＝「AIに渡す用の構造化 Markdown エクスポート」**を提供（ユーザー案に一致）。経営資料＋関連アイデア/情報/コンセプトを1つの Markdown に束ねてコピー/ダウンロード → 社外/社内の任意 LLM に貼って生成。
  - 利点＝データ主権を保持（機微資料を勝手に外部送信しない）・AI コスト/ポリシー判断を利用者側に委ねる・実装が軽い。
- **Phase 2＝in-app 生成（プロバイダ差し替え式）**。ISO56001 §6 の意図/戦略/方針のたたき台を生成し、人が確定。
  - **既定＝オンプレの無料 LLM**（2026-09-28 合意・点5）＝自社ホストの OSS モデルを **OpenAI 互換エンドポイント**（Ollama／vLLM／llama.cpp 等）で受け、アプリは**共通の LLM プロバイダ抽象**（`LLMProvider` インターフェース＝`generate(prompt) -> text`）経由で呼ぶ。**機微な経営資料が社外に出ない**のが既定（データ主権）。速度は遅くて可（バッチ/非同期でよい）。
  - **クラウド生成AIは有料オプション**＝会社設定で「クラウドを使う」を明示 opt-in にした会社のみ、クラウドプロバイダ（Claude 等）に切替可（課金・送信ポリシー同意ゲート付き）。抽象が同一なのでプロバイダ差し替えだけで両対応。
  - モデル/エンドポイント/送信可否/課金プランは**会社設定**で制御。既定はオンプレ（無料）・クラウドは料金オプション。
- 生成結果は**必ず人手レビュー前提**（AI は下書き・確定は管理者）。出力先は §3.1 の構造化フィールド（意図/方針/戦略/…）に対称。

## 9. API/画面の当たり（Phase 1）

- API（新規 or 拡張）＝経営資料 CRUD（管理者）／整合率 read（アイデア詳細に同梱 or 別 read）／情報の率集計 read（ダッシュボード or 経営資料詳細）／Markdown エクスポート。**新ドメインレターは実装時に採番**（例＝R 経営資料）。
- 画面＝(1) 経営資料の一覧/登録/詳細（管理者・DataTable 踏襲）／(2) SC-22 に整合バッジ／(3) 経営資料詳細に「機会率/脅威率/影響率」＋ワードクラウド＋関連情報/アイデア／(4) エクスポートボタン。**新規 UI は既存を踏襲**（[[reuse-existing-ui-no-new]] 方針）。

## 10. セキュリティ/データ保護

- 経営資料は**機微**。会社 DB 内テナント分離・アクセスは管理者スコープ・**外部送信は既定オフ**（LLM 連携は明示 opt-in＋会社設定）。
- 手動主義＝サーバーは外部 URL を取りに行かない（SSRF 面を増やさない・情報インプットと同じ）。
- Markdown エクスポートは**利用者の明示操作**でのみ生成（自動送信しない）。

## 11. 決定事項（2026-09-28 ユーザー合意）

1. **合意**＝率は Phase 1 は決定的（キーワード/手入力集計）で割り切る（LLM は Phase 2）。
2. **合意**＝整合率コインは初回のみ・段階加点・軽め（順位指標にしない）。
3. **合意（修正あり）**＝入力は貼付だけでなく **ISO56001 の用語に合わせた構造化入力画面**にする（意図・方針/コミットメント・戦略・重点領域・目標・期間＝§3.1）。ファイルは MVP はテキスト/Markdown 貼付・PDF/Docx 抽出は後段 seam。
4. **合意**＝トークン基盤はポリモーフィック `entity_tokens` に一般化（`chat_thread` と同じ owner_type/owner_id 方式・`info_tokens` を含めて整理）。
5. **合意（追補）**＝Phase 1 は Markdown エクスポートのみ。in-app 生成（Phase 2）は **オンプレ無料 LLM を既定**・**クラウド生成AIは有料オプション**（プロバイダ差し替え式・§8）。
6. **合意**＝自動関連付け（TF-IDF auto-link）は本要望と同時に仕上げる（トークン基盤を共有）。
7. **合意（2026-09-29・意味的一致の方式）＝A-2**＝整合率の「意味的一致」は**埋め込み（ベクトル cosine）を LLM 基盤の OpenAI 互換 `/embeddings` 経由**で取得（モデルは基盤側＝backend に焼き込まない＝データ主権・横断集約）。当初案の「fastembed を backend に焼き込む（A-1）」は横断 LLM ゲートウェイ設計（`ローカルLLM連携_設計.md`）に反するため**不採用**。**方式 B（LLM 判定＝生成で整合度＋根拠文）は別要件**（整合率は決定的が要る＝コインの公平性）。会社別に **キーワード/意味/ハイブリッド** を選択（`companies.alignment_method`・SC-92）。ハイブリッド式は既定 B（0.5/0.5・config 可変・会社 UI には出さない＝過剰回避）。方式変更で整合率を全再計算＋**差分コイン付与**（初回超えのみ・下げない）。既定モデル `bge-m3`・env 可変。**A-2 は B の重い AIジョブ基盤を要さない**（埋め込みは同期・軽量）＝薄い embeddings クライアント＋`entity_embeddings` 永続化＋`SimilarityProvider` で完結。**実装済み（2026-09-29・R-TC-202〜206）**。

## 12. フェーズ計画（合意後）

1. **土台**＝トークン一般化（`entity_tokens`）＋アイデア/コンセプト/経営資料のトークン化。
2. **経営資料エンティティ**＝CRUD＋画面（管理者）。
3. **整合率**＝算出＋SC-22 バッジ＋コイン（G 台帳・冪等）。
4. **機会/脅威/影響率**＝`impact_class` 集計 read＋経営資料詳細に表示。
5. **自動関連付け**＝TF-IDF auto-link（N.6 実装）。
6. **Markdown エクスポート**＝AI 連携の入口。
7. （Phase 2）LLM 連携＝意味的整合/機会脅威判定・ISO 意図/戦略/方針の in-app 生成（opt-in）。

> 各 Phase 1 項目は着手時に データモデル/API設計/画面設計/テスト(TC) の正本へ反映（設計書ファースト）。テストは [テスト規約](../規約/テスト規約.md) §5 の TC 先行。

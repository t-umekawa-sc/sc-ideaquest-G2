# クエストの「発見＋フォロー＋参加リクエスト」— 設計ドラフト

> 状態: **ドラフト（方向性の骨子・要議論／2026-09-16 起票）**。ユーザー相談から起票。参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) に準拠。
> 確定後の正規化先＝[要件定義 README](../要件定義/README.md)（新規 FR）・[データモデル](../データモデル.md)・[API設計 C](../API設計/C_クエスト・パーティー・権限.md)・[画面設計 SC-10/SC-12/SC-01](../画面設計/screens/)・[H 通知](../API設計/H_通知.md)。
> 関連の既存決定＝[can_access_quest（C.0 門番）](../API設計/C_クエスト・パーティー・権限.md)・SC-01 ダッシュボードの「自分のクエスト」分離（実装済み・2026-09-16）。

## 0. 要旨（何を・なぜ）

「クエストをフォローしたい」というユーザー要望を検討した結果、**単体のフォローは成立しない**ことが判明。核心は **クエストの発見（ディスカバリ）動線が無い**こと。フォローも、社内レビューで挙がった **参加リクエスト** も、いずれも「自分が参加していないクエストを見つけられる」ことが前提。よって **発見・フォロー・参加リクエストは1つの機能群としてまとめて設計する**。

## 1. 背景・現状の制約（なぜ今できないか）

- **参加＝作成者の指名のみ**：パーティー員は作成者が追加する方法しかない（自薦・参加申請の導線が無い）。
- **可視範囲＝参加者限定**：クエスト参照の門番 `can_access_quest`＝作成者 or **有効パーティー員**（＋参加部署条件）。一覧 `GET /quests` も「参加中クエスト＋自分の下書き」だけを返す。→ **会社の全クエストを一覧する発見カタログが無い**。
- 従って **「参加していないクエストをフォローする」は原理的に発生しない**（見えないものはフォローできない）。フォロー中クエストの分離セクションは常に空になる。
- 社内レビュー指摘：**「参加するクエストにリクエストを出せるように」**（＝参加リクエスト）。これも発見が前提。

## 2. 機能群と依存関係

```
1. クエスト発見（ディスカバリ）          ← 前提（これが無いと 2 は無意味）
   ＝自分が入っていない会社/部署のクエストを閲覧できるカタログ
2a. フォロー（見張り）      ＝発見したクエストを、参加せず watch（更新/結果/新着を通知）
2b. 参加リクエスト（入れて）＝発見したクエストへ参加を申請 → 作成者が承認/却下
```

- **1 が土台。2a と 2b は 1 の上のアクション**。フォローは「関心はあるが今は入らない」、参加リクエストは「入りたい」。両者は併存（フォローしてから参加申請、も自然）。

## 3. 可視範囲の再設計（本機能群の肝・要決定）

**「誰に・どのクエストを・どこまで見せるか」** を決めるのが最重要。案:

- **発見カタログの範囲**（候補）:
  - (a) **会社全体**：会社内の全ての公開クエスト（recruiting/in_progress/evaluating）を一覧・タイトル/テーマ/カテゴリ/作成者/締切/人数まで見せる（中身＝アイデア/チャットは参加後）。
  - (b) **所属部署（クエストグループ）に紐づくもの**：自分の所属部署が参加部署のクエストのみ。会社全体クエスト（部署 0 件＝全体公開）も含む。
  - **推奨＝(b) を既定**（部署の壁を尊重）＋作成者が「会社全体に公開（発見可）」を選べるフラグ。会社文化で温度差があるため会社設定で既定を切替（§4.11 ゲームモードと同様の会社デフォルト＋個人/クエスト単位上書きの発想）。
- **見せる粒度**：発見カタログでは **メタ情報のみ**（件名/テーマ/カテゴリ/作成者/締切/参加人数/アイデア件数）。**中身（アイデア本文・チャット・評価）は参加後**（＝ `can_access_quest` は現状維持で「中身の門番」に徹する）。発見は別の緩い可視判定を新設する。
- **draft は対象外**（作成者のみ）。

## 4. データモデル案

- **`quest_follows`**（新テーブル・アイデアの follows と分離）: `id / quest_id / user_id / created_at`・`UNIQUE(quest_id, user_id)`。※アイデアの follows と対象が別・集計/通知の混線回避のため別テーブルを推奨。
- **`quest_join_requests`**（新テーブル）: `id / quest_id / user_id / status(pending/approved/rejected/withdrawn) / message? / created_at / decided_at / decided_by`・`UNIQUE(quest_id, user_id) WHERE status='pending'`（多重申請防止）。承認＝`quest_members` に追加（既定権限）。
- **クエストの発見可否**（可視範囲・§3）: `quests.discoverable`（enum: `party_only`（現状）/`department`/`company`）等のフラグ、または会社デフォルト＋クエスト上書き。要 §3 決定。

## 5. API 案（正規化先＝API設計 C）

- **発見カタログ**: `GET /quest-catalog`（or `GET /quests?scope=discover`）＝発見可能クエストのメタ一覧（部署/会社の可視判定・検索/カテゴリ/締切ソート・ページング §1.8）。自分の参加状態（member/follow/pending）を各行に付す。
- **フォロー**: `POST /quests/{id}/follow` / `DELETE /quests/{id}/follow`（発見可能なクエストにのみ許可）。
- **参加リクエスト**: `POST /quests/{id}/join-request`（pending 作成）／`GET /quests/{id}/join-requests`（作成者/quest_admin）／`POST /quests/{id}/join-requests/{uid}/approve|reject`（承認で members 追加＝既定権限）／`DELETE`（申請取消）。
- **通知（H・新種別）**: `join_request_received`（作成者へ・申請が来た）／`join_request_decided`（申請者へ・承認/却下）／`quest_updated`（フォロワーへ・版/結果更新）等。dedup/ゲーム除外は §H.1/§4.11 に従う。

## 6. 画面・ダッシュボード案

- **発見カタログ画面（新規 SC-xx or SC-10 にタブ追加）**：会社/部署の発見可能クエストをカード一覧。各カードに「フォロー ★」「参加をリクエスト」。検索/カテゴリ/締切ソート。
- **ダッシュボード（SC-01）セクション構成**（フォロー実装後の最終形）:
  - **自分のクエスト**（作成/運営）＝別セクション（**実装済み** 2026-09-16・`is_owner`）。
  - **参加中クエスト**（他者作成で参加）＝**フォロー中のものを ★＋上位に優先表示**（重複時はここに1枚・フォロー側に二重表示しない）。※ユーザー決定（2026-09-16）。
  - **フォロー中のクエスト**（参加していない・watch のみ）＝新セクション（**発見が実装されて初めて中身が入る**）。
  - **参加リクエストの状況**（自分の pending/結果）＝小セクション or 通知で代替。
- **クエスト詳細（SC-12）**：作成者に「参加リクエスト一覧（承認/却下）」タブ。非参加者には（発見経由で来た場合）メタ＋「参加をリクエスト」だけ見せ、中身は隠す。

## 7. 重複時の表示（ユーザー決定・2026-09-16）

- クエストが「参加中」かつ「フォロー中」＝**参加中を主に・フォローは ★ で併記し、フォロー中の参加中クエストを上位に優先表示**（重複カードは出さない）。
- 「自分が作成したクエスト」＝**別セクション「自分のクエスト」**（実装済み）。

## 8. 論点・要決定（次アクション）

1. **可視範囲（§3）** ＝ 発見カタログの既定範囲（部署/会社）と作成者の公開フラグ、会社デフォルトの持ち方。**最重要・先に決める**。
2. **参加リクエストの承認フロー** ＝ 承認で付与する既定権限（comment/vote/idea_create か）・作成者以外（quest_admin）も承認可か。
3. **フォローの通知範囲** ＝ フォロワーへ流すイベント（版更新/結果確定/新着アイデア/募集締切 等）と粒度。
4. **発見カタログの門番** ＝ `can_access_quest`（中身の門番）とは別の「発見可否」判定を新設する方針の確認。
5. **段階実装**（案）: ①発見カタログ（read・可視判定）→ ②参加リクエスト（申請/承認）→ ③フォロー（watch/通知）。②③は①の後なら順不同。

## 9. スコープ外（本ドラフトでは扱わない）

- クエストの一般公開（社外）・招待リンク等は対象外（社内テナント内の発見のみ）。
- 既存の `can_access_quest`（中身の門番）は原則現状維持（発見は別判定）。

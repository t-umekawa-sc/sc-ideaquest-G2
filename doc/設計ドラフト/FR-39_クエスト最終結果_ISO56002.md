# FR-39 クエストの最終結果（成果総括・ISO 56002 準拠）— 設計ドラフト

> 状態: **ドラフト（レビュー待ち・2026-09-13）**。社内レビュー指摘「クエストの最終結果の機能」を ISO 56002（イノベーション・マネジメントシステム — 手引）に沿って仕様化する。
> 本ドラフトは実装前のレビュー用。確定後に [要件定義 README](../要件定義/README.md) の FR-39 本文と [SC-12 クエスト詳細](../画面設計/screens/SC-12_クエスト詳細.md)・[データモデル](../データモデル.md)・[API設計 C](../API設計/C_クエスト・パーティー・権限.md) へ正規化する。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) に準拠。ISO 56002 の節番号は「ISO56002 §x」と明記する（本プロジェクト文書の §x と区別するため）。

## 1. 目的となぜ ISO 56002 か

- **クエスト＝1つのイノベーション・イニシアチブ**（ある機会・テーマに対し、アイデアを募集→評価→選定する取り組み）と捉える。
- ISO 56002 の狙いは **「価値の実現（value realization）」**。イニシアチブは「機会→コンセプト→検証→展開」の流れを辿り、**ISO56002 §9 パフォーマンス評価**と**ISO56002 §10 改善（学び）**で締める。
- 現状の ideaquest はアイデアの**評価・選定まで**は実装済みだが、**クエストを閉じる際の「成果の総括・学び・次アクション」を残す場が無い**。＝「最終結果」機能でここを埋める。
- **なぜ専用機能にするか**：選定・評価は個々のアイデア単位で分散しており、クエスト全体としての「何を得たか／次に何をするか」が一望できない。ISO56002 §9/§10 に対応する**クローズ成果物**を1画面に集約し、組織の学びとして再利用できるようにする。

## 2. ISO 56002 → ideaquest マッピング

| ISO 56002（該当節・趣旨） | 最終結果でのセクション | データ源 |
|---|---|---|
| §4.2 価値実現 / §8.3 展開（deployment） | **① 成果サマリ**＝選定アイデア（複数可）・期待価値 | `ideas.is_selected`＋評価総評/価値（D/F・既存） |
| §8.3 イニシアチブのゲート判断 | **② 意思決定の記録**＝選定/不選定と根拠 | 選定＋評価スコア/総評（F・既存） |
| §9 パフォーマンス評価（監視・測定・分析） | **③ 参加・評価サマリ**＝定量指標 | パーティー人数・アイデア数・投票総数・評価実施数・観点別平均（C/D/F/G・既存集計） |
| §10 改善（不適合・是正・継続的改善＝学び） | **④ 振り返り・学び**＝総括コメント（成果・学び・課題） | **新規テキスト**（owner/quest_admin 記入） |
| §8.3 展開 / §10 継続 | **⑤ 次アクション**＝後続への引き継ぎ | **新規テキスト**＋任意で複製導線（既存の複製・FR §4.5） |

> ①②③は既存データの合成（新規ロジック最小）。④⑤のみ新規の保存項目。

## 3. 画面（どこに・何を・いつ）

- **場所**：[SC-12 クエスト詳細](../画面設計/screens/SC-12_クエスト詳細.md) に **「🏁 結果」タブ**を追加。**クエストが `completed`（完了）のときのみ表示**（`evaluating` 以前は非表示、または「準備中」プレースホルダ）。
- **タブ内の構成**（上から）：
  1. **成果サマリ**：選定アイデアのカード（タイトル・投稿者・評価平均 n/5・価値）。選定 0 件なら「選定なしで完了」。総アイデア数/選定数のサマリ。
  2. **参加・評価サマリ**：パーティー人数・アイデア数・投票総数・評価実施数・観点別平均（新規性/影響度/実現度/適合性/コスト）の分布（バー等）。
  3. **意思決定の記録**：アイデア別に「選定/不選定・評価平均・総評抜粋」。評価の公開範囲（`evaluation_visibility`）を尊重（limited は範囲外に非表示）。
  4. **振り返り・学び**（owner/quest_admin が編集）：`summary`（成果）・`learnings`（学び・課題）。改行保持（レビュー#5）。
  5. **次アクション**（owner/quest_admin が編集）：`next_actions`（自由記述）＋任意「このクエストを複製して次を作る」導線（既存複製・参加グループ/パーティー引き継ぎ済み）。
- **編集 UI**：④⑤は owner/quest_admin にのみ編集ボタン（インライン or モーダル）。パーティー員は閲覧のみ。

## 4. 誰が・いつ

- **閲覧**：`completed` クエストのパーティー員（門番＝C.0 と同一・範囲外は 404）。評価結果は `evaluation_visibility` を尊重。
- **編集（④⑤の総括）**：`owner` / `quest_admin` のみ。
- **出現タイミング**：クエストを `completed` に遷移（C.5）した時点で「結果」タブが出現。総括は完了後いつでも追記・修正可。

## 5. データモデル（新規最小）

新規テーブル **`quest_outcomes`**（クエスト1件＝0..1）を追加（quests への列追加ではなく別テーブル＝監査/拡張性・§設計方針）。

| 列 | 型 | 制約 | 説明 |
|---|---|---|---|
| `quest_id` | uuid | PK, FK quests(id) | 対象クエスト |
| `summary` | text | null 可 | 成果サマリ（総括） |
| `learnings` | text | null 可 | 学び・課題（ISO56002 §10） |
| `next_actions` | text | null 可 | 次アクション |
| `updated_by` | uuid | FK users(id) | 最終更新者 |
| `updated_at` | timestamptz | NOT NULL | 更新日時 |

- ①②③は既存（`ideas.is_selected`・`evaluations`・投票・`quest_members`）の集計で導出＝新規列不要。
- 会社DB（テナント）に migration 追加。物理削除は行わない方針に合わせ、クエスト論理削除時も保持（監査）。

## 6. API（最小・C ドメインに追加）

| メソッド/パス | 用途 | 入力 | 応答 |
|---|---|---|---|
| `GET /quests/{quest_id}/result` | 最終結果の取得（`completed` のみ・門番 C.0） | パス: `quest_id` | 成果サマリ（選定アイデア[]）・参加/評価サマリ（指標）・意思決定（アイデア別・可視性尊重）・総括（summary/learnings/next_actions/updated_by/updated_at） |
| `PUT /quests/{quest_id}/result` | 総括の保存（`owner`/`quest_admin`） | ボディ: `summary?`/`learnings?`/`next_actions?`（あるべき全体像） | 保存後の総括 |

- 集計は既存 application（F 評価集計・D 一覧・C パーティー・G ランキング相当）を再利用し、`GET result` は**読取合成の殻**にする（新業務ロジック最小・I ダッシュボード集約と同方針）。
- `completed` 以外での `GET` は 409（`invalid_state`）または空プレビュー（要相談・§8）。

## 7. 権限・可視性・セキュリティ

- 門番＝`repository.can_access_quest`（C.0 単一ソース）。範囲外 404。
- 総括編集は owner/quest_admin（サーバー再検証）。
- 評価の観点別スコア/総評は `evaluation_visibility`（party/limited）を尊重（limited は投稿者＋評価者＋owner/管理のみ）。
- 総括テキストは表示時サニタイズ（§2.2・XSS 対策・全文検索スニペットと同方針）。

## 8. 未確定（レビューで決めたい点）

1. **価値の定量化（KPI/指標）**：ISO56002 §9 は測定を推奨。最終結果に定量 KPI 入力欄（例＝削減額・工数・件数）を設けるか？ 設けるなら項目定義が必要（自由記述の指標行 or 固定項目）。
2. **プレビュー時期**：`completed` 前（`evaluating`）に「結果（暫定）」を出すか、完了後のみか。
3. **後続イニシアチブ（展開）**：次アクションから「後続クエストを作成」を複製導線でつなぐか（既に複製は参加グループ＋パーティー引き継ぎ済み）。
4. **通知/フィード**：完了＝結果確定時にパーティーへ通知（H）やチームフィード（FR-36 成果系）へ流すか。
5. **選定の複数可否**：現状 `ideas.is_selected` は複数可。最終結果での「主選定/次点」区別を付けるか。
6. **ゲーミフィケーション**：完了総括の記入に XP を付与するか（ISO56002 の学び定着を促す動機付け）。付けるなら G 台帳へ。

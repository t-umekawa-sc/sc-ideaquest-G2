# AI駆動型アイデア生成 — 設計ドラフト（クエスト文脈からのアイデア案生成）

> 状態: **ドラフト（2026-10-02 起票・主要論点すべて確定＝§7）**。クエスト詳細（SC-12）の機能として、**クエスト本文＋関連づけられた情報インプット＋登録済みアイデア**を AI（LLM）に読ませ、**新規アイデア案を生成**する。生成物は **AI 由来と分かる**よう表示し、**起動ユーザーの下書き（draft）**として保存 → 人がレビュー・編集・公開する。起動は owner/quest_admin のみ・公開 XP なし・繰り返しガードレール付き（§5/§6/§7）。
> 社内呼称に合わせ**「AI駆動型アイデア生成」**で統一（ユーザー向け用語は既存の「AI」に揃える。内部実装は LLM／AIジョブ基盤）。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) 準拠。
> 関連正本＝[ローカルLLM連携 設計](ローカルLLM連携_設計.md)（AIジョブ基盤・ゲートウェイ・通知・進捗・モデルピッカー／本書はその利用側）／[API設計 S_AIジョブ・LLM連携](../API設計/S_AIジョブ・LLM連携.md)（`task_type`・`POST /ai-jobs`・`GET /ai-models`）／[API設計 D_アイデア]（アイデア CRUD）／[情報インプット機能 設計](情報インプット機能_設計.md)（関連情報＝`info_links`）／[データモデル](../データモデル.md)（`ideas`・`ai_jobs`・`notifications`）／[画面設計 SC-12]・[SC-21/22]／[コーディング規約](../規約/コーディング規約.md) §2（セキュリティ・プロンプトインジェクション）。

## 0. 位置づけ・狙い

- クエストは「①機会の特定」の器。参加者のアイデアが集まる場だが、**出だしが鈍い／観点が偏る**ことがある。AI が**クエストの文脈（課題文・集まった情報・既存アイデア）を踏まえた案**を提示することで、**発想の呼び水**と**観点の網羅**を助ける。
- **設計の芯**＝AI は**提案者の一人**であって決裁者ではない。生成物は必ず**下書き（draft）として人のレビューを経る**。人間のアイデアと**明確に区別**でき（AI バッジ）、採否は従来どおり投票・評価・選定で決まる。
- **既存基盤に素直に乗せる**＝新規の LLM クライアントは作らない。[ローカルLLM連携 設計] の AIジョブ基盤に **新 `task_type=idea_generate` を1本追加**し、入力の組み立てと結果のアイデア化（draft 保存）だけを新規実装する（＝呼び出し側は `enqueue` して完了通知を待つだけ・[spec is source of truth]）。

## 2. ジョブ定義（`task_type=idea_generate`）

[API設計 S](../API設計/S_AIジョブ・LLM連携.md) §S.2 の登録パターンに追記する。

| 項目 | 値 |
| --- | --- |
| `task_type` | `idea_generate` |
| 既定モデルキー | **`qwen3-swallow`**（日本語の生成品質重視・`iso_generate` と同系。会社/ユーザーが `GET /ai-models` から上書き可＝§3.4 論理モデルキー） |
| 実行方式 | `queued-worker`（ローカル・ポーリング・N 件制御。応答は数分許容） |
| 入力 (`input`) | `{quest_id, count, (任意) focus_note}`＝**参照＋件数のみ**。本文はワーカーが実行直前に収集（機微本文の滞留を最小化・§3） |
| `ref_*` | `ref_quest_id`（完了通知の遷移先＝SC-12）。生成した draft 群は `result` に ID 配列で保持 |
| 出力 (`result`) | `{idea_ids:[uuid], count, model, truncated?}`（JSON Schema 構造化・§4） |
| 課金/使用量 | `ai_usage_events` に記録（既存・トークン/コスト） |

- **件数ガード**＝`count` は **1〜会社上限（既定3・システムハードキャップ5）**。範囲外は 422（§6）。
- **モデル選択**＝[ローカルLLM連携 設計] §9.2 のモデルピッカーを SC-12 の起動 UI に埋め込み（候補1件でも常設）。解決順＝明示 `model` > `task_type` 既定 > グローバル既定（§S.2）。

## 3. 入力コンテキストの組み立て（ワーカー実行時）

> ワーカーがジョブ実行直前に会社 DB から収集してプロンプト化する（入力は参照で持つ＝[ローカルLLM連携 設計] のデータ保護方針）。

収集対象（いずれも**当該クエスト／会社スコープ内**・論理削除除外）：

1. **クエスト本文**＝タイトル・説明・（あれば）目的/背景/制約・期間・対象（[画面設計 SC-11/12] の項目）。
2. **関連づけられた情報インプット**＝当該クエストに `info_links`（`target_type=quests`・未棄却）で紐づく情報の**タイトル＋要約＋影響分類**。本文全文ではなく**要約主体**でトークンを抑える（長文は要約/先頭切り詰め・`truncated` を立てる）。
3. **登録済みアイデア**＝当該クエストの `ideas`（`deleted_at IS NULL`）の**件名＋価値（+本文要約）**。対象＝**公開済み（`status=published`）＋同一クエストの既存 AI 下書き（`generated_by_ai=true`・`status=draft`）**。**目的＝重複回避と差分発想**（「既出と被らない／既出を発展させる案を出す」ようプロンプトで指示）。**前回の AI 下書きも渡す**ことで、複数回実行が“劣化コピーの量産”でなく**反復リファイン**として機能する（同時実行ガード §6-2A と対）。
4. **任意の焦点メモ**＝起動ユーザーが「この観点で」と添える自由記述（`focus_note`・任意）。

- **プロンプト設計**＝システムプロンプトで役割（新規事業/改善アイデアの起案者）・出力スキーマ・制約（会社の既存アイデアと重複しない・各案に `title/body/value` を必ず付ける・日本語）を固定。**ユーザー提供文字列（情報本文・クエスト文・focus_note）はデータ扱い**で引用展開し、指示として解釈させない（プロンプトインジェクション対策・[コーディング規約] §2・出力は JSON Schema で構造化）。
- **トークン予算**＝関連情報・既存アイデアは件数/長さに上限を設け、超過分は要約/件数制限で収める（超過時 `truncated=true`）。上限値は env/設定で調整可（最小スペック前提）。

## 4. 生成結果の扱い（アイデア draft 化）

- LLM 出力は **JSON Schema 構造化**＝`{ideas:[{title, body, value, (任意)stakeholders[], (任意)rationale}]}`。`title/body/value` は `ideas` の必須3項目に対応（[データモデル] §5.10）。
- ワーカーが各案を **`ideas` に `status=draft` で保存**：
  - `author_id` ＝ **起動したユーザー本人**（D＝推奨）。
  - `generated_by_ai` ＝ `true`（新規列・§4-1）。
  - `quest_id` ＝ 対象クエスト。`is_selected=false`・`current_revision=1`。
  - `stakeholders` があれば `idea_stakeholders` に投入（任意）。
- **公開（published）にはしない**＝必ず人のレビューを経る（E 合意）。生成直後は author 本人にのみ見える draft（既存 draft の可視範囲と同じ）。
- **完了通知**＝`notifications.type=ai_task_done`＋`ref_quest_id`（＋生成件数）。選択で SC-12 のアイデアタブ（自分の下書き）へ遷移（[ローカルLLM連携 設計] §8 の通知/遷移を再利用）。進捗は WebSocket `ai_jobs:{user_id}`（§5.6 進捗）。
- **失敗時**＝`ai_jobs.status=failed`＋`notifications.type=ai_task_failed`。draft は作らない（部分成功時は作れた件数のみ保存し `truncated/partial` を通知）。

### 4-1. `ideas` への追加列

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `generated_by_ai` | AI生成フラグ | boolean | NOT NULL, default `false` | true＝AI駆動型アイデア生成で起案。SC-21/22/一覧で AI バッジ表示 |
| `ai_job_id` | 生成ジョブID | uuid | NULL 可, FK→ai_jobs | 由来追跡（監査/分析）。手動起案は NULL。**持つことを確定（§7-2）** |

- **なぜ作者＝起動ユーザーか**（D）＝既存の権限/可視範囲/編集/公開フロー（draft は本人のみ・本人が編集して公開）に**無改修で乗る**。「AI 専用アカウントを作者」にすると、可視範囲・編集権限・XP 付与・一覧の著者列など**横断的に特例**が要る（却下）。「AI が書いた」情報は `generated_by_ai` バッジで担保する。
- **編集で AI バッジは残すか**＝公開時/編集後も `generated_by_ai` は**残す**（由来の事実）。ただしバッジ文言は「AI生成（編集済み可）」等とし、人が手を入れた旨は版履歴（`idea_revisions`）で追える。
- **XP の扱い（2026-10-02 確定）**＝**`generated_by_ai=true` のアイデアは公開しても公開 XP を付与しない**。理由＝AI に出させて即公開するだけの**荒稼ぎを完全に回避**し、XP の意味（人の発想への報酬）を保つ。一方、**投票・評価・選定（is_selected）の報酬は従来どおり**＝公開後にコミュニティ/評価者が価値を認めれば AI 由来でも正当に報われる（＝“良い AI 案を磨いて通す”行為は評価される）。手動アイデアの公開 XP は不変。
  - **実装メモ**＝公開処理（`POST /ideas/{id}/publish`）で `generated_by_ai` を見て公開 XP 付与を分岐。投票/評価/選定の付与経路は分岐しない。XP バランスの最終確認は[ゲーム感フェーズ]の受入（GF-AC）で突合。

## 5. 画面（SC-12 拡張）

- **起動 UI**＝SC-12（クエスト詳細）のアイデアタブ付近に「**AIでアイデアを生成**」ボタン。クリックで起動ダイアログ：
  - **生成件数**（1〜会社上限・既定は会社設定の既定値）、**モデルピッカー**（[ローカルLLM連携 設計] §9.2・候補1でも常設）、**焦点メモ**（任意）。
  - 「生成する」で `POST /quests/{quest_id}/ideas:generate`（内部 enqueue・§8）→ 202。ダイアログは閉じ、**進捗はトースト/AI処理状況（SC-04）＋完了通知**で追う（同期待ちしない＝[ローカルLLM連携 設計] の UX）。
- **起動権限（2026-10-02 確定）**＝**所有者（owner）とクエスト管理者（quest_admin）のみ**。一般参加者は起動できない（ボタン非表示）。理由＝AI 生成はコスト（会社予算）を消費し、生成物のレビュー責任が伴うため、**クエストの運営責任者に限定**するのが妥当（一般参加者は従来どおり自分でアイデアを起案できる）。
- **起動可否（状態）**＝クエストが[completed-quest freeze UI standard]で凍結（完了等）されている場合は UI 側で無効化＋tooltip（完了クエストに新規アイデア不可）。同一クエストで生成ジョブが実行中の間も無効化（§6-2A）。
- **結果の見え方**＝生成完了後、SC-12 のアイデアタブ「自分の下書き」に AI バッジ付き draft が並ぶ。ユーザーは SC-21（編集モーダル）で中身を確認・調整 → 公開。
- **AI バッジ**＝一覧行・SC-22 詳細・SC-21 編集に `generated_by_ai` のバッジ（[デザイン標準] のバッジ/チップ標準に合わせる・アイコン＋「AI生成」）。[reuse existing UI]＝新規 UI を作らず既存バッジ部品を流用。
- **生成中の明示**＝AI処理状況（SC-04）に `idea_generate` ジョブが並ぶ（既存画面・`ref_quest_id` で遷移）。

## 6. 会社別設定・実行ガードレール

### 6-1. 生成件数の上限（会社別・上限のみ）

- [ローカルLLM連携 設計] §4.2 の `company_ai_model_settings`（会社別 AI 設定）と同系の**会社別設定**として**生成件数上限**を持たせる（E の合意＝**上限のみ・下限は min=1 固定**）。
- 格納先＝**会社設定の1値 `idea_gen_max_count`（既定3）**として持つ（§7-1 で確定＝専用テーブルは作らず会社設定キーで開始）。LLM 設定画面（[ローカルLLM連携 設計] §9.3）に項目追加。
- **ハードキャップ＝システム上限5**（会社がそれ以上に設定できない・コスト暴走防止）。`count` は `1..min(会社上限,5)`・範囲外は 422。
- **なぜ上限のみか**＝生成件数は LLM コスト（トークン/課金・`ai_usage_events`）に直結するため**コスト統制**として上限は有効。下限はユーザーが多めに出して採る案だけ残せばよく、強制は捨てる手間を増やすだけ（実益薄）。

### 6-2. 繰り返し実行のガードレール（2026-10-02 確定）

1クエストで何度も起動できる前提で、**時間クールダウンは設けず**（恣意的で正当な試行錯誤を妨げる）、実害（コスト／下書きの散らかり／重複／キュー圧迫）に直接効く2つを置く。会社の月予算（`company_ai_model_settings`）が最終コスト上限のバックストップ。

- **A. 同時実行ガード（必須）**＝同一クエストで `idea_generate` が `queued`/`running` の間は新規起動を**拒否（409）**。UI はボタンを「生成中…」で無効化（§5）。→ 連打・ジョブ積み上げ・キュー圧迫を根本的に防ぐ。実装は enqueue 前に「当該 `ref_quest_id` × 未完了ジョブ」を確認。
- **B. 未処理 AI 下書きの上限（確定）**＝同一クエストに `generated_by_ai=true` かつ `status=draft`（`deleted_at IS NULL`）の下書きが**`idea_gen_max_count × 2`**（既定 max3 → **6**）以上たまっている間は、新規起動を**拒否（409＋「下書きを整理してください」）**。→ 既存をさばく（公開/削除）まで量産を止める＝**レビュー消化量に連動**する非恣意的な上限。コスト暴走・散らかり・重複を自己抑制。
  - 上限値は `idea_gen_max_count × 2` を**導出値**として開始（別の会社設定キーは当面作らない。必要なら Phase2 で独立キー化）。
- **C. dedup コンテキストへ前回下書きを投入（§3-3 と対）**＝次回生成時、公開済みアイデアに加え**同一クエストの既存 AI 下書き**も「被らせない」で渡す。A により同時実行が無いので、常に直前結果を踏まえられる＝反復リファイン化。
- **連打の二重 enqueue** は `Idempotency-Key`（§8）でも防がれる（同一クリックの重複送信）。A はそれと別で「異なるクリックによる重複ジョブ」を防ぐ。

## 7. 論点の確定（2026-10-02）

いずれも確定。カッコ内は確定理由の要旨。

1. **会社別上限の格納先**＝**会社設定の単一キー `idea_gen_max_count`（既定3）**で開始（task 固有設定を小さく始める／専用テーブルは過剰）。LLM 設定画面（[ローカルLLM連携 設計] §9.3）に項目追加。→ §6-1。
2. **`ai_job_id` 列**＝**持つ**（NULL 許容）。由来追跡＝監査・「どのクエストで AI 生成が効いたか」分析に有用。→ §4-1。
3. **公開時の XP**＝**`generated_by_ai=true` は公開 XP を付与しない**。投票/評価/選定の報酬は従来どおり（荒稼ぎ回避＋良案を磨いて通す行為は評価）。XP バランスは[ゲーム感フェーズ]受入で最終確認。→ §4。
4. **重複回避の強度**＝**MVP はプロンプト指示のみ**（既存公開アイデア＋前回 AI 下書きを渡して被らせない）。生成後の類似度フィルタ（`entity_tokens`/埋め込み）は **Phase2**。→ §3-3・§6-2C。
5. **情報インプットの反映範囲**＝関連情報は未棄却を渡し、**`refuting`（反証）も渡して「反証を踏まえた案に」と指示**（“揺さぶる”思想と整合）。→ §3。
6. **FR 採番**＝**新規 FR を1本**起こす（ユーザー価値が独立）。
7. **実行権限**＝**owner/quest_admin のみ**（コスト消費＋レビュー責任が伴うため運営責任者に限定）。→ §5・§8。
8. **繰り返し実行**＝時間クールダウンなし。**同時実行ガード（A・必須）＋未処理 AI 下書き上限 `idea_gen_max_count×2`（B）＋前回下書きの dedup 投入（C）**。会社月予算がバックストップ。→ §6-2。

**正式反映の順序**＝新規 FR 起票 → データモデル（`ideas.generated_by_ai`/`ai_job_id`・会社設定 `idea_gen_max_count`）→ API（S に `idea_generate` 追記・D に `:generate` 追記）→ 画面（SC-12 起動／SC-21・22 AI バッジ）→ 遷移図 → テスト md（TC 採番）。

### 7-1. Phase2 送り / 継続検討
- 生成後の**類似度フィルタ**（重複排除の自動化）。
- 未処理下書き上限の**独立会社設定キー化**（当面は `idea_gen_max_count×2` の導出値）。
- 変数差し込み（focus 以外の文脈自動注入）・**関連情報が0件のクエスト**での生成品質改善（現状はクエスト本文のみで生成可・§3）。

## 9. セキュリティ / データ主権（確認）

- **テナント分離**＝入力収集・draft 保存とも会社 DB 内で完結（他社情報は混入しない）。

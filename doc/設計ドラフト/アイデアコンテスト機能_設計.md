# アイデアコンテスト機能 — 設計ドラフト（クエスト非依存のアイデア公募・投票/評価・会期表彰）

## 0. 要旨（何を作るか）

- **アイデアコンテスト**＝クエストに縛られず、アイデア単体を投稿し、**不特定多数の参加者が投票・チャット**でやり取りする場。**評価は偏り防止のため運営（管理者）が指名する審査員**が担う（当初は「投稿者が指名」案だったが、公平性重視で2026-09-30に方針転換・§5.2）。公開中のアイデアには**参加リクエスト→承認**で加われる。**一定期間の会期**で賛成投票数・獲得評価点・活動貢献を集計し、**優秀アイデア/貢献者を表彰**（XP・コイン・実績・称号）する。
- 「アイデアコンテスト」は一般用語（アイデアソン／イノベーションチャレンジ／アイデア公募／オープンイノベーション）。本機能は **「社内公募型 × ゲーミフィケーション表彰」を主軸**に、DEMO公開部分だけ**クラウドソーシング型**の色を持つハイブリッド。
- **アーキの芯＝クエストを器に再利用（B案・§2）**。コンテスト1件につきクエスト1行を1:1で backing コンテナにし、**アイデア/投票/評価/チャット/ランキング/XP の既存機構を無改修で共有**。コンテスト固有の差分だけを薄い上乗せ層に閉じる。→ **「クエストの機能を抜き取って使う」＝コードは共有・一か所直せば両方直る**（DRY・§2.3）。
- **期間モデル＝会期枠＋ステータスタブのハイブリッド（§4）**。コンテスト実体で会期を管理し、内部アイデアに `応募中/入賞/殿堂入り/お蔵入り` のステータスをタブで整理。`mode: bounded`（締切・表彰あり）と `mode: rolling`（常設・N日自動アーカイブ）を同じ器で表現。
- **表彰・貢献度は既存 `activities` 元帳＋ランキング集計を再利用（§6）**。集計軸だけ拡張（賛成投票数・平均評価点・活動件数）。付与は `ledger.grant`（冪等 `reason='contest_award'`）＋「入賞」実績で完結。
- **公開/非公開モード（§8）**＝会社単位 `companies.access_mode`。`public`（デモ）＝ホームページ→セルフサインアップ→メール認証→`role=general` 作成→**コンテストのみ操作可**（一般ユーザーは非コンテストEPを 403・SC-50 着地でダッシュボードの逃げ道も封鎖）。会社コードは**デプロイ設定で自動供給**（`DEMO` をロジックに焼かない・§8.1）。セルフサインアップ詳細は FR-47。
- **社内向け追加（§7）**＝コンテストの有望アイデアを**正式クエストへ昇格**（`アイデア→クエスト作成`）＋**ユーザーへのクエスト作成権限**を新設。

## 1. 位置づけ・スコープ

### 1.1 一般用語としてのアイデアコンテスト

| 型 | 概要 | 本機能との距離 |
|---|---|---|
| 社内公募型 | 社内改善・新規事業アイデアを社員から募集 | **主軸** |
| クラウドソーシング型 | 社外の不特定多数から募る（無印良品IDEA PARK 等） | DEMO公開で採用 |
| ハッカソン/アイデアソン型 | 短期集中で発散 | 会期型 `bounded` が近い |

典型フロー＝**テーマ設定 →（会期の）公募 → 投票・審査 → 入賞発表・表彰**。本機能はこれを既存のゲーミフィケーション（XP/コイン/実績/ランキング）に載せる。

### 1.2 スコープ（合意）

- **非公開モード会社（`access_mode='private'`・従来）**＝自社ユーザー向けにコンテスト開催。メニューは従来＋コンテスト。可視範囲＝会社全体（パーティー限定ではない）。
- **公開モード会社（`access_mode='public'`・デモ）**＝一般公開。ホームページからリンク、セルフサインアップで参加。**ログイン後はコンテストのみ操作可**（他は 403）。
- 両者は**同一のコンテスト機能**。違いは会社単位の **`companies.access_mode`**（§8.0）のみ。
- **社内のみ**の付随機能＝アイデア→クエスト昇格・クエスト作成権限（§7）。

### 1.3 クエストとの関係（何を抜き取るか）

| クエストの機能 | コンテストで | 方針 |
|---|---|---|
| アイデア投稿/編集/版（`ideas`/`idea_revisions`） | そのまま | **共有（無改修）** |
| 投票（`votes`） | そのまま | **共有（無改修）** |
| 評価（`evaluations`/`evaluation_scores`・5観点+総評） | そのまま | **共有（無改修）**。ただし評価者は**運営が指名する審査員**（②会社レベル能力）に変わる（§5.2） |
| チャット（`chat_thread`/`chat_groups`・SC-24） | そのまま | **共有（無改修）**。アイデア単位チャットは既存流用 |
| ランキング/XP/コイン/実績（`activities`・`aggregate_ranking`） | そのまま＋軸拡張 | **共有＋拡張**（§6） |
| アクセス制御（パーティー所属＋部署ゲート） | **置換** | 単一ポリシー解決で「会社全体/参加者」に分岐（§2.3） |
| 参加（`quest_members` を管理者が追加） | **置換** | **参加リクエスト→承認**（§5.1） |
| 評価者権限（クエスト単位で付与） | **置換** | **運営（管理者）が指名する審査員＝②会社レベル能力**（§5.2・§5.3） |
| ライフサイクル（`quests.status`） | 流用＋意味づけ | 会期の開始/締切/確定にマップ（§4） |

## 2. アーキテクチャ（B案＝クエストを器に再利用）

### 2.1 データの器

```
contests (会社DB・新規)                       quests (既存・無改修)
  id (PK)                                       id (PK)
  quest_id (FK→quests, UNIQUE) ───1:1──────────▶ status (draft/recruiting/in_progress/evaluating/completed)
  mode (bounded|rolling)                         ... 既存カラムをそのまま利用
  （公開性は companies.access_mode）          ideas (既存・無改修)
  starts_at / ends_at                            quest_id (FK→quests) ← コンテスト用クエストを指す
  status (draft|open|judging|closed|archived)    author_id / title / body / value
  theme / description / prize_config(jsonb)      status (draft|published)
  created_* / updated_* / deleted_*              is_selected  ← 入賞フラグに流用可

votes / evaluations / evaluation_scores / chat_groups / chat_thread / activities
  … すべて idea_id / quest_id 経由で既存のまま接続（コンテストを意識しない）
```

- **アイデアは従来どおり `quest_id` を持つ**（NOT NULL のまま）。その `quest_id` が「コンテスト用クエスト」を指すだけ。**`ideas` テーブルもアイデア系サービスも一切変更しない**。
- コンテスト固有属性は **`contests` テーブル**に外付け。クエストは backing コンテナに徹する。
- **`ideas.quest_id` を nullable にする案（A案）は不採用**（アクセス制御総取替で影響大）。B案は壁を回避しつつ共有を最大化する。

### 2.2 レイヤ（バックエンド4層・§3.4）

```
[contest ドメイン (tenant/contests)]  ← コンテスト固有: CRUD・会期・参加リクエスト・審査員付与(②能力)・表彰確定
        │ 内部的にクエスト/アイデアの application を呼ぶ（重複実装しない）
        ▼
[idea / vote / evaluation / chat / gamification (既存)]  ← 共有・無改修
```

- コンテスト層は**アイデア系を再実装しない**。既存の application（投稿・投票・評価・チャット）を**呼び出すだけ**。これが「一か所直せば両方直る」の実体。

### 2.3 唯一の分岐点＝アクセス/参加ポリシー

アイデアの可視性・投票/コメント可否は、現状「当該クエストのパーティー所属＋部署ゲート」で判定している。コンテストは範囲が違う（会社全体 or 参加者）。ここを**フォークせず単一のポリシー解決関数**に集約する（チャットの `_resolve_host` と同じ思想）:

```
resolve_idea_access(quest, user):
  if quest is contest-backed:
     可視 = 会社全員（テナント内・パーティー/部署ゲート非依存）
     投票 = Tier1 参加者（案X）／ チャット = Tier2 承認者（投稿者承認）
     評価 = contest_evaluator（審査員）保持者のみ（§5.2）
  else (通常クエスト):
     従来のパーティー所属＋部署ゲート
```

- **判定の入口を1か所**にすることで、アクセス仕様の変更もクエスト/コンテスト双方に一度で効く。
- 認可はサーバー権威（API設計 §1.6）。UIの出し分けだけに依存しない。
- なお**会社の公開/非公開は別レイヤ**＝`companies.access_mode`（§8.0）。`public` 会社では一般ユーザーの**非コンテストEPを 403** で塞ぐ（アクセス範囲の解決とは独立した外周ガード）。

> **決定A/A'（2026-09-30）**: **案X**を採用＝**投票は Tier1 参加者全員に開放**（公平性）、**チャット（コメント）は Tier2＝アイデア投稿者の承認制**（荒れ対策・心理的安全性）。**評価は「コンテストアイデア評価権限」を持つユーザーのみ**（クエストの評価者と同型・§5.3）。DEMOでも同じ。

## 3. データモデル差分

### 3.1 新規テーブル

**`contests`（会社DB）** — §2.1 参照。主なenum:
- `mode`: `bounded`（会期・締切・表彰）／`rolling`（常設・N日で自動アーカイブ）
- ~~`visibility`~~: **廃止**（公開性は会社単位の `companies.access_mode` に一本化・§8.0）。コンテストの参加範囲は Tier1/Tier2 で表現
- `status`: `draft`→`open`（公募中）→`judging`（締切後・審査/集計）→`closed`（表彰確定）→`archived`
- `prize_config` (jsonb): 表彰軸と上位N・付与XP/コイン・実績コードのマップ（§6.3）
- `auto_archive_days` (int, NULL可): `rolling` 時のアイデア自動アーカイブ日数

**`contest_participants`（会社DB）** — Tier1：コンテスト参加（閲覧＋自分のアイデア投稿・§5.1）
- `contest_id` (FK) / `user_id` (FK)
- `status`: `requested`（申請中）／`approved`（承認）／`rejected`／`left`
- `requested_at` / `decided_at` / `decided_by`（＝管理者）
- UNIQUE(`contest_id`,`user_id`)
- ※ `public`（DEMO）はサインアップで自動 `approved`（決定G・§8.2）

**`idea_participants`（会社DB）** — Tier2：個別アイデアへの参加（投票・チャット・§5.1）
- `idea_id` (FK) / `user_id` (FK)
- `status`: `requested`／`approved`／`rejected`／`left`
- `requested_at` / `decided_at` / `decided_by`（＝**アイデア投稿者**）
- UNIQUE(`idea_id`,`user_id`)
- ゲート＝**チャットは本表 `approved`**。**投票は Tier1（`contest_participants`）に開放**（案X決定・§5.1）

**`user_capabilities`（会社DB・新規）** — ②会社レベル能力の**単一レジストリ**（§5.3・決定D）。既存 `info_curators`（§5.37）も**本表へ統合**（決定・2026-09-30）。
- `id` / `user_id` (FK→users) / `capability` / `granted_by_id` (FK→users, NULL可) / `granted_at` (default now()) / `revoked_at` (NULL可・論理剥奪／行は残す監査) — **`info_curators` と同形**（`capability` 列が増えるだけ）
- `capability`: `info_curator`（情報判定権限＝既存 `info_curators` を移行）／`quest_create`（クエスト作成）／`contest_create`（コンテスト作成）／`contest_evaluator`（**コンテストアイデア評価権限＝審査員**）
- UNIQUE(`user_id`,`capability`) WHERE `revoked_at IS NULL`（有効な付与は能力ごと1行・`info_curators` の `UNIQUE(user_id) WHERE revoked_at IS NULL` を一般化）
- **評価者ゲート**＝`capability='contest_evaluator'` 保持者のみ評価可（＝クエスト `quest_member_permissions.evaluator` の会社レベル版）。付与は **system_admin / company_account_admin**（決定J）。将来は実績で自動付与も（Phase2）。
- **`info_curators` 統合の移行**（実装タスク・別セッションと要調整）: (1) 既存行を `user_capabilities(capability='info_curator')` へデータ移行（`granted_by_id`/`granted_at`/`revoked_at` 保持）／(2) 情報インプット（ドメインN・API N.0）の参照を差し替え／(3) 移行期は互換ビュー `info_curators`（`SELECT ... WHERE capability='info_curator'`）を置くか、クリーンカットオーバー。**データモデル §5.37 は「`user_capabilities` へ統合済」に更新**（正式反映フェーズ）。
- ※ 旧案の `idea_evaluator_nominations`（投稿者がアイデア単位で指名）は**不採用**（偏り防止のため運営指名へ・§5.2）。

### 3.2 既存テーブルの扱い（変更しない）

- `ideas`／`votes`／`evaluations`／`evaluation_scores`／`chat_*`／`activities`／`achievements`＝**スキーマ変更なし**。
- `is_selected`（既存）を**入賞フラグ**として流用（クエストの「選定」と同義に扱う）。
- `activities.quest_id`（既存・ランキングスコープ用）に**コンテスト用クエストのid**が入るので、コンテスト内ランキングは既存の `scope='quest:{id}'` で**そのまま集計可能**。
- **決定E**: **コンテスト全体チャットは MVP 不要**（アイデア単位チャットのみ）。告知はコンテスト説明＋通知で代替。必要になれば `chat_thread.owner_type='contest'` を1値追加（安価）で後付け。

**`contest_idea_flags`（会社DB・新規）** — アイデアの恒久ステータス（`ideas` 無改修のため外付け・決定B）
- `idea_id` (FK) / `flag` / `contest_id` (FK) / `granted_by` / `granted_at`
- `flag`: `shelved`（お蔵入り）／`hall_of_fame`（殿堂入り＝会期を超えた顕彰）
- 入賞は既存 `is_selected` を流用。タブ（§4.2）はこの3情報から導出。

**`companies`（管理DB・新規カラム2つ）** — 公開/非公開モードとセルフサインアップ（§8）
- `access_mode ∈ {private, public}`・既定 `private`（§8.0）。認可・メニュー・導線の権威。`public`（デモ）＝一般ユーザーはコンテスト系以外 403。旧 `contests.visibility='public'` は本カラムに一本化して廃止。
- `self_signup_enabled` (boolean・既定 `false`)（§8.2・決定M）。`true` の会社のみセルフサインアップ可（`public`/`private` 問わず opt-in）。

### 3.3 冪等・監査

- 表彰付与は `activities` の冪等キー `(user_id, kind, reason='contest_award', ref_type, ref_id)` で二重付与防止（既存パターン）。
- コンテストの状態遷移（`open→judging→closed`）とその副作用（付与/通知）は監査ログ対象。

## 4. 期間モデル（会期枠＋ステータスタブ）

### 4.1 会期＝コンテスト状態 × backing クエスト状態

| コンテスト `status` | 意味 | backing quest `status`（マップ） | できること |
|---|---|---|---|
| `draft` | 準備中（管理者編集） | `draft` | 公開前設定 |
| `open` | 公募中 | `recruiting`/`in_progress` | 投稿・投票・評価・チャット |
| `judging` | 締切後の審査/集計 | `evaluating` | 投稿締切・評価/集計・順位算定 |
| `closed` | 表彰確定 | `completed` | 読み取り凍結・表彰表示・付与済 |
| `archived` | 保管 | `completed` | 閲覧のみ（殿堂入り/お蔵入り） |

- **`bounded`**: `starts_at`/`ends_at` で自動 `open→judging`（締切）→管理者確定 or スケジューラで `closed`。
- **`rolling`**: `ends_at` なし。`auto_archive_days` 経過アイデアを自動で「お蔵入り」へ。表彰は定期スナップショット（例: 月次）または随時。

### 4.2 アイデアのステータス（タブ）

コンテスト詳細のアイデア一覧を、以下でタブ整理（案3の採用部分）:

| タブ | 対応状態（導出元） | 説明 |
|---|---|---|
| 応募中 | `published` かつ `contest_idea_flags` に `shelved` 無し | 投票・評価の受付中 |
| 入賞 | `is_selected=true`（既存） | 当該会期で表彰されたアイデア |
| 殿堂入り | `contest_idea_flags.flag='hall_of_fame'`（決定B） | 会期を超えて顕彰（複数会期の最上位等） |
| お蔵入り | `contest_idea_flags.flag='shelved'`（`rolling` は自動付与） | 期限切れ・不採用 |

> **決定B（2026-09-30）**: 「殿堂入り」は**永続の小テーブル `contest_idea_flags`**（§3.2）で保持。`prize_config`（会期ごとの賞設定）では表さない。`ideas` は無改修。

## 5. 参加・評価者指名フロー

### 5.1 参加は2階層（決定・2026-09-30）

投稿者が承認するには先にアイデアが存在する必要があるため、参加を**2階層**に分ける（A＝承認者のみ／C＝投稿者が承認 を両立させる唯一の整合形）。

| 階層 | 何に参加 | できること | 承認主体 | テーブル |
|---|---|---|---|---|
| **Tier1: コンテスト参加** | コンテスト（枠） | 閲覧＋**自分のアイデア投稿＋投票**（案X） | 管理者（DEMOはサインアップで自動 `approved`＝決定G） | `contest_participants` |
| **Tier2: アイデア参加** | 各アイデア | **チャット（コメント）** | **そのアイデアの投稿者**（C） | `idea_participants`（新規） |
| 評価 | 各アイデア | 5観点評価 | **運営（管理者）が付与する審査員**（②能力・§5.3） | `user_capabilities`（`contest_evaluator`） |

- **心理的安全性**＝各アイデアの投稿者が「自分のアイデアの場」の参加者をキュレーション。荒れの発生源（チャット）を投稿者管理下に置く。
- 通常クエストの「管理者がメンバー追加」を**リクエスト駆動＋投稿者承認**に置換。
- **Tier2 用に `idea_participants`（会社DB）を新設**: `idea_id`(FK)/`user_id`(FK)/`status`(requested|approved|rejected|left)/`decided_by`（＝投稿者）/UNIQUE(idea_id,user_id)。`contest_participants`（§3.1）は Tier1 用。
- **案X 採用（決定）**＝**投票は Tier1（`contest_participants`）に開放**、**チャットは Tier2（`idea_participants`・投稿者承認）**。ゲートは §2.3 の単一ポリシー解決関数で分岐。

> **フロー**: `Tier1参加（閲覧/投稿/投票 可）→ あるアイデアで議論したい → そのアイデアに参加リクエスト（idea_participants: requested）→ 投稿者が承認 → チャット可`。

### 5.2 評価者＝運営が指名する審査員（決定・2026-09-30）

- **当初案（投稿者がアイデア単位で評価者を指名）は不採用**。理由＝投票同様に**評価が偏るリスク**があり、投稿者が自分に有利な評価者を選べてしまう。→ **評価は運営（system_admin / company_account_admin）が付与した「審査員」＝`contest_evaluator` 能力の保持者のみ**が行う（中立性の担保）。
- 審査員は**運営スタッフ想定**。将来は**実績（achievements）で一般ユーザーにも自動付与**する余地を残す（Phase2）。
- 評価そのもの（5観点1〜5点＋総評必須・下書き/確定・`visibility`）は**既存 `evaluations` を無改修で使用**。「投票は参加者全員／評価は審査員のみ」の構図（クエストの投票/評価と同型）。
- 付与UIは会社アカウント管理（SC-93）系を踏襲（新規UIを増やさない）。台帳＝`user_capabilities`（§3.1・§5.3）。

> **決定J'（2026-09-30）**: 審査員能力のスコープは**会社横断**（`contest_evaluator` を持てば全コンテストを評価可）。`user_capabilities` だけで動き割当テーブル不要。必要になれば per-contest パネル割当を後付け。

### 5.3 権限モデル（3スコープ）— 新規権限の位置づけ

既存・新規の権限は**3つのスコープ**に整理できる（既存もこの3層で説明可）。新規権限はどのスコープに属すかを明確化する。

| スコープ | 何に効くか | 付与者 | 既存 | 新規（今回） |
|---|---|---|---|---|
| **① システムロール**（`accounts.role`・全体） | アプリ全体の立場 | 運営/会社管理者 | `system_admin` / `company_account_admin` / `general` | （追加なし） |
| **② 会社レベル能力**（`user_capabilities` 単一レジストリ・会社横断） | 会社内でその行為をできるか | **system_admin / company_account_admin** | **情報判定権限**（→ `info_curator` に統合） | **クエスト作成権限**（`quest_create`）／**コンテスト作成権限**（`contest_create`）／**コンテストアイデア評価権限**（`contest_evaluator`＝審査員） |
| **③ スコープ内権限**（対象単位で付与） | 特定クエスト/コンテスト/アイデア内での可否 | 対象の所有者/管理者/投稿者 | クエスト内＝`quest_member_permissions`（`owner`／`quest_admin`（クエスト管理）／`evaluator`（評価者）／`vote`（投票）／`idea_create`（**作成＝アイデア作成**）／`comment`（コメント）） | コンテスト内＝**Tier1参加**／**Tier2参加**（チャット） |

**レビュー指摘・決定（用語の整理）**:
- ⚠️ **クエストの「作成」＝アイデア作成（`idea_create`）**であり、**クエスト自体の作成ではない**。今回新設の**「クエスト作成権限」（`quest_create`）は別物**（②会社レベル）。混同しないよう文言を分ける。
- 「情報判定権限」は②会社レベルの既存能力。新設3権限（`quest_create`／`contest_create`／`contest_evaluator`）も同じ器に載せると一貫する。
- **決定J**: **コンテストアイデア評価権限（`contest_evaluator`＝審査員）は②会社レベル**へ。付与者＝**system_admin / company_account_admin**（偏り防止・§5.2）。当初の「投稿者が指名（③・per-idea）」案は**不採用**。
- **決定I**（=b）: **コンテスト作成権限（`contest_create`）は②能力として一般ユーザーにも個別付与可**。Q4「枠作成は管理者のみ」は「**管理者＋能力付与された人**」へ緩和。
- **決定K**（=b）: **クエスト作成権限の移行**＝現在クエストを作成している既存ユーザーには自動付与（維持）、以降の新規は付与制。会社アカウント管理者は常時保持。

**② 会社レベル能力の器（決定D＝汎用テーブルに全集約）**:
- **新規 `user_capabilities(id, user_id, capability, granted_by_id, granted_at, revoked_at)`** を②能力の**単一レジストリ**にする。**既存 `info_curators`（§5.37）も本表へ統合**（`capability='info_curator'`）＝1能力1テーブルの増殖を止め、付与/剥奪の経路・管理UI・監査を1本化（DRY）。`info_curators` とはカラムが同形なので移行は素直（§3.1 に移行手順）。
- 対象能力＝`info_curator`／`quest_create`／`contest_create`／`contest_evaluator`。付与UIは会社アカウント管理（SC-93）系を踏襲。
- ⚠️ 統合は情報インプット（ドメインN）の参照差し替えを伴うため、**実装は別セッション（impl 進行中）と要調整**。本ドラフトは設計意図の確定まで（コードは触らない）。

## 8. 公開／非公開モードとセルフサインアップ（決定・2026-09-30）

### 8.0 公開/非公開モード＝会社単位の設定（`companies.access_mode`）

**新規 `companies.access_mode ∈ {private, public}`（既定 `private`）** を会社（テナント）単位の設定にする。これが**権威**（authz/メニュー/導線の唯一の正）。旧 `contests.visibility='public'` は**廃止**し、コンテストの公開性はこの会社設定に一本化（コンテストの参加範囲は Tier1/Tier2 で表現）。

| モード | メニュー | 着地画面 | バックエンド | 用途 |
|---|---|---|---|---|
| **`private`（非公開・従来）** | これまで通り＋**コンテスト**を追加 | SC-01 ダッシュボード（従来） | 制限なし（従来の認可） | 通常運用の会社 |
| **`public`（公開・デモ）** | **コンテストのみ**（＋プロフィール/設定/ログアウト） | **SC-50 コンテスト一覧**（SC-01 は出さない） | **一般ユーザーはコンテスト系以外 403** | デモ用会社（例: DEMO） |

- **バックエンド強制（ユーザー要件）**: `session.company.access_mode='public'` かつ `role=general` のリクエストは、**コンテスト系エンドポイントの許可リスト以外すべて 403**（`forbidden`）。UI非表示に依存しない（API設計 §1.6・サーバー権威）。
  - 許可リスト＝コンテスト/アイデア(コンテスト配下)/投票/評価/チャット＋認証・セッション・プロフィール・通知（コンテスト関連）。
  - **決定O**: **管理者は例外**＝`system_admin` / `company_account_admin` は `public` 会社でも自分の管理系EP（モデレーション/アカウント管理）を保持（デモ運営に必要）。403 は `role=general` にのみ適用。
- **ダッシュボードの逃げ道対策（決定P）**: `public` では **SC-01 を描画せず SC-50 に着地**。ナビ・ヘッダー・カード内リンクからクエスト等へ飛べない構成にする（クエスト系 `<Link>` を出さない）。＝「リンクでクエストに飛ぶ」事故を UI と 403 の二重で封じる。**「クエストへ飛んで困るのは `public`（デモ）」で確定**（`private` は全員社員でクエスト可のため問題化しない）。

### 8.1 会社コードの出し分け＝「デプロイ設定」と「会社設定」を分離（推奨）

**課題**＝デモではログイン時に会社コードを入力させたくない。が、`DEMO` をロジックに焼き込むのは避けたい。
**解**＝2層に分離する:

1. **権威（DB）＝`companies.access_mode`**：認可・メニュー・403 はこれで判定（上記 §8.0）。
2. **ログインUX（デプロイ設定）＝既定会社コード**：デモ用サーバーにだけ「このデプロイの既定会社コード」を設定（**環境変数 `IQ_DEFAULT_COMPANY_CODE=DEMO`**、または**ホスト名→会社マッピング**）。設定がある deployment では、ログイン画面が**会社コード欄を隠して自動セット**する。

- これは **「既定会社が設定された単一テナント運用（キオスク的）」という汎用機能**であり、`DEMO` リテラルをコードに焼かない（設定値を読むだけ）。本番サーバーは当該設定を持たない → 従来どおり会社コード入力。
- デモ用サーバーは本番と**別デプロイ**（ユーザー前提）なので、この分離が自然。
- フロントは公開ブートストラップ（例 `GET /public/bootstrap`）で「既定会社コードの有無」を取得し、あれば SC-00 の会社コード欄を非表示＋自動セット。

> **決定L**: 既定会社コードの供給は **環境変数 `IQ_DEFAULT_COMPANY_CODE`**（デモ用サーバーのみ設定）。ホスト名マッピングは採らない。

### 8.2 セルフサインアップのフロー（決定・セキュリティA反映）

**許可条件（決定M）**＝会社に**新規フラグ `companies.self_signup_enabled`（既定 `false`）** が `true` の場合のみセルフサインアップ可。`public` 会社も含め**既定は不可**（opt-in）。デモ会社と、希望する `private` 会社で明示的に有効化。現行 FR-03「管理者発行のみ」を、この opt-in で限定的に緩和。

```
1. ログイン画面（SC-00）で「アカウント作成」リンク → SC-05 アカウント作成
2. 会社コード・ログインID・メールアドレス・設定するパスワード を入力して送信
   （public デプロイでは会社コードは §8.1 で自動セット＝入力欄なし）
   → サーバー: 対象会社が self_signup_enabled か検証（否なら一様reject）。
   → ★アカウントはまだ作らない★。入力を pending（署名トークン／otp_challenges に束ね）で保持。
     PW は即 Argon2id ハッシュ化して pending に保持（平文保持しない）。
3. サーバーがメールへ認証コードを送信（otp_challenges.purpose=email_verify を流用）
4. 次画面＝多要素認証と同じUI（SC-00 状態C 流用）で認証コードを入力 → 検証
5. ★検証成功で初めて accounts を INSERT★（一意性は commit 時にチェック）
   ・role=general／company_id=解決値／status=active（決定N＝即active）
   ・email_verified_at=now・password_set=true
   → outbox で会社DBミラー ＋ Tier1 自動 approved（決定G）
   ＋ system_admin / company_account_admin へ「新規登録」通知メール（レート制限/ダイジェスト）
```

**確定・指摘**:
- ✅ 既存の **email_verify OTP＋MFA画面（SC-00 状態C）を再利用**（UIを増やさない）。PWは登録時入力なので `password_setup` リンク不要。→ 旧「初回PW=password_setup 流用」を上書き。
- 🔴 **決定A（構造）＝検証前にアカウント/一意値を作らない**（手順5で初めて INSERT）。手順2で作ると login_id/email の**スクワッティング**（正規登録の妨害＝DoS）と accounts 汚染が起きる。→ 詳細は §8.4。
- **決定N**＝メール認証成功で**即 `active`**（デモの摩擦最小）。
- ⚠️ **QG 割当は `public` では不要**（コンテストは会社全体・パーティー/部署ゲート非依存）。管理者通知は**モデレーション/把握**目的。QG 割当が要るのは「`private` 会社でセルフ登録を許し、かつ業務メニューも使わせる場合」のみ。

### 8.3 既存基盤の使いどころ

| 要素 | 実装 |
|---|---|
| デモ会社 | seed で予約作成（`company_code='DEMO'`・`status=active`・**`access_mode='public'`**・**`self_signup_enabled=true`**・`game_mode_default` は表彰演出を出すなら true・`mfa_required` は運用判断） |
| メール認証 | `otp_challenges.purpose=email_verify`＋`POST /auth/email-verify/confirm`（既存）を流用 |
| ログインUX | SC-00 を流用。public デプロイは会社コード欄を非表示＋自動セット（§8.1・env `IQ_DEFAULT_COMPANY_CODE`） |
| メニュー/着地 | `access_mode` で分岐（§8.0）。public は SC-50 着地・コンテストのみ |

### 8.4 セキュリティ設計（正本＝[セキュリティ対策一覧](../WEBアプリ開発時のセキュリティ対策一覧.md)・[コーディング規約](../規約/コーディング規約.md) §2 と突合。FR-47 実装の必須要件）

セルフサインアップは未認証・公開の書込口＝攻撃面。以下を**必須要件**とする（§番号は セキュリティ対策一覧）。

| # | 項目 | 要件 | 対策一覧 |
|---|---|---|---|
| **A** | 検証前に作らない（**構造・最重要**） | 手順2の入力は **pending（署名トークン/`otp_challenges` に束ね）** で保持し、**コード検証成功で初めて `accounts` INSERT**（一意性は commit 時）。→ login_id/email スクワッティング（DoS）と accounts 汚染を防止 | §4 |
| **B** | 列挙耐性 | 会社コード/`self_signup_enabled`/login_id/email 重複を **in-band で明かさない**。UIは一律「コードを送信しました」。既存メールには **out-of-band で「既にアカウントがあります」メール**。既存 password-setup の一様応答（202）に倣う | §4・§14 |
| **C** | OTP ブルートフォース | 認証コードは **短命（例10分）・単回・試行回数ロック・定数時間比較・推測不可トークンに束ねる**。**再送もレート制限**（メール爆撃防止） | §1・§9・§13 |
| **D** | パスワード | 手順2で受領後 **即 Argon2id ハッシュ化**（平文保持/ログ出力禁止）。**最低文字数＋漏洩PW拒否**。TLS 必須 | §1・§11・§12 |
| **E** | マスアサインメント/権限固定 | `role=general`・`company_id=解決値`・`status`・capabilities は**サーバーが権威設定**。client の `role/company_id/is_admin/capability` 等は**無視**（別会社/管理者昇格を防止） | §2・§4 |
| **F** | テナント/会社コード改竄 | client が別会社コードを送っても、サーバーが **対象会社の `self_signup_enabled=true` を再検証**。否は一様reject（`private` 会社への勝手な登録を防止） | §2 |
| **G** | CSRF/Origin・自動化 | 未認証POSTでも **Origin/Sec-Fetch 検証**。**IP/メール単位レート制限＋新規作成の時間窓上限**、public は **CAPTCHA**。使い捨てメールドメインの扱いを検討 | §7・§9・§10 |
| **H** | 即 active の濫用面 | 即 active＋Tier1＋投稿可 → **新規アカウントの投稿レート制限・モデレーション・通報**必須。**管理者通知の大量化**（サインアップ爆撃）を **レート制限/ダイジェスト化** | §9・§2 |
| **I** | セッション | サインアップ後に自動ログインするなら **新規セッション発行（固定化対策）**。`email_verify` トークンで**既存アカウントのセッションを取得できない**よう purpose を厳格分離 | §3 |
| **J** | ログ・監査・PII | PW/コードをログに出さない。試行を **request_id/tenant 付きで監査**。public は **データ保持/削除方針**（デモ後クリーンアップ）。PII最小化（表示名以外を要求しない） | §12・§15 |

- **公開モードの外周ガード**（§8.0 の 403）も認可の一部＝`role=general` × `public` 会社で非コンテストEPを塞ぐ（§2）。
- **モデレーション/通報**＝公開投稿の不適切コンテンツ対応（H と併せて運用設計）。

> **セルフサインアップの詳細仕様（画面SC-05・API・上記A〜Jの実装）は FR-47 として本節を土台に別途詰める**（本セッションはコード非改修）。

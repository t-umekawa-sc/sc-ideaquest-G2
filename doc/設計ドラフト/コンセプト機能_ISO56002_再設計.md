# コンセプト機能と ISO 56002 — 再設計ドラフト（FR-39 の ISO 対応を置換）

> 状態: **ドラフト（2026-09-15 セッションで方向合意・詳細レビュー待ち）**。本書は [FR-39 設計ドラフト](FR-39_クエスト最終結果_ISO56002.md)／[FR-39 設計意図](FR-39_ISO56002との関係と設計意図.md) の **ISO 対応マッピングを見直し・置換**する。
> **なぜ置換するか**＝前回は「アイデア＝②コンセプト創造／評価5観点＋選定＝③検証」と置いたが、再考の結果 **「ピア採点＋選定は“選別（screening）”であって、前提を証拠で de-risk する ISO③コンセプト検証ではない」** と判断した（ユーザー明言）。真の検証（前提の証拠検証・採算 viability・複数コンセプトの競合）を独立させる方が ISO56002 に忠実で、価値実現の確度が上がる。
> **実装済み機能も見直し対象**（SC-12「🏁 結果」タブ・`QuestResultTab.tsx`・`quest_outcomes` 等）。
> 参照表記は [ドキュメント作成規約](../規約/ドキュメント作成規約.md) に準拠。ISO 56002 の節は「ISO56002 §x」と明記（本プロジェクト文書の §x と区別）。関連＝[要件定義 README](../要件定義/README.md) FR-39・[データモデル](../データモデル.md) §5.32／§5.30・[SC-12 クエスト詳細](../画面設計/screens/SC-12_クエスト詳細.md) §4.5・[API設計 C](../API設計/C_クエスト・パーティー・権限.md) C.8。

## 0. 要旨（何を変えるか）

| | 旧（現・正本 FR-39） | 新（本ドラフト） |
|---|---|---|
| アイデア（現行アプリ） | ② コンセプトの創造 | **① 機会の特定 ＋ アイデアの発散・選別**（②③には未到達） |
| 評価5観点＋選定 | ③ コンセプトの検証 | **選別（screening）**＝有望アイデアの絞り込み |
| クエスト最終結果 | 検証済みコンセプト票（④への橋） | **アイデア選別の申し送り＝コンセプト段の入力**（改称・再定義。削除しない） |
| コンセプト創造・検証 | （アイデア/評価が兼ねる） | **新「コンセプト段」が担う**（②＋③） |
| ソリューション開発・導入 | ④⑤＝将来拡張 | ④⑤＝将来拡張（変わらず） |

→ 変わるのは主に**言葉と位置づけ**＝現行のアイデア/投票/チャット/評価/選定の機構はそのまま活き、「機会を掘り有望アイデアを**選別**する段」と再定義する。FR-39 の「検証済みコンセプト票」は**新コンセプト段への申し送り**に読み替える。

## 1. 新しい ISO 56002 対応マップ

ISO56002 §8.3 のプロセス「① 機会の特定 → ② コンセプトの創造 → ③ コンセプトの検証 → ④ ソリューションの開発 → ⑤ 導入（価値の実現）」に対し、ideaquest を **アイデア段 → コンセプト段** の2段構えで載せる。

| ISO56002 工程 | ideaquest の段・活動 | 成果物 |
|---|---|---|
| ① 機会の特定 | クエスト作成（テーマ・目的） | クエスト |
| （①→②の橋） | **アイデア段**＝アイデア投稿・チャット・投票・評価・**選定**（＝発散と選別） | 選別済みアイデア（申し送り） |
| ② コンセプトの創造 | **コンセプト段**＝選別アイデアから価値の指針を定め“解の候補”を記述 | コンセプト（候補・複数可） |
| ③ コンセプトの検証 | 同段＝**前提の証拠検証・採算(viability)・複数コンセプトの競合と選定** | 検証済みコンセプト（Go/Pivot/Kill） |
| ④ ソリューションの開発 | 将来拡張（別段/別ツール） | — |
| ⑤ 導入・価値の実現 | 将来拡張 | — |

> ISO56002 §9（パフォーマンス評価）・§10（改善）は両段に横断（検証記録・振り返り）。

## 2. アイデア段（現行アプリ）の再定義

- 現行の `ideas`／投票／`chat`／`evaluations`／`is_selected` は**そのまま**「機会を掘り、有望アイデアを選別する」段として活きる。**機構は無変更**。
- 変わるのは**用語と位置づけ**：評価5観点＋選定＝「③検証」ではなく**選別**。FR-39 の結果票＝**選別結果の申し送り**（＝コンセプト段の入力）。
- **連結 seam は既存**＝FR-39 §2.2/§3 の「次アクションから複製で後続クエストを起票」が、そのまま**アイデア段 → コンセプト段への引き継ぎ**になる（後述 §5 で正本化方針）。

## 3. コンセプト段（新機能）

### 3.1 入力
- クエストの**選別済みアイデア（任意数）**＋その結果タグを持ち越す。**複数アイデア → 収束**。

### 3.2 コンセプト⇄ソリューションの境界（確定）
コンセプト＝「この方向で・誰のために・どんな価値で作る価値があるか＋採算が合うか、を**経営が次段へ投資判断できる**まで証拠で固める」。ソリューション＝「何をどう作るか＋計画」。

| | コンセプト（本機能） | ソリューション（後段・将来） |
|---|---|---|
| 狙う価値・対象 | ✅ | — |
| 競合・位置づけ | ✅ 方針 | 詳細分析 |
| 解の形態/方向 | ✅ ＋**必要な能力の粗いスケッチ**（“X ができること”レベル） | ❌ |
| 機能の詳細・機能数・仕様 | ❌ | ✅ |
| 前提の検証 | ✅ 前提→方法→結果→判定（de-risk） | 実装後の実地検証 |
| 採算・事業性(viability) | ✅ コスト/収益モデル/ROI（**必須**） | 詳細見積り・収支計画 |
| 計画書 | ❌ | ✅ |
| 判定 | ✅ Go/Pivot/Kill＋根拠 | 開発可否・優先度 |

**なぜ**＝機能数・計画まで抱えるとソリューション開発（別物・肥大化）になる。コンセプトは「投資判断に足る証拠」で止める。

### 3.3 コンセプト成果物スキーマ（第一版）
- **由来**：選別済みアイデア（複数）＋結果タグ
- **課題・機会**
- **狙う価値（価値提案）＋対象**（ユーザ／既存顧客／市場）
- **競合・差別化**
- **解の形態＋必要な能力（粗）**
- **前提と検証**：`{前提, 検証イベント[{検証方法, 結果, 判定(支持/反証/保留), 検証実施日, 規模}]}` × 複数（クエスト単位で共有・重要度はコンセプト毎・§3.5）
- **採算・事業性(viability)**：コスト・収益モデル・ROI（**必須**・経営説得の核）
- **総合判定**：Go / Pivot / Kill ＋根拠

### 3.4 複数コンセプト＋選定（ISO 標準）
1 つのアイデア群から **N 個の候補コンセプト**を立て、各々が同じループ（§3.7）を回り、**評価者/owner が勝ち残りを選定**して（将来の）ソリューション段へ昇格。**投票・評価・結果タグはコンセプト単位**（チャットのみ分割・§3.7）。

### 3.5 前提と検証（ISO③ の実体・複数コンセプトで共有可）
各前提を `前提 → 検証（検証方法・結果・判定・検証実施日・規模）` で記録。**判定＝支持／反証／保留**。反証は方向の pivot/kill に繋がる（**否定結果こそ価値＝筋の悪い方向を早く殺す**・ISO56002 §8.3/§9）。
- **検証の記録＝検証イベント**：1 前提に**検証イベントを 1 件以上**持つ（`検証方法・結果・判定・**検証実施日**・**規模（サンプル数/対象の記述）**`）。前提の現在の判定＝最新イベント。**検証実施日と規模を必ず残す**理由＝(a) **エビデンスは古びる**（実施日が古い前提は再検証を促す・ISO56002 §9 継続的モニタリング）、(b) **規模＝検証の強さ**（n=3 と n=50 は重みが違う＝§3.6「前提検証の強さ」の材料）。再検証は**新イベント追記**で履歴が残る（なぜ・いつ判定が変わったか辿れる）。記録の作成/更新時刻は別途監査列。
- **前提・検証は第一級エンティティ（クエスト＝イニシアチブ単位の“検証プール”）として持ち、コンセプトへ M:N でリンク**する。同じアイデア群から競合する複数コンセプトは**同じ前提（市場・対象・技術実現性など）を共有**しがちで、**一度の検証（ヒアリング等）を複数コンセプトで再利用**できる（DRY・ISO56002 §7 知識/エビデンスは組織資産）。**共有前提とコンセプト固有前提の両対応**。
- **リンクに“重要度（criticality）”を任意で持たせる**＝同じ前提でも「このコンセプトにとって致命的か／補助的か」はコンセプトごとに異なるため（評価・判定の重み付けに使う）。**エビデンス（方法/結果/判定）は単一ソース（共有）、重要度はリンク単位**。
- **反証は全リンク先へ波及**：共有前提が反証に転じたら、**リンクする全コンセプト**の評価を **「要再評価（stale）」にマーク**し、各**作成者＋評価者へ通知**（評価者は再評価可）。1 情報インプットの反証（§4）→ 1 前提 → 複数コンセプト、と波及が繋がる。
- **編集権限**：共有前提は複数コンセプトに影響するため、編集は**検証プール所有（クエスト owner/quest_admin 等）に寄せる**（個別コンセプト owner が他コンセプトの根拠を勝手に変えない）。

### 3.6 評価者の評価観点（コンセプト版・仮採用）
| 観点 | 見るもの |
|---|---|
| 望ましさ (desirability) | 狙う価値が明確・対象が本当に欲しがるか（検証の裏付け込み） |
| 実現可能性 (feasibility) | 形態・必要能力が現実的か |
| 採算・事業性 (viability) | コスト/収益モデル/ROI が筋か |
| 前提検証の強さ | 主要な前提が“証拠で”検証されているか（言い張りを弾く・ISO 固有ゲート） |
| 差別化 | 競合に対する位置づけ |

＋各観点スコア＆コメント、**評価者の Go/Pivot/Kill 推奨**。複数コンセプトが競うので、評価は**候補比較・選定の道具**も兼ねる。結果タグ＝選定コンセプトの要約＋Go 判断。

### 3.7 チャット構成（コンセプトは多面的なので複数ルーム）
- **総合ルーム（1・必須）**＝横断議論＋最終 Go/Pivot/Kill の場（アイデアの単一ルームに相当する母屋）。
- **グループ・ルーム（3〜5）**＝意味の束で分ける（例〔価値・対象・競合〕〔解の形態〕〔採算〕）。**項目単位にはしない**（断片化回避）。
- **前提と検証＝前提 1 件＝1 スレッド**（前提→方法→結果→判定に紐付く）。
- **未読/メンション/活発度はコンセプト単位でロールアップ＋各ルーム個別**の二段。
- **データモデル**＝チャットは **親（コンセプト）× スコープ（グループ）** に属す。スコープは**小さな固定集合＋前提スレッド**に限定（自由増殖させない）。
- 軽量代替（不採用寄り）＝1 ルーム＋セクションタグ。

### 3.8 ループ機構は一般化して共有
チャット議論／投票／評価／結果タグ／版管理／通知／realtime の**機構はアイデアと同型**＝一般化して共有（DRY・[コーディング規約](../規約/コーディング規約.md) §2.3）。**別途設計するのは中身**（§3.3 の入力項目・議論観点・評価観点）。将来のソリューション段でも同機構を再利用できる。

## 4. 情報インプット機能との連携（別ドメイン・要約）

情報インプット（外部 WEB 情報を**手動貼り付け**で登録→属性付与→関連リンク）は、アイデア/コンセプトを能動的に駆動する知識レイヤ＝差別化の芯。詳細は別メモに切り出す（本書は連携点のみ）。
- **info ↔ アイデア/コンセプトのリンクは種別付き**＝**関連（中立）／裏付け（supporting）／反証・脅威（challenging）**。
- **反証リンク → 対象に flag＋通知**（§3.5 の再評価と接続）＝「この情報が前提を揺るがすかも」。
- **属性 `情報分類` は複数値**（マルチタグ）。うち **`自社技術・ナレッジ`** は高価値な一値＝作成時に**実現可能性ヒント**として優先サジェスト。
- **MVP の動作（明確化）**：
  1. **自動・動的リンク**＝ワードクラウド/キーワードの**一致度が高い info は、アイデア/コンセプト画面に自動で関連リンクを動的に表示**（種別の既定＝**関連（中立）**）。再計算は info 追加やアイデア/コンセプト保存など関連変化時。**閾値＋上位 N** で件数を抑える。自動リンクは低コミット＝**通知は出さない**（ノイズ許容）。
  2. **種別は後から手動変更**＝人がそのリンクを**裏付け／反証・脅威**へ変更（→反証なら §3.5 の通知＋要再評価が発火）。
  3. **任意リンクの手動追加**＝自動で拾われない info も、人が**任意にアイデア/コンセプト（や前提）へ手動リンク**できる（＋不要な自動リンクは棄却可）。
  4. **Phase2**＝矛盾（反証・脅威）の**自動検出**（意味解析／将来 LLM・コスト/データ保護判断つき）。
- **⚠️ 実装漏れ防止（2026-09-21・関連リンク対象ピッカー）**：SC-50 情報インプットの**関連リンク対象ピッカー**（対象を検索して選ぶ専用ダイアログ・見本＝`style-guide.html`「10d」）は、**現時点で `ideas`／`quests` のみ実装**（backend `app/tenant/info/repository.py::search_link_candidates` が ideas/quests だけを検索し、`concepts`/`assumptions` は `else: return []`＝未実装ドメインのため空を返す）。**コンセプト段を実装する時に、関連リンクの対象へ `concepts`（コンセプト）と `assumptions`（前提）を必ず追加すること**。具体的には次を漏れなく対応する：
  1. backend `search_link_candidates` の `concepts`/`assumptions` 分岐を実装（concept/assumption テーブルをタイトル検索＋文脈メタ＝由来クエスト等を返す）。
  2. 対象ピッカーの**種類チェックボックス**に「🧩コンセプト／📌前提」を有効化、**コンセプト絞込**（クエスト絞込と同型）を実運用に接続。
  3. `InfoLinkCandidateDTO` の文脈メタ（由来クエスト・状態・期限相当）を concept/assumption でも返す。
  4. 対象解決（`add_link` の target_id 解決）を concept/assumption へ拡張。
  - 型・ラベルは既に `InfoLinkTarget`（frontend types.ts）と `LINK_TARGET_VALUES`（backend schemas.py）に 4 種とも定義済み＝**器はあるが中身（検索/解決）が未実装**の状態。ピッカー UI も 4 種を出す口を持つ（現状 concepts/assumptions は候補ゼロ）。

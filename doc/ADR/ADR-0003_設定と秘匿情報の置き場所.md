# ADR-0003 設定と秘匿情報の置き場所（.env の管理項目・メール(SMTP)設定）

- ステータス: **確定（2026-08-09 ユーザー承認）** / 値・項目は運用で調整可
- 対象: バックエンド全体の設定管理方針。とくに**メール送信(SMTP)設定を `.env`（環境変数）に置き、DB には置かない**ことの確定と、`.env` で管理する項目の明文化。
- 関連: [`../規約/コーディング規約.md`](../規約/コーディング規約.md)（§2.3 DRY・§3.5 意図的選択）・[`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.5（メール送信基盤）・[`ADR-0001_認証・セッション基本パラメータ.md`](ADR-0001_認証・セッション基本パラメータ.md)・[`../データモデル.md`](../データモデル.md) §4.4（アダプタ抽象化）・§14（ブートストラップ `BOOTSTRAP_ADMIN_PASSWORD`）・[`../要件定義/README.md`](../要件定義/README.md)（メール送信基盤は TBD）

> 目的＝「SMTP サーバ設定を `.env` に書くか DB に持つか」という問いに決着をつけ、あわせて **`.env` で管理する項目**（何を env に置くか・どれが秘匿か・本番での供給方法）を1箇所に明文化する。
> 個々の値の根拠（TTL・レート制限など）は各 ADR / API 設計が正。本 ADR は**置き場所と供給方法**の方針を担う。

---

## 1. コンテキスト

- 現状、設定は `impl/backend/app/core/config.py` の `Settings`（pydantic `BaseSettings`）が**環境変数から**読む。`.env` は `.gitignore` で追跡外（`impl/.env.example` が既定値のひな形）。compose が env を組み立ててコンテナへ渡す。
- メール送信（[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.5）は `dev=MailHog / prod=SMTP` をポート（`MailSender`）で抽象化。接続先は `SMTP_HOST/SMTP_PORT`、差出人は `MAIL_FROM`。
- 「この SMTP 設定をどこに置くか（`.env` か DB か）」が未確定だった。マルチテナント（管理DB1＋会社DB N）ゆえ「会社ごとに変える設定は DB」という筋があり、SMTP がそれに該当するかを判断する必要がある。

## 2. 決定

### 2.1 原則＝「設定は“何の軸で変わるか”で置き場所を決める」

- **デプロイ環境で変わる**（dev/stg/prod・接続先・秘密）→ **環境変数（`.env` / 本番はシークレットマネージャ）**。
- **テナント（会社）で実行時に変わる**（会社属性・業務データ・`mfa_required` 等）→ **DB**。

理由＝env は「プロセス起動時に環境が与える1組の値」、DB は「実行時にテナント/エンティティ単位で引く値」。混同すると、環境依存値を DB に入れて起動前依存の循環を作る／テナント値を env に入れてマルチテナントを壊す、のいずれかになる。

### 2.2 [採用] メール(SMTP)設定は `.env`（環境変数）。DB には置かない

SMTP は 2.1 の**デプロイ環境軸**に属する。根拠:

1. **設計上プラットフォーム共通の単一基盤**＝全設計文書が `dev=MailHog / prod=SMTP（SES 等）` と記し、**会社ごとに別 SMTP** の記述は無い（[`要件定義 README`](../要件定義/README.md)「メール送信基盤(SMTP/送信サービス)は TBD」＝**選定**が未決なだけで単一基盤前提）。`password-setup/request` も会社DBに触れずコントロールプレーンで送信する。
2. **秘匿情報を含む**＝本番 SMTP は通常ユーザ名/パスワードや API キーを伴う。これをアプリDBの行に平文で置くのは秘匿管理の原則に反する（→ 2.4 のシークレットマネージャで供給）。
3. **ブートストラップ依存の回避**＝メール送信は初期セットアップ（初回PW設定・[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md)）で必要になり得る。その設定自体を DB に置くと障害時のブラスト半径が広がり、循環依存も生む。

### 2.3 [採用] `.env` で管理する項目（カタログ）

`Settings`（`config.py`）と compose が受け渡す環境変数を、**秘匿/非秘匿**で分類する。**秘匿は本番でシークレットマネージャ供給（2.4）**、非秘匿は環境ごとの構成値。

**A. 秘匿（Secret・本番はシークレットマネージャ経由・`.env` には dev 用の弱い値のみ）**

| 変数 | 用途 | 備考 |
|---|---|---|
| `POSTGRES_PASSWORD` | DB 接続パスワード | dev は `ideaquest` |
| `SMTP_USER` / `SMTP_PASSWORD` | 本番 SMTP 認証（**将来追加**） | 現 MailHog は認証なしのため未使用。prod SMTP 選定時に `Settings`＋`.env.example` へ追加 |
| `BOOTSTRAP_ADMIN_PASSWORD` | 最初の system_admin 初期PW（[`データモデル`](../データモデル.md) §14 案(a)・**運用/将来**） | ハードコード既知PW禁止＝必ず供給された強い秘密 |

**B. 非秘匿（環境依存の構成値・`.env` / compose 既定で可）**

| 変数 | 用途 |
|---|---|
| `APP_ENV` | 実行環境（`dev`/`prod` 等） |
| `POSTGRES_HOST` / `POSTGRES_PORT` / `POSTGRES_USER` / `CONTROL_DB_NAME` | DB 接続（パスワード以外） |
| `REDIS_URL` | Redis 接続 |
| `SMTP_HOST` / `SMTP_PORT` | メール送信先（dev=`mailhog:1025`） |
| `MAIL_FROM` | 差出人アドレス（既定 `no-reply@ideaquest.example`） |
| `APP_BASE_URL` | メールリンクの基点（フロントの `password-setup` を開く） |
| `ALLOWED_ORIGINS` | CSRF/Origin 許可リスト |
| `COOKIE_SECURE` | Cookie の Secure 属性 |
| `SESSION_IDLE_TTL_SECONDS` / `SESSION_ABSOLUTE_TTL_SECONDS` | セッション TTL（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md)） |
| `LOGIN_RATE_LIMIT_MAX` / `LOGIN_RATE_LIMIT_WINDOW_SECONDS` | ログインのレート制限（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6） |
| `PASSWORD_SETUP_TTL_SECONDS` | 設定リンク TTL（[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md)） |
| `PW_REQUEST_RATE_LIMIT_MAX` / `PW_REQUEST_RATE_LIMIT_WINDOW_SECONDS` | `request` レート制限（[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.3） |

**compose/ホスト側のみ（アプリ `Settings` は読まない・ポート公開やひな形用）**: `DB_PORT` / `REDIS_PORT` / `BACKEND_PORT` / `FRONTEND_PORT` / `MAILHOG_SMTP_PORT` / `MAILHOG_UI_PORT`。

> 運用ルール: **秘匿値の実体は `.env`（dev 専用・`.gitignore` で追跡外）にのみ置き、リポジトリには `.env.example`（ダミー/既定）だけをコミット**する。新しい設定を足すときは `Settings`・`.env.example`・compose の三点を揃える（drift 防止）。

### 2.4 [採用] 本番の秘匿値供給＝シークレットマネージャ経由（`.env` 平文ファイルは dev 限定）

- **受け渡し方式は env のまま**（アプリは環境変数を読むだけ・コード不変）だが、**値の供給元**を環境で替える:
  - **dev** = 平文 `.env` ファイル（compose が読む・追跡外）。
  - **本番** = シークレットマネージャ（AWS Secrets Manager / SSM SecureString、GCP Secret Manager、HashiCorp Vault、K8s Secrets+KMS 等）が**実行時にプロセスへ環境変数として注入**。暗号化保管・アクセス制御・監査・ローテーション・バージョニングが付く。
- **平文 `.env` ファイルを本番サーバへ置かない**（ディスク流出・バックアップ混入・権限管理難・手動ローテーションの回避）。具体的なマネージャ製品の選定はインフラ確定時（TBD・[`要件定義 README`](../要件定義/README.md)）。

### 2.5 [委譲・将来] 会社ごとのメール設定（BYO-SMTP / ブランディング）

将来 **会社ごとに差出人 identity・Reply-To・テンプレート/ブランディング・（BYO 時の）接続先** を変えたい要件が出た場合のみ、それら**テナント設定**を DB に持つ拡張を別 ADR で検討する。ただしその場合でも **接続の秘匿値（PW/APIキー）は暗号化またはシークレットストア参照**とし、生値をテーブルに置かない。現行 MVP は**プラットフォーム共通の単一基盤**（文言も暫定・i18n 後続）ゆえ**対象外**。今 DB 化するのは早すぎる一般化（[`コーディング規約`](../規約/コーディング規約.md) §2.3・§3.5）。

## 3. 検討した代替案（不採用）

- **SMTP 設定を DB（テナント設定 or グローバル設定テーブル）に置く**＝不採用。2.2 のとおり環境軸の設定・秘匿値を含む・ブートストラップ依存を生む。会社ごとに変える要件も現状無い（2.5 で将来委譲）。
- **本番も平文 `.env` ファイルで運用**＝不採用。流出・バックアップ混入・ローテーション運用のリスク（2.4）。
- **秘匿値をコード/リポジトリに直書き**＝不採用（論外・[`セキュリティ対策一覧`](../WEBアプリ開発時のセキュリティ対策一覧.md)）。

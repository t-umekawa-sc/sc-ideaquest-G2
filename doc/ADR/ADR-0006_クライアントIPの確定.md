# ADR-0006 クライアント IP の確定（信頼プロキシ・転送ヘッダ）

- ステータス: **確定（2026-08-10 ユーザー承認）** / 値は運用で調整可（env）
- 対象スライス: ドメイン A の**横断基盤**＝`POST /auth/login`・`POST /auth/password-setup/request` が使う「クライアント IP」の求め方。**backend のみ**（応答・契約は不変）。
- 関連: [`ADR-0001_認証・セッション基本パラメータ.md`](ADR-0001_認証・セッション基本パラメータ.md)（§2.6 (IP+login_id) レート制限）・[`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md)（§2.3 (IP+company_code+login_id) レート制限）・[`ADR-0005_アカウント一時ロック.md`](ADR-0005_アカウント一時ロック.md)（§2.2 (IP+login_id) ロック）・[`ADR-0003_設定と秘匿情報の置き場所.md`](ADR-0003_設定と秘匿情報の置き場所.md)（設定は env）・[`../WEBアプリ開発時のセキュリティ対策一覧.md`](../WEBアプリ開発時のセキュリティ対策一覧.md)（§206 転送ヘッダの信頼範囲を限定）・[`../本番デプロイ要件.md`](../本番デプロイ要件.md)（本 ADR が課すデプロイ側の保証）

> 目的＝ログインのレート制限（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md)/[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md)）とアカウント一時ロック（[`ADR-0005`](ADR-0005_アカウント一時ロック.md)）が **(IP+…) 単位**で成り立つ前提＝「backend が見る IP が実クライアント IP であること」を保証する方式を確定する。設計方針（列挙耐性・DoS 回避＝(IP+login_id) 単位）は各 ADR が正で、本 ADR は**その前提を満たすための IP 確定ロジック**を埋める。

---

## 1. コンテキスト（なぜ必要か＝現状の欠陥）

- 本アプリのブラウザ経路は **同一オリジンのリバプロ／薄い BFF 経由**（[`API設計/README.md`](../API設計/README.md) §15/§36＝`Web(リバプロ)＋Next.js(rewrite)＋FastAPI`）。dev では Next.js の `rewrites()` が `/api/v1/*` を backend へプロキシする。
- backend は IP を `request.client.host`（**直近ピア**）で取っていた（`router.py`）。uvicorn は `--proxy-headers` 無しで起動。
- 結果＝**全ブラウザ経由リクエストの `client.host` がプロキシの IP に潰れる**。`(IP+login_id)` が `(固定プロキシIP+login_id)` ＝実質 **login_id 単位（アカウント全体）** に縮退し、
  - [`ADR-0005`](ADR-0005_アカウント一時ロック.md) §2.2 が「可用性 DoS」として**明示的に不採用にした account 単位ハードロックと同じ挙動**になる（どの IP からでも 5 回失敗で本人を締め出せる）。
  - [`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md)/[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md) の (IP+…) レート制限も同様に縮退する。
- 既存テストが緑なのは `TestClient` が app へ直接当たり IP を差し替えられるため＝**実配線を通らず縮退を検知できていなかった**。
- セキュリティ一覧 §206「プロキシ配下では転送ヘッダーを信頼する範囲を限定する」は、**転送ヘッダ（XFF）を信頼できるプロキシからのみ・範囲限定で採用する**ことを要件化しており、現状は未達。

## 2. 決定

### 2.1 [採用] 「信頼プロキシのホップ数」から実クライアント IP を確定（アプリ層・env）

`X-Forwarded-For`（XFF）を **右から数えて `trusted_proxy_count` ホップ分は自陣のプロキシ**とみなし、その 1 つ外側（＝クライアント側）の値を実クライアント IP とする。**左端固定取得は採らない**（クライアントが XFF 先頭を詐称できるため・§3）。

- **env**: `trusted_proxy_count`（既定 **0**）。0＝プロキシ無し（直アクセス／テスト）＝`request.client.host` をそのまま使う。
- **確定ロジック（純粋関数）**: `chain = XFF をカンマ分割 + [直近ピア]` とし、`idx = len(chain) - 1 - trusted_proxy_count` の要素を返す。`idx < 0`（XFF が想定より短い＝設定過大 or 直アクセス）は**安全側で最外（`chain[0]`）**にフォールバック。
  - 例（`trusted_proxy_count=1`・XFF は最外プロキシが「受け取ったピア」を付与）: `XFF="203.0.113.9"`, peer=`P1` → `chain=["203.0.113.9","P1"]` → `idx=0` → `203.0.113.9`。
  - 詐称例: クライアントが `XFF="1.2.3.4"`（偽）を送っても、正しく設定されたプロキシが**実ピアを付与/上書き**する限り、右から数えるため偽値は無視される（§3・デプロイ要件で担保）。
- **配置（DRY）**: 純粋関数 `resolve_client_ip(peer_ip, forwarded_for, trusted_proxy_count)` を `core/net.py` に、リクエスト束縛の薄いラッパ `get_client_ip(request)` を `core/deps.py` に置き、**`login` と `password-setup/request` の両方で共用**（意図的選択・コーディング規約 §3.5／DRY §2.3）。

### 2.2 [採用] 既定は 0（フェイルセーフ）＋本番は必須設定＋起動時ガード

- 既定 **0** は「直アクセス／テストで壊れない」安全側。ただし**本番で 0 のままだと §1 の縮退が残る**ため、これはデプロイ側の必須設定とする（[`../本番デプロイ要件.md`](../本番デプロイ要件.md)）。
- **起動時ガード（採用）**＝`APP_ENV=prod` かつ `trusted_proxy_count=0` の場合は**起動ログに警告**を出す（設定漏れの早期検知）。ハードエラーにはしない（例外的な直結構成もあり得るため）。

### 2.3 [採用] 実クライアント IP の“正しさ”はデプロイ側で担保（案 C を本番要件化）

アプリ層のホップ数解釈が正しく効くには、**最外の信頼プロキシが XFF を確定させる**必要がある。[`../本番デプロイ要件.md`](../本番デプロイ要件.md) に次を必須要件として記載する:

- 最外リバプロは**クライアント由来の `X-Forwarded-For`/`X-Real-IP` を上書き（またはクライアント値を破棄して自分が受けたピアを付与）**する。
- backend 手前の**信頼プロキシ段数と `trusted_proxy_count` を一致**させる。
- 可能なら `/api/v1/*` を**エッジから FastAPI へ直結**（Next.js を API データ経路から外す）とホップ数が 1 に固定でき、Next の XFF 転送挙動に依存しなくて済む。

## 3. 検討した代替案（不採用）

- **uvicorn `--proxy-headers` ＋ `--forwarded-allow-ips`**＝不採用（第一候補だったが）。取り出し位置が版依存で**なりすまし耐性が曖昧**、`forwarded-allow-ips` を広く取ると XFF 詐称で任意 IP を名乗れる。アプリ層の明示的ホップ数解釈のほうが**テスト可能**でレビューしやすい（本アプリの test-first 方針に合う）。将来 uvicorn 前段を固定できるなら併用可。
- **XFF の左端（最初の値）を実クライアントとする**＝不採用。左端はクライアントが自由に詐称できる（プロキシは通常「追記」するため偽値が残る）。右から信頼ホップ分を数える方式なら詐称を無視できる。
- **IP を使わず account 単位でロック/制限**＝不採用（[`ADR-0005`](ADR-0005_アカウント一時ロック.md) §2.2 の DoS 回避と矛盾）。

## 5. 残課題 / 既知の限界

- **dev（compose）で Next.js の `rewrites()` が XFF を転送するかは未検証**＝転送しない場合、dev では実ブラウザ IP を得られない（`trusted_proxy_count` を上げても Next の IP が最外になる）。dev のレート制限/ロックは縮退したままでも許容（保護対象は本番）。本番は §2.3 でエッジ確定を必須化して回避する。
- **分散 IP 総当り**＝IP 単位の原理的限界（[`ADR-0005`](ADR-0005_アカウント一時ロック.md) §2.2 と同じ）。本 ADR は「実 IP を正しく得る」までで、IP 分散攻撃自体の対策は別（将来の異常検知）。

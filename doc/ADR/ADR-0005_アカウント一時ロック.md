# ADR-0005 アカウント一時ロック（ログイン連続失敗）基本パラメータ

- ステータス: **確定（2026-08-09 ユーザー承認）** / 値は運用で調整可（env・下記 [採用] 参照）
- 対象スライス: ドメイン A のログインハードニング＝`POST /auth/login` の連続失敗に対する一時ロック（第二層防御）＋ロック通知メール。**backend のみ**（frontend への応答は既存の一律 401 のまま変わらない）。
- 関連: [`../API設計/A_認証・セッション.md`](../API設計/A_認証・セッション.md)（A.0/A.1・列挙耐性/総当り対策の正）・[`ADR-0001_認証・セッション基本パラメータ.md`](ADR-0001_認証・セッション基本パラメータ.md)（§2.6 委譲元・(IP+login_id) レート制限）・[`ADR-0004_MFA・信頼端末基本パラメータ.md`](ADR-0004_MFA・信頼端末基本パラメータ.md)（§2.5 委譲元・OTP 失敗上限）・[`ADR-0003_設定と秘匿情報の置き場所.md`](ADR-0003_設定と秘匿情報の置き場所.md)（設定は env）・[`../WEBアプリ開発時のセキュリティ対策一覧.md`](../WEBアプリ開発時のセキュリティ対策一覧.md)

> 目的＝[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6・[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) §2.5 で「後続 ADR へ委譲」とされた**アカウント一時ロック**の方式・具体値・応答・解除経路・保持先を確定する。既存の (IP+login_id) レート制限（10回/5分＝429・[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6）と OTP 失敗上限（5・[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) §2.1）の上に載る**第二層**として設計する。
> 方針（列挙耐性＝一律 401・固定化対策・pre-auth 分離）は A.0/A.1 が正で、本 ADR はそれを**変更せず**ロックの具体を埋める（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md)/[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) と同じ役割）。

---

## 1. コンテキスト

[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6 は「アカウント一時ロック（連続失敗 N→T 分・解除経路）」を、**列挙耐性との衝突**（実在アカウントだけロックすると存在が漏れる）・**DoS 悪用**（他人 ID を故意に失敗させてロック）・**解除経路**（自動/管理者/PW 再設定）・**OTP 連続失敗との連動**を理由に MFA/ハードニングスライスへ委譲していた。MFA コア（[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md)）が縦に通ったため、本 ADR でロックを確定する。

現状の一次防御＝`login_fail:{ip}:{login_id}` の固定窓（10回/5分→429・[`security.py`](../../impl/backend/app/core/security.py) `check_login_rate_limit`）と、MFA verify の OTP 失敗上限（5＋pre-auth 失効）。本 ADR はこれらを置換せず**追加**する。

## 2. 決定

### 2.1 [採用] ロックのしきい値・期間は env（DB 不採用）

[`ADR-0003`](ADR-0003_設定と秘匿情報の置き場所.md) §2.1（デプロイ環境軸→env）に従い、既存のレート制限しきい値と同じく `config.py`（env・非秘匿＝[`ADR-0003`](ADR-0003_設定と秘匿情報の置き場所.md) §2.3 B 群）に置く。会社別に変える要件は無い。

**[採用]（2026-08-09 ユーザー確認・運用で調整可）**:

| env 変数 | 意味 | 既定 |
|---|---|---|
| `login_lock_max_attempts` | ロックまでの連続失敗回数（窓内） | **5** |
| `login_lock_ttl_seconds` | ロック期間＝連続失敗の計数窓 | **900（15分）** |
| `login_lock_notify_cooldown_seconds` | 同一アカウントへのロック通知メールの最小間隔 | **3600（60分）** |

### 2.2 [採用] ロックは (IP+login_id) 単位（アカウント全体はロックしない）

失敗計数もロックも既存レート制限と同じ **(IP+login_id)** 単位にする。**アカウント全体（account 単位）のハードロックは採らない**。

> **前提（重要）**＝ここでいう「IP」は**実クライアント IP**でなければ本節の DoS 回避が成立しない。リバプロ/BFF 配下では backend が見る IP がプロキシに潰れ得るため、IP の確定は [`ADR-0006_クライアントIPの確定.md`](ADR-0006_クライアントIPの確定.md)（信頼プロキシ段数）と [`../本番デプロイ要件.md`](../本番デプロイ要件.md) §1 で担保する。

- **理由（DoS 対策の根幹・ユーザー選択 2026-08-09）**＝account 単位ロックは、攻撃者が被害者の login_id を故意に失敗させるだけで**本人を締め出せる**（可用性 DoS）。(IP+login_id) 単位なら、ロックされるのは**攻撃元 IP からの当該 ID への試行だけ**で、被害者本人（別 IP）のログインは妨げない。列挙耐性とも両立する（下記 §2.3・存在に依らず同じ挙動）。
- **トレードオフ（明示）**＝分散 IP からの低速総当りには (IP+login_id) 単位は原理的に弱い。ここは第一層のレート制限・OTP・（将来の）異常検知で補う。単一 IP からの総当りには本ロックが効く。
- **計数の意味**＝`login_fail_streak:{ip}:{login_id}` を**認証失敗のたびに +1**（窓 TTL＝`login_lock_ttl_seconds`）。`login_lock_max_attempts` に達したら `login_lock:{ip}:{login_id}`（TTL＝`login_lock_ttl_seconds`）を張り、streak をリセット。**認証成功で streak と lock を削除**（成功試行はカウントしない）。
- **ロック TTL は据え置き**＝ロック中の追加試行では lock の TTL を延長しない（[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) §2.2 pre-auth と同じ思想）。攻撃者がロックを無限延長できないようにする＝ロックは発火から固定 15 分で必ず解ける。

### 2.3 [採用] ロック中の応答は「常に一律 401 unauthenticated」

ロック中でも応答は**通常の誤資格と同一の 401 `unauthenticated`**（`Retry-After` も残時間も返さない）。

- **理由（列挙耐性・ユーザー選択 2026-08-09）**＝423/429＋残時間を返すと「そのアカウントが存在し、かつロックされている」ことを攻撃者に漏らす。一律 401 なら攻撃者への信号はゼロ（A.1 の「照合失敗・不在・未設定は一律 401」と一貫）。
- **本人へのフィードバックは別経路（§2.4 通知メール）で回復**する。一律 401 が奪う「本人への気づき」だけを out-of-band で補う。
- 評価順序＝`check_login_rate_limit`（10回/5分→429・既存の粗い上限）→ **lock 判定（ロック中なら即 401）** → 資格照合。ロック中は資格照合に到達しない（タイミングを一定化するためダミー照合の扱いは実装で A.1 に合わせる）。

### 2.4 [採用] ロック通知メール（本人へ out-of-band・実在アカウントのみ・スロットルあり）

ロックが**発火した瞬間**（streak が閾値に達し lock を新規に張った時）に、当該 login_id が実在・active なら本人メールへ通知する。

- **列挙耐性を壊さない理由**＝メールは本人の受信箱に届く out-of-band 通知で、攻撃者（別人）は観測できない。宛先が無ければ**黙って何もしない**（応答は一律 401 のまま・存在は漏れない）。
- **必須のスロットル（メール爆撃対策）**＝ロックが何回発火しても、同一アカウントへの通知は `login_lock_notify_cooldown_seconds`（既定 60分）に**1通**まで（キー `lock_notified:{account_id}` に TTL）。これが無いと (IP+login_id) 単位ゆえ IP を回されて通知自体が嫌がらせ手段になる。ロック期間ごと（15分）ではなくアカウント単位クールダウン（60分）で律速。
- **本文は汎用**＝「あなたのアカウントで多数のログイン失敗があり一時的に制限しました。心当たりが無ければパスワードを再設定してください」。攻撃元 IP・MFA 有無・回数などの詳細は載せない。既存の [`MailSender`](../../impl/backend/app/infra/mail.py)`.send(to, subject, body)` を再利用（[`ADR-0003`](ADR-0003_設定と秘匿情報の置き場所.md) の SMTP 設定）。

### 2.5 [採用] 解除経路＝(a) 15分自動解除 ＋ (b) PW 再設定成功で即解除

- **(a) 自動解除**＝Redis の TTL（`login_lock_ttl_seconds`）で自然失効。運用不要で DoS 影響を 15 分に限定する基本線（必須）。
- **(b) PW 再設定成功で即解除**＝本人がメール経由で PW 再設定（`complete_password_setup`・[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md)）を完了したら、当該 login_id のロック/streak を一掃する（本人到達の証拠＝安全に即解除してよい）。(IP+login_id) 単位のため IP は不定なので、`login_lock:*:{login_id}` と `login_fail_streak:*:{login_id}` を **SCAN で削除**（PW 再設定は稀イベント＝SCAN 許容）。
- **管理者手動解除は本スライス範囲外**＝管理 API/画面が未整備のため後続（ユーザー選択 2026-08-09）。(a)(b) で本人救済は成立する。

### 2.6 [採用] MFA（OTP）失敗はログインロックに連動させない

`mfa/verify` の OTP 連続失敗は本ロックにカウントしない（ユーザー選択 2026-08-09）。

- **理由**＝OTP 失敗は既に `otp_max_attempts`(5)＋pre-auth 失効で拘束済み（[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) §2.4）。別エンドポイント・別セッション（pre-auth）単位で、ログイン（資格照合）の失敗とは意味が違う。二重の上限が絡むと解除経路が複雑化する。ロックは「PW 総当り」に絞る。

### 2.7 [採用] 保持先は Redis（DB 不採用）

失敗カウンタ・ロック・通知クールダウンはいずれも短命の揮発値で、自動解除（TTL）が本質。[`ADR-0004`](ADR-0004_MFA・信頼端末基本パラメータ.md) の login OTP/pre-auth と同じく Redis に置く。

- キー＝`login_fail_streak:{ip}:{login_id}`（TTL 窓）・`login_lock:{ip}:{login_id}`（TTL 15分）・`lock_notified:{account_id}`（TTL 60分）。
- **不採用＝`accounts` に `locked_until` 列**を持つ案。account 単位ロックを採らない（§2.2）ため列が (IP+login_id) を表現できず不適。監査要件が出たら別途ログ/DB へ（後続）。

## 3. 検討した代替案（不採用）

- **account 単位のハードロック**＝不採用。他人による可用性 DoS を招く（§2.2）。(IP+login_id) 単位で DoS 影響を局所化。
- **account 単位＋指数バックオフ（遅延）**＝不採用。UX はマイルドだが、遅延保持のためサーバリソース（コネクション/スレッド）を拘束し、実装・テストも複雑（今回は不要な複雑さ）。
- **ロック中に 423/429＋残時間を返す**＝不採用。存在＋ロック状態を漏らす（§2.3）。本人フィードバックは通知メールで代替。
- **通知メールを送らず一律 401 のみ**＝不採用。本人がロックに気づけない。out-of-band 通知＋スロットルで列挙耐性を保ったまま気づきを与える（§2.4）。
- **ロック状態を DB（`accounts.locked_until`）に保持**＝不採用（§2.7）。

## 5. 残課題 / 既知の限界

- **閾値ちょうど（5回目）の送信レイテンシ**＝通知は同期送信のため、実在アカウントの 5 回目失敗だけメール送信分の遅延が乗り、非実在との**弱いタイミングオラクル**になり得る。クールダウンで 2 回目以降は乗らず、値も小さい（攻撃者は正確に 5 連続失敗させ境界の時間差を測る必要がある）。将来 outbox/worker で**非同期送信**にすれば解消（[`ADR-0002`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.4 の outbox と同じ基盤）。MVP では許容。
- **分散 IP 総当り**＝(IP+login_id) 単位の原理的限界（§2.2 トレードオフ）。将来の異常検知/評判ベース制限は別スライス。
- **管理者による強制解除・ロック可視化**＝管理面が整うまで後続。

# ADR-0002 初回・再設定パスワード基本パラメータ

- ステータス: **確定（2026-08-08 ユーザー承認）** / 値は運用で調整可（下記 [採用] 参照）
- 対象スライス: ドメイン A「状態B/D＝初回・再設定パスワード設定」（`POST /auth/password-setup/{request,verify,complete}`）
- 関連: [`../API設計/A_認証・セッション.md`](../API設計/A_認証・セッション.md)（A.7・正）・[`../API設計/README.md`](../API設計/README.md) §1.7・[`../データモデル.md`](../データモデル.md) §4.4（`otp_challenges`）・§4.6（`account_sync_outbox`）・[`../WEBアプリ開発時のセキュリティ対策一覧.md`](../WEBアプリ開発時のセキュリティ対策一覧.md)・[`ADR-0001_認証・セッション基本パラメータ.md`](ADR-0001_認証・セッション基本パラメータ.md)

> 目的＝PW設定/再設定スライスを実装するために、`A_認証・セッション.md` A.7／A.8 で「実装時に確定」とされていた具体値（PWポリシー・リンクTTL・トークン方式・レート制限）を決める。
> 設計上の方針（列挙耐性で常に `202`・メールリンク基盤に一本化・単回トークン）は `A_認証・セッション.md` A.7 が正で、本 ADR はそれを**変更せず具体値を埋める**（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) と同じ役割）。
> 各項目に **[採用]（この値で実装）** か **[委譲/範囲外]** を付す。

---

## 1. コンテキスト

`A_認証・セッション.md` A.7 は「初回PW設定／自己サービス再設定／管理者再設定」を**同一のメールリンク基盤**（`otp_challenges` purpose=`password_setup`・単回・72h）に一本化し、`request` は列挙耐性で常に `202` と決めている。一方で **PWポリシーの具体値・トークンの生成/保存方式・`request` のレート制限**は「実装時に確定」（`A_認証・セッション.md` A.8）として保留されている。本スライス（状態B/D）を動かすにはこれらが要る。

## 2. 決定

### 2.1 設定リンクトークン（`otp_challenges` purpose=`password_setup`）
- **[採用]** トークン＝CSPRNG 32バイトを base64url（≒256bit・`A_認証・セッション.md` A.0「意味を埋め込まない」）。メールリンクのクエリに載せる（例 `…/password-setup?token=…`）。
- **[採用]** 保存は**ハッシュのみ**（`otp_challenges.code_hash`）。高エントロピー乱数のため**SHA-256** で十分（Argon2id はログインPWのような低エントロピー入力向け＝ここは不要・[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.5 と用途が異なる）。平文は保存もログ出力もしない（セキュリティ一覧 3・15）。
- **[採用]** TTL＝**72時間**・**単回**（`A_認証・セッション.md` A.7／`データモデル.md` §4.4 で確定済み）。`verify` は失効/使用済で `410 token_expired`。`complete` 成功でトークン消費（`used_at` を打つ）。
- **[採用]** `request` は当該アカウントの**未使用の既存 `password_setup` チャレンジを失効**してから新規発行（最新リンクのみ有効＝多重リンクの取り違え防止・`A_認証・セッション.md` A.7）。

### 2.2 PW ポリシー（`complete` のサーバ検証・`A_認証・セッション.md` A.9-④）
- **[採用]（2026-08-08 ユーザー確認・運用で調整可）** **最低8文字／英字を1以上／数字を1以上**（SC-00 §4 の記載どおり＝MVP 最小）。違反は `422 { code:"validation_error", errors:[…] }`（`API設計 README.md` §1.7・`errors[]` は違反項目を列挙）。
- **[範囲外・後続]** 漏えい済み・よく使われるPWの拒否リスト（`A_認証・セッション.md` A.9-④の後半）は本スライスでは実装せず、後続のセキュリティ・ハードニングで導入する。理由＝MVP を小さく通すことを優先し、拒否リストの配布/更新運用は独立した関心事のため（判定を純粋関数に閉じておけば後から差し込める）。
- **[採用]** ポリシー判定は**純粋関数**（domain・DB非依存）で実装しユニットテスト対象にする（コーディング規約 §3.1・§3.3）。クライアント検証は補助でサーバが最終判断（SC-00 §6）。

### 2.3 `request`（自己サービス再設定要求）のレート制限・列挙耐性
- **[採用]** 応答は**常に `202 { status:"accepted" }`**（アカウント有無・`password_set` 状態・会社状態に依らず同一・`A_認証・セッション.md` A.7）。実メール送信は**「会社が `active` かつアカウントが `active`」の場合のみ**（該当しなければ無送信で同一応答）。
- **[採用]（2026-08-08 ユーザー確認・運用で調整可）** レート制限＝**(IP＋company_code＋login_id) 単位で 5回/10分**を超えたら抑止する（`A_認証・セッション.md` A.8）。**ただし超過時も応答は `202` を維持**（`429` を返すと「多く要求された＝実在の可能性」を漏らすため。列挙耐性を優先し、超過分は無送信で握る）。理由＝`request` は未認証・列挙攻撃の的になりやすく、ログイン（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6 は `429` 明示）とは秘匿要件が異なる。
- **[採用・限定]** タイミング差抑制＝応答は存在有無に依らず `202`（本文も同一）とする。ただし**本スライスはメール送信を同期（post-commit）で行う**ため、実送信する eligible 経路は無送信経路より応答が遅く、**残余のタイミング差が残る**（既知の MVP 限界）。**完全な等時間化は非同期送信（outbox/worker）導入時に対応**する（それまでは応答コード/本文の秘匿で一次防御・`A_認証・セッション.md` A.9-⑤）。

### 2.4 `complete` 成功時の副作用
- **[採用]** `accounts.password_hash` を Argon2id（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.5）で更新し `password_set=true`。トークン消費（`used_at`）。**当該アカウントの全アクティブセッションを破棄**（`A_認証・セッション.md` A.9-③）。
- **[採用]** ここでは**セッションを新規発行しない**（設定後は通常ログイン画面へ・SC-00 §5）。
- **[実装済み（2026-08-11・outbox/worker スライス）]** `account_sync_outbox` への同一Tx INSERT（会社DB `users` へ `password_set` ミラー・`データモデル.md` §4.6・`A_認証・セッション.md` A.7）は**実装済み**。`complete_password_setup` が accounts 更新と同一Tx で outbox 1行を積み、常駐ワーカ（`worker.py`→`account_sync.application.process_outbox_once`）が会社DB `users.password_set` へ冪等反映する（TC＝[`../テスト/B_会社・アカウント.md`](../テスト/B_会社・アカウント.md) B-TC-001〜005）。※当初は委譲としていた（理由＝ワーカ未実装／`users` に `password_set` 列なし／ログインは管理DB `accounts` 直参照でミラー未反映でも認証は正しい）が、本スライスで table＋INSERT＋適用＋列追加をまとめて導入した。
- **[委譲・後続]** 信頼端末（`trusted_devices`）の失効（`A_認証・セッション.md` A.9-③）は `trusted_devices` テーブルが MFA スライスで導入されるため、本スライスでは対象外（PW完了→全セッション破棄までを担保）。
- **[委譲・後続]** セキュリティ通知（`security_password_changed`・`A_認証・セッション.md` A.9-⑧）はドメイン H（通知）実装時に post-commit で発火。本スライスでは通知しない。

### 2.5 メール送信基盤
- **[採用]** dev＝**MailHog**（SMTP `mailhog:1025`・Web UI `:8025`）。prod＝SMTP。送信は**ポート（インターフェース）で抽象化**し（`データモデル.md` §4.4「アダプタで抽象化」）、テストは**フェイク送信**（送信内容を捕捉）で検証する。件名/本文の文言は暫定（i18n 本格対応は後続）。
- **[採用]** SMTP 設定（接続先・認証情報・差出人）の**置き場所は環境変数（`.env`／本番はシークレットマネージャ）で、DB には置かない**。方針と `.env` 管理項目は [`ADR-0003_設定と秘匿情報の置き場所.md`](ADR-0003_設定と秘匿情報の置き場所.md) が正。

## 3. 検討した代替案（不採用）

- **トークンを Argon2id でハッシュ**＝不採用。トークンは 256bit の高エントロピー乱数で総当り不能なため、遅いハッシュは不要（検証コストだけ増える）。SHA-256 で必要十分。
- **`request` 超過時に `429` を返す**＝不採用。「要求が多い＝実在の可能性」を未認証者に漏らし列挙耐性を損なう。ログイン（[`ADR-0001`](ADR-0001_認証・セッション基本パラメータ.md) §2.6）は ID/PW 照合が前提のため `429` を許すが、`request` は常に `202` に倒す。
- **PWポリシーを NIST 式（12文字・文字種不問）にする**＝今回は不採用（SC-00 §4 の記載＝8文字＋英数字に合わせる）。長さ重視への移行は運用で調整可（本 ADR の値は差し替え可能）。
- **outbox を本スライスで実装**＝不採用（§2.4 の理由）。worker・`users` 列拡張とまとめる方が手戻りが少ない。

## 4. 影響

- 実装＝`backend/app/control_plane/auth`（password-setup の4層）・`backend/app/core`（config で SMTP/APP_BASE_URL・PWポリシー/レート制限値）・`backend/app/infra/mail`（送信ポート＋MailHog 実装）・control migration に `otp_challenges`。`compose.yaml` に `mailhog`。
- テスト＝[`../テスト/A_認証.md`](../テスト/A_認証.md) の A-TC-030 以降（`202` 一律・`410 token_expired`・`422` PWポリシー・complete で全セッション破棄・メール送信条件）。
- 2.2 PWポリシー・2.3 レート制限は **2026-08-08 にユーザー承認で確定**（運用で調整可）。outbox（2.4）は後続スライスへ委譲。

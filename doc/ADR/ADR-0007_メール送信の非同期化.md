# ADR-0007 メール送信の非同期化（メールアウトボックス）

- ステータス: **確定（2026-08-11 ユーザー承認）** / 値（env・§2.8）は運用で調整可。決定＝機構＝DB アウトボックス（§2.1）・ワーカ＝別プロセス（§2.3）・秘匿値＝専用列隔離＋送信時レンダリング＋送信後破棄（§2.7）・配送＝at-least-once＋`status=sending` 緩和（§2.5）・`done` 行の掃除はメールワーカが retention 経過後に削除（§2.7・§2.3）・テストのドメイン記号は A 相乗り（§4）。
- 対象スライス: 認証系のシステム生成メール（**MFA の OTP／初回・再設定パスワード設定リンク／アカウント一時ロック通知**）の送信を、リクエスト経路から切り離して**非同期化**する。**backend のみ**（フロント応答・ステータスは不変）。
- 関連: [`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md)（§2.3 request の列挙耐性・§2.4 で言及した outbox 基盤・§2.5 メール抽象化）・[`ADR-0004_MFA・信頼端末基本パラメータ.md`](ADR-0004_MFA・信頼端末基本パラメータ.md)（OTP 送信）・[`ADR-0005_アカウント一時ロック.md`](ADR-0005_アカウント一時ロック.md)（§2.4 通知メール・§5 弱いタイミングオラクル＝本 ADR の主動機）・[`ADR-0003_設定と秘匿情報の置き場所.md`](ADR-0003_設定と秘匿情報の置き場所.md)（設定は env・SMTP 秘匿）・[`../データモデル.md`](../データモデル.md)（§4.4 otp_challenges・§4.6 account_sync_outbox＝流用元の型・§8-①）・[`../WEBアプリ開発時のセキュリティ対策一覧.md`](../WEBアプリ開発時のセキュリティ対策一覧.md)（3・15＝秘匿値をログに出さない）

> 目的＝現在**同期送信**（リクエスト処理中に SMTP を叩く）しているシステム生成メールを、「管理 DB のアウトボックスに積む→常駐ワーカが送る」方式に変え、[`ADR-0005_アカウント一時ロック.md`](ADR-0005_アカウント一時ロック.md) §5 で MVP 許容とした**弱いタイミングオラクル**と、SMTP 失敗が応答コードを汚す綻びを解消する。機構の型は既存の [`../データモデル.md`](../データモデル.md) §4.6 `account_sync_outbox`（DB→DB ミラー）を**踏襲するが別テーブル・別ユースケース**（メールは DB ミラーではない）。

## 1. コンテキスト

### 1.1 現状（同期送信）と、それが生む3つの綻び

認証フローは以下を**リクエスト処理中に同期送信**している（[`auth/application.py`](../../impl/backend/app/control_plane/auth/application.py)・[`infra/mail.py`](../../impl/backend/app/infra/mail.py) `MailSender.send`）:

- `_send_otp_email`（MFA・login 分岐）・`_send_password_setup_email`（`password-setup/request`）・`_send_lock_notification`（login 失敗でロック発火時）。

同期送信は次を生む:

- **(a) 弱いタイミングオラクル**（[`ADR-0005_アカウント一時ロック.md`](ADR-0005_アカウント一時ロック.md) §5）＝ロック発火（実在 active の 5 回目失敗）でのみ SMTP 送信分の遅延が乗り、非実在との応答時間差になり得る。
- **(b) 列挙耐性を壊す 500**＝一律 401（login）や常に 202（`password-setup/request`）で存在を隠す設計なのに、SMTP が落ちると 500 が返り「送信を試みた＝実在」を漏らす。
- **(c) request の残余タイミング差**（[`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.3）＝実在時のみ送信が走るため、常に 202 でも送信有無で時間差が残る。

いずれも「**送信という重く失敗し得る I/O を、応答を返す経路から外す**」ことで根治する。

### 1.2 流用できる資産＝§4.6 account_sync_outbox

[`../データモデル.md`](../データモデル.md) §4.6 の `account_sync_outbox`（管理 DB→会社 DB `users` ミラー）で、**アウトボックス＋常駐ワーカ**（[`worker.py`](../../impl/backend/app/worker.py)・`process_outbox_once`）の型は既に縦通し済み。本 ADR はこの**型（enqueue は呼び出し側 Tx に相乗／ワーカが再試行しながら適用／`attempts` 上限で `failed`）を踏襲**する。ただし**用途が違う**（DB ミラーではなくメール送信）ため別テーブル・別ユースケースにする（[`../データモデル.md`](../データモデル.md) §4.6 は「DB ミラー専用」）。

## 2. 決定

### 2.1 [採用] 機構＝管理 DB のメールアウトボックス（Redis キュー不採用）

**2026-08-11 ユーザー選択**。送信すべきメールを管理 DB のテーブル `mail_outbox` に 1 行 INSERT し、常駐ワーカが取り出して SMTP 送信する。

- **理由**＝(1) 確実配送（DB の耐久性で「積んだのに消えた」を避ける）、(2) [`../データモデル.md`](../データモデル.md) §4.6 の実装資産（ワーカ・再試行・`attempts`/`failed` 運用）をそのまま流用でき新規実装が小さい、(3) `failed` 行が DB に残り可視化/手動対応の足場になる。
- **不採用＝Redis キュー**＝軽量だが、(1) 揮発性で確実配送に追加設計が要る、(2) §4.6 と別系統になり資産流用が効かない。メールは「取りこぼしたくない」ので確実性を優先（[`../データモデル.md`](../データモデル.md) §4.6 の設計判断＝「otp_challenges 同様 Redis も可だが確実性重視で DB」と一貫）。

### 2.2 [採用] 保持先＝管理 DB の新テーブル `mail_outbox`（account_sync_outbox に相乗りしない）

送信元 3 種はすべてコントロールプレーン（`control_plane/auth`）で発生し、宛先の確定に会社 DB を要さない。よって**管理 DB に置く**。§4.6 の `account_sync_outbox` とは**別テーブル**にする（列も意味も異なる）。**完成本文（秘匿値入り）は保存せず**、秘匿値は専用列 `secret` に隔離し、件名/本文はワーカが送信時にレンダリングする（§2.7）。

- **テーブル案（[`../データモデル.md`](../データモデル.md) に §4.7 として追記予定）**:

  | 列 | 型 | 意味 |
  |---|---|---|
  | `id` | uuid (PK) | 行識別（ランダム・順序は表さない） |
  | `seq` | BIGSERIAL/Identity (unique) | 挿入順の単調増加キー（取り出しの安定順序・§4.6 の `seq` と同じ思想） |
  | `to_email` | text | 宛先（enqueue 時に確定） |
  | `category` | text | `otp` / `password_setup` / `lock_notification`（テンプレ選択・可視化・監視） |
  | `locale` | text NULL | enqueue 時に確定した宛先の言語（`accounts.locale`・i18n）。NULL＝システム既定 |
  | `secret` | text NULL | 秘匿値（OTP コード／設定リンクのトークン）を**単独で**保持。`lock_notification` は NULL。**送信成功／端末失敗で NULL 化**（§2.7） |
  | `account_id` / `company_id` | uuid NULL | 監視/相関用（任意） |
  | `status` | text | `pending` / `sending` / `done` / `failed`（§2.5） |
  | `attempts` | int | 送信失敗リトライ回数（`mail_outbox_max_attempts` 超で `failed`） |
  | `claimed_at` | timestamptz NULL | `sending` へ遷移した時刻（§2.5 の再送判定用） |
  | `created_at` | timestamptz | 生成時刻 |
  | `processed_at` | timestamptz | 送信完了（または `failed` 確定）時刻 |

- **件名・本文は列に持たない**＝`category`＋`locale`＋`secret`＋設定（有効期限等）から**ワーカが送信時にレンダリング**する（テンプレは 1 箇所＝メールレンダリング関数に集約）。これにより秘匿値を含む完成本文を DB に置かない（§2.7）。
- `account_id`/`company_id` は任意（NULL 可）。宛先解決は enqueue 時に済ませ、ワーカは会社 DB に触れない（§4.6 と違い両プレーンを跨がない）。

### 2.3 [採用] ワーカは account_sync とは別プロセスに分離（2026-08-11 ユーザー選択）

メール送信ワーカを account_sync ワーカ（[`worker.py`](../../impl/backend/app/worker.py)）とは**別プロセス**にする。エントリは `python -m app.mail_worker`（compose に第 2 の worker サービス）。本体は `process_mail_outbox_once()`（テストは §4.6 同様この関数を直接呼ぶ＝常駐不要）。

- **理由**＝SMTP 詰まり（タイムアウト待ち・10s・[`infra/mail.py`](../../impl/backend/app/infra/mail.py)）が account_sync の DB ミラー反映に波及しない（**障害隔離**）。メールと DB ミラーは律速も監視も分けられる。
- **コスト（明示）**＝常駐プロセス/監視対象が 1 つ増える。compose の worker サービスを複製し entrypoint（`python -m app.mail_worker`）と poll interval だけ差し替える（env は既存アンカー共有）。
- **`mail_outbox` のライフサイクルはこのワーカが単独で所有**＝送信・再送（§2.5）に加え `done` 行の掃除（§2.7）も本ワーカが担う（テーブルを触る常駐主体を 1 つに集約＝別 cron/プロセスを増やさない）。

### 2.4 [採用] メールは独立処理＝順序保証・HOL ブロッキングは設けない

§4.6（account_sync）は「同一 account を seq 順に直列・失敗で後続を止める（HOL）」が必須だった（DB ミラーの因果順）。**メールにこの制約は無い**（各メールは独立事象）。よってワーカは:

- 送信対象（`pending`、および §2.5 で `sending` のまま滞留し再送へ戻した行）を `seq` 昇順で取り出し（安定順序のためだけ）、**各行を独立に送信**。1 件の失敗は他をブロックしない（`attempts++` して次へ）。`done`／端末 `failed` は対象外。
- **理由**＝OTP・設定リンク・ロック通知の間に因果順は無い。ある 1 通の SMTP 失敗で後続の別ユーザー宛が止まると可用性を損なう。

### 2.5 [採用] 配送保証＝at-least-once ＋ `status=sending` で重複を緩和（2026-08-11 ユーザー選択）

「SMTP 送信成功」と「`status=done` 書込」は別 I/O で単一 Tx にできず素朴には重複し得る。これを `sending` 中間状態で緩和する:

1. `pending` 行を 1 件、`UPDATE ... SET status='sending', claimed_at=now WHERE id=? AND status='pending'`（**該当 1 行を原子的に確保**）してから SMTP 送信する（複数ワーカ/多重巡回でも二重取得しない）。
2. 送信成功＝`status=done`＋`secret=NULL`＋`processed_at`。
3. 送信失敗＝`attempts++`・`status` を `pending` へ戻す（上限超で `failed`＋`secret=NULL`）。
4. **`sending` のまま `mail_outbox_sending_reclaim_seconds` を超えた行**（＝送信直後〜`done` 書込前でクラッシュした疑い）だけを `pending` へ戻して再送対象にする。

- 正常時の二重送信はほぼ消える（`done` を書く前提で進む）。**残るのはクラッシュ窓（SMTP 成功〜`done` 書込の間）だけ＝at-least-once**。その重複は無害（OTP/通知/リンクの重複受信は安全・トークンは単回/TTL・§3）。exactly-once は SMTP 側の重複排除が要り過剰。

### 2.6 [採用] enqueue は「積むだけ」で応答を返す（同一 Tx は取れる箇所のみ）

呼び出し側（application 層）は SMTP を叩かず `mail_outbox` へ 1 行 INSERT して即応答する。これで §1.1 の (a)(b)(c) が消える（送信経路に SMTP が無い＝遅延も 500 も出ない）。

- **同一 Tx で積める箇所**＝`password-setup/request`（管理 DB に `otp_challenges` を作る Tx がある）は、その Tx に enqueue を相乗せ、**「チャレンジ作成」と「メール送信予約」を原子化**（片方だけ成立を防ぐ）。
- **周辺に DB 書込が無い箇所**＝MFA の OTP 送信（pre-auth は Redis）・ロック通知（計数は Redis）は、**単独 INSERT**（それ自体が独立 Tx）。原子化の相手はないが、目的（送信を経路から外す）は達成される。

### 2.7 [採用] 秘匿値は専用列に隔離し、送信時にレンダリング、送信後に破棄（2026-08-11 ユーザー選択）

同期送信では OTP/設定リンクトークンは**メモリ上を通過するだけ**だったが、非同期化では一時的に at-rest する。露出面を最小化するため、**完成本文を保存せず秘匿値を隔離する**:

- **完成本文（秘匿値入り）を DB に持たない**＝`mail_outbox` は秘匿値を `secret` 列に**単独で**持ち、件名/本文はワーカが送信時に `category`＋`locale`＋`secret`＋設定からレンダリングして SMTP へ渡す（§2.2）。これにより「OTP や設定リンクを埋め込んだ完成テキスト」が DB に残らない。
- **送信成功／端末失敗（`failed` 確定）で `secret` を NULL 化**＝秘匿値の at-rest 期間を「積んでから送るまで（通常 秒オーダー）」に限定。`category`/`to_email`/タイムスタンプは監査・可視化のため残す（`failed` でも `secret` は落とす＝手動再送は新規 enqueue でやり直す）。
- `lock_notification` は秘匿値なし（`secret` は最初から NULL・本文は完全に静的）。
- 併せて **秘匿値・本文はログに出さない**（既存方針・セキュリティ一覧 3・15）。管理 DB は元々 `password_hash` 等を持つアクセス限定層。
- **`done` 行の掃除（2026-08-11 ユーザー選択）**＝メールワーカ（§2.3）が `done` かつ `processed_at` が `mail_outbox_done_retention_seconds`（既定 7日）より古い行を削除する（毎巡ではなく間引いて DELETE・別 cron を立てない）。`secret` は送信時に落ちているので秘匿は残らないが、直近の `done` 行を短期保持することで「いつ誰へ送ったか」をサポート/障害調査で追える（mail_outbox は監査の正本ではない＝長期保持は不要）。**`failed` 行は自動削除しない**（手動対応が要る異常シグナル＝§4.6 の `failed` と同じ扱い）。

### 2.8 [採用] しきい値は env（[`ADR-0003_設定と秘匿情報の置き場所.md`](ADR-0003_設定と秘匿情報の置き場所.md) B 群）

§4.6 の `outbox_*` に倣う。会社別に変える要件は無い。

| env 変数 | 意味 | 既定 |
|---|---|---|
| `mail_outbox_max_attempts` | 送信リトライ上限（超で `failed`） | **5** |
| `mail_outbox_poll_interval_seconds` | メールワーカ（別プロセス・§2.3）のポーリング間隔 | **1.0** |
| `mail_outbox_sending_reclaim_seconds` | `sending` のまま放置された行を再送対象へ戻す閾値（§2.5） | **60** |
| `mail_outbox_done_retention_seconds` | `done` 行をメールワーカが削除するまでの保持期間（§2.7・サポート調査の猶予） | **604800（7日）** |

## 3. 検討した代替案（不採用）

- **Redis キュー**＝§2.1。揮発性・§4.6 と別系統。確実性重視で不採用。
- **account_sync_outbox に相乗り（同一テーブル）**＝列も意味も異なり（ミラー vs 送信）、HOL/順序制約も逆（§2.4）。テーブルを混ぜると両者の運用が絡む。別テーブルにする（§2.2）。
- **メールワーカを account_sync worker に相乗り（同一プロセス）**＝プロセスは増えないが、SMTP 詰まりが DB ミラー反映に波及する。障害隔離を優先し別プロセスにした（§2.3）。
- **同期送信のまま + SMTP 失敗を握り潰す**＝(b)(c) の一部は緩和できるが (a) タイミング差は残り、送信の確実性も無い（落ちたら消える）。非同期化が本筋。
- **exactly-once 配送**＝§2.5。SMTP 側重複排除が要り過剰。重複無害なので at-least-once（＋`sending` 緩和）を採る。
- **完成本文（秘匿値入り）を `body` 列に保存**＝不採用。秘匿値の at-rest を最小化するため、秘匿値は `secret` 列に隔離し送信時レンダリングにした（§2.7）。locale は enqueue 時に `accounts.locale` で確定（[`../データモデル.md`](../データモデル.md) §8-⑬）。

- **テスト**（[`../規約/テスト規約.md`](../規約/テスト規約.md) §5.1・red 必須）:
  - int＝enqueue で行が積まれる／`process_mail_outbox_once` で `FakeMailSender` に届き `done` 化＋`secret` が NULL 化（§2.7）／SMTP 失敗で `attempts++`・上限で `failed`（`secret` も NULL）／独立処理（1 件失敗が他を止めない・§2.4）／`sending` 滞留の再送（§2.5）。
  - api（列挙耐性の回帰）＝`password-setup/request` が SMTP 不達でも **202 のまま**（500 にならない・(b) 解消）／login 失敗でロック発火しても **401 のまま**・応答時間に送信分が乗らない（(a) 解消）。
  - **テストパターンのドメイン記号**＝**A に相乗り**（`A-TC-0xx`・2026-08-11 決定）。送信元が `control_plane/auth` の 3 種のみで横断範囲が狭いため新記号は設けない。
- **相互参照更新**＝[`ADR-0005_アカウント一時ロック.md`](ADR-0005_アカウント一時ロック.md) §5・[`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md) §2.3/§2.4 の「将来 outbox で非同期化」を本 ADR-0007 への参照に更新。[`../テスト/A_認証.md`](../テスト/A_認証.md) §5.1 補足の「通知メールの非同期化は後続」を更新。

## 5. 残課題 / 既知の限界

§2 の方式・値・細目（`done` 掃除＝§2.7／テスト記号＝§4）は **2026-08-11 にユーザー承認で確定**。以降は本 ADR に沿って実装する。

**実装の順序（本 ADR 確定後）**:

- [`../データモデル.md`](../データモデル.md) §4.7 追記 → テストパターン追記（A 相乗り・red-green・[`../規約/テスト規約.md`](../規約/テスト規約.md) §5.1）→ 実装。

**既知の限界 / 後続**:

- **クラッシュ窓の重複送信**＝§2.5。SMTP 成功〜`done` 書込の間で落ちると 1 通重複し得る（無害）。exactly-once は採らない。
- **`failed` 行の監視/アラート・手動再送 UI**＝管理面が整うまで後続（§4.6 の `failed` 可視化と共通課題）。手動再送は新規 enqueue でやり直す（`secret` は破棄済みのため・§2.7）。
- **他の送信系メール**（[`../データモデル.md`](../データモデル.md) §8-⑳ の `security_password_changed` 等・ドメイン H）も将来この基盤に載せられる（本スライスは認証系 3 種に限定）。

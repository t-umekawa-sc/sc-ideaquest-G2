# ADR-0009 管理者によるメールアドレス確認（opt-in・現アドレスの到達/所有確認）

- ステータス: **確定（2026-08-23 ユーザー承認）** / 値（TTL 等・env）は運用で調整可。決定＝**管理者経路のメール編集は現状どおり no-block（即反映・一意検証のみ）を維持しつつ、opt-in の「確認メール送信」アクションで現アドレスの到達/所有確認を行い、`accounts.email_verified_at` に確認状態を残す**。確認は `otp_challenges` に**新 `purpose=email_verify`** を足して縦通し（A.7/ADR-0008 と同型・単回・TTL 72h）・確定 EP は未認証（トークンが認可）・一覧に「未確認/確認済み」バッジ。
- 対象スライス: ドメイン B の**管理者によるアカウント編集**（[`../API設計/B_会社・アカウント・所属.md`](../API設計/B_会社・アカウント・所属.md) B.2〔system_admin・全社〕/ B.2.1〔会社アカウント管理者・自社〕）＋公開 confirm EP（[`../API設計/A_認証・セッション.md`](../API設計/A_認証・セッション.md)）＋画面 SC-92/SC-93。
- 関連: [`ADR-0008_メール変更のダブルオプトイン.md`](ADR-0008_メール変更のダブルオプトイン.md)（本人自己変更＝新アドレスへの**変更**を pending で確定／本 ADR は**現アドレスの確認**で別意味・§2.2 の切り分け）・[`ADR-0002_初回・再設定パスワード基本パラメータ.md`](ADR-0002_初回・再設定パスワード基本パラメータ.md)（設定リンクトークン＝単回/TTL/`otp_challenges` の型・確定 EP は未認証）・[`ADR-0007_メール送信の非同期化.md`](ADR-0007_メール送信の非同期化.md)（認証イベント由来メールは `mail_outbox` に `mail_category` 追加で載せてよい）・[`../データモデル.md`](../データモデル.md)（§4.2 accounts／§4.4 otp_challenges／§4.7 mail_outbox）。

> 目的＝管理者によるメール編集（[`B_会社・アカウント・所属.md`](../API設計/B_会社・アカウント・所属.md) `PATCH .../accounts/{id}`）は**会社内一意検証のみで即反映**し、新アドレスが「本人が受信できる実在アドレス」かを確認しない。タイプミス・誤登録で、以後の初回PW設定/再設定リンク・OTP・通知が届かない宛先が identity に固定され得る（本人が締め出される）。本 ADR は**編集の手軽さ（no-block）を保ったまま**、管理者が任意で（opt-in）現アドレスの到達/所有を確認し、その状態を可視化できるようにする。

---

## 1. コンテキスト

### 1.1 現状と綻び
- 管理者編集（B.2 `PATCH .../accounts/{id}`・B.2.1 `PATCH /admin/accounts/{id}`）は `email` を即更新（一意検証のみ）＝到達確認なし。自己変更（K.3・ADR-0008）だけがダブルオプトインで到達確認済み＝**管理者経路にギャップ**。
- 「確認済みかどうか」を保持する列が無い＝一覧で未確認アドレスを見分けられず、押し忘れ・気づけない。

### 1.2 流用できる資産
- **`otp_challenges`**（§4.4）＝単回・TTL・`purpose` 別トークン基盤（`password_setup`/`email_change` で縦通し済み）。**新 `purpose=email_verify` を足すだけ**（スキーマ変更なし）。
- **`mail_outbox`**（ADR-0007）＝認証イベント由来メールの非同期送信。確認リンクを **`mail_category=email_verify_link`** で載せる。
- **公開 confirm EP パターン**（A.7 `password-setup/complete`・ADR-0008 `me/email/confirm`）＝未認証＝トークンが認可。同型で `email-verify/confirm` を足す。

---

## 2. 決定

### 2.1 [採用] 編集は no-block 維持＋opt-in 確認（現アドレスの到達/所有確認）
- **編集（`PATCH email`）は即反映のまま**（一意検証のみ・現状踏襲）。**ただし email が実際に変わったら `email_verified_at=NULL`**（新アドレスは未確認へリセット）。
- **管理者 opt-in アクション「確認メールを送信」**（B.2/B.2.1 に新 EP）＝対象アカウントの**現 `email` 宛**に確認リンク（`mail_category=email_verify_link`）を送付。`otp_challenges`（`purpose=email_verify`・単回・TTL `email_verify_ttl_seconds`＝72h・当該アカウントの旧 `email_verify` チャレンジは失効＝最新リンクのみ有効）。応答＝**202**（受理）。
- **確定（`POST /auth/email-verify/confirm {token}`・未認証＝トークンが認可）**＝トークン照合（`purpose=email_verify`・未使用・未期限切れ／無効・期限切れ・使用済は一律 **410 `token_expired`**）→ トークンが束ねる `email` が**現在の `accounts.email` と一致することを確認**（確認送信後に管理者が別アドレスへ再編集した場合は不一致＝**409 `stale`**／`email_verified_at` は変えずやり直しを促す）→ `accounts.email_verified_at=now`・チャレンジ単回消費 → 監査記録。応答＝200（未認証のため最小ボディ `{status:"verified"}`）。
- **なぜ pending を使わないか**＝現アドレスは既に `email` に確定済みで「予約（pending）」ではない。確認は状態フラグ（`email_verified_at`）の更新だけで足りる。ADR-0008 の `pending_email` を流用すると「変更」と「確認」の意味が混線する。

### 2.2 [採用] `email_change`（ADR-0008）と `email_verify`（本 ADR）は purpose を分ける
- `email_change`＝**新アドレスへ変更**（`pending_email`→確定で `email` を書き換え）。`email_verify`＝**現アドレスの到達/所有確認**（`email` は不変・`email_verified_at` を刻むだけ）。**確定時の副作用が異なる**（前者は identity 書き換え＋ミラー enqueue／後者はフラグ更新のみ・ミラー不要）ため、confirm の分岐を単純に保つべく purpose を分離（ADR-0008 §2.2 と同思想＝共有テーブルは purpose で用途を分ける・DRY より意味の明確さ）。
- **自己変更（K.3・ADR-0008）の confirm 成功時も `email_verified_at=now` を刻む**＝ダブルオプトインで到達確認済みのため、「確認済み」概念を両経路で統一（一覧バッジが自己変更後も正しく「確認済み」を示す）。

### 2.3 [採用] `accounts.email_verified_at`（新規列・nullable timestamptz）
- 現 `email` が到達/所有確認済みになった日時。**未確認は NULL**。**`email` が変わったら必ず NULL リセット**（管理者 `PATCH`・自己 `PATCH /me` 経由の変更・ADR-0008 の確定はその確定で now を刻む）。migration＝control（`pending_email` の次のリビジョン）。
- **不採用＝boolean `email_verified`**＝「いつ確認したか」を監査/UI（例「2026-08-23 確認済み」）で使えるよう timestamptz にする。

### 2.4 [採用] 一覧の可視化＋アクション（SC-92/SC-93）
- アカウント一覧のメール列（またはメール列の副表示）に**「未確認/確認済み」バッジ**（`email_verified_at` の有無）。`GET .../accounts` の各行に `email_verified`（bool・`email_verified_at != null`）を含める。
- ⋯ RowMenu に**「確認メールを送信」**（active 行）。実行＝上記 202 → 成功トースト「確認メールを送信しました」。**確認済みでも再送可**（アドレス変更後の再確認）。

### 2.5 [採用] スコープ（MVP）
- MVP は**情報提供**（バッジ＋任意送信＋確認状態）に留める。「未確認だと通知/リンクを送らない」等の**強制はしない**（後続で要検討）。理由＝強制は初回PW設定フロー（発行直後は必ず未確認）と衝突し、運用を止めるため。
- **認可**＝送信 EP は B.2（system_admin・全社）/ B.2.1（company_account_admin・自社）の既存認可に従う。confirm EP は未認証（トークンが認可）。
- **列挙耐性**＝confirm の無効/期限/使用済は一律 410。送信 EP は管理者認証下のため列挙耐性の特別扱いは不要（対象 account は認可済み文脈）。

## 3. 影響
- **データモデル**＝`accounts.email_verified_at` 追加／`otp_purpose` に `email_verify`／`mail_category` に `email_verify_link`。
- **API**＝B.2/B.2.1 に `POST .../accounts/{id}/email-verification`（送信）／A に `POST /auth/email-verify/confirm`（確定・未認証）／`GET .../accounts` の行に `email_verified`。`PATCH email` の副作用に「変更時 `email_verified_at=NULL`」。
- **画面**＝SC-92/SC-93 の一覧バッジ＋⋯アクション。
- **実装**＝別スライス（md 先行→red-green）。公開時 XP 等の外部依存なし。

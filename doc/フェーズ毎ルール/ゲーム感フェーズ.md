# ゲーム感（juiciness）フェーズ 進め方ルール

> **本ファイルがこのフェーズの進め方の正本**（安定・コミット管理）。`handoff.md`（毎回全文上書き）には都度の状況だけを書き、進め方は**本ファイルを参照**する。関連の正本＝受入台帳 [`テスト/ゲーム感受入.md`](../テスト/ゲーム感受入.md)（GF-AC）／横断標準 [`画面設計/デザイン標準.md`](../画面設計/デザイン標準.md) §4.9／テスト必須観点 [`規約/テスト規約.md`](../規約/テスト規約.md) §6。

## 1. 目的と原則（非同期パイプライン）
- 「ゲーム感」はこのシステムの差別化要素＝**どんどん増やす**。ユーザーの手動受入は遅く、実装は速い前提で、**実装を受入待ちで止めない非同期パイプライン**で回す（ユーザー決定 2026-08-27）。
- **各増分は純粋に加算的な視覚レイヤ**＝backend/挙動は不変・既存を壊さない。純ロジックが出れば必ず抽出して **md 先行→vitest red-green**、視覚は **GF-AC でブラウザ受入**（純ロジックが無い視覚のみ増分は正直に GF-AC のみ）。
- **すべての演出は抑制設定を尊重**（デザイン標準 §4.9）＝実効 = OS `prefers-reduced-motion` **OR** ユーザー設定 `accounts.reduce_motion`。新規演出は必ず (a) 単一 seam（CSS `[data-anim-reduced]` キルスイッチ／JS `lib/motion.ts` `reduceMotion()`）に載せ、(b) **抑制 ON で出ない/情報は残るケースをテストに必ず含める**（テスト規約 §6）。

## 2. ブランチ／コミット運用
- 作業ブランチ＝**`feature/game-feel`**。**このブランチへは standing 承認で増分ごとに commit+push を自走**（「push it」を待たない）。
- **`main` への push・マージはユーザー承認後**（GF-AC を一通り受入後にバッチで）。backend 契約変更を含む増分（例 #8 step2・アニメ設定）も feature ブランチで進め、main へは承認フロー。

## 3. 受入とゲーム実装の並行運用＝QAスタックの動かし方
> 今セッションの躓き（F5でCSS剥がれ／ログイン500／MailHogにコード来ず）はすべて compose の起動作法ミス。以下を守れば防げる。

- **QAスタックは workers 込みでフル起動**＝`cd impl && docker compose --profile workers up -d --build`。**worker と mail-worker を必ず上げる**（無いと初回PW/OTP/メール変更等の**コードが MailHog(:8025) に永遠に届かない**／worker はアカウント同期）。
- **QAフロントは「本番ビルド」配信**（`impl/frontend/Dockerfile` = `next build && next start`・`ARG BACKEND_ORIGIN=http://backend:8000` を build 時に焼く）＝ハッシュ CSS で **F5 でも剥がれない**。`next dev` はオンデマンド compile がリロードと競合して無スタイル化するので **QA には使わない**（素早いコード反復のみ host `npm run dev`）。
- **コミットはコンテナに焼かれる＝反映には再ビルド**。push 後に QA するなら **`docker compose up -d --build frontend`**、**backend 変更を含むなら backend も `--build`**（旧 backend だと新フィールドを 422 で弾く等の不整合）。migration 適用＝`docker compose run --rm -T -v "$PWD/backend:/app" backend python -m scripts.bootstrap`（冪等）。
- **pytest とブラウザQAは排他**＝pytest は**ワーカ停止必須**（`docker compose stop worker mail-worker`・mail_outbox 競合でフラキー）→終わったら **start で戻す**。**pytest の cwd は必ず `impl`**（`$PWD/backend` マウント／`impl/backend` に居ると `No module named scripts`）。mail を使わない単体 api テストなら worker 上げたままでも可。
- 受入で不具合が出たら「**自分の作業が影響するか**」を即コード/ログで裏取りし、該当すれば正直に own して即修正（例：今回のログイン500は本番ビルド化の副作用＝`BACKEND_ORIGIN` ビルド時未設定と特定・修正済み）。
- ポート＝frontend:3000／backend:8000(`/healthz`)／db:5432／redis:6379／minio:9000/:9001／mailhog:8025。ログイン＝`ACME-01`/`user@acme.example`/`Passw0rd!`。

## 4. 各増分の品質ゲート（毎回）
- frontend＝`cd impl/frontend` で `npx tsc --noEmit`（クリーン）／`npx vitest run`（全 green）／`npm run build`（EXIT=0・`next build` は稀に transient で落ちる＝1回落ちたら再実行）。
- backend（変更時）＝上記のワーカ停止・cwd=impl で `pytest`（red-green 証跡は commit＋`テスト/red確認台帳.md`）。
- 全体＝repo ルートで `python3 scripts/check_tc_traceability.py`（✅・GF-AC と `src/**/*.test.ts` は走査対象外＝frontend 単体の追跡は domain md の TC 行で担保）。

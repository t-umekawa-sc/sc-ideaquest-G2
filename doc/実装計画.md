# 実装計画（backend 接続フェーズのロードマップ）

> 目的＝**画面移植完了後の「backend 接続フェーズ」を、どのドメイン/画面をどの順で実装するか**の正本。
> 進め方は [フロントエンド実装フロー規約](規約/フロントエンド実装フロー規約.md) §1.1（**1画面単位ループ**＝必要EP特定→テスト先行4層実装→fixtures を実APIへ差替→ユーザー動作確認〔受入ゲート〕→クローズ）。
> 方針決定＝**2026-08-19・ユーザー選択**。実装順＝**アカウント登録→クエスト管理→アイデア→評価→その他**。
> **ファイル/画像アップロード（添付・背景画像・アバターアイコン）は後回しにせず、関係フェーズで同時に実装する**（本計画の明示要件）。

## 0. 現状（2026-08-19 時点）

- **実装済み（backend 接続済み）**: A 認証（SC-00）／B 会社・アカウント・所属（admin＝SC-90/91/92/93・**アカウント発行/編集/無効化/PW再設定/所属が一通り実装済み**）／K identity＋残高（SC-03・**画像アップロードは未**）／G 台帳 canonical（`activities`＋ログイン XP＋`GET /me/activities`）。
- **未実装（本計画で進める）**: **MinIO 画像/ファイル基盤**（`app/infra` は cache/mail のみ・K.4 署名URL は現状 None）／K 画像アップロード／C クエスト・パーティー・権限／D アイデア・添付・版・投票・フォロー／E チャット・リアクション・魔法／F 評価／G 残り（ショップ/装備/魔法/実績/ランキング）／H 通知／I ダッシュボード集約／J 全文検索（PGroonga）／L リアルタイム（WS）。
- 設計の正＝`doc/API設計/{A..L}_*.md`・`doc/データモデル.md`・`doc/画面設計/screens/*.md`＋`mocks/*.html`。

## 1. 依存関係（この順序の根拠）

- **C（クエスト/パーティー/権限）が背骨**＝D/E/F と時系列フィード（API設計 G.5.1）の**門番**（C.0＝当該クエストのパーティー所属で閲覧/操作可否を判定）。→ アイデア・評価の前に C を置く。
- **MinIO 基盤は最初に確立**＝アバター/背景（K）で先に作り、D の添付（FR-26）で再利用（同じ署名URL/アップロード/検証の共通層）。
- **G の付与（XP/コイン/SP）は各ドメイン着地時に発火**＝`app.tenant.gamification.ledger.grant` を D（投稿/投票）・E（チャット）・F（評価/選定/評価連動コイン）から呼ぶ（台帳 canonical は実装済み・データモデル §7/§5.27）。
- **H 通知・I 集約はイベント源（D/E/F/G）が揃ってから厚くする**。
- 各フェーズ内は §1.1 の 1画面ループ＋受入ゲートで進める。

## 2. フェーズ別計画

### フェーズ1：アカウント登録 ＋ 画像アップロード基盤（MinIO ＋ K 画像 → B 検証）
- **1-a. MinIO 画像/ファイル基盤（新設）**: `app/infra/storage`（S3/MinIO クライアント・**短TTL 署名URL 発行**・アップロード・**MIME allowlist＋サイズ上限検証**）。API設計 §1.10・データモデル §8-⑦準拠。以降の全アップロードで再利用。
- **1-b. アバターアイコン アップロード（K）**: `PUT`/`DELETE /me/avatar-image`（multipart）＋会社DB `users.avatar_image_path`。一覧/ランキング/コメントのアイコン表示に反映。未設定時は「頭文字＋カラー」フォールバック（既存）。画面 SC-03 §4.2。
- **1-c. 背景画像 アップロード（K.4・FR-30）**: ヘッダーのユーザーメニューから設定/リセット→**その利用者の全認証画面に反映**（薄スクリム）。`users` に背景パス。
- **1-d. アカウント登録（B）受入確認＋穴埋め**: 発行/編集/無効化⇄再有効化/PW再設定/所属（admin ルータ実装済み）を e2e/手動で通し、不足を補う。SC-92/93/90。
- **受入基準**: アバター/背景を実際にアップロード→表示反映、無効/超過サイズは拒否。アカウント発行→初回 PW 設定→ログインまで一気通貫。
- **依存**: なし（A/B/K 実装済み＋MinIO 新設）。

### フェーズ2：クエスト管理（C）
- **C ドメイン**: quest/party/権限（C.0 門番）・クエストグループ参照制限（FR-15）。作成/一覧/詳細/編集/締切・終了/ステータス（募集中/進行中/評価中/完了）。パーティー編成（FR-22）・クエスト権限（所有者/管理/評価者/投票/作成/コメント・FR-27）。
- **画面**: SC-10 クエスト一覧／SC-11 作成モーダル／SC-12 詳細（タブ：アイデア/全文検索/パーティー/概要）／SC-90 参加管理（一部済）。
- **画像**: クエストアイコン（画像・任意・FR-20）を MinIO 基盤で実装（後回しにしない）。フォールバック＝件名頭文字＋所有者アバター＋クエストカラー。
- **受入基準**: グループ内かつ自分がパーティー参加中のクエストのみ表示、権限に応じた操作可否。
- **依存**: B（アカウント/所属）。→ これで D/E/F/フィードの門番が揃う。

### フェーズ3：アイデア（D）
- **D ドメイン**: アイデア CRUD（FR-01/02）／版・差分（idea_revisions・FR-34）／投票（votes・FR-23・匿名化設定）／フォロー（follows・FR-28）／**添付ファイル（MinIO・FR-26＝1-a を再利用）**。
- **画面**: SC-21 作成／SC-22 詳細（更新履歴・議論活発度 FR-35）／SC-12 一覧タブ。
- **G 連動発火**: 投稿 +50XP（`idea_post`）・投票 +5XP（`vote`・各アイデア初回のみ・日次上限）＝`ledger.grant`。→ SC-03 獲得履歴/フィードに反映。
- **H 初着手**: フォロー/コメント/更新の通知（`notify()` を post-commit）。
- **受入基準**: アイデア投稿→添付表示→投票で XP 付与→履歴反映。版差分表示。
- **依存**: C（クエスト/権限）＋1-a（MinIO）。

### フェーズ4：評価（F）
- **F ドメイン**: 5観点×5点採点＋観点別コメント＋総評（必須）＋公開範囲（既定=パーティー/限定）＋下書き（FR-25/FR-29）。選定（`POST/DELETE /ideas/{id}/select`）。
- **画面**: SC-25 評価。
- **G 連動発火**: 評価実施 +30XP（`evaluation`）・選定 +200XP（`selection`・初回のみ）・**評価連動コイン**（`evaluation_coin`・F.4 確定トリガ＝全 submitted or completed の早い方・データモデル §8-⑱）＝`ledger.grant`。
- **受入基準**: 評価確定で XP、締切/全員提出でコイン確定（冪等）。
- **依存**: C（評価者権限）＋D（対象アイデア）。

### フェーズ5：その他（依存順）
1. **E チャット**（SC-24）＝アイデア別チャット・履歴・**添付（MinIO 再利用）**・`@`メンション・既読位置（chat_reads・データモデル §8-⑰）・リアクション（FR-32）・魔法発動（FR-33・`user_spells` 参照）。チャット +5XP（`chat`・日次上限）。
2. **G 残り**＝ショップ SC-30（`GET /items`＋購入・coin_spend・Idempotency-Key）／装備 SC-31（`PUT /me/equipment`）／魔法 SC-32（`unlock`・sp_spend）／実績 SC-40（台帳フック即時付与・データモデル §8-⑲）／ランキング SC-41＋クエスト内（`GET /rankings`）。
3. **H 通知 全面**（SC-02・一覧/既読・取得時レンダリング＝データモデル §8-⑳）。
4. **I ダッシュボード集約**（SC-01 各パネル実データ）＋**時系列フィード**（`GET /quests/{id}/activities`〔SC-12〕・`GET /me/feed`〔SC-01〕＝API設計 G.5.1・C 済みで接続可）。
5. **J 全文検索**（PGroonga・SC-12 検索タブ・FR-31）。
6. **L リアルタイム配信**（WS・チャット/通知・API設計 §1.12）。

## 3. アップロード（添付/背景/アバター）の扱い（明示方針）

- **後回しにしない**。MinIO の共通基盤を**フェーズ1で確立**し、各機能で再利用する：
  - アバターアイコン・背景画像＝**フェーズ1**（K）。
  - クエストアイコン＝**フェーズ2**（C・FR-20）。
  - アイデア添付＝**フェーズ3**（D・FR-26）。チャット添付＝**フェーズ5-1**（E）。
- 実体は MinIO、物理名はハッシュ化、DB はパス＋元ファイル名。取得は短TTL 署名URL（パス直返し禁止・API設計 §1.10）。サイズ/MIME はサーバー検証（データモデル §8-⑦）。

## 4. 進捗管理

- 各フェーズ/画面の完了＝**ユーザー受入**（§1.1 step4・DoD）。完了状況は本ファイルと `handoff.md` §7 で追う。
- 数値/金額/上限は初期値（要件定義 §6・データモデル §7・後でバランス調整可）。

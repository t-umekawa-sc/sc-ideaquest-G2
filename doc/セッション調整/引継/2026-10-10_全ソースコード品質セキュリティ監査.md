#### AUDIT-001 — 汎用 `POST /ai-jobs` が task_type/ref 無制限で評価者認可ゲートを迂回（会社内 IDOR＋コスト誘発）
- 分類: セキュリティ / 重要度: **High** / 確度: **確認済み**（本セッションで再検証）
- 対象: `impl/backend/app/tenant/ai_jobs/router.py:69-78` `enqueue_ai_job`／`impl/backend/app/tenant/ai_jobs/application.py:113-151` `enqueue`／`impl/backend/app/tenant/ai_jobs/schemas.py`（`AiJobEnqueueRequest`：`task_type: str`・`input: dict` 任意）
- 発生条件: 会社内の任意の認証ユーザー（`require_me` のみ・評価者権限不要）が `POST /ai-jobs` に `{"task_type":"idea_evaluate","input":{"idea_id":"<任意>"},"ref_idea_id":"<任意>"}` を送る。
- 影響: 本来 `evaluations/application.py:138-159 regenerate_ai_evaluation` は `_require_evaluator`＋`_guard_not_completed`（完了クエスト不可）で**評価者のみ**に制限。しかし汎用口の `enqueue` は model 妥当性・月次予算しか検証せず、**task_type のホワイトリストも ref への認可委譲も無い**。結果：(1) 評価権限の無いメンバーが任意アイデア/コンセプトへ AI 評価ジョブを走らせ（AI 評価はコイン/集計に算入＝評価データ汚染）、(2) 当人が requester になるため `GET /ai-jobs/{job_id}` で `result.text`（5観点スコア＋総評）を取得でき本来見えない評価結果を読める、(3) `iso_generate`/`concept_evaluate` も同様に任意起動可＝LLM コスト誘発。
- 根拠: `enqueue`（application.py:125-140）は `requested_model` の registry/予算検証のみ。`ai_eval.build_messages`（`evaluations/ai_eval.py`）は idea の存在/非削除しか見ず requester 可視性を検証しない。router は `require_me` のみ（admin 系 EP とは別）。
- 既存バックログとの関係: **新規発見**（AI ジョブ認可の穴は台帳・姉妹引継いずれにも無し）。
- 推奨修正方針: `application.enqueue` に **task_type ホワイトリスト**を導入し、汎用口では参照ID系（`idea_evaluate`/`concept_evaluate`/`iso_generate`）を 403/422 で拒否して各ドメイン専用 EP 経由に限定する。または汎用口自体を `require_company_account_admin` に格上げ（管理/デバッグ用途の docstring と整合）。ドメイン EP が内部で呼ぶ内部 enqueue 関数はそのまま。
- 修正時の注意点: 各ドメイン専用 EP（evaluations 再評価・concepts 評価・経営資料生成）は内部で enqueue を呼ぶため、公開 router の `POST /ai-jobs` だけを絞ること。既存の正規フローを壊さない。
- 推奨テスト: 非評価者が `POST /ai-jobs {task_type:idea_evaluate}` → 403/422（S ドメイン api テスト）。評価者の正規再評価 EP は緑のまま。

#### AUDIT-002 — 残高（コイン/SP）更新に行ロックが無く、別アイテム/別魔法の同時消費で overspend（double-spend レース）
- 分類: バグ（トランザクション/データ整合性） / 重要度: **High** / 確度: **可能性が高い**（コードで機序確定・並列実測は未実施）
- 対象: `impl/backend/app/tenant/gamification/ledger.py:35-50 _apply_balance`（`user.coin_balance -= amount` 等の ORM 絶対値書込み）／呼出 `impl/backend/app/tenant/shop/application.py:185-207 purchase_item`・`impl/backend/app/tenant/gamification/application.py:72-98 unlock_spell`／`impl/backend/app/tenant/profile/repository.py:13 get_user_by_account`（`with_for_update` 無し）
- 発生条件: 同一ユーザーが**異なる 2 アイテム（または 2 魔法）を同時 POST**（ダブルクリック/並列リクエスト）。両 Tx が同じ残高を読み、各々チェック通過、各々 `balance = <読んだ値> - price` を**絶対値**で書く。
- 影響: UNIQUE(user_id,item_id) / 付与冪等は**同一**アイテムの二重購入のみ防ぐ。異なるアイテムの同時購入は防げず、所持コインを超えて消費され得る。`_apply_balance` は相対 UPDATE でなく Python 側 read-modify-write の絶対値書込みのため、**DB の `CHECK(coin_balance >= 0)`（migration 0020）も発火せず正残高のまま overspend が成立**（例: 残高100・各60 → 両者が 40 を書込み、合計120消費で残高40）。SP も同機序。
- 根拠: `ledger._apply_balance:42 user.coin_balance -= amount`（絶対値）。残高系で `with_for_update` は未使用（唯一の行ロックは `ai_jobs/repository.py:70` のワーカ取得）。tenant セッションは PG 既定 READ COMMITTED（`db/` に isolation 指定なし）。
- 既存バックログとの関係: **新規発見**。
- 推奨修正方針: 消費経路でユーザー行を `select(User)...with_for_update()` で取得（悲観ロック）する、または `UPDATE users SET coin_balance = coin_balance - :amt WHERE id=:id AND coin_balance >= :amt` のアトミック相対更新＋affected rows=0 を 409「残高不足」に写像。`ledger.grant` の呼出口（shop/gamification 両方）で一元対応推奨。
- 修正時の注意点: `_apply_balance` を相対 UPDATE 化する場合、ORM の `user.coin_balance` キャッシュと DB 実値の乖離（返却する `balance` 値）に注意。付与（GAIN）系も同経路のため回帰確認。
- 推奨テスト: 同一ユーザー・異アイテム同時購入で残高が負または over にならないこと（int レベルの並行テスト or ロック経路の単体）。再現テストを修正に同梱（デグレ防止・テスト規約§5.3）。
- 修正完了の判定: 並行消費で残高が所持量を超えない・CHECK 違反 500 でなく 409 が返る。

## 監査したが問題なしを確認した主な項目（誤検知防止の記録）

- **テナント分離**: 全 tenant EP で company_id はセッション由来（ヘッダ/ボディ/パスから company を取る経路なし）。WS 配信は `hub._dispatch` が `payload.company_id != conn.company_id` を遮断（最後の砦）。クロステナント漏洩経路は検出せず。
- **認可の鮮度**: `system_role`/`status=active` を毎リクエスト control DB から再読込。無効化はセッション purge。自己編集は `AccountUpdateSelfRequest` が `system_role` を落とし権限昇格不可。
- **XSS**: frontend の `dangerouslySetInnerHTML`（10 箇所）は全てサーバ側 `pm_to_html`（`core/richtext.py`・`nh3`/allowlist・`javascript:`/`data:` 拒否・link `rel` 付与）経由。client での HTML 文字列組立なし。LLM 出力はテキストノード描画。
- **ワーカ堅牢性**: `FOR UPDATE SKIP LOCKED` 取得・`reclaim_stuck_running` 孤児回収・`attempts` 上限で poison を failed 終端・SIGTERM グレースフル停止・LLM 呼出中は DB 接続非保持。
- **search**: PGroonga は `text()`＋bindparam でバインド（f-string 連結なし）・snippet は `pgroonga_snippet_html` でエスケープ。コード全体の DDL/DML への f-string 連結は AUDIT-008 の `create_database` のみ。
- **付与冪等**: XP/コイン/SP 付与（GAIN）・ログインボーナス・実績・finalize は `exists_ref`/部分 UNIQUE `uq_activities_grant_ref` で二重付与防止（※消費 SPEND のレースは AUDIT-002）。
- **migration 連鎖**: control(20)/company(66) とも単一 head・down_revision 連続・revision 重複/欠落参照なし。timestamp は全て `timezone=True`（naive なし）。
- **Jasper/MinIO/SSRF**: jasper は internal network 隔離・POST+report_key allowlist・S2S `compare_digest`・危険 API（subprocess/eval/pickle/yaml.load）不使用。LLM/MinIO endpoint は env 固定でユーザー入力 URL 経路なし＝SSRF 該当なし。info/strategy に外部 HTTP フェッチ経路なし（手動貼付仕様）。

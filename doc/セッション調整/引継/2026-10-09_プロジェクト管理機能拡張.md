# 引き継ぎ: プロジェクト管理機能の拡張（カンバン／マイタスク横断／依存関係／仕様確定投票）

- 日付: 2026-10-09
- 引き渡す側: 調査/設計セッション（現 MVP の実装範囲を調査→拡張方針をユーザーと合意→設計ドラフト化）
- 対象: プロジェクト／タスク管理（solutions ドメイン Q・FR-43）／SC-70・71・72・新 SC-73（案）／ダッシュボード SC-01 の 1 ゾーン
- 関連設計ドラフト: [doc/設計ドラフト/プロジェクト管理機能拡張_設計.md](../../設計ドラフト/プロジェクト管理機能拡張_設計.md)（本件の詳細。北極星＝[ソリューション開発機能_設計](../../設計ドラフト/ソリューション開発機能_設計.md)）

## 背景・目的

現状のプロジェクト管理は「WBS＋担当＋状態＋期日＋タスクチャット＋完了報酬」という **MVP（薄く縦通し）**まで実装済（backend ドメイン Q 全 EP／SC-70・71・72 green）。日常運用に必要な **(a) 俯瞰（今どこで詰まっているか）**／**(b) 毎日の入口（自分は何をやるか）**が欠けている。ユーザーと相談し、**既存スキーマ・既存 EP でほぼ埋められる**拡張を段階投入する方針で合意（2026-10-09）。

実装セッションは、本引継＋設計ドラフトを受けて、**Phase A（カンバン＋マイタスク横断）から**着手するのがよい（DDL 不要・最速で実用価値）。B（依存）・C（投票）は器が既にあり独立投入可。

## 調査結果（事実・Explore で裏取り済）

- **backend ドメイン Q**＝`impl/backend/app/tenant/solutions/`（router.py / application.py / orm.py）。プロジェクト CRUD・開発メンバー・タスク CRUD/ツリー・recent-chats の全 EP 実装済。認可は application.py が最終権威（`can_access_project` ＝ owner OR project_member OR quest_party OR access_group）。
- **データモデルの"器"（先出し済・MVP 未配線）**＝`tasks.estimate_value`/`estimate_unit`/`planned_start`/`planned_end`/`actual_start`/`actual_end`（nullable）、`task_dependencies` テーブル、`spec_decisions`/`spec_decision_votes` テーブル。→ **Phase B/C は DDL 最小（有効化中心）**。[データモデル](../../データモデル.md) §5.49-5.53。
- **完了報酬**＝`users.delivery_xp`（開発 XP・イノベーション XP と別軸）＋コイン。冪等＝`activities(reason='task_done', ref_type='tasks', ref_id=<task_id>)` の存在チェック。→ **カンバン done 投入でそのまま発火できる**。
- **frontend 実装済**＝`ProjectListView`（SC-70）/`ProjectDetailView`（SC-71・タブ=WBS/開発メンバー/導入価値実現）/`ProjectMembersForm`/`ProjectDeploymentPanel`/`TaskForm`（SC-72）/`TaskChatView`。WBS に既存クイックフィルタ（すべて/進行中/完了/ブロック/自分のタスク）あり。状態＝todo/doing/done/blocked。
- **「最低限のタスク管理のみ」の根拠**＝CSV 取込・工数見積・計画/実績日程・依存・仕様投票・外部 PM 同期・ガント等が未配線（器のみ or 非実装）。設計哲学＝ISO56001 ④⑤を薄く通す MVP。

## 残作業候補（バックログ化する想定）

> 実装セッションがこれを[バックログ台帳](../../バックログ/未実装・ギャップ一覧.md)に起票する。起票時は備考に出典 `(出典: セッション調整/引継/2026-10-09_プロジェクト管理機能拡張.md)` を必須で付ける。各項目は独立投入可。

**Phase A（DDL 不要・最優先）**
- [ ] A-1 カンバンボード（SC-71 新タブ「ボード」）＝status レーン＋カード＋D&D で `PATCH /tasks/{id}` status 更新。done 投入で完了報酬発火。新規 EP 不要。
- [ ] A-1 権限＝lead/owner は全カード D&D 可／member は自分担当カードのみ（既存認可踏襲）。移動不可は draggable=false＋tooltip。
- [ ] A-1 reduce-motion 尊重（D&D 演出抑制・framer 不使用）＋style-guide にカード/レーンのモック先行。
- [ ] A-2 マイタスク横断 backend＝新 EP **`GET /me/tasks`**（サーバー委譲・DataTable クエリ契約・assignee=me×can_access_project・project 名 join・削除済除外）。API設計 Q に表形式で追記。
- [ ] A-2 マイタスク横断 frontend＝専用一覧（新 SC-73 案・共有 DataTable）＋SC-01 ダッシュボード 1 ゾーン（直近期日 N 件）。
- [ ] A テスト＝API（自分担当のみ/漏れ無し/期日ソート）＋e2e（ボード D&D・done デルタ演出・member 制限・reduce-motion）。TC 行を `doc/テスト/` に先出し。

**Phase B（器あり・依存関係）**
- [ ] B 依存登録/解除 EP＝`POST/DELETE /tasks/{id}/dependencies`（循環 409・越境 422）＋ツリー応答に `dependencies`/`blocked_by_count`。
- [ ] B frontend＝タスク編集に「先行タスク」ピッカー（対象選択ダイアログ流用・アイコン付き候補）＋WBS/ボードにブロックバッジ。
- [ ] B（要確認）自動ブロック＝先行未完で status を自動書換えするか。**既定 OFF（バッジ表示のみ）推奨**。
- [ ] B 保留＝ガント描画（planned_*/actual_* 器＋依存）は別タスク。

**Phase C（器あり・仕様確定投票）**
- [ ] C 投票 EP＝`POST/GET /projects/{id}/spec-decisions`・`POST /spec-decisions/{id}/votes`・`PATCH /spec-decisions/{id}`（締切り）。1 人 1 票・権限・投票 XP。コンテスト投票資産を流用。
- [ ] C frontend＝SC-71 新タブ「意思決定」（争点一覧/起票/投票/確定）。
- [ ] C 保留＝確定の自動タスク化・deployment 自動反映。

## 受け側への申し送り

- **前提/注意**＝本件は solutions ドメインを**別セッションが実装中**のタイミングで起票した設計。**正本・台帳・実装コードは本調査セッションでは一切触っていない**（ドラフト＋本引継のみ）。実コードと設計ドラフトに食い違いがあれば [spec-is-source-of-truth] に従い判断（ドラフトは第一版なので実装の実態に合わせて調整可）。
- **壊しやすい箇所**＝(1) カンバン done 投入は既存の冪等ロジックに必ず乗せる（二重付与防止）。(2) D&D は framer 不使用（[modal-no-framer-css-only] の精神）＋reduce-motion 必須。(3) `GET /me/tasks` は can_access_project を必ず通す（他社/非アクセス漏れ防止）。
- **未確定点（ユーザー確認対象）**＝①マイタスク横断の画面番号（SC-73 でよいか）とダッシュボードゾーン追加の調整先（SC-01 実装者）②B の自動ブロックを入れるか（既定 OFF 推奨）③ボードのレーン内並べ替えを Phase A に含めるか（設計は「含めない＝status 一本」）。
- **正本反映の想定先（実装セッションが実施）**＝[API設計 Q](../../API設計/Q_ソリューション開発.md)（新 EP 群）／[画面設計 SC-71](../../画面設計/screens/SC-71_プロジェクト詳細.md)（ボード/意思決定タブ）＋SC-73 新規／[実装計画](../../実装計画.md)（フェーズ順）／[バックログ台帳](../../バックログ/未実装・ギャップ一覧.md)（上記残作業）。データモデルの器は既出のため追記不要の見込み（要確認）。

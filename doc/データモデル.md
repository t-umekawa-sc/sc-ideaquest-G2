## 1. 全体構成（2 層 DB）

エンティティは **2 種類の DB** に分かれて格納される（README 第9節）。

- **管理 DB（コントロールプレーン / システム共通・1 つ）**
  認証・テナント振り分けに必要な情報を全社横断で保持。ログイン時にここで所属会社を判定し、当該 **会社 DB** へ動的ルーティングする。
- **会社 DB（データプレーン / 会社ごとに物理分離・別コンテナ）**
  各社のクエスト・アイデア・チャット・ゲーミフィケーション等の機密データを隔離して保持。

```mermaid
flowchart TB
  subgraph CP["管理 DB（システム共通・1つ）"]
    companies["companies（会社）"]
    accounts["accounts（アカウント）"]
    trusted_devices["trusted_devices（信頼済み端末）"]
    otp_challenges["otp_challenges（OTPチャレンジ）"]
    system_audit_logs["system_audit_logs（監査ログ）"]
    account_sync_outbox["account_sync_outbox（会社DB同期）"]
    mail_outbox["mail_outbox（メール送信アウトボックス）"]
  end
  subgraph DP1["会社 DB #1（テナントA・物理分離）"]
    UserA["users / quests / ideas / chat_messages ..."]
  end
  subgraph DP2["会社 DB #N（テナントN・物理分離）"]
    UserN["users / quests / ideas / chat_messages ..."]
  end
  accounts -->|company_id| companies
  companies -.->|接続先識別子→.env| DP1
  companies -.->|接続先識別子→.env| DP2
  accounts -.->|account_id（論理対応・DB跨ぎFKなし）| UserA
```

**DB 跨ぎの参照は物理 FK を張れない**（別インスタンスのため）。管理 DB の `accounts` と 会社 DB の `users` は **`account_id`（UUID）で論理的に対応付け**る。整合はアプリ層で担保し、**認証系属性（`login_id`/`email`/`status`/`password_set`/`system_role`/`last_login_at`）は `accounts` を源泉に `users` へ一方向ミラー**する（アウトボックス＝§4.6 `account_sync_outbox`・冪等/結果整合）。これによりユーザ一覧は会社 DB 単独で描画できる（§5.3・§8-①）。

## 2. 命名規約・共通方針

- **物理テーブル名**: スネークケースの **複数形**（例: `quests`, `idea_revisions`, `evaluation_scores`）。
- **論理名（日本語）**: 各テーブル定義の見出しに「物理テーブル名（複数形 snake_case）＋日本語論理名」を、各カラムに「物理名＋日本語論理名」を併記する。ER 図のエンティティ名も物理テーブル名（複数形）に揃える。
- **カラム名**: スネークケース（英小文字）。
- **主キー**: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`。
  - 理由: マルチテナント・列挙耐性（連番推測を避ける）・MinIO オブジェクトキーや URL への露出耐性。`pgcrypto`（or PG13+ の `gen_random_uuid()`）前提。
- **タイムスタンプ**: `timestamptz`（UTC 保存・表示層で JST 変換）。
- **共通監査カラム（全テーブル共通装備）**: どのレコードも「**だれが・いつ・どのプログラムで**」登録／最終更新したかを追えるよう、**登録3点**（`created_at`/`created_by_id`/`created_program`）と**更新3点**（`updated_at`/`updated_by_id`/`updated_program`）を **全テーブルに必ず持たせる**。詳細は **§2.1**。
- **論理削除**: アカウントは無効化（`status=disabled`）＝論理削除（入力履歴は残す）。**`quests`/`ideas` は `deleted_at`＋`deleted_by_id` トゥームストーン**（一覧/参照は `deleted_at IS NULL` で絞る）、`quest_group_members`／`quest_members` は `removed_at`、`chat_messages` は `is_deleted`。その他も原則物理削除しない設計を優先（監査・履歴保持）。
- **外部キー**: 会社 DB 内は物理 FK を張る。**DB 跨ぎ**（accounts↔users＝`account_id` の論理対応）は **論理参照**（FK なし・アプリ整合）。**FK カラムの命名規則は §2.2** に定める。
- **Enum**: PostgreSQL の `ENUM` 型 or `text + CHECK`。本書では値集合を §3 に集約。実装ではマイグレーション容易性から `text + CHECK` を推奨（値追加が軽い）。
- **金額/ポイント**: XP・コイン・SP は `integer`（残高系は 0 以上を保証＝`CHECK (>= 0)`）。
- **添付/画像パス**: MinIO オブジェクトキー（ハッシュ名）を `text` で保持。バケット/プレフィックスは会社ごとに論理分離（実体名は元ファイル名と別）。

### 2.1 共通監査カラム（全テーブル共通装備）

**方針**: **すべてのテーブル**（管理 DB・会社 DB とも）に、以下の **6 カラムを共通装備**する。目的は「**どのレコードも、だれがいつどのプログラムで登録し、最後に更新したかが分かる**」こと。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `created_at` | 登録日時 | timestamptz | NOT NULL, default now() | レコード作成時刻（UTC） |
| `created_by_id` | 登録者ID | uuid | NULL 可 | 登録した操作者。**会社 DB→`users`／管理 DB→`accounts`**。システム/バッチ登録は NULL（`created_program` で識別） |
| `created_program` | 登録プログラム | text | NOT NULL | 登録元プログラム識別子（例: API エンドポイント名・バッチ名・画面 ID `SC-xx`・`migration`・`seed`） |
| `updated_at` | 更新日時 | timestamptz | NOT NULL, default now() | **更新の都度** now() に更新（作成時は登録日時と同値） |
| `updated_by_id` | 更新者ID | uuid | NULL 可 | 最終更新の操作者。参照先は `created_by_id` と同じ。システム/バッチ更新は NULL |
| `updated_program` | 更新プログラム | text | NOT NULL | 最終更新元プログラム識別子（作成時は `created_program` と同値） |

- **命名**: `created_by_id`/`updated_by_id` は §2.2 の操作者規則（`<動作>_by_id`）に従う。プログラム列は `_program` サフィックス（`text`）。
- **参照先**: `created_by_id`/`updated_by_id` は会社 DB では `users`、管理 DB では `accounts` を指す。会社 DB 内は物理 FK（`ON DELETE RESTRICT`）、`accounts` を跨ぐ管理 DB 側は原則同一 DB 内 FK。**利用者を伴わない登録**（メール OTP 発行・監査ログ・プロビジョニング等）は `*_by_id` を NULL とし、`*_program` に処理主体を必ず残す。
- **更新の担保**: `updated_at`/`updated_by_id`/`updated_program` はアプリ層で更新の都度必ずセットする（または `BEFORE UPDATE` トリガで `updated_at` を強制）。監査ログ（`system_audit_logs`）や版管理（`idea_revisions`）は変更内容の履歴、本 6 カラムは各行の最終状態のメタ、と役割を分ける。
- **記載の省略**: 本 6 カラムは全テーブル共通のため、以降の各テーブル定義（§4・§5）および ER 図では **一律に列挙を省略**する（6 カラムは本規約によりすべてのテーブルに自動付与される）。各定義表・ER 図に監査カラムは記載しない。なお `created_at` を並び順・集計キーに使うインデックス定義（例: `(chat_group_id, created_at)`）は、カラムが本規約で存在することを前提にそのまま記す。

### 2.2 外部キー（FK）の命名規則

**基本規則**: FK カラム名 ＝ **`<参照先テーブル名の単数形>_id`**。

- 例: `company_id`→`companies` / `quest_id`→`quests` / `idea_id`→`ideas` / `evaluation_id`→`evaluations` / `chat_group_id`→`chat_groups`。
- **単数化**: 複数形を素直に単数化する。不規則・複合語は以下に従う。
  - `companies`→`company`（`company_id`）、`activities`→`activity`（`activity_id`）
  - `quest_categories`→`quest_category`、`idea_stakeholders`→`idea_stakeholder`、`chat_messages`→`chat_message`（複合語は末尾のみ単数化）

**例外規則（役割名を付ける場合）**: 参照先が一意に決まらない／意味を明確にしたい場合は **役割名** を用いる。命名は原則 `<役割>_<参照先単数形>_id`、慣用的に参照先が自明なものに限り `<役割>_id` を許容し、**定義表に参照先（`FK→<table>`）を必ず明記**する。

1. **意味的な役割 / 同一テーブルへ複数 FK**:
   - `<役割>_id`（参照先が自明なもの）: `owner_id` / `author_id` / `editor_id` / `evaluator_id` / `recipient_id`（いずれも→`users`）
   - `<役割>_<単数形>_id`（明確化）: `mentioned_user_id`（→`users`）、`actor_account_id`（→`accounts`）
2. **自己参照**: `<役割>_<単数形>_id`。例: `requires_spell_id`（→`spells`）、`reply_to_message_id`（→`chat_messages`）
3. **操作者（誰が〜したか）**: `<動作>_by_id`（**末尾は必ず `_id`**）。例: `uploaded_by_id`（→`users`）、`granted_by_id`（→`users`）
4. **任意・多態的な参照**（1 カラムで種別により参照先が変わり得る／複数の参照候補を並べる通知等）: 接頭辞 `ref_` ＋ `<単数形>_id`。例: `ref_idea_id` / `ref_chat_message_id` / `ref_idea_revision_id` / `ref_achievement_id`。型を持たず ID のみの汎用参照は `ref_id`（FK なし）＋判別列 `ref_type`（enum・参照先テーブル名）で表す（多態参照の discriminator。例: `activities.ref_type`/`ref_id`・§5.27）。

**共通ルール**:

- FK カラムは **必ず `_id` で終える**（`_by` 単独等は使わない）。
- **参照先は定義表の `FK→<table>` 表記または説明で必ず明示**（役割名から参照先が読み取れない場合の曖昧さ回避）。
- **DB 跨ぎの参照**（`accounts`↔`users` の `account_id` 対応）は物理 FK を張らない **論理参照**。カラム名は同一規則に従い、定義表に「論理参照→…」と明記する。
- 会社 DB 内は物理 FK を張り、`ON DELETE` は原則 **`RESTRICT`**（履歴保持のため物理削除を避け、論理削除/トゥームストーンを優先）。

### 4.1 companies（会社 / テナント）

会社（テナント）。**会社単位の設定フラグ**（投票匿名化・管理者への開示・MFA 必須）を保持する（SC-92 会社設定で編集）。**参照タイミング**＝`mfa_required` はログインフロー時／`vote_anonymized`・`hide_voters_from_managers` は**表示時に都度参照**（投票表示＝API設計ドメイン D）。実行時は本テーブルを毎回引かず **Redis `company_config:{company_id}` キャッシュ経由**で読み、**設定変更（`PATCH .../settings` 等）時にキャッシュを無効化して次リクエストから即時反映**する（キャッシュ内容・無効化契機の一覧＝API設計 §1.14）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `company_code` | 会社コード | text | NOT NULL, UNIQUE | 業務上の会社識別コード（全社で一意）。ログイン時の会社指定・管理表示に使用（`db_identifier` とは別の対人向けコード） |
| `name` | 会社名 | text | NOT NULL | |
| `db_identifier` | 会社DB識別子 | text | NOT NULL, UNIQUE | 会社 DB の識別子（接続情報の実体は `.env`。ここはキー/参照のみ） |
| `status` | 状態 | company_status | NOT NULL, default `active` | active / suspended（メンテ中）。**カラム既定は `active`（定常状態）だが、会社作成 API は作成時に明示的に `suspended` を渡す**＝MVP は DBプロビジョニングが手動（compose 手編集）で作成時点では会社DBが未整備のため。プロビジョニング完了後に運営が `active` へ切替（SC-91 §4.2/§5・API設計 B） |
| `color` | 会社カラー | text | NOT NULL, default（既定色） | プリセットパレットの hex（クエストカラーと同方式） |
| `icon_image_path` | 会社アイコン画像パス | text | NULL 可 | 会社アバター/アイコン（MinIO キー・任意）。未設定時は「頭文字＋会社カラー」タイル |
| `vote_anonymized` | 投票匿名化フラグ | boolean | NOT NULL, default `true` | ON=集計数のみ表示 |
| `hide_voters_from_managers` | 管理者への投票者非開示フラグ | boolean | NOT NULL, default `true` | 匿名時に所有者/管理者へも投票者を隠す |
| `mfa_required` | MFA必須フラグ | boolean | NOT NULL, default `true` | メール OTP による MFA を必須化 |
| `game_mode_default` | ゲームモード会社既定 | boolean | NOT NULL, default `true` | 会社全体のゲーム層UI（演出・ショップ/きせかえ/魔法・実績・ランキング・ゲーム系通知・チャット魔法）の**既定** ON/OFF（SC-91 会社設定で編集・レビュー#2）。`true`＝ゲーム層あり（現行挙動）。**個人の実効値は `accounts.game_mode_override` が非 NULL ならそれを優先し、NULL なら本既定を継承**（未操作の個人＝本既定に即追従＝会社統制点）。**ゲームのロジック（XP/コイン付与・レベル計算等）は本フラグと無関係に据え置き**＝UI 表示の出し分けのみ（レビュー#2 §6）。`vote_anonymized` 等と同様 `company_config:{company_id}` キャッシュ経由で参照 |

- インデックス: `UNIQUE(company_code)`、`UNIQUE(db_identifier)`、`(status)`。
- **会社コードのフォーマット規約（初期値・調整可）**: 半角英大文字・数字・ハイフン（`A–Z` / `0–9` / `-`）、**4〜20 文字**、**先頭は英字**、**全社で一意**、**大小文字は区別しない**（入力を大文字へ正規化して保存・照合）。原則**作成時に確定し以後不変**（対人向け識別子のため変更は運用影響大）。
- 注: `hide_voters_from_managers` は `vote_anonymized=false`（記名モード）のとき意味を持たない（アプリ側で無効化表示・SC-92）。
- **運営テナント（プラットフォーム管理用の予約会社）＝ seed で 1 社（§8-⑮）**: system_admin アカウントの収容先。会社コードは予約値（例 `OPS`）・`status=active`・専用会社DB を持つ。**一般テナントと同じ物理構造**だが業務利用しない（クエスト等を作らない）＝**用途で分離**。「会社レス（`company_id` を持たない）アカウント」は非採用（案A）＝`accounts.company_id` の `NOT NULL` を維持。運営テナント自体は削除/無効化不可（ロックアウト防止・API設計 B.6）。

- 注: `login_id`・`email` はいずれも**会社内で一意**（会社跨ぎでは重複可＝独立テナント。グローバル一意は要件外）。**ログインは「会社コード（`companies.company_code`）で会社を特定 → その会社内で login_id → password」の流れ**（全社同一 URL・会社選択式にはしない＝§8-② 決定）。会社コードは端末に記憶してプリフィル可。
- **会社 DB `users` へのミラー（源泉＝本テーブル）**: `login_id` / `email` / `display_name` / `status` / `password_set` / `role`（→users.`system_role`） / `last_login_at` / `locale` は会社 DB `users` に**一方向でミラー複製**し、ユーザ一覧を会社 DB 単独で描画できるようにする（API 往復を避ける）。**源泉（source of truth）は本 `accounts`** で一意検証もここで行い、変更は §4.6 `account_sync_outbox` 経由で会社 DB へ反映する。詳細は §8-①。
- **system_admin アカウントの所属＝運営テナント（§4.1・§8-⑮）**: `company_id` は運営テナント（予約会社・例 `OPS`）を指す（会社レスは非採用＝案A）。**認可は所属ではなく `role=system_admin`（コントロールプレーン）で判定**するため、運営者は業務クエストに参加しなくてよい。**最初の system_admin は seed で作成**（ブートストラップ・§8-⑮／API設計 B.5）。**最後の system_admin は剥奪/無効化不可**（ロックアウト防止・API設計 B.6）。

### 4.4 otp_challenges（OTP チャレンジ・メール認証コード）

**実体は Redis 等の TTL 付き一時ストアを基本（§8-⑨ 決定）**。10 分 TTL で自動失効・試行回数もそこで管理し、管理 DB のテーブルとしては持たない（バッチ削除不要）。以下の定義は **Redis を導入しない構成で DB 化する場合の代替**（この場合は期限切れのバッチ削除が必要）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `account_id` | アカウントID | uuid | NOT NULL, FK→accounts | |
| `code_hash` | コードハッシュ | text | NOT NULL | `login`＝6 桁コードのハッシュ／`password_setup`・`email_change`＝リンクトークンのハッシュ |
| `purpose` | 用途 | otp_purpose | NOT NULL | login / password_setup / email_change |
| `expires_at` | 有効期限 | timestamptz | NOT NULL | **`login`＝発行から 10 分／`password_setup`（初回/再設定リンク）＝発行から 72 時間／`email_change`（メール変更確認リンク）＝発行から 24 時間**（`email_change_ttl_seconds`・ADR-0008）（SC-90 発行フロー決定 2026-07-20・失効時は管理者が再送） |
| `attempts` | 試行回数 | int | NOT NULL, default 0 | 上限で失効 |
| `used_at` | 使用日時 | timestamptz | NULL 可 | 単回使用＝`complete`／`confirm` 成功で打刻し以後は無効（`verify`/`complete`/`confirm` とも 410）。NULL＝未使用。`password_setup`・`email_change` で共用 |

- インデックス: `(account_id, purpose)`。
- **初回パスワード設定フロー（SC-93 会社アカウント管理者 / SC-92 システム管理者 のアカウント発行・PWリセット）**: `purpose=password_setup` の単回トークンをメールリンクで送付（TTL 72h）。送信基盤は dev=MailHog／prod=SMTP（SES 等）をアダプタで抽象化。`login` の 6 桁 OTP（TTL 10 分）とは用途・期限が異なる。
- **メール変更確認フロー（ドメイン K・`POST /me/email`・ダブルオプトイン・ADR-0008）**: `purpose=email_change` の単回トークンを**新メール**へリンク送付（TTL 24h・`email_change_ttl_seconds`）。到達確認（リンククリック＝`POST /me/email/confirm`）で `accounts.pending_email`→`email` を確定。最新要求のみ有効（旧 `email_change` チャレンジは失効）。

> **クエストグループ所属は管理 DB に持たない（§8-① 決定・2026-07-20）**: ユーザー × クエストグループの所属は **会社 DB `quest_group_members`（§5.5）を唯一の正**とする。ログイン時の参照範囲判定は会社 DB 接続後に行うため管理 DB 側の保持は不要（かつては `account_quest_groups` を管理 DB に置く案があったが、二重管理・機密性の観点で廃止）。割当操作（SC-90/SC-92）は対象会社の DB `quest_group_members` に対して行う。

| `action` | 操作種別 | text | NOT NULL | 例: `account.issue`/`account.edit`/`account.disable`/`account.enable`/`account.password_reset`/`company.create`/`company.update`/`company.settings_update`/`quest_group.create`/`quest_group.rename`/`quest_group.delete`/`membership.add`/`membership.remove` |

### 4.6 account_sync_outbox（会社DB同期アウトボックス）

`accounts` の `login_id`/`email`/`status`/`password_set`/`role`(→`system_role`)/`last_login_at`（および氏名等の付随情報）を**会社 DB `users` へ一方向ミラー**するためのアウトボックス。**アカウント発行/編集/無効化/PWリセット、および本人のプロフィール編集**で `accounts` を更新するのと**同一トランザクション**で 1 行 INSERT し、常駐ワーカ（または定期ジョブ）が対象会社 DB の `users` へ冪等に適用する（会社 DB は別インスタンスのため 2 相コミットは行わず、アウトボックス＋再試行で結果整合を担保）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | 行識別（ランダム・順序は表さない） |
| `seq` | 連番 | bigint | NOT NULL, Identity, UNIQUE | 挿入順の単調増加キー。取り出し/直列適用の順序に使う（uuid `id` は生成順を表さないため） |
| `account_id` | アカウントID | uuid | NOT NULL, FK→accounts | 対象アカウント |
| `company_id` | 会社ID | uuid | NOT NULL, FK→companies | 反映先会社 DB の特定に使用 |
| `op` | 操作種別 | sync_op | NOT NULL | `upsert`（発行/編集）/ `disable`（無効化）/ `enable`（再有効化） |
| `payload` | 反映内容 | jsonb | NOT NULL | `users` へ反映する値（`login_id`/`email`/`status`/`password_set`/`system_role`/`last_login_at`/`locale`/`display_name` 等）。会社 DB 側で **`account_id` をキーに upsert**（冪等） |
| `status` | 同期状態 | sync_status | NOT NULL, default `pending` | `pending` / `done` / `failed` |
| `attempts` | 試行回数 | int | NOT NULL, default 0 | 失敗時のリトライ回数（上限超で `failed`＝要手動対応） |
| `processed_at` | 処理日時 | timestamptz | NULL 可 | 反映完了時刻 |

- インデックス: `(status, seq)`（未処理の取り出し順）、`(account_id)`、`(company_id, status)`。
- **処理フロー（ワーカ・実装で固定する仕様）**:
  1. **書込側（同一トランザクション）**: エンドポイント処理が `accounts` を更新するのと**同一 Tx**で本テーブルへ 1 行 INSERT（`status=pending`）。両方コミット or 両方ロールバック＝「反映すべき仕事」の記録が原子的に残る（＝dual-write を避ける）。
  2. **取り出し**: 常駐ワーカ（`worker.py`・コーディング規約 §3.4）が `status=pending` を **`seq`（挿入順の単調増加）昇順**で読む。
  3. **接続先解決**: 行の **`company_id` → 管理DB `companies.db_identifier` → `.env` の接続情報**で反映先の会社 DB を解決（`get_tenant_session`）。※接続情報の実体は `.env`、管理DB `companies` は参照キー（§4.1）。
  4. **適用（冪等）**: 会社 DB で `payload` を **`account_id` をキーに `users` へ upsert**。発行（初期所属を相乗する場合）は **`users` → `quest_group_members` の順**で適用＝FK 順序を保証（API設計 B.5）。
  5. **消し込み/リトライ**: 成功で `status=done`・`processed_at` 記録。失敗は `attempts++` でリトライ、上限超で `status=failed`（要手動対応・監視/アラート対象）。
- **冪等性**: 会社 DB 側は `account_id` をキーに upsert（同一イベントの再適用が安全＝**at-least-once** 配信を前提）。反映先 `users` 行が未作成でも upsert で作成される（プロビジョニング直後の初回同期を兼ねる）。
- **順序（厳密・実装で固定）**: **同一 `account_id` は `seq`（＝挿入順＝因果順。壁時計ではない）で直列適用**。**失敗時はその `account_id` の後続を先に進めない（ヘッドオブライン・ブロッキング）**＝#3 が失敗したら #4 以降を待たせる（古い状態が新しい状態を上書きする退行を防ぐため）。**異なる `account_id` 間は独立**＝並列処理可（1 アカウントの `failed` 滞留が他アカウントを止めない）。
- `otp_challenges` 同様、実体を Redis/ジョブキューにする案もあるが、確実性重視で管理 DB にアウトボックステーブルを持つ本方式を基本とする（§8-①）。
- **適用対象＝発行/編集/無効化/PW/プロフィール（新規ミラー含む）**。**既存アカウントの所属変更（B.3）は user ミラー済みのため outbox を介さず会社 DB へ直接 upsert/トゥームストーン**（順序問題がなく直書きで十分・API設計 B.5）。

### 4.7 mail_outbox（メール送信アウトボックス）

認証系のシステム生成メール（**MFA の OTP／初回・再設定パスワード設定リンク／アカウント一時ロック通知**）を**非同期送信**するためのアウトボックス（[`ADR/ADR-0007_メール送信の非同期化.md`](ADR/ADR-0007_メール送信の非同期化.md)）。§4.6 `account_sync_outbox` と**型は同じ**（積む→常駐ワーカが処理→再試行→`attempts` 上限で `failed`）**だが用途は別**＝DB ミラーではなく**メール送信**で、**会社 DB を跨がない**（宛先は enqueue 時に確定）。application 層は SMTP を叩かず本テーブルへ 1 行 INSERT して即応答し、**専用のメールワーカ（account_sync とは別プロセス `mail_worker.py`）**が取り出して SMTP 送信する。これで同期送信が生む弱いタイミングオラクル・SMTP 失敗時の 500・列挙耐性の綻びを解消する（ADR-0007 §1）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | 行識別（ランダム・順序は表さない） |
| `seq` | 連番 | bigint | NOT NULL, Identity, UNIQUE | 挿入順の単調増加キー。取り出しの**安定順序**に使う（uuid `id` は生成順を表さない＝§4.6 の `seq` と同じ思想） |
| `to_email` | 宛先 | text | NOT NULL | 送信先メールアドレス（enqueue 時に確定） |
| `category` | 種別 | mail_category | NOT NULL | `otp` / `password_setup` / `lock_notification`（テンプレ選択・可視化・監視） |
| `locale` | 言語 | locale | NULL 可 | enqueue 時に確定した宛先の言語（`accounts.locale`・i18n）。NULL＝システム既定 |
| `secret` | 秘匿値 | text | NULL 可 | OTP コード／設定リンクのトークンを**単独で**保持。`lock_notification` は NULL。**送信成功／端末失敗で NULL 化**（完成本文は保存しない・下記） |
| `account_id` | アカウントID | uuid | NULL 可, FK→accounts | 監視/相関用（任意）。送信自体は本列に依存しない |
| `company_id` | 会社ID | uuid | NULL 可 | 監視/相関用（任意） |
| `status` | 送信状態 | mail_status | NOT NULL, default `pending` | `pending` / `sending` / `done` / `failed` |
| `attempts` | 試行回数 | int | NOT NULL, default 0 | 送信失敗リトライ回数（`mail_outbox_max_attempts` 超で `failed`） |
| `claimed_at` | 確保日時 | timestamptz | NULL 可 | `sending` へ遷移した時刻（滞留再送の判定に使用・下記 4） |
| `created_at` | 生成日時 | timestamptz | NOT NULL, default now | enqueue 時刻 |
| `processed_at` | 処理日時 | timestamptz | NULL 可 | 送信完了（または `failed` 確定）時刻 |

- インデックス: `(status, seq)`（未処理の取り出し順）、`(account_id)`（相関）。
- **件名・本文は列に持たない**＝`category`＋`locale`＋`secret`＋設定（有効期限等）から**メールワーカが送信時にレンダリング**する（テンプレは実装 1 箇所に集約）。これにより **OTP や設定リンクを埋め込んだ完成本文を DB に残さない**（秘匿値の at-rest 最小化・ADR-0007 §2.7）。
- **処理フロー（メールワーカ・実装で固定する仕様・ADR-0007 §2.4/§2.5）**:
  1. **enqueue（積むだけ）**: application 層が本テーブルへ 1 行 INSERT（`status=pending`）して即応答。`password-setup/request` は `otp_challenges` 作成と**同一 Tx**に相乗せて原子化。OTP 送信・ロック通知は周辺に DB 書込が無いため**単独 INSERT**。
  2. **確保→送信**: `pending` を `seq` 昇順で取り出し、`UPDATE ... SET status='sending', claimed_at=now WHERE id=? AND status='pending'` で**該当 1 行を原子的に確保**してから SMTP 送信（多重巡回でも二重取得しない）。
  3. **消し込み/リトライ**: 成功で `status=done`＋`secret=NULL`＋`processed_at`。失敗は `attempts++`・`status=pending` へ戻す（上限超で `status=failed`＋`secret=NULL`）。
  4. **滞留の再送**: `sending` のまま `mail_outbox_sending_reclaim_seconds`（既定 60 秒）を超えた行（＝SMTP 成功〜`done` 書込の間でクラッシュした疑い）だけを `pending` へ戻す。
  5. **掃除**: `done` かつ `processed_at` が `mail_outbox_done_retention_seconds`（既定 7 日）より古い行を**メールワーカが**削除（間引いて DELETE・別 cron を立てない）。`failed` 行は自動削除しない（要手動対応の異常シグナル）。
- **配送保証＝at-least-once**: 「SMTP 送信」と「`done` 書込」は単一 Tx にできないため、クラッシュ窓で**まれに重複送信**し得る（OTP/通知/リンクの重複受信は無害・トークンは単回/TTL）。exactly-once は採らない（ADR-0007 §2.5）。**順序保証・HOL ブロッキングは無い**＝各メールは独立事象で、1 通の失敗が他を止めない（§4.6 の直列適用とは対照的）。
- **§4.6 account_sync_outbox との違い（要点）**: (a) 会社 DB を**跨がない**（宛先確定のみ・ワーカは SMTP だけ）／(b) **順序不要・独立処理**（因果順が無い）／(c) 秘匿値を `secret` 列に隔離し送信後破棄／(d) 別プロセスの**メールワーカ**が処理（障害隔離）。
- `otp_challenges`・`account_sync_outbox` 同様、実体を Redis/ジョブキューにする案もあるが、**確実配送重視で管理 DB にアウトボックステーブルを持つ本方式を基本**とする（ADR-0007 §2.1）。

### 5.6b quest_group_links（クエスト×クエストグループ＝参加部署／アクセス条件・複数部署横断）

**1クエストに紐づく「参加部署（クエストグループ）」の多対多（0..N・2026-09-11 再決定・FR-38）**。役割は**アクセス条件（門番）**＝*参照するには、作成者を除き、いずれかの参加部署に現在所属していること*。**主グループ（primary）の概念は廃止**（フラットな 0..N・すべて同格）。

- **アクセス条件（門番）である**＝可視性・詳細・チャット・アイデア・評価すべてで「現在いずれかの参加部署に所属」を要求（§5.6/C.0）。**アクセスの都度、現在の所属で再判定**（異動で外れたら参照不可＝動的失効）。
- **参加者（候補）の範囲を縛る**＝パーティー候補は参加部署の有効所属者に限定（会社全体ではない）。参加資格のない部署のユーザーの追加は 422（§5.8/C.3）。
- **メンバーピッカーの部署フィルタも参加部署のみ**（参加部署に無い部署の人は追加できない＝そもそも候補に出さない）。
- **作成者の所属は不問**＝作成者は別格で、参加部署のどれにも所属していなくてよい（PM 的関与など。部署選択は会社の全部署ディレクトリから可）。
- **可変**＝作成後も追加/除外できる（`owner`/`quest_admin`・API C.2）。**0 件も可**＝その場合は部署条件なしで、**参照可は作成者＋名指しパーティー員のみ**（名指しは会社の有効ユーザー全体から選べる・異動失効なし）。1 件以上設定すると、以降は候補・アクセスがその参加部署に絞られる。
- **部署を外すと**、その部署にしか所属しないパーティー員は**再判定で参照不可**になる（除外自体は許容＝異動と同じ扱い。UI は影響人数を警告）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `quest_id` | クエストID | uuid | NOT NULL, FK→quests | |
| `quest_group_id` | クエストグループID | uuid | NOT NULL, FK→quest_groups | 参加部署（クエストグループ） |
| `created_at` | 追加日時 | timestamptz | NOT NULL, default now() | 部署を関連付けた日時 |

- インデックス: **`UNIQUE(quest_id, quest_group_id)`**（同一部署の重複関連付け防止）、`(quest_group_id)`（部署→クエスト逆引き＝一覧の部署絞込）。**主グループの部分 UNIQUE は廃止**。
- **関連部署の追加/除外は行の挿入/削除**（軽量な関係行・監査は `system_audit_logs`／クエスト編集履歴）。
- **【将来拡張フック】動的メンバーシップ導出**＝本モデルは既に**アクセスを現所属で再判定**するため、異動による**失効**は自動。将来さらに部署所属者を**自動でパーティー追加**（既定権限付与・参加通知 H・チャット購読）まで踏み込む場合の**アンカーは本テーブル**で、実装時に `quest_members.source`（`manual`／`group:<id>`）等の provenance 列を追加する。**現時点では追加は名指し（`manual`）のみ**（投機的な列は今は置かない）。

### 5.8b quest_join_requests（クエスト参加リクエスト・FR-40）

発見カタログ（SC-13）から出す参加申請。作成者/`quest_admin` が承認/却下し、承認で `quest_members` に追加。**1ユーザー1行（全体一意）**で status 遷移により「却下→後日承諾」を1行で表現する（部分ユニークにしない＝却下行を残す）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `quest_id` | クエストID | uuid | NOT NULL, FK→quests | |
| `user_id` | 申請者ID | uuid | NOT NULL, FK→users | 発見可能（`can_discover_quest`）なクエストにのみ申請可（C.8） |
| `status` | 状態 | join_request_status | NOT NULL, default `pending` | pending/approved/rejected/withdrawn（§3 enum・遷移規則） |
| `message` | 申請メッセージ | text | NULL 可 | 任意の一言（申請時） |
| `created_at` | 申請日時 | timestamptz | NOT NULL, default now() | |
| `decided_at` | 決定日時 | timestamptz | NULL 可 | 承認/却下した日時 |
| `decided_by_id` | 決定者ID | uuid | NULL 可, FK→users | 承認/却下を実行した作成者 or `quest_admin` |

- インデックス: **`UNIQUE(quest_id, user_id)`**（1ユーザー1行・全体一意＝却下行を残して後日 `rejected→approved` するため**部分ユニークにしない**）、`(quest_id, status)`（クエスト×状態＝パーティータブの pending/rejected 一覧）、`(user_id, status)`（申請者ダッシュボード）。
- **承認（`→approved`）**＝同一 UoW で `quest_members` に追加（既定権限 comment/vote/idea_create・トゥームストーン再利用）＋`decided_at`/`decided_by_id` 記録。post-commit で申請者へ通知（H `join_request_decided`）。
- **却下（`→rejected`）は非終端**＝行を残し一覧下部に表示。`rejected→approved`（後日承諾）は作成者/`quest_admin` のみ。`rejected→pending`（申請者の再申請）は当面不可。
- **取消（`→withdrawn`）**＝申請者本人が `pending` を取り下げ。

### 5.14b chat_thread（チャットスレッド・会話の単一の親／ホスト非依存）

**チャット中核（`chat_messages`/`chat_reads`/`reactions`＋従属の mentions/quotes/attachments）の唯一の所属**。中核は `thread_id` ただ一つで動く＝**ホスト非依存の自己完結サブシステム**（§3.8「ループ機構は一般化して共有」・FR-42・migration 0035）。将来どの機能にチャットを足しても**中核の migration/分岐は不要**＝ホスト側が `chat_thread` を 1 本持つだけでよい（＝二度と分離しない）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `owner_type` | ホスト種別 | text | NOT NULL, CHECK in (`idea`,`concept_scope`) | ポリモーフィック所有者の種別。将来拡張は**値を足すだけ** |
| `owner_id` | ホストPK | uuid | NOT NULL | ホストのリンク表 PK（`idea`→`chat_groups.id` / `concept_scope`→`concept_chat_scopes.id`）。**ソフト参照**（逆引き用・FK は張らない） |

- 制約: `UNIQUE(owner_type, owner_id)`（1 ホスト 1 スレッド・冪等生成 `ensure_chat_thread`）。インデックス `(owner_type, owner_id)`。
- **非対称の設計意図**: 中核の子テーブル（message/read/reaction）→ `chat_thread` は**堅い FK**。thread → ホストは owner_type/owner_id の**ソフト参照 1 箇所のみ**（案X）。これにより中核はホストの意味を知らずに済み、ホスト種別の分岐は application の門番 resolver（`_resolve_host`）1 箇所に閉じる。
- 門番（購読 L.2・投稿/編集/削除/リアクション）は owner_type で分岐＝`idea`＝公開+パーティー / `concept_scope`＝draft 可視性+パーティー。realtime 購読トピックは `chat:{thread_id}`。

通常（絵文字）＋魔法（SP 解放・エフェクト）の 2 層。**装飾/社交演出のみ**（XP/評価/投票に非影響）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `chat_message_id` | チャットメッセージID | uuid | NOT NULL, FK→chat_messages | |
| `thread_id` | スレッドID | uuid | NOT NULL, FK→chat_thread | 魔法の「1 チャット 1 回」制約に使用（§5.14b・migration 0035・旧 `chat_group_id` から張替）。ホスト非依存 |
| `user_id` | ユーザーID | uuid | NOT NULL, FK→users | |
| `type` | リアクション種別 | reaction_type | NOT NULL | normal / magic |
| `emoji` | 絵文字コード | text | NULL 可 | 通常時の絵文字 |
| `spell_id` | 魔法ID | uuid | NULL 可, FK→spells | 魔法時の Spell 参照 |

- 制約:
  - `CHECK ((type='normal' AND emoji IS NOT NULL AND spell_id IS NULL) OR (type='magic' AND spell_id IS NOT NULL AND emoji IS NULL))`
  - **魔法①**: `UNIQUE(thread_id, user_id, spell_id) WHERE type='magic'`（1 チャット〔thread〕につき「同一ユーザー × 同一 Spell」1 件・ホスト非依存）

- 注: `thread_id` は `chat_message_id` から辿れるが、部分ユニーク制約に用いるため非正規化して保持（§5.14b）。
- **通常リアクションの絵文字（§8-⑪ 決定）**: 候補・バリデーションは **`reaction_emojis` マスタ（`is_active=true`）を正**とする（任意絵文字ピッカーにはしない）。`emoji` は絵文字文字を保持（後で無効化しても過去分は残る）。**同一ユーザー×同一絵文字は不可**（上記 UNIQUE）＝1 ユーザーが 1 メッセージに付けられる通常リアクションは最大でセットの種類数。魔法は既存ルール（1 メッセージ 1 魔法・早い者勝ち）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |

>
> **編集権限（2026-09-21 確定・[API N.0](API設計/N_情報インプット.md)）＝フィールド群でオーナーが違う**（従来の「curated 後は curator のみ編集」を上書き）:
> - **内容**（`title`/`body_html`/`source_url`/参考資料）＝**作成者のみ**（`status` 非依存・curator も不可）。新規作成は会社内 active 全員（＝各自が作成者）。**内容の編集履歴を保持**（下記 Phase C 追加）。

> **Phase C 追加テーブル**（実装済み・migration `0029`/`0030`）:

> - **内容の編集履歴（revisions）**＝`title`/`body_html`/`source_url`＋**`attachments`（参考資料の表示名一覧・昇順／2026-09-22 追加＝§17 で参考資料も「内容」）**のスナップショット＋編集者＋日時（アイデア版管理と同型）。判定後も作成者が内容を編集できるため、triage 時点の内容を追跡可能にする。`info_item_revisions`（migration `0029`）＝`info_item_id` FK・`revision`（版番号）・`editor_id` FK・`changes`（JSONB スナップショット）・`created_at`。**更新履歴は「何が変わったか」を見せる**＝前版比の変更フィールド（`changed_fields`）と差分（テキストは語句差分・参考資料は旧→新）を**表示時にサーバーが前版と比較して算出**（`GET /info-items/{id}/revisions/{revision}/diff`・§85・アイデア §5.14 と同方式）。旧スナップ（`attachments` 無し=None）は誤検知回避で差分対象外。**参考資料の追加/削除だけでも保存単位で1版**（DFT-N-002）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `info_item_id` | 情報ID | uuid | NOT NULL, FK→info_items | |
| `target_type` | 相手種別 | info_link_target | NOT NULL | ideas/concepts/quests/assumptions（discriminator） |
| `target_id` | 相手ID | uuid | NOT NULL | 多態参照＝物理 FK なし（§2.2 #4） |

| `rejected_at` | 棄却日時 | timestamptz | NULL 可 | 自動リンクを人が「不要」と棄却（非表示・**行は残す**＝物理削除しない）。**再計算の upsert は既存行の `rejected_at` を尊重＝棄却済み auto リンクは復活しない**（[API N.6](API設計/N_情報インプット.md)） |

### 5.38〜5.45 コンセプト段（FR-42・[コンセプト機能 ISO56001 再設計](設計ドラフト/コンセプト機能_ISO56001_再設計.md)）

> **第一版（2026-09-24）**。ISO 56001 ②コンセプトの創造＋③コンセプトの検証（原本 §8.3.3/§8.3.4）を担う新ドメイン。**ループ機構（議論/評価/情報リンク/版）はアイデア段と同型を一般化して共有**（§3.8・DRY）＝チャットは §5.16/§5.31 を最小侵襲拡張（§5.45）、評価は `evaluation_status`/`evaluation_visibility` enum を共有、情報リンクは `info_links`（`target_type='concepts'/'assumptions'`）を流用。**中身（入力項目 §3.3・評価観点 §3.6）はコンセプト固有に別設計**。権限はクエスト権限（FR-27）を踏襲（詳細は [API設計 P](API設計/P_コンセプト.md)）。
> **スコープ境界（[コンセプト機能 ISO56001 再設計](設計ドラフト/コンセプト機能_ISO56001_再設計.md) §1.1）**＝`concepts.quest_id`／`assumptions.quest_id` は**クエスト内（ホームスコープ／検証プールのスコープ）**を指す（将来 `initiative_id` へ一般化しうる継ぎ目）。**クエストをまたぐコンセプトは直接持たず**、横断は「収束クエスト」（複数ソース取り込みの後続クエスト）で実現。**④ソリューション開発・⑤導入はクエスト外＝PM/WBS 領域**（本テーブル群は go 判定まで）。**ER 図・画面（SC-xx）は本テーブル群を基に別途起こす（次アクション）**。

### 5.38 concepts（コンセプト＝アイデアからの昇華）

> ②コンセプトの創造の成果物（§3.3）。**クエスト（＝イニシアチブ/検証プール）に属す**。1アイデア群から N 候補が競い、owner が勝ち残りを選定（`is_selected`）。粒度＝「経営が投資判断できる証拠」まで（機能仕様/計画はソリューション段＝持たない）。`ideas`（§5.10）と同型。

| `author_id` | 作成者ID | uuid | NOT NULL, FK→users | |

| `value_proposition` | 狙う価値（価値提案） | text | NULL 可 | ISO §8.3.3 value proposition |
| `target` | 対象 | text | NULL 可 | ユーザ/既存顧客/市場 |
| `differentiation` | 競合・差別化 | text | NULL 可 | |
| `solution_form` | 解の形態＋必要能力（粗） | text | NULL 可 | "Xができる"レベル（仕様に踏み込まない＝境界） |
| `viability` | 採算・事業性（価値実現モデル） | jsonb | NOT NULL, default `'{}'` | ISO §8.3.3 value realization model＝コスト/収益モデル/ROI 等の柔軟構造（**確定時の必須検証は API 層**） |

- 権限＝クエスト権限（FR-27）踏襲：作成/編集＝所属クエストの owner/quest_admin＋作成者、選定（`is_selected`）＝owner/quest_admin、評価＝evaluator。情報リンク＝`info_links`（`target_type='concepts'`）・反証で要再評価（§5.35・§3.5）。

### 5.39 concept_source_ideas（コンセプトの由来アイデア・M:N）

コンセプトがどの**選別済みアイデア**から昇華したか（§3.1・複数アイデア→収束）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `concept_id` | コンセプトID | uuid | NOT NULL, FK→concepts | |
| `idea_id` | アイデアID | uuid | NOT NULL, FK→ideas | 由来（同一クエストの選別済みアイデア） |

### 5.40 assumptions（前提＝クエスト単位の検証プール・第一級・§3.5）

> ③コンセプトの検証の中核（原本 §8.3.3 out/§8.3.4「critical uncertainties or **assumptions**」）。**クエスト（イニシアチブ）単位の検証プール**として持ち、コンセプトへ M:N（§5.42）。競合する複数コンセプトが同じ前提を共有し、1回の検証を再利用（DRY）。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `quest_id` | クエストID | uuid | NOT NULL, FK→quests | 検証プールの単位 |
| `statement` | 前提の記述 | text | NOT NULL | 「〜が成り立つはず」 |
| `current_verdict` | 現在の判定 | assumption_verdict | NOT NULL, default `inconclusive` | **最新の `assumption_validations`（§5.41）から導出したキャッシュ**。イベント追記で更新 |
| `created_by_id` | 作成者ID | uuid | NULL 可, FK→users | 共通監査（§2.1） |
| `created_at` | 作成日時 | timestamptz | NOT NULL, default now() | |

- インデックス: `(quest_id)`、`(quest_id, current_verdict)`（反証の抽出）。
- 編集権限＝**検証プール所有（クエスト owner/quest_admin）に寄せる**（個別コンセプト owner が他コンセプトの根拠を勝手に変えない・§3.5）。情報リンク＝`info_links`（`target_type='assumptions'`）・反証で要再評価。

### 5.41 assumption_validations（検証イベント・追記型で履歴・§3.5）

1前提に**1件以上**。検証手段＝ISO §8.3.4 tests/experiments/pilots/studies。**追記型**＝再検証は新イベントを足して履歴を残す（なぜ・いつ判定が変わったか辿れる）。前提の現在判定＝最新イベント。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `assumption_id` | 前提ID | uuid | NOT NULL, FK→assumptions | |
| `method` | 検証方法 | text | NOT NULL | tests/experiments/pilots/studies 等の記述 |
| `result` | 結果 | text | NULL 可 | 得られた事実・データ |
| `verdict` | 判定 | assumption_verdict | NOT NULL | supported/refuted/inconclusive（§3.5） |
| `validated_on` | 検証実施日 | date | NOT NULL | **エビデンスの古さ**（古い前提は再検証を促す・ISO56001 §9.1 継続的モニタリング） |
| `scale` | 規模 | text | NULL 可 | サンプル数/対象の記述＝**検証の強さ**（n=3 と n=50 の重み差） |
| `created_by_id` | 記録者ID | uuid | NULL 可, FK→users | 監査 |
| `created_at` | 記録日時 | timestamptz | NOT NULL, default now() | 監査（`validated_on`〔実施日〕とは別＝記録日を区別） |

- インデックス: `(assumption_id, validated_on DESC)`（最新イベント＝現在判定の導出）、`(assumption_id, created_at)`。
- **反証波及**＝`verdict=refuted` の追記で、リンク先の全 `concept_assumption_links.is_stale=true`＋各コンセプトの作成者/評価者へ通知（post-commit・§5.42・§3.5）。前提の `current_verdict` も更新。

### 5.42 concept_assumption_links（コンセプト↔前提 M:N＋重要度・§3.5）

前提を複数コンセプトで共有しつつ、**重要度はリンク単位**（同じ前提でもコンセプトごとに致命/補助が違う）。エビデンス（方法/結果/判定）は前提側の単一ソース。

| --- | --- | --- | --- | --- |

| `concept_id` | コンセプトID | uuid | NOT NULL, FK→concepts | |
| `assumption_id` | 前提ID | uuid | NOT NULL, FK→assumptions | 同一クエストの検証プール |
| `criticality` | 重要度 | concept_criticality | NOT NULL, default `major` | critical/major/minor（評価・判定の重み付け） |
| `is_stale` | 要再評価フラグ | boolean | NOT NULL, default `false` | 共有前提が反証に転じたら true（§5.41 波及）。再評価で解除 |

### 5.45 concept_chat_scopes（コンセプト議論ルーム・§3.7／concept_scope ホストの owner adapter）

> コンセプトは多面的なので**複数ルーム**＝総合1＋グループ3〜5＋前提スレッド。**チャット機構はアイデアと同型を一般化して共有**（§3.8・DRY）＝各スコープが `chat_thread`（§5.14b・`owner_type='concept_scope'`・`owner_id=concept_chat_scopes.id`）を 1 本持ち、チャット中核（`chat_messages`§5.16 / `chat_reads`§5.31 / `reactions`§5.18）は `thread_id` ただ一つで動く。

| 物理名 | 論理名 | 型 | 制約 / 既定 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | ID | uuid | PK | |
| `concept_id` | コンセプトID | uuid | NOT NULL, FK→concepts | 親コンセプト |
| `kind` | 種別 | concept_chat_scope_kind | NOT NULL | overall/group/assumption（§3 enum） |
| `label` | ルーム名 | text | NULL 可 | group の束名（例〔価値・対象・競合〕）。overall/assumption は導出可 |
| `assumption_id` | 前提ID | uuid | NULL 可, FK→assumptions | `kind=assumption` のとき紐付く前提（前提1件=1スレッド） |
| `position` | 並び順 | int | NOT NULL, default 0 | ルーム表示順 |

- インデックス: `(concept_id, position)`、`UNIQUE(concept_id, kind, assumption_id)`（同一前提スレッドの重複防止・overall は concept 内 1 件）、`(assumption_id) WHERE assumption_id IS NOT NULL`。
- **overall は必須1**（コンセプト作成時に自動生成＝スコープ生成時に `chat_thread` も冪等生成）。group は 3〜5 の小さな固定集合（自由増殖させない・§3.7）。assumption スレッドは前提リンク時に用意。
- **チャット独立化（案X・2026-09-26 改訂・migration 0035）**: 当初の「`chat_messages`/`chat_reads` に `concept_chat_scope_id` を足す最小侵襲拡張（2026-09-24）」は、ホストを増やすたびに中核の migration/分岐が要る**閉じた列挙**だった。これを `chat_thread`（§5.14b）に一般化し、中核は `thread_id` ただ一つで動く**自己完結サブシステム**へ（＝将来どのホストにも無改修で載る・二度と分離しない）。**reactions/mentions/chat_message_quotes/attachments は `chat_messages` にぶら下がるため無改修で共有**。未読/メンション/活発度は**コンセプト単位ロールアップ＋各ルーム個別**の二段（§3.7・アプリ集計）。

### 5.46 concept_votes（コンセプト投票・賛成/反対・§3.4）

## 6. 全文検索の索引（FR-31）

- 対象（会社 DB）: `ideas`（`title`/`body`/`value`/`note`）＋ `chat_messages`（`body`）＋ **`attachments`（`original_name`＝添付ファイル名・§8-④ 決定）**。
- **エンジン ＝ 決定（2026-07-20）: PGroonga**（日本語の分かち書き不要・`pgroonga_score`・`pgroonga_snippet_html`。DB 内完結・追加コンテナ不要）。代替＝**pg_bigm**（採用しない・記録のみ）。将来高精度化＝Meilisearch / OpenSearch＋kuromoji（別コンテナ・同期要）。
  - **導入**: 検索は会社スコープのため**拡張は会社 DB のみ**に導入（管理 DB は不要）。会社 DB の migration で `CREATE EXTENSION pgroonga` ＋ 索引作成。Postgres イメージに PGroonga を同梱（カスタムイメージ）。
- 索引例（PGroonga）:
  - `CREATE INDEX idx_ideas_fts ON ideas USING pgroonga ((title || ' ' || body || ' ' || value || ' ' || coalesce(note,'')));`
  - `CREATE INDEX idx_chat_messages_fts ON chat_messages USING pgroonga (body);`
  - `CREATE INDEX idx_attachments_fts ON attachments USING pgroonga (original_name);`

## 7. 集計・派生値の扱い（XP/コイン/SP/ランキング）

数値は初期値・調整可（README 第6節）。

- **XP 付与**: 自アイデア選定=200 / アイデア投稿=50 / 評価実施=30 / ログイン=10 / 投票=5 / チャット=5。`activities(kind=xp_gain)` に記録し、`users.xp` を更新。
  - **日次上限（§8-⑥ 決定・初期値）**: ログイン=1回/日（10XP/日）＝**付与契機は「新しい JST 日の最初の認証済みリクエスト」**（ログイン成功に限らない・持続セッションでも毎日成立・API設計 A.1／G.6）／**投票=XP対象は5回/日**（最大25XP/日）／**チャット=XP対象は10回/日**（最大50XP/日）。上限超過分は行動自体は成立するが XP は付与しない。判定は `(user_id, reason, created_at の JST 日付)` 集計（日境界 JST＝§7 ランキング週起点と同一基準）。
  - **投票 XP は各アイデアにつき初回のみ（§8-⑥ 決定）**: 賛成/反対の**切替・取消・再投票では追加付与しない**（トグルでの稼ぎ防止）。冪等判定＝`activities(kind=xp_gain, reason='vote', ref_type='ideas', ref_id=<idea_id>)` の存在（投票行を削除→再作成しても元帳は残るため二重付与なし）。日次上限は「初回投票が成立した回数」に対して効く。
- **レベル**: Lv n→n+1 必要 XP = `100+(n-1)×50`（総量式の線形上昇）。`users.level` は `xp` の従属キャッシュ。レベルアップで **SP+1**（`activities(kind=sp_gain, reason=levelup_sp)`＋`users.skill_point_balance` 更新）。**レベル上限は設けない（§8-⑥ 決定）**＝XP 従属の進捗表示・過剰 SP は無害に累積（魔法は有限）。
- **コイン**: 行動では付与せず、**評価点連動のみ**（希少）。全評価者×全 5 観点の均等平均 `avg` に対し `round(avg × 10)`（最大 50/アイデア）を投稿者へ付与。**加えて実績獲得ボーナス**（ティア連動 20/50/150）。**確定タイミング＝一括確定（§8-⑥／トリガの具体は §8-⑱・API設計 F.4 が canonical）**: **アイデア単位で 1 回だけ**確定し、**(a) その時点で当該クエストの `evaluator` 権限保持者（有効所属）が全員そのアイデアを `submitted` 済みになった瞬間**、または **(b) クエストが `completed` に遷移した時**の**いずれか早い方**で平均を確定して付与する。**付与後は取り消さない/再計算しない**（都度再計算は使用済みコインとの矛盾＝残高マイナスを招くため不採用。確定はスナップショット）。冪等性＝`activities`（`reason=evaluation_coin`,`ref_type=ideas`,`ref_id=idea_id`）の存在で二重付与を防ぐ（投票 XP と同方式）。`visibility` は表示制御のみでコイン平均計算には影響しない（全 `submitted` 評価で算出）。評価者本人の「評価実施+30XP」は提出時に即付与（別枠・`reason=evaluation`）。
- **SP 消費**: 魔法解放（`user_spells` 追加＋`activities(kind=sp_spend)`＋残高減算）。前提魔法の解放済みが必要（スキルツリー）。
- **コイン消費**: ショップ購入（`user_items` 追加＋残高検証＋減算＋`activities(kind=coin_spend)`）。サーバー側で残高・価格を検証。
- **ランキング**（SC-41 / ダッシュボード週間 / クエスト内週間）: スコア＝期間内の **獲得 XP＋獲得コイン**（`activities` から集計）。SP は対象外。クエスト内ランキングは `activities.quest_id` で絞る。
  - **週起点/TZ/タイブレーク（決定・2026-07-20）**: 週起点＝**月曜 00:00（JST／Asia-Tokyo 固定）**。集計は `created_at`（UTC 保存）を JST 換算して週境界を判定。同点タイブレーク＝**獲得 XP → 獲得コイン → 先に到達した順**（同スコアなら XP が多い方、なお同じならコイン、なお同じなら当該スコア到達が早い方）。会社別 TZ は当面対象外。
- **実装方針**: 残高（`users.xp/coin_balance/skill_point_balance`）は **キャッシュ**で持ちつつ、真実は `activities` 元帳。整合性のため付与/消費は必ず `activities` 追記＋残高更新を **同一トランザクション**で行う。

15. **運営テナント seed＋最初の system_admin ブートストラップ ＝ 決定（2026-07-31）**: 「どの会社にも属さないアカウント」は**非採用**（案A）。`accounts.company_id` は `NOT NULL` を維持し、**運用専任の system_admin は seed で用意する「運営テナント（プラットフォーム管理用の予約会社）」に収容**する。狙い＝(a) 既存のログイン（会社コード）・一意制約（`UNIQUE(company_id, …)`）・ミラー/outbox 機構を**変更せず流用**、(b) プラットフォーム初期化時（会社 0 件）の**最初の system_admin をどう作るか**というブートストラップ問題を解決。**手順**: プロビジョニング/初期 seed で ①運営テナント（`companies` に予約会社コード〔例 `OPS`〕・`status=active`・専用会社DB）を作成 → ②`accounts` に最初の system_admin（`role=system_admin`）を INSERT → ③通常の outbox で会社DB `users` へミラー → ④初回ログイン。**初期パスワードの与え方は 3 択（2026-08-02 改定・メールは必須にしない＝seed は DB 直アクセスのため）**: **(a) 既定＝安全に供給された初期PW（env 例 `BOOTSTRAP_ADMIN_PASSWORD`）を Argon2id ハッシュして `password_set=true` で投入＋初回ログイン時に強制変更**（メール不要）／(b) `password_set=false` で seed しメールリンク（A.7・`otp_challenges` purpose=`password_setup`）で設定（メール基盤が稼働する環境）／(c) `password_set=false` のまま setup トークンを seed がコンソール/運用チャネルへ out-of-band 出力。**デフォルト/ハードコードの既知パスワードは禁止**（必ず供給された強い秘密）。**認可は所属ではなく `role=system_admin`（コントロールプレーン）で判定**するため、運営者は業務クエストに参加しなくてよい（テナント業務データへの足跡ゼロは運用で担保）。**運営テナント自体・最後の system_admin は削除/無効化不可**（ロックアウト防止・API設計 B.6）。厳密な職務分離（構造的にテナントデータ不可視）が要件化されたら、コントロールプレーン専用の運用者アイデンティティ＋専用ログイン（案B）へ拡張＝将来。※テーブル変更なし（既存構造で表現・API設計 B.0/B.5）。
16. **アカウント管理と参加管理の職務分離（SoD）＝会社アカウント管理者を新設 ＝ 決定（2026-08-01・API設計ドメインB）**: 従来 QG管理者に集約していた「アカウントのライフサイクル管理（発行/無効化/identity 編集/PW 再設定）」と「QG への参加（メンバーシップ）管理」を**2 役割に分離**する。**なぜ**＝QG管理者が会社DB内アカウントを参照可能（緩和）になると、「任意の既存アカウントを自 QG に追加 → 無効化/identity 改変」で**会社全体のアカウントを破壊/乗っ取りできる権限昇格**が生じるため。SoD でこれを構造的に防ぐ。
    - **`system_role` に `company_account_admin` を追加**（`{system_admin, company_account_admin, general}` の 3 値化）。**会社アカウント管理者**＝自社（セッション会社）**全アカウント**の発行/無効化/identity 編集/PW 再設定を担うが、**会社設定・プロビジョニング・`system_role` 付与（`company_account_admin`/`system_admin`）は不可**（それらは system_admin）。**per-group `admin`（QG管理者）の任命/剥奪は自社スコープで可**（2026-08-02 改定・下記）。会社スコープの役割なので `system_role`（会社/全社スコープの保管場所）に置く＝B案の原則「スコープ↔保管場所を一致」に合致（per-group の `quest_group_members.role` には入れない）。既存のミラー機構（`accounts.role`→`users.system_role`）にそのまま載る＝追加列不要。
    - **QG管理者（`quest_group_members.role=admin`）は「参加選択専任」に縮小**＝自社ディレクトリ参照＋**既存アカウントを自 QG に参加追加/除外**（`quest_group_members` の per-group 操作）のみ。**発行/無効化/identity/PW は不可**（会社アカウント管理者へ移管）＝アカウント破壊系を持たない。
    - **`system_role` 付与（`company_account_admin`/`system_admin`）は system_admin のみ**（同格/上位を増やす真の権限昇格は集約・§8-① 踏襲）。**per-group `admin`（QG管理者）の任命/剥奪は system_admin＋会社アカウント管理者（自社スコープ）＝2026-08-02 改定**（委譲運用「system_admin→会社アカウント管理者→QG管理者→メンバー」に対応。`admin` は下位権限＝越権にならない・API設計 B.2.1/B.7.2）。QG管理者は member 追加のみ（`admin` 任命不可）。テーブル変更なし（enum 値追加のみ）。反映＝§3 Enum一覧・§4.2 accounts.role・§5.3 users.system_role・§5.5 role／API設計 ドメイン B（B.0/B.0.1/B.2.1/B.3/B.6/B.7.2）・README §2-B。**画面反映＝完了（2026-08-02）**＝SC-90 参加ピッカー化・**会社アカウント管理者の発行画面＝新規 SC-93（所属エディタに member/admin セグメント）**・SC-92 の system_role 3値表示（＋要件定義 README・画面遷移図・SC-01 管理導線・mocks/index.html）。
17. **チャット既読位置テーブルの新設 ＝ 決定（2026-08-07・API設計ドメインE）**: SC-24 の**未読セパレータ/未読件数**の裏付けとして `chat_reads`（§5.31・`UNIQUE(chat_group_id, user_id)`・`last_read_message_id` アンカー）を**新設**する（会社DB＝28→29 テーブル）。**なぜ**＝`notifications.is_read`（ヘッダーベル用）はチャットの既読位置を表現できず、SC-24 §9 で TBD 扱いだったため。**既読更新（`POST /ideas/{idea_id}/chat/read`）はクエスト完了後も許可**（読み取り系の副作用＝共有コンテンツ不変・凍結対象外・API設計 E.5/C.5）。不採用＝(a) メッセージ単位の既読テーブル（行数爆発）、(b) Redis のみ保持（永続要件＝再ログインで未読が消えるのは不可）。反映＝§5.1 ER・§5.31・API設計 ドメイン E（E.1/E.5）・README §2-E。
18. **評価連動コインの確定トリガ／`activities.reason=evaluation_coin` ＝ 決定（2026-08-07・API設計ドメインF）**: 投稿者コイン（`round(全 submitted 評価者×全5観点の均等平均 ×10)`・最大50）の**一括確定トリガを具体化**＝**(a) 当該アイデアで `evaluator` 権限保持者（有効所属）が全員 `submitted` 済みになった瞬間（各確定時にサーバー判定）／(b) クエスト `completed` 遷移**の**いずれか早い方**で、**アイデア単位に1回・付与後再計算なし**（§7・§8-⑥）。**なぜ**＝スケジューラ基盤（MVP 未整備）に依存せず決定的に確定でき、`completed=凍結` と整合し、全員評価済みなら締切前でも早期付与できるため。台帳は投稿者コイン `reason=evaluation_coin`（`ref_type=ideas`）を新設し、存在で冪等（`activities` §5.27・投票 XP と同方式）。**選定は API設計 F 保有**（`POST/DELETE /ideas/{id}/select`・owner/quest_admin・複数アイデア可・XP+200 は初回選定で付与し取消時も再計算/剥奪しない）。**限定公開（`visibility=limited`）は範囲外へ完全非表示**（集計も返さない）。反映＝§5.27・§7・API設計 ドメイン F・C（`transition(→completed)` の確定フック注記）・README §2-F。
19. **実績付与＝台帳(activities)フックで即時判定／`reason` 追加 ＝ 決定（2026-08-07・API設計ドメインG）**: 実績（`achievements`）の付与は**専用の判定テーブル/スケジューラを設けず**、G の**台帳 `activities` 追記の post-commit フック**で当該ユーザーの関連実績のみを再判定し、達成なら `user_achievements` 作成＋ティア連動コイン報酬（`achievement_reward`・20/50/150）＋通知（`achievement`）を**即時・冪等**（`UNIQUE(user_id, achievement_id)`）に行う。**なぜ**＝全付与行動は既に `activities` を書くため判定契機を一元化でき、スケジューラ基盤（MVP 未整備）不要で即時通知/付与できるため。判定条件は `achievements.condition`（jsonb）＝**スキーマ変更不要**。連続ログインは `activities(reason=login)` の日付連続で導出（新テーブル不要）。**`activities.reason` に `spell_unlock`（SP消費・魔法解放・`ref_type=spells`）と `achievement_reward`（コイン付与・実績報酬・`ref_type=achievements`）を明記**（§5.27・自由文字列の例に追加）。反映＝§5.27・API設計 ドメイン G・README §2-G。
20. **通知の本文は取得時レンダリングで多言語化／`notifications.params` 追加・`body` NULL 可 ＝ 決定（2026-08-07・API設計ドメインH）**: 通知本文を発火時に確定テキストで保存せず、**`GET /notifications` で受信者の現在 `locale`** に応じてテンプレ（H のメッセージカタログ・§8-⑬）＋`params`＋`ref_*` から**取得時に組み立てる**。**なぜ**＝受信者がロケールを切り替えたら既存通知も表示言語が追従する（i18n を最大化）ため。**スキーマ変更＝`notifications.params jsonb`（NULL 可・可変値のイベント時点スナップショット＝`actor_name`/`count`/`xp`/`coin`/`tier`/`device`/`ip`/`at` 等）を追加し、`body` を NULL 可（既定ロケールのフォールバック/キャッシュ）に緩和**（新テーブルなし・列追加のみ）。ref から辿れる値（idea 件名・`achievements.name_{locale}`）は都度解決、辿れない/変わりうる値は `params` に凍結。**通知生成は各発火ドメインが H の通知サービス `notify()` を post-commit で呼ぶ**（§3.5-(3)）・**1 イベント×1 宛先は最も具体的な種別で1件に集約**（重複排除）。反映＝§5.24・API設計 ドメイン H・README §2-H。
21. **時系列アクティビティフィード＝`activities` の絞り込み表示（新テーブル不要）＝ 決定（2026-08-19・API設計ドメインG）**: 「自分／クエスト参加メンバー／参加クエスト横断のアクティビティを時系列表示したい」という要件（要件定義 FR-36）を、**専用テーブルやイベントログを新設せず**、既存の元帳 `activities`（§5.27）を軸（`user_id`／`quest_id`／`kind`・`reason`／`created_at`）で絞り込んで表示することで満たす。**なぜ**＝XP/コイン/SP を動かす行動（投稿/投票/チャット/評価/選定/実績/レベルアップ 等）は既にすべて `activities` を書くため、フィードは元帳のビューで表現でき、二重の書き込み口・整合リスクを避けられる（ランキング §7 が `activities` を集計するのと同一思想）。**プライバシー（初期値・調整可）**＝他者に見せるフィード（SC-12/SC-01）は**成果系のみ**（`idea_post`/`selection`/`achievement_reward`/`levelup_sp`）とし、私的な経済行動（`shop_purchase`/`spell_unlock`/`login`）や匿名性に関わる行動（`vote`＝投票匿名化 §8-⑯/FR-23・`evaluation`/`evaluation_coin`＝評価公開範囲に従属）は出さない。**自分の履歴（SC-03）は全種別**。**依存**＝クエスト範囲/参加メンバー判定は C（パーティー所属）、行のリンク付きレンダリング（アイデア名等の ref 解決）は D/E に依存（H 通知と同じ制約）。**スキーマ変更なし**（`activities.quest_id`/`ref_type`/`ref_id` を活用）。反映＝API設計 ドメイン G（G.5.1）・要件定義 FR-36・画面 SC-01/SC-12/SC-03。

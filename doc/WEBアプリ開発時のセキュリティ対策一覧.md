# WEBアプリ開発時のセキュリティ対策一覧

WEBアプリ開発では、アプリのコードだけでなく、設計・インフラ・運用・開発工程を含めて対策する必要があります。以下は、一般的な業務システムで利用できる実践的なチェックリストです。

OWASP Top 10 は主要なリスクを把握するための入口として有用ですが、具体的な要件定義・設計・テストには OWASP ASVS を併用するのが適しています。

参考: <https://owasp.org/Top10/2021/>

> 本プロジェクトでの位置づけ: 本一覧の対策は **`doc/コーディング規約.md` §2.2「セキュリティ対策（必須遵守）」** で全工程での実施を義務化している。各ドメイン（`doc/API設計/`）・各画面（`doc/画面設計/`）のレビュー時に関連章を突合して設計へ落とす（例: 認証系＝1/3/7/14/15。ドメイン A は `doc/API設計/A_認証・セッション.md` §A.9 で突合済み）。

---

## 1. 認証

- ID・パスワードによる本人確認を行う
- 管理者や機密情報を扱うユーザーには多要素認証を導入する
- パスワードは平文で保存しない
- パスワードは Argon2id、bcrypt、PBKDF2 などでソルト付きハッシュ化する
- パスワードの最低文字数を設定する
- よく使われるパスワードや漏えい済みパスワードを拒否する
- ログイン失敗回数を制限する
- ブルートフォース攻撃に対して、遅延・一時ロック・レート制限を行う
- ログインエラーで「ユーザーが存在するか」を判別できないようにする
- パスワード再設定トークンに十分なランダム性と有効期限を設定する
- パスワード変更時に現在のパスワードを再確認する
- メールアドレスや多要素認証設定の変更時に再認証する
- 管理者アカウントを一般利用アカウントと分ける
- 初期パスワードや共通アカウントを残さない
- OAuth、OpenID Connect、SAML を自己流で実装せず、実績のあるライブラリや認証基盤を使う

## 2. 認可・アクセス制御

認証済みであることと、対象データを操作する権限があることは別です。各 API・各データに対して、サーバー側で認可判定を行います。

- ロールや権限を明確に定義する
- 原則としてアクセス拒否とし、必要な権限だけを許可する
- 画面の表示・非表示だけで認可を済ませない
- すべての API で認可を確認する
- URL や ID を書き換えて、他人のデータを閲覧・更新できないことを確認する
- 所属会社、部署、テナントをまたいでデータを参照できないようにする
- 管理者機能には管理者権限を必須とする
- 作成・参照・更新・削除の権限を個別に検討する
- バッチ処理、CSV 出力、ファイルダウンロードにも認可を適用する
- サーバー側で対象レコードの所有者やテナントを確認する
- UUID を使っていても、推測されにくいことだけに依存しない
- 退職・異動・契約終了時に権限を速やかに停止する
- 権限変更履歴を記録する

## 3. セッション管理・トークン管理

セッション ID は認証情報と同等に扱います。Cookie を使う場合は、Secure、HttpOnly、SameSite などを適切に設定し、セッション ID に個人情報や意味のある情報を直接含めないことが推奨されます。

参考: <https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html>

- セッション ID を十分にランダムな値にする
- セッション ID を URL のクエリ文字列に含めない
- 認証成功時にセッション ID を再発行する
- 権限変更時にもセッションを再発行する
- ログアウト時にサーバー側のセッションを無効化する
- 無操作タイムアウトを設定する
- セッションの絶対有効期限を設定する
- Cookie に Secure を設定する
- Cookie に HttpOnly を設定する
- Cookie に適切な SameSite を設定する
- Cookie の Domain と Path を必要最小限にする
- JWT の有効期限を短くする
- JWT の署名アルゴリズムをサーバー側で固定する
- JWT の iss、aud、exp、nbf などを検証する
- アクセストークンとリフレッシュトークンを分ける
- リフレッシュトークンをローテーションする
- トークンをログに出力しない
- ブラウザの localStorage に長期間有効な機密トークンを保存しない
- パスワード変更やアカウント停止時に既存セッションを失効させる

## 4. 入力値検証

- すべての入力値を信用しない
- フロントエンドだけでなく、サーバー側でも検証する
- 許可する形式を定義するホワイトリスト方式を基本とする
- 文字数の上限・下限を設定する
- 数値の範囲を確認する
- 日付や時刻の形式・範囲を確認する
- 列挙値は許可された値だけを受け付ける
- 配列の件数に上限を設定する
- JSON やリクエスト本文のサイズに上限を設定する
- 想定外のプロパティを無視または拒否する
- 改行コードや制御文字を必要に応じて拒否する
- URL、メールアドレス、電話番号などを用途に応じて検証する
- Unicode の正規化や見た目の似た文字を考慮する
- 二重エンコードやデコード順序に注意する
- HTTP ヘッダーの値にも改行などを入れられないようにする
- クエリ条件、並び順、カラム名にも許可リストを設ける

## 5. SQL インジェクション対策

- SQL を文字列連結で組み立てない
- プリペアドステートメントまたはパラメーター化クエリを使う
- ORM を使っていても、生 SQL 部分を確認する
- 動的なテーブル名・列名・並び順には許可リストを使う
- DB 接続ユーザーに必要最小限の権限だけを与える
- アプリケーションから DB 管理者アカウントを使わない
- 読み取り処理と更新処理の権限分離を検討する
- エラーメッセージに SQL 文やテーブル名を表示しない
- ストアドプロシージャ内でも文字列連結を避ける

## 6. XSS 対策

- 出力先に応じてエスケープする
- HTML 本文、HTML 属性、JavaScript、URL、CSS を区別する
- テンプレートエンジンの自動エスケープを無効化しない
- React の `dangerouslySetInnerHTML` などを安易に使わない
- ユーザー入力を HTML として表示する場合はサニタイズする
- 信頼できるサニタイズライブラリを使う
- JavaScript の `innerHTML`、`document.write`、`eval` を避ける
- Content Security Policy を設定する
- インラインスクリプトをできるだけ避ける
- URL の `javascript:` スキームを拒否する
- Markdown を HTML に変換する場合もサニタイズする
- SVG ファイルを表示する場合はスクリプト混入を考慮する

## 7. CSRF 対策

- Cookie 認証を使う更新系リクエストには CSRF 対策を行う
- CSRF トークンを検証する
- Cookie に適切な SameSite を設定する
- Origin または Referer を補助的に検証する
- GET リクエストでデータ更新を行わない
- 重要操作ではパスワード再入力や再認証を求める
- 独自ヘッダーを要求する方式を検討する
- CORS 設定を CSRF 対策の代わりにしない
- CSRF トークンを URL に含めない

## 8. ファイルアップロード

アップロードされたファイルは、拡張子だけで判断せず、種類・サイズ・内容を検査し、公開領域から分離して保存する必要があります。圧縮ファイルは展開時の攻撃や多様なファイル混入にも注意が必要です。

参考: <https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html>

- 許可する拡張子を限定する
- MIME タイプだけを信用しない
- ファイルのシグネチャを確認する
- ファイルサイズに上限を設ける
- ファイル名をサーバー側でランダムな名前に変更する
- 元のファイル名をパスとして使用しない
- `../` などのパストラバーサルを防ぐ
- Web 公開ディレクトリ外に保存する
- ダウンロードはアプリ経由で認可を確認する
- アップロードファイルに実行権限を与えない
- ウイルス・マルウェアスキャンを行う
- 画像は可能なら再エンコードする
- Office、PDF、SVG などの能動的コンテンツに注意する
- ZIP 爆弾や大量展開を防止する
- 展開後の合計サイズ・ファイル数を制限する
- 同名ファイルによる上書きを防止する
- ダウンロード時に適切な `Content-Type` を設定する
- 必要に応じて `Content-Disposition: attachment` を指定する

## 9. API セキュリティ

- API ごとに認証・認可を実施する
- リクエスト件数を制限する
- ユーザー単位、IP 単位、API キー単位でレート制限する
- 一覧 API の最大取得件数を制限する
- ページングを必須にする
- API レスポンスに不要な項目を含めない
- DB モデルをそのままレスポンスにしない
- 更新可能な項目を明示する
- Mass Assignment を防ぐ
- GraphQL ではクエリ深度や複雑度を制限する
- API キーを URL に含めない
- API キーを定期的に更新できるようにする
- Webhook に署名検証を導入する
- リプレイ攻撃対策としてタイムスタンプや一意値を検証する
- OpenAPI／Swagger を本番環境で無制限に公開しない
- 廃止した API を停止し、古いバージョンを放置しない

## 10. CORS・ブラウザセキュリティ

- CORS の許可元を具体的に指定する
- 認証情報を許可する場合に `Access-Control-Allow-Origin: *` を使わない
- 許可する HTTP メソッドを限定する
- 許可する HTTP ヘッダーを限定する
- オリジン判定を部分一致で行わない
- `https://example.com.attacker.com` などを誤許可しない
- CSP を設定する
- `X-Content-Type-Options: nosniff` を設定する
- `Referrer-Policy` を設定する
- `Permissions-Policy` を設定する
- クリックジャッキング対策として CSP の `frame-ancestors` を設定する
- 必要に応じて `X-Frame-Options` も設定する
- HTTPS 環境では HSTS を設定する
- 機密レスポンスに適切な `Cache-Control` を設定する

## 11. HTTPS・通信の暗号化

- すべての通信を HTTPS 化する
- HTTP から HTTPS へリダイレクトする
- TLS 1.2 以上を基本とする
- 古い暗号スイートやプロトコルを無効化する
- 証明書の有効期限を監視する
- 証明書の自動更新を設定する
- 内部 API や管理画面も HTTPS 化する
- 外部サービス接続時に証明書検証を無効化しない
- 自己署名証明書を無条件に信頼する処理を入れない
- 外部 API の URL を HTTPS に固定する
- プロキシ配下では転送ヘッダーを信頼する範囲を限定する

## 12. 機密情報・個人情報の保護

- 保存する個人情報を必要最小限にする
- パスワード、API キー、秘密鍵をソースコードに書かない
- `.env` や設定ファイルを Git に登録しない
- シークレット管理サービスを利用する
- 本番・検証・開発環境でシークレットを分ける
- DB 内の重要情報を暗号化する
- 暗号鍵と暗号化データを別に管理する
- キーのローテーションを可能にする
- クレジットカード情報を可能な限り保持しない
- 個人情報を画面・CSV・ログへ過剰に出力しない
- マスキング表示を行う
- バックアップも暗号化する
- テスト環境に本番の個人情報をそのままコピーしない
- 不要になったデータを削除するルールを設ける
- URL や QR コードに機密情報を直接含めない

## 13. 暗号化・乱数

- 独自の暗号方式を作らない
- 標準的で実績のある暗号ライブラリを使う
- 暗号学的に安全な乱数生成器を使う
- 一般的な疑似乱数をトークン生成に使わない
- AES-GCM など認証付き暗号を使用する
- 固定 IV や固定 Nonce を使わない
- 秘密鍵を Git やコンテナイメージに埋め込まない
- 暗号鍵へのアクセス権を限定する
- 古いハッシュアルゴリズムをセキュリティ用途に使わない
- MD5 や SHA-1 をパスワード保存に使わない

## 14. エラー処理

- 利用者向けエラーと内部ログを分ける
- スタックトレースを画面に表示しない
- SQL 文、接続文字列、内部パスを表示しない
- フレームワークのデバッグモードを本番で無効化する
- 予期しない例外を共通処理で捕捉する
- エラーごとに追跡用 ID を発行する
- 詳細情報は追跡用 ID とともにサーバーログへ記録する
- 認証・認可エラーの情報を出しすぎない
- 外部サービスのエラー本文をそのまま返さない
- リトライ可能なエラーと不可能なエラーを区別する

## 15. ログ・監査

- ログイン成功・失敗を記録する
- ログアウト、パスワード変更、権限変更を記録する
- 管理者操作を記録する
- データの登録・変更・削除を監査できるようにする
- 操作者、日時、対象、操作内容、結果を記録する
- IP アドレスやユーザーエージェントを必要に応じて記録する
- ログにパスワードを出さない
- セッション ID、アクセストークン、API キーを出さない
- 個人情報や機密情報を必要以上に出さない
- ログインジェクションを防ぐ
- ログの改ざん・削除を防止する
- サーバー間の時刻を同期する
- ログの保存期間を決める
- 異常なログインや大量アクセスを検知する
- アラートの通知先と対応手順を決める
- 正常系ログを大量に出して異常を埋もれさせない

## 16. SSRF・外部通信

- ユーザーが指定した URL へサーバーから無制限にアクセスしない
- 接続先ドメインや IP を許可リストで制限する
- localhost やプライベート IP への接続を拒否する
- クラウドのメタデータサービスへの接続を防ぐ
- DNS 解決前後の IP を確認する
- リダイレクト先も再検証する
- `file:`、`gopher:` など不要なスキームを拒否する
- 接続タイムアウト、読み取りタイムアウトを設定する
- 応答サイズに上限を設定する
- 外部通信をネットワークレベルでも制限する
- 外部コンテンツをそのまま内部レスポンスに流さない

## 17. OS コマンド・パス操作・テンプレート

- ユーザー入力を OS コマンド文字列に連結しない
- シェルを経由せず安全な API を使う
- 実行するコマンドを許可リストで限定する
- ファイルパスを正規化する
- 基準ディレクトリ外へのアクセスを拒否する
- `../` や絶対パスを検査する
- シンボリックリンクを考慮する
- テンプレート式にユーザー入力を直接埋め込まない
- XML を扱う場合は外部エンティティを無効化する
- 安全でないデシリアライズを避ける
- オブジェクト型をユーザー入力から自由に指定させない

## 18. 業務ロジック上の不正対策

ツールによる脆弱性スキャンでは、業務ロジックの不備を十分に検出できません。

- 金額や数量をクライアント側の値だけで決定しない
- サーバー側で金額・割引・税額を再計算する
- 承認前のデータを確定扱いにしない
- 承認者が自分自身を承認できないようにする
- 二重送信・二重登録を防止する
- 冪等性キーや一意制約を利用する
- 在庫数や残高をトランザクション内で確認する
- 同時更新による競合を考慮する
- 画面遷移の順番に依存しない
- 非表示項目を書き換えられても問題がないようにする
- 無料試用やクーポンを繰り返し利用できないようにする
- 日付変更、キャンセル、差し戻しなどの例外フローを確認する
- CSV 出力や一括更新による大量取得・大量変更を制限する

## 19. データベース

- DB をインターネットへ直接公開しない
- アプリケーションサーバーからのみ接続可能にする
- DB ユーザーを用途別に分ける
- 最小権限を適用する
- 初期アカウントや初期パスワードを変更する
- 通信を暗号化する
- バックアップを暗号化する
- バックアップからの復元を定期的に試験する
- 監査ログを設定する
- 削除処理や一括更新に保護策を設ける
- テナント ID などの絞り込み漏れをテストする
- 重要な整合性はアプリだけでなく制約でも保護する

## 20. サーバー・クラウド・ネットワーク

- 開発・検証・本番環境を分離する
- 本番サーバーへのアクセスを限定する
- 管理画面を VPN や社内ネットワークに限定する
- ファイアウォールで必要なポートだけを許可する
- SSH や RDP をインターネットへ直接公開しない
- 踏み台、VPN、ゼロトラストアクセスを利用する
- OS やミドルウェアへ定期的にパッチを適用する
- 不要なサービスやポートを停止する
- デフォルトアカウントを無効化する
- クラウド IAM に最小権限を適用する
- ストレージを誤って公開しない
- セキュリティグループの `0.0.0.0/0` を見直す
- WAF を補助的に利用する
- DDoS 対策を検討する
- 本番環境で管理用ポートやデバッグポートを公開しない
- IaC の設定もレビュー・スキャンする

## 21. コンテナ・Docker

- 公式または信頼できるベースイメージを使う
- バージョンを明示する
- 不要なツールをイメージに含めない
- コンテナを root ユーザーで実行しない
- シークレットを Dockerfile へ書かない
- シークレットをイメージレイヤーへ残さない
- ホストの Docker ソケットを安易にマウントしない
- 特権モードを使わない
- 読み取り専用ファイルシステムを検討する
- CPU・メモリなどのリソース制限を設定する
- ベースイメージの脆弱性をスキャンする
- 使用しない Linux capabilities を削除する
- コンテナ間のネットワークを必要最小限に分離する
- 本番用イメージに開発用設定やソースマップを含めない

## 22. 外部ライブラリ・サプライチェーン

- 依存ライブラリを定期的に更新する
- 脆弱性情報を自動検出する
- Dependabot などの更新通知を利用する
- ロックファイルをリポジトリに登録する
- 不要なライブラリを削除する
- メンテナンスされていないライブラリを避ける
- パッケージ名のタイプミスに注意する
- インストールスクリプトの実行内容を確認する
- CDN の外部スクリプトを無条件に信用しない
- 必要に応じて Subresource Integrity を設定する
- ビルド環境や CI/CD の権限を制限する
- SBOM を生成・管理する
- ビルド成果物の署名や来歴確認を検討する
- 廃止・脆弱化したライブラリの対応期限を決める

## 23. Git・ソースコード管理

- Git リポジトリへパスワードや秘密鍵を登録しない
- `.gitignore` を適切に設定する
- シークレットスキャンを有効化する
- 誤って登録したシークレットは履歴から削除するだけでなく失効させる
- main ブランチへの直接 push を制限する
- プルリクエストとレビューを必須にする
- CI/CD 設定ファイルもレビューする
- リポジトリへのアクセス権を最小限にする
- 退職者や異動者のアクセス権を削除する
- 個人アクセストークンに必要最小限のスコープを設定する
- PAT やデプロイキーに有効期限を設定する
- 本番環境のシークレットを PR 実行環境へ無条件に渡さない

## 24. セキュリティテスト

- 単体テストに認可・入力値検証のテストを含める
- 他人の ID を指定した場合のテストを行う
- 未認証、権限不足、期限切れトークンをテストする
- SAST でソースコードを静的解析する
- DAST で稼働中アプリを動的診断する
- 依存ライブラリの脆弱性スキャンを行う
- コンテナイメージをスキャンする
- IaC をスキャンする
- シークレットスキャンを行う
- ファジングを検討する
- リリース前に脆弱性診断を行う
- 重要システムでは第三者によるペネトレーションテストを行う
- 検出した脆弱性の対応期限を重大度別に決める
- 修正後に再テストする
- スキャナーで問題なしでも安全と断定しない

## 25. CI/CD・リリース

- ビルド環境と本番環境を分離する
- CI/CD 用アカウントを最小権限にする
- 本番デプロイに承認フローを設ける
- 開発者全員が本番へ直接デプロイできないようにする
- デプロイ履歴を記録する
- 成果物を環境ごとに手作業で変更しない
- 同じ成果物を検証後に本番へ昇格させる
- ロールバック手順を準備する
- マイグレーション失敗時の復旧手順を用意する
- CI ログにシークレットを表示しない
- 外部からの PR に本番シークレットを渡さない
- リリース前チェックを自動化する
- 緊急リリース後にも必ずレビューを行う

## 26. 可用性・DoS 対策

- リクエストサイズを制限する
- ファイルサイズを制限する
- API のレート制限を行う
- DB クエリのタイムアウトを設定する
- 外部 API のタイムアウトを設定する
- 無制限リトライを行わない
- 正規表現による過剰な CPU 消費を防ぐ
- 一覧・検索の最大件数を設定する
- 高負荷処理を非同期化する
- ジョブキューの件数や同時実行数を制限する
- キャッシュの最大サイズを設定する
- アップロード容量やユーザーごとの保存容量を制限する
- ヘルスチェック、監視、アラートを設定する
- バックアップと災害復旧手順を整備する

## 27. 運用・インシデント対応

- セキュリティ責任者を決める
- 脆弱性情報の確認担当を決める
- インシデント発生時の連絡先を決める
- アカウントやトークンの緊急失効手順を用意する
- サーバー隔離手順を用意する
- ログ保全手順を用意する
- バックアップからの復旧手順を用意する
- 定期的に復旧訓練を行う
- セキュリティパッチの適用期限を決める
- 脆弱性の重大度判定方法を決める
- 委託先や外部サービスの障害・漏えい時の連絡経路を確認する
- 個人情報漏えい時の報告・通知手順を確認する
- 定期的にアカウントと権限を棚卸しする
- 使用していない環境やサービスを廃止する

## 28. 開発工程で実施すること

セキュリティ対策は、完成後に診断するだけでは不十分です。NIST の SSDF も、セキュアな開発プラクティスを既存のソフトウェア開発ライフサイクル全体へ組み込むことを推奨しています。

参考: <https://csrc.nist.gov/pubs/sp/800/218/final>

### 要件定義

- 扱うデータと機密度を整理する
- 利用者・ロール・権限を整理する
- 保存期間と削除ルールを決める
- 法令、契約、社内規程を確認する
- セキュリティ要件を非機能要件として明記する

### 設計

- データフロー図を作成する
- 信頼境界を明確にする
- 脅威モデリングを行う
- 認証・認可方式を設計する
- ログ・監査・監視を設計する
- 障害時や侵害時の影響を小さくする構成にする

### 実装

- セキュアコーディング規約を用意する
- 共通認証・認可処理を利用する
- セキュリティ機能を各開発者が個別実装しない
- コードレビューを行う
- 静的解析、依存関係検査、シークレット検査を自動化する

### テスト

- 正常系だけでなく異常系をテストする
- 認証回避、権限昇格、他人のデータ参照をテストする
- 攻撃文字列や大量データを入力してテストする
- 外部診断または第三者レビューを行う

### リリース・運用

- 本番設定をレビューする
- デバッグ機能を無効にする
- 初期アカウントを削除する
- 監視・通知を有効にする
- 脆弱性対応・アップデートを継続する

# テスト規約（設計書→テストパターン→テストコードの連鎖）

> 目的＝**「設計書 → テストパターン → テストコード」を一直線に辿れる**ようにする。
> 仕様の正は各設計書（`doc/API設計/`・`doc/画面設計/`・`doc/データモデル.md`）、
> 「何を確認するか」の正は本ディレクトリの**テストパターン md**（`doc/テスト/<ドメイン>_*.md`）、
> 「どう確認するか」の正は**テストコード**。三者を **TC-ID** で結ぶ。

---

## 1. トレーサビリティ（本規約の核）

- **TC-ID**＝テストケースの一意識別子。形式＝`<ドメイン>-TC-<連番3桁>`（例 `A-TC-001`）。
  - ドメイン記号は API設計のファイル接頭辞に合わせる（A〜L）。
  - 連番はドメイン内で一意・欠番可（削除しても再利用しない＝履歴の安定）。
- **3方向リンクの規約**:
  1. テストパターン md の各行は **`根拠` 列に設計節**を必ず書く（例 `A_認証・セッション.md A.1`・`SC-00 §5`）。
  2. テストコードは **関数名と docstring に TC-ID を埋める**（例 `def test_a_tc_001_login_success():` ／ docstring 先頭に `A-TC-001`）。
  3. 逆引き＝TC-ID で全文検索すれば「パターン md の行」と「テスト関数」が対で見つかる。
- **SoT（Single Source of Truth）の分担**（重複を書かない・規約 §2.3 DRY）:
  - 期待する**振る舞い/エラーcode/スキーマ**＝設計書・**OpenAPI**（エラーcodeの網羅は OpenAPI が SoT＝API設計 README §1.7）。テストパターン md はそれを**参照**し、値を再定義しない（`code=unauthenticated`（A.1）のように出典を併記）。
  - **確認すべきケースの集合**＝テストパターン md。
  - **実行手順・アサーション**＝テストコード。

### 1.1 テストパターン md の構成（各節に「テスト範囲の概要」を必須）

- **テストパターン md の各節（`##`／`###`）は、TC 表の前に「その節のテスト範囲の概要」を必ず記載する**（先頭に引用ブロック `>` 1〜数行を推奨）。TC 表だけを置くことは禁止。
- 概要に含める要素:
  1. **対象**＝どのエンドポイント／機構／画面を検証する節か（例: `POST /admin/companies/{id}/quest-groups`）。
  2. **範囲（と非対象）**＝この節が何をカバーし、何を別節/別スライスに委ねるか（例: 「作成のみ・削除は §4.x」）。
  3. **前提・使うフィクスチャ**＝seed 会社／factory／会社DB への直接 seed 等、テストの土台。
  4. **仕様の出典**＝設計節への参照（`根拠` 列と重ならない範囲で・API設計 B.3 等）。
- **なぜ**＝表（TC 行）だけだと「この節が全体として何を保証し・何を保証しないか」が読み取れず、**カバレッジの抜け・節間の重複・設計との drift** の温床になる。節の概要があれば、設計→テストの対応と**非対象の明示**が一目で分かり、レビューと再開（handoff）が速い。
- 例＝`doc/テスト/B_会社・アカウント.md` の各節冒頭の `>` ブロック（対象 EP・範囲・前提・出典・test-first か後追いか）。

### 1.2 テストパターン表の必須列（`目的` 列）

- TC 表の列は **`TC-ID` / `階層` / `目的` / `前提` / `操作` / `期待` / `根拠`** の順とする（**`目的` は `階層` の右**）。
- **`目的`＝そのテストが何を保証するのか（仕様上の意図・狙い）**を簡潔に書く（15〜45字目安・体言止め可・句点なし）。`操作`/`期待` の単なる言い換えではなく、「**なぜこのケースを確認するのか＝担保したい性質**」を書く（例: 列挙耐性の担保／認証と CSRF の評価順序の固定／HOL ブロッキングで順序保証／存在秘匿／Mass Assignment 防止／固定窓で計数が延長しないこと）。
- **なぜ**＝`目的` があると、表を読むだけで「各ケースが仕様のどの性質を守るためにあるか」が分かり、設計→テストの**意図**の対応が追える。`期待`（何が起きるか）と `目的`（なぜ確認するか）を分けることで、カバレッジの過不足や設計との drift も見つけやすく、レビュー/再開（handoff）が速い。

## 2. テスト階層（レベル）

| レベル | 対象 | 依存 | 例 | ツール |
| --- | --- | --- | --- | --- |
| **unit** | domain 層の純粋関数（§3.1・DB非依存） | なし | `daily_login_bonus_due()`（A.1/G）・入力正規化 | pytest |
| **integration（int）** | repository＋実DB（テナント解決・Tx・冪等） | Postgres | セッション永続・台帳の一意制約 | pytest＋テストDB |
| **api** | エンドポイント（router→application→domain→repository の縦貫） | Postgres＋Redis | `POST /api/v1/auth/login` の status/Set-Cookie/body | pytest＋ASGI TestClient |
| **e2e**（任意） | ブラウザ実操作（画面↔API） | フルスタック（compose） | SC-00 でログイン→SC-01 到達 | Playwright |

- **原則＝ピラミッド**: unit を厚く、api を要所に、e2e はハッピーパス中心に薄く。
- **どのレベルで書くか**はテストパターン md の `階層` 列で指定する。

## 3. バックエンド（pytest）の約束

- place＝`backend/tests/<domain>/`。ファイル名＝`test_<domain>_<観点>.py`。
- **命名**＝`test_<tcid小文字>_<短い説明>`（例 `test_a_tc_002_wrong_password_401`）。docstring 1行目に `A-TC-002` と根拠設計節。
- **DBフィクスチャ**＝テストごとにトランザクションを張って**ロールバックで隔離**（副作用を残さない）。マルチテナントは「管理DB＋テスト用会社DB1つ」を**セッションスコープで用意**し、行データはテスト単位でロールバック。
- **シード/ファクトリ**＝最小の「1社＋1アカウント（＋必要なら会社DB users）」を作るヘルパを用意（`conftest.py`）。値は決め打ちを避け factory 関数で生成。
- **秘匿値をログに出さない**（PW/セッションID/OTP/トークン＝セキュリティ一覧 3・15）。テストでも生の秘匿値をアサーションメッセージに出さない。
- **失敗を繰り返す TC はレート制限/将来のアカウントロックに引っかからないよう隔離する**＝テストごとに別 `login_id`/IP を使うか、失敗回数を閾値未満に保つ（ADR-0001 §2.6・ロックは MFA スライスで導入予定のため、既存 TC が将来も壊れないようにする）。

## 4. フロント（Playwright・e2e／任意レベル）

- place＝`frontend/e2e/`。ケースは `<screen>.spec.ts`（例 `sc-00-login.spec.ts`）。
- テスト名に TC-ID を含める（例 `test('A-TC-020 login happy path', …)`）。
- e2e は**契約の最終確認**（Cookie セッションが実ブラウザで確立し保護画面へ到達する等）に限定し、細かな分岐は api レベルで担保する。

## 5. 追加・変更のフロー（red を必ず経由する）

1. 設計書が確定/変更。
2. 該当ドメインのテストパターン md に TC 行を追加/更新（`根拠` を明記）。**← ここを飛ばさない**（md 無しでテストコードを書かない。ドメインの md が無ければ新規作成する）。
3. テストコードを TC-ID 付きで実装。
4. **red を目視**＝実装前にそのテストを走らせ、**対象の振る舞いに起因する失敗**で落ちることを確認する（§5.1）。実装先行の後追いなら「ガード/アサーションを一時無効化→red 目視→復元」を実施し `doc/テスト/red確認台帳.md` に記録。
5. 実装（またはバグ修正）を入れて **green** にする。
6. 変更に伴い旧 TC を消す場合は md とコードの両方から消す（TC-ID は再利用しない）。

- **DoD ゲート（トレーサビリティ検査・再発防止）**: テスト追加/変更をコミットする前に **`python3 scripts/check_tc_traceability.py`** を実行し ✅（テストコードの全 TC-ID が `doc/テスト/*.md` に対応行を持つ）を確認する。❌（code のみに在る TC-ID）は「手順2 を飛ばした／綴り違い」の検出＝コミット前に解消する。CI / pre-commit に組み込むと自動で担保できる。

### 5.1 red-green の原則（全レベル必須＝unit/int/api/e2e）

- **なぜ**＝「最初から緑」のテストは、対象を実際に呼んでいない／pytest に収集されていない／フィクスチャが例外を握りつぶす、等で **緑のまま何も検証していない** ことがある。一度 red を目視すること自体がテストの検証になる。
- **red は「対象の振る舞いに起因する失敗」であること**＝想定した status／エラー code／スキーマ／戻り値のアサーションで落ちる red を確認する。未実装ゆえの `ImportError`・関数/シンボル未定義（`NameError`／JS の `is not a function`・`ReferenceError`）・ルート未定義の 404・接続エラーのような **無関係な失敗で満足しない**（それはテストが対象に到達していない証拠）。**コミット等の証跡に「関数未定義で赤」「未実装の 404 で赤」とだけ書かれている状態は本原則に不適合**＝behavior-red を目視していない。
- **対象がまだ存在しない test-first**（新規の関数/クラス/エンドポイント）＝**最小スタブを先に置いて「対象は在るが誤り」の状態を作り、アサーションで落とす**。具体的には、関数なら**誤値/空を返すスタブ**（例 `return new URLSearchParams()` や `return None`）、エンドポイントなら**ルートだけ定義して 501/誤 body を返すハンドラ**を置き、`ImportError`／未定義／ルート 404 ではなく**期待値との差分（例 `期待[a,b,c] ≠ 実際[]`・`422 ≠ 200`）で red を目視**してから本実装で green にする。証跡には**観測した actual**（差分の実測値）を書く（「未定義で赤」ではなく「`sort` 未対応で `[c,a,b]≠[a,b,c]` で落ちた」の形）。
- **実装が既にある後追いテスト**（自然に red が出ない場合）＝**アサーションを一時反転**して red を確認→戻す（実装は触らない＝安全）。反転しても red にならなければ、そのアサーションは効いていない。
- **証跡の置き場所**＝経路で使い分ける（二重管理を避ける）:
  - **test-first**（実装前にテストを書き自然な red を得た）＝その TC を通したコミットのメッセージに1行残す（例 `red確認済: A-TC-071 は verify 前は 401 で落ちることを目視`）。落ちた理由／status を短く書く。複数 TC をまとめて足した場合は代表例＋件数で可。
    - **書式（必須項目）**＝`red確認済(test-first): <TC-ID[,…]> ＝ <実装/反転前の状態> で <観測した actual（status／戻り値／差分の実測値）> により落ちることを目視 → 実装後 green（<n> passed）`。
      - **`観測した actual` は必須**＝「対象に到達した証拠となる実測値」を書く。これが埋められない red は behavior-red が成立していない（下の NG 例）。
      - 良い例＝`red確認済(test-first): B-TC-133 は format/columns 無視で JSON 200 を返し 422 でなく 200 で落ちる → green（172 passed）`。
      - **NG 例（本原則に不適合・§5.1 冒頭）**＝「関数未定義で赤」「ルート未定義 404/405 で赤」「ImportError で赤」＝いずれも actual を書けない＝アサーション未到達。スタブ（誤値/501）を先に置き、期待値との差分で red を出し直す。
  - **後追い（反転手技で確認）**＝反転は `git checkout` で戻すためコミット差分に痕跡が残らない。[`../テスト/red確認台帳.md`](../テスト/red確認台帳.md) に TC-ID 行（反転した主アサーション／観測 red）を追記し、コミットメッセージは台帳を参照する。書式は台帳の既存表に従う（コミット側に別書式を作らない＝二重メンテ回避）。

### 5.2 テストは必ず設計書に根拠を持つ（設計書ファースト）

- **テストパターンは設計書（SoT）に記された振る舞いからのみ起こす**。設計書に無い振る舞いを確認したくなった場合は、**先に設計書へ追記する**＝該当する `doc/API設計/*`・`doc/データモデル.md`・`doc/ADR/*` の適切な節に、既存トーンで 1〜数文を足す→その節を `根拠` 列に引いてテストパターン化する。**設計書に根拠の無いテストを残さない**（テストだけが仕様を主張する状態＝設計との drift の温床）。
- **既存テストの再レビュー**で「設計書に載っていない挙動を検証している行」を見つけたら、同様に**設計書へ追記して `根拠` を張り直す**。テスト側の `期待` は原則変えない（実装と一致しているなら設計書が実態に追随する＝設計書の記述不足を埋める向き）。設計・実装・テストの三者が食い違う場合は、どれを正とするかを判断し（多くは設計書の記述不足）、必要なら別途 ADR/設計判断として明示する。
- 追記した設計節は、対応する TC の `根拠` 列に必ず反映する（3方向リンクの維持・§1）。設計文書間で用語/列名がぶれている場合（例: 単回消費の列名）は、データモデルの実列を正として揃える。

## 6. 共通の必須観点（全ドメイン・認可の抜け穴防止）

各エンドポイントのテストパターンには、その性質に応じて次を**必ず**含める（drift しやすい認可の穴を体系的に塞ぐ）:

- **セッション必須EP**＝「**セッション無し → 401 `unauthenticated`**」を必ず1件置く（例 A-TC-012／A-TC-015）。
- **状態変更系EP（CSRF 対象）**＝「**CSRF トークン無し/不一致 → 403 `csrf_failed`**」を1件（例 A-TC-014）。認証と CSRF の**評価順序**（セッション無し＝401 が先・セッション有り＋CSRF 欠落＝403）が対で分かるようにする。
- **テナント/門番のあるEP**＝「**他テナント/権限外 → 404（存在秘匿）**」を1件（該当ドメインで追加）。
- **冪等EP（`Idempotency-Key`）**＝「**同一キー再送 → 同一結果（副作用1回）**」を1件（該当ドメインで追加）。

# リポジトリ構成規約

> リポジトリ直下の**トップレベル構成**と、ファイルの置き場所を定める。
> 実装内部のディレクトリ（バックエンド4層・フロント feature 構成）は [`コーディング規約.md`](./コーディング規約.md) §3.4／§4.1 が正（本規約では重複させずポインタとする＝DRY・同 §2.3）。
> 文書間参照の表記は [`ドキュメント作成規約.md`](./ドキュメント作成規約.md) に従う。

## 1. トップレベル構成（`doc/` と `impl/` を対にする）

```
リポジトリ直下/
├── doc/          設計（要件定義・データモデル・API設計・テストパターン・ADR・画面設計・規約）
├── impl/         実装（実行できるアプリ一式）
│   ├── backend/       バックエンド（内部構成＝コーディング規約 §3.4）
│   ├── frontend/      フロントエンド（将来・内部構成＝コーディング規約 §4.1）
│   ├── compose.yaml   ローカル開発オーケストレーション
│   └── .env.example   環境変数の既定値（実値 `.env` は追跡外）
├── CLAUDE.md     各種規約への入口（毎セッション自動読込）
└── handoff.md    セッション引き継ぎメモ
```

- **設計は `doc/`・実装は `impl/`**。ルート直下に実装コードや `compose` を散らかさない。
- **`impl` は implementation の一般的略語**。`docker compose` は **`impl/` ディレクトリで実行**する（`cd impl && docker compose up`）。
- **なぜ**＝設計（doc）と実装（impl）をルートで明確に分離し、どこに何があるかを一目で分かるようにするため（2026-08-08 ユーザー決定）。
  - **不採用**＝`src/`（`compose`/`.env` は厳密にはソースでない）／`app/`（バックエンド内部の Python パッケージ名 `app` と衝突し `app/backend/app/…` が紛らわしい）／`apps/`（`compose`/`.env` を直下に置くのが不自然）。

## 2. ファイル配置のルール

- 実装コード・設定・オーケストレーションは **`impl/` 配下**に置く。
- 設計・仕様・規約・ADR・テストパターンは **`doc/` 配下**に置く（テストパターン＝`doc/テスト/`・ADR＝`doc/ADR/`）。テスト**コード**は実装なので `impl/backend/tests/` 等に置く。
- **画面API連携＝`doc/画面設計/画面API連携/`**（画面ごと1ファイル＝`SC-xx_*.md`）。画面が API を**どの順番で呼び、結果〔成功・各エラー〕を画面にどう反映するか＋Cookie/CSRF の配線**を定める連携仕様。**リクエスト/レスポンスの項目やエラーコードは書かない**（それらは OpenAPI と各 API 設計が正＝DRY・コーディング規約 §2.3）。「インタフェース」は UI と紛らわしいため用いない。
- **秘密情報（実 `.env`・鍵）はコミットしない**（`.gitignore`・コーディング規約 §2）。テンプレートは `*.env.example` を追跡する。
- 実装内部のモジュール分割・層構成は本規約では定めない＝**コーディング規約 §3.4（バックエンド）／§4.1（フロント）が正**。

## 3. 適用方針

- **新規のファイル/ディレクトリは本規約に準拠**。既存の配置は移設の機会に順次是正（ドキュメント作成規約と同じ折衷方針）。

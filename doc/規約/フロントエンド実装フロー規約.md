# フロントエンド実装フロー規約（画面モック先行 → バックエンド接続）

> **位置づけ**＝実装スキャフォールド段階における**フロント（画面）実装の進め方**を定める。構造（フォルダ・レイヤ責務）は [`コーディング規約.md`](コーディング規約.md) §4、テストのトレーサビリティ/red-green は [`テスト規約.md`](テスト規約.md)、見た目の正は [`../画面設計/デザイン標準.md`](../画面設計/デザイン標準.md)、遷移の正は [`../画面設計/画面遷移図.md`](../画面設計/画面遷移図.md) が持つ。本規約はそれらを**どの順で組み上げるか**を規定する（構造/見た目のルールは重複定義しない＝DRY・コーディング規約 §2.3）。
> **方針決定＝2026-08-12（ユーザー選択）**。従来の「ドメイン縦スライスで backend まで一気に通す」から、**画面モック先行（フロント先行）→ 後追いで backend 接続**へ切り替える。理由＝(a) 設計がモック完備（全画面 HTML＋`shared.css`）で「正」が揃っている、(b) 先に全画面の UI/動線を固めると後の接続が「データ差し込み」だけになり整合の二度手間が消える、(c) 全画面を繋いで俯瞰することで動線の抜けを早期に発見できる。

## 1. 全体フロー（2段階）

1. **画面モック先行（クリッカブル・プロトタイプ）**＝全画面のモックを Next.js に移植し、**画面遷移とダイアログ呼び出しを実配線**する。**バックエンド接続は不要**、一覧等は**デモデータ**でよい。目的＝UX/動線をブラウザで確認・合意できる状態にする。
2. **バックエンド接続（画面群ごと）**＝プロトタイプがつながったら、**画面群単位で「モック整合済みの画面 → backend 接続」**を回す。データ源をデモデータから実 API へ差し替える（下記 §4 の seam）。

- **粒度＝画面群ごとに「移植 → 接続」を小さく回す**（2026-08-12 選択）。共通基盤（デザインシステム・App シェル・全ルート雛形＋ナビ・URL モーダル基盤）を先に一度だけ用意し（Phase 0）、以降は認証→ダッシュボード→管理→クエスト→アイデア/チャット/評価→ゲーム層→通知、の群で進める。**接続フェーズの粒度は §1.1 で「1画面単位」に詳細化した（2026-08-19）**。
- 接続順序の推奨は [`../要件定義/README.md`](../要件定義/README.md) と各ドメイン設計に従う（例＝クエスト C → アイデア D → チャット E → 評価 F → ゲーミフィケーション G。台帳・オブジェクトストレージ等の基盤は接続時に前倒し）。

## 1.1 バックエンド接続は画面単位で回す（1画面ずつ・受入ゲート付き）

> **方針詳細化＝2026-08-19（ユーザー選択）**。§1 の接続段階（2段階目）を**画面群ではなく1画面単位**で回す。理由＝(a) 1画面に必要な EP だけをテスト先行で薄く縦に通せて差分が小さい、(b) 1画面ごとに実ブラウザで動作確認・仕様調整の合意点を作り、齟齬を早期に潰せる、(c) 完了を「画面」で数えられ進捗が見える。

**1画面の接続ループ**:

1. **必要 EP の特定**＝対象画面の [`../画面設計/screens/SC-xx_*.md`](../画面設計/screens/) と [`../API設計/`](../API設計/) から、その画面が呼ぶ EP を洗い出す（未実装 EP は設計＝正で確認する）。
2. **backend をテスト先行で実装**＝EP 単位に [`テスト規約.md`](テスト規約.md) §5.1 の red-green を経て 4層（[`コーディング規約.md`](コーディング規約.md) §3.4）で実装する。**その画面に必要な範囲のみ**に絞る（参照先/発火元ドメインが未実装で忠実に作れない部分は、範囲を明示して後続スライスへ送る）。
3. **フロント差替**＝feature の取得関数を fixtures から実 API へ差し替える（§4 の seam）。既存の相互作用 e2e はその画面について実 API で green にする（§8）。
4. **ユーザー動作確認（受入ゲート）**＝実装者はここで一旦止め、**ユーザーがブラウザで動作確認**する。不具合・仕様調整はこの段で洗い出して反映する（設計と食い違えば §7 に従い設計＝正で設計側を修正）。
5. **1画面クローズ**＝受入で合意できたら当該画面を「接続完了」とし、次の画面へ進む。

- 着手する画面の順は §1 の接続順序推奨（ドメイン C → D → E → F → G …）と整合させつつ、**依存の少ない画面から**選ぶ（参照先テーブルや発火元ドメインが未実装で忠実に作れない画面は後回し）。

## 2. デザインシステム＝`shared.css` を単一の正として採用（段階移行）

- モックの見た目の正は [`../画面設計/mocks/shared.css`](../画面設計/mocks/shared.css)（全モックが参照）。これを **Next.js の単一デザインシステムとして採用**し、共通部品（`components/ui`・`components/pixel`＝業務層/ゲーム層）へ移植する（2026-08-12 選択）。
- **段階移行**＝既存のアドホック CSS（`features/*/**.css` 等の個別スタイル）は**順次 `shared.css` ベースへ寄せて廃止**する。トークン/クラスの重複定義を残さない（`shared.css` を唯一の情報源にする）。
- 二層構成（**業務層＝クリーン／ゲーム層＝CRTガラス**・1レイヤー1マテリアル）を守る（デザイン標準・コーディング規約 §4）。

## 3. モーダル＝URL 付き（Parallel Routes ＋ Intercept Routes）を標準とする

- 登録・編集・（一覧/ダッシュボードから開く）詳細は **URL を持つモーダル**（`@modal` スロット＋`(.)` Intercept・直アクセス/リロードはフルページ）で実装する（コーディング規約 §4／デザイン標準 §モーダルダイアログ §111）。ナビ shell を組む Phase 0 で本方式へ移行する（2026-08-12）。
- モーダルの共通挙動（ヘッダードラッグ移動・最大化/復元・本文スクロール・Esc/バックドロップ/フォーカストラップ・狭幅フルスクリーン）はデザイン標準 §105-107 準拠＝**共通部品に集約**し各画面で再実装しない。

## 4. デモデータの seam（後の接続を楽にする）

- 各 feature に **`fixtures.ts`（デモデータ）を置き、型は OpenAPI 生成の `src/lib/api/schema.d.ts` に合わせる**（手書きの独自型でモックしない）。→ 接続フェーズは**データ源を `fixtures` から `api.ts` へ差し替えるだけ**で済み、レイアウトの手戻りが出ない。
- 画面/コンポーネントは「データ源が fixtures か api か」を**1箇所で切り替えられる**構造にする（例＝feature の取得関数を1本にし、実装を差し替える）。業務計算はフロントに書かない（コーディング規約 §1・§4）。

## 5. ルートの正＝画面遷移図

- App Router のルート構成は [`../画面設計/画面遷移図.md`](../画面設計/画面遷移図.md) から起こす。**動線の抜けを見つけたら、まず画面遷移図を更新してから実装に反映**する（図を SoT に保つ）。
- 画面と設計文書のトレーサビリティ＝ルート/画面は **SC-ID** で [`../画面設計/screens/SC-xx_*.md`](../画面設計/screens/) と対応づける。

## 6. 既に backend 接続済みの画面の扱い

- 既に実 API 接続＋e2e がある画面（ログイン・SC-90/91/92/93 等）は、**接続を維持したまま**本デザインシステム/シェルに載せて**モック整合**する（2026-08-12 選択）。**デモデータへ退行させない**（動くコードとテスト資産を捨てない）。

## 7. 完了の定義（DoD）＝モック一致

- 画面は**画面モックと一致**して初めて「実装完了」とする（レイアウト・列/項目・コピー・空状態・**モーダルの共通挙動**を含む）。機能が通るだけでは未完。
- **モックが設計（データモデル/API設計）と矛盾する場合は設計を正**とし、モック・画面遷移図の方を修正する（例＝一覧が返さない列は出さない・最小射影を破らない）。矛盾の解消は該当設計文書への追記/修正で行う（テスト規約 §5.2 の「設計書ファースト」と同じ向き）。
- **接続フェーズの完了**は §1.1-4 の**ユーザー受入（実データでの動作確認合意）**をもって確定する（本節のモック一致に加える）。

## 7.1 検証・レビュー由来の指摘は「正の md」に先に反映（spec-first・2026-08-22）

ユーザーの手動検証やレビューで出た**仕様の追加/変更・不具合対応の方針**は、**まず該当の正 md に追記/改定してからコードを変更**する（DoD＝その記述に一致・§5 の「動線は画面遷移図を先に更新」「§7 設計を正」と同じ向き）。**どの md が正か（振り分け）**:

| 指摘の種類 | 反映先（正） |
| --- | --- |
| **横断 UI 標準**（入力検証エラー表示・DataTable 挙動・トースト・確認ダイアログ 等） | [`../画面設計/デザイン標準.md`](../画面設計/デザイン標準.md)（＋見本は `mocks/style-guide.html`） |
| **画面固有**（項目・コピー・遷移・空状態） | [`../画面設計/screens/SC-xx_*.md`](../画面設計/screens/) |
| **画面をまたぐ動線** | [`../画面設計/画面遷移図.md`](../画面設計/画面遷移図.md) |
| **API 契約**（EP・パラメータ・応答） | [`../API設計/`](../API設計/)（`{A..L}_*.md`／`README.md`） |
| **用語・ラベル** | デザイン標準 §4.6 |

- **やみくもに追記しない（判断基準）**: **既存の正 md が既にその挙動を規定している「純粋なコード不具合」は、新規の仕様追記は不要**（コード修正のみ）。例＝「一覧→詳細→戻るでページが戻る」不具合は、デザイン標準 §4.5⑨ が既にページ復元を規定済み＝**バグ修正であって仕様追記ではない**（挙動が曖昧なら §4.5⑨ に一文追記して明確化する程度に留める）。
- **大きな横断標準は見本先行**: デザインに関わる横断標準は、`mocks/style-guide.html` に**サンプルを追加してユーザーがレビュー→最終確定**してから全画面へ適用する（例＝入力検証エラー §4.7）。確定前は md 側に「**レビュー待ち**」と明記する。
- **実装着手時に見つけた設計時点の文書間不整合も、コード前に正の md を最新化する（spec-first の一般則・設計書は常時最新に保つ／ユーザー方針 2026-08-22）**: 検証/レビュー由来に限らず、実装の精読で「ある正 md の記述が別の正 md に未反映」だと気づいたら、**まず関係する全ての正 md を相互整合させてから**コードを書く。例＝C.2 publish の参加通知（`quest_party_invited`）が H の発火元台帳・`notification_type` enum・`notifications.ref_quest_id` に未登録だったので、H 実装より前に データモデル §3/§5.24 と H.0 に登録した（後続ドメインの実装漏れを台帳で防ぐ）。跨るドメインを後回しにする場合も、**トリガー/型/参照は先に登録**し、実装側は no-op フック＋TODO を残す。

## 8. テスト

- **プロトタイプ段階**＝backend 不要の**ナビゲーション/ダイアログ相互作用の e2e**（デモデータ・Playwright）で「遷移が繋がる・モーダルが開閉する」を担保する。
- **バックエンド接続段階**＝[`テスト規約.md`](テスト規約.md) の通り、設計書 → テストパターン → テストコードで **red-green**（§5.1）を経由する。既存の実接続 e2e は接続維持の画面で**維持**する。
- テストパターン md の TC 表・目的列・トレーサビリティ（TC-ID）はテスト規約に従う。

# ドメイン J. 全文検索（テナントプレーン）＝詳細確定（2026-08-08）

> API 全体規約は [`README.md`](./README.md) 第1章（特に **§1.11 全文検索〔PGroonga〕**・§1.8 一覧・§1.5 会社DB動的ルーティング・§1.6 認可）を参照。索引定義はデータモデル **§6（PGroonga）**・§8-④。門番（パーティー所属）は [`C_クエスト・パーティー・権限.md`](./C_クエスト・パーティー・権限.md) C.0、検索対象の実体は [`D_アイデア・添付・版・投票・フォロー.md`](./D_アイデア・添付・版・投票・フォロー.md)（`ideas`・`attachments`）・[`E_チャット・リアクション・魔法発動.md`](./E_チャット・リアクション・魔法発動.md)（`chat_messages`）。本ファイルはドメイン J の分割レビュー成果。

対象画面＝**SC-12 クエスト詳細「🔍 全文検索」タブ**（＋将来のグローバル検索）。すべて**テナントAPI**（会社DB＝`ideas`/`chat_messages`/`attachments` の PGroonga 索引）。データモデル §6・§5.10 ideas・§5.15 chat_messages・§5.12 attachments・§3。コーディング規約 §1・**§2.2（③クエリのパラメタ化・④XSS＝スニペットのサニタイズ）**・§3.1（薄い CRUD の読取合成）準拠。

**この分割レビューでユーザー選択により確定（2026-08-08）**:
- **下書き（`draft`）は本人分も含め FTS 対象外**（J.0・共有前の WIP は全文検索に出さない）。
- **検索はオフセットページング（`page`/`per_page`）**＝関連度スコア順の UNION で件数表示も要るため（J.4・§1.8 のオフセット用途に一致）。

## J.0 責務境界・アクター・可視範囲

- **責務**＝会社DB の PGroonga 索引に対する**横断全文検索**（`ideas`＋`chat_messages`＋`attachments` を UNION してスコア順）と、ハイライトスニペット生成。索引の**正**はデータモデル §6（本ドメインは検索 API を規定）。新しい業務ロジックは持たず、**可視範囲は各ドメインの門番規則を WHERE 述語として適用**（コーディング規約 §1）。
- **アクター＝認証済みユーザー全員**（テナント内・`company_id` はセッション由来＝§1.5・クエリで受けない）。未認証＝**401**。
- **門番＝パーティー所属＋クエストグループ所属の AND**（C.0/D.0/E.0 と同一）：`GET /quests/{id}/search` は当該クエストの `quest_members`（`removed_at IS NULL`）**かつ**当該クエストグループの `quest_group_members`（`removed_at IS NULL`）に自分の有効行がなければ **404 `not_found`**（どちらか欠けても 404＝パーティーに居てもグループ非所属なら 404・存在秘匿）。`GET /search` は**「パーティー所属かつグループ所属が共に有効」なクエストの和集合**に限定（テナント分離で自社のみ）。
- **可視範囲（検索対象に含める行・サーバー強制の WHERE 述語）**:
  - **アイデア**＝`status='published'` かつ `deleted_at IS NULL`、かつ**門番（パーティー所属＋クエストグループ所属の AND・上記）を満たすクエスト内**（chat/attachment もこの可視クエストを継承）。**下書き（`draft`）は本人分も含め対象外**（共有前の WIP。本人下書きはダッシュボード〔I〕/一覧〔D.1〕で到達）。
  - **チャット**＝可視な公開アイデアの `chat_groups` 配下の `chat_messages` で **`is_deleted=false`**（トゥームストーンは本文を監査保持するが検索対象外・E.1）。
  - **添付**＝上記の可視アイデア（`attachments.idea_id`）または可視チャットメッセージ（`attachments.chat_message_id`）に紐づく `original_name`。親が非可視/削除/トゥームストーンなら対象外。
  - **`completed` クエストは検索可**（内容は残る・読み取り専用の凍結は書き込みのみ・C.5）。
  - **匿名化（`vote_anonymized`）・評価 `visibility`** は FTS の対象要素ではない（投票者・評価は索引対象外）ため無関係。
- **重要（索引と可視範囲の分離）**：PGroonga 索引はテーブル全行に張るが、**可視範囲は索引ではなくクエリの WHERE 述語（パーティー範囲・`published`・`deleted_at IS NULL`・`is_deleted=false`）で強制**する。索引ヒットをそのまま返さない（下書き/他パーティー/削除の漏洩防止）。
- 認可失敗＝**403**／範囲外・対象なし＝**404**／未認証＝**401**。

## J.1 検索エンドポイント

| メソッド/パス | 概要 | リクエスト（クエリ） | レスポンス |
| --- | --- | --- | --- |
| `GET /quests/{quest_id}/search` | クエスト内 全文検索（SC-12 全文検索タブ） | `q`（必須・検索語）・`types?`（`idea,chat,attachment` の CSV・既定 all）・`page?`/`per_page?`（§1.8・既定 `per_page=20`・上限100） | `{data:[検索行], page_info:{total, page, per_page}}` |
| `GET /search` | テナント内 横断全文検索（自分の全パーティー和集合・将来のグローバル検索） | 同上 | 同上（各行に `quest` 文脈を含む） |

- **`q`（検索語）**＝PGroonga のクエリとして**パラメタ化**して渡す（§2.2 ③・文字列連結しない）。空/空白のみは 422 `validation_error`（or 空結果）。複数語は既定 AND（詳細な演算子・最小文字数は J.6 TBD）。
- **`types`**＝返す種別の絞り込み（`idea`/`chat`/`attachment`・複数可・既定 all）。README §1.11 の `types` に準拠（SC-12 §113 の `scope=` は旧記法＝実装時に追随）。
- **スコープ**＝`GET /quests/{id}/search` は当該クエスト1件、`GET /search` は自分が有効所属する全クエスト（`quest_members.removed_at IS NULL`）。どちらも J.0 の可視範囲述語を AND する。

## J.2 検索対象・索引（PGroonga・データモデル §6 が正）

- **対象列**＝`ideas`（`title`/`body`/`value`/`note`）・`chat_messages`（`body`）・`attachments`（`original_name`）。索引例は §6（`USING pgroonga`）。
- **エンジン＝PGroonga**（日本語の分かち書き不要・`pgroonga_score`・`pgroonga_snippet_html` を DB 内で完結・追加コンテナ不要）。拡張は**会社DBのみ**に導入（§6）。
- **索引の更新＝同期（リアルタイム）**：PGroonga は通常の PostgreSQL インデックスで、対象行の書込トランザクション内で索引も更新される＝**外部エンジンのような別同期処理は不要**（SC-12 §131「更新方式 TBD」を本決定で解消）。将来の高精度化（あいまい/シノニム/タイポ許容）は Meilisearch/OpenSearch＋kuromoji（別コンテナ・同期要）へ差し替え可能（§6・現状は不要）。

## J.3 結果表現・ランキング・スニペット

- **結果＝3種を UNION し `pgroonga_score` 降順の単一リスト**（種別バッジで区別・SC-12）。同スコアのタイブレークは `created_at` 降順（J.6 TBD）。種別間のスコア重み付けは MVP では素の `pgroonga_score`（per-type ブースト無し・J.6 TBD）。
- **検索行（各要素）**:
  `{type:'idea'|'chat'|'attachment', field〔一致した列名＝title/body/value/note/original_name〕, quest:{id, title}, idea_id, idea_title, chat_message_id?〔chat/添付がチャット由来のとき〕, attachment_id?〔添付のとき〕, snippet_html, score, target}`。
  - **所属アイデア**（`idea_id`/`idea_title`）は常に付与（チャット・添付も親アイデアに属する）。`quest` 文脈は横断 `GET /search` の導線・グルーピング用（クエスト内でも一貫して返す）。
  - **`snippet_html`**＝`pgroonga_snippet_html` によるハイライト済み断片（サーバー生成）。**PGroonga がユーザー文を HTML エスケープし、ハイライトタグのみを注入**する（J.5）。
  - **`target`**＝親への導線ヒント＝`idea`→アイデア詳細（SC-22・`/idea/{idea_id}`）／`chat`・`attachment`→チャット（SC-24・`chat_message_id` を指す）。フロントは ID から導線を組み、添付ヒットは該当添付を示す。
- **0件/空**＝`{data:[], page_info:{total:0, page, per_page}}`（SC-12 の空表示）。

## J.4 ページング（オフセット・§1.8 の例外理由）

- **オフセット（`page`/`per_page`＋`page_info.{total, page, per_page}`）を採用**（§1.8 の「総件数が要る画面」向けオフセット形）。**なぜカーソルでないか**＝(1) 結果は関連度スコア順の UNION で**時系列フィードではない**（カーソル方式が想定する「新着が増えても安定」の利点が効かない）、(2) **異種テーブル横断のスコアで不透明カーソルを組むのは非現実的**、(3) SC-12 が件数（`total`）と `page=` を要求する。結果集合は通常小さくオフセットの弱点（深いページのズレ）は実害が小さい。

## J.5 セキュリティ対策マッピング（`doc/WEBアプリ開発時のセキュリティ対策一覧.md` 突合・§2.2）

- **クエリインジェクション（③）**：`q` は PGroonga 演算子へ**バインド変数で**渡し、SQL/検索式へ文字列連結しない。`types`/`page` は列挙・数値でサーバー検証（想定外は 422）。
- **XSS（④・スニペット）**：`snippet_html` はサーバー生成で **PGroonga がユーザー文を HTML エスケープ＋既知のハイライトタグのみ注入**。フロントは**許可リスト（ハイライト span のみ許可）でサニタイズして描画**し、**生の `dangerouslySetInnerHTML` は使わない**（§2.2 ④＝`dangerouslySetInnerHTML` 原則禁止）。
  - **`pgroonga_snippet_html` の出力形（誤読防止）**：断片（戻り値は `text[]`）内で **ユーザー文中の `< > & "` のみを実体参照へエスケープ**し、一致キーワードを **`<span class="keyword">…</span>`（エスケープしない"生の"HTML タグ）**で囲む。**タグは二重エスケープしない／フロントで「デコードして表示」する工程も無い**＝そのまま HTML として描画すれば、エスケープ済みユーザー文は文字として表示され、`<span>` だけがハイライトとして効く。**"生きている"タグは PGroonga が注入した `<span class="keyword">` のみ**（ユーザー由来マークアップは残らない）ため原理的に安全で、上記の許可リストサニタイズは**多層防御**（バージョン差・想定外への保険）。※HTML 文字列を一切扱いたくない場合の代替＝API が**構造化セグメント**（`[{text, hit:bool}]`）を返しフロントが `<span>` を自前生成する（`dangerouslySetInnerHTML` を完全回避・J.6 の将来オプション）。
- **認可・IDOR（②）**：可視範囲を**索引ではなくクエリ WHERE で強制**（パーティー範囲・`published`・非削除・非トゥームストーン）。範囲外クエスト/他人の下書き/他テナントは結果に一切出さない（J.0）。`GET /quests/{id}/search` の門番不一致は 404。
- **情報漏洩なし**：スニペットも可視対象行からのみ生成（非可視行は検索段で除外済み）。
